기본 export(`default`)를 `windows`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-windows`를 설치하고 앱의 `plugins`에 `windows`를 등록합니다. 명령 핸들러나 setup은 이 패키지의 `windows`를 호출합니다. 화면에서도 같은 경로를 import하며 해당 뷰의 commands에 `plugin.windows.<작업>`을 허용해야 합니다.

창 제어 플러그인은 Windows와 macOS에서 실행합니다. macOS는 `list`, `create`, `recreate`,
`show`, `showInactive`, `hide`, `focus`, `close`, `isVisible`, `isFocused`, `isDestroyed`,
창 식별자 조회(`getById`, `getCurrent`, `getFocused`, `getLastActive`, `listInstances`),
`getReadiness`와 `windows.readiness`, `setContentProtection`, `isContentProtected`,
아래 WebView 기본 제어를 지원합니다.
`getSnapshot`, `windows.changed`, 크기와 위치, 상태 변경, `activate`, `blur`,
`openDevTools`를 포함한 그 외 작업은 `UNSUPPORTED`입니다. Linux와 모바일은 네이티브 호스트를 지원하지 않습니다.
플러그인을 등록하지 않은 앱도 설정한 시작 창과 WebView를 사용할 수 있습니다.

크기와 DPI 처리는 [Per Monitor v2](https://learn.microsoft.com/en-us/windows/win32/hidpi/dpi-awareness-context)를 사용하므로 Windows 10 버전 1703 이상이 필요합니다.

```ts
import { defineApp } from "@bunaway/backend";
import windows from "@bunaway/plugin-windows";
export default defineApp({ modules: [], plugins: [windows] });
```

## 사용자 타이틀바와 표시 옵션

선언과 생성별 `options.window`에 `titlebar: "custom"`을 지정하면 시스템 caption을
제거하고 네이티브 resize 테두리와 시스템 메뉴를 유지합니다. 기본 `"system"`은 기존 창과 같습니다.
생성 후 모드 변경과 네이티브 caption 버튼 overlay는 지원하지 않습니다.
`getTitlebar({ view, windowId? })`는 전체화면에서도 생성 시 모드를 반환합니다.

```css
.titlebar { app-region: drag; user-select: none; }
.titlebar button, .titlebar input, .titlebar a { app-region: no-drag; }
```

WebView2가 현재 문서의 CSS 영역을 hit-test하므로 페이지 탐색, zoom과 DPI 변경 때
좌표 목록을 다시 보낼 필요가 없습니다. 드래그 영역은 창 이동, 더블 클릭 최대화/복원과
우클릭 시스템 메뉴에 사용됩니다. 입력 요소에는 `no-drag`를 지정하고 키보드로 접근 가능한
이름 있는 button으로 최소화, 최대화와 닫기 동작을 제공하세요. 해당 동작은 기존 창 API와
권한을 사용합니다. `title`은 네이티브 접근성 이름으로 계속 유지합니다.
네이티브 resize 테두리는 `setResizable`을 따르며 `setMovable`, `setMaximizable`,
`setClosable`의 사용자 동작 제한도 유지합니다. 전체화면 해제는 원래 caption과 frame을 복원합니다.
완전히 테두리 없는 창과 자동 snap-layout 버튼 overlay는 아직 제공하지 않습니다.

custom 모드는 WebView2의 `ICoreWebView2Settings9`가 필요합니다.
이를 제공하지 않는 런타임은 창 준비에 `UNSUPPORTED`를 반환하며 조용히 drag를 무시하지 않습니다.
CSS 영역은 이 창에서 허용된 문서에 적용되므로 신뢰하는 origin만 허용해야 합니다.
[WebView2의 non-client region 계약](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2settings9)을 사용합니다.

`alwaysOnTop`과 `skipTaskbar`는 선언 및 생성별 boolean이며 기본 `false`입니다.
`setAlwaysOnTop({ view, windowId?, alwaysOnTop })`과 `isAlwaysOnTop({ view, windowId? })`은
일반 창보다 위에 표시하는 상태를 변경하고 조회합니다. 권한은 `windows.setAlwaysOnTop`, `windows.isAlwaysOnTop`입니다. 활성화와 표시 상태, 크기는 바꾸지 않습니다.
Windows의 owner 관계에 따라 관련 창의 Z 순서도 영향을 받을 수 있습니다.

`setSkipTaskbar({ view, windowId?, skipTaskbar })`과 `isSkipTaskbar({ view, windowId? })`은
명시적인 tool-window 제외 상태를 변경하고 조회합니다. 권한은 `windows.setSkipTaskbar`, `windows.isSkipTaskbar`입니다. 제외하면 작업 표시줄과 Alt+Tab에
나타나지 않습니다. owned 또는 focusable:false 창은 이 값이 false여도 작업 표시줄에 없을 수 있습니다.
변경은 숨겨진 일반 창에서만 허용하며 표시 중, 최소화, 최대화 또는 전체화면이면 `BUSY`입니다.
같은 값의 재설정은 상태와 무관하게 성공합니다. 먼저 전체화면을 해제하고 restore, hide한 뒤
변경하고 필요하면 showInactive로 표시하세요. 암묵적인 hide/show나 포커스 이동은 하지 않습니다.

`contentProtection`은 선언 및 생성별 boolean이며 기본 `false`입니다.
`setContentProtection({ view, windowId?, contentProtection })`은 `null`을 반환하고
`isContentProtected({ view, windowId? })`은 boolean을 반환합니다. 권한은 `windows.setContentProtection`,
`windows.isContentProtected`입니다. 켜면 스크린샷과 화면 공유에서 창을 제외하며, 창 상태와 관계없이 언제든 변경할 수 있습니다.
생성할 때는 첫 표시 전에 적용합니다.
Windows는 `WDA_EXCLUDEFROMCAPTURE`로 창을 캡처에서 제외합니다. Windows 10 버전 2004 이전은 이 값을
`WDA_MONITOR`처럼 처리해 창을 캡처에 남기고 내용만 검은색으로 표시합니다. 호출이 거부되면
`WDA_MONITOR`로 다시 시도합니다. 끄면 `WDA_NONE`으로 되돌립니다.
조회는 OS의 `GetWindowDisplayAffinity` 값을 읽으므로 두 방식 모두 `true`입니다. 어느 쪽도 적용할 수 없으면
변경은 `INTERNAL` 오류로 실패하고 창 생성도 실패합니다.
macOS는 `NSWindow.sharingType`을 `None`(보호) 또는 `ReadOnly`(해제)로 설정합니다. macOS 15 이상에서는
ScreenCaptureKit 기반 캡처가 이 값을 무시할 수 있으므로 캡처 제외를 보장하지 않습니다.

`requestAttention({ view, windowId?, mode? })`는 작업 표시줄 버튼만 깜박여 사용자의 주의를 끕니다.
`cancelAttention({ view, windowId? })`는 깜박임을 멈추고 버튼을 원래대로 되돌립니다.
권한은 `windows.requestAttention`, `windows.cancelAttention`입니다. `mode`의 기본값은
`untilFocused`이며 창이 전경 창이 되면 멈춥니다. 이미 전경 창이면 바로 멈춥니다.
`continuous`는 `cancelAttention`을 호출할 때까지 계속 깜박입니다. 반복 호출은 이전 mode를 교체하고,
깜박이지 않을 때의 취소도 성공합니다. 제목 표시줄은 건드리지 않으며 포커스, 표시 상태와 Z 순서를
바꾸지 않으므로 `focus`와는 별개입니다. 숨겨진 창, skipTaskbar 창과 owned 창은 작업 표시줄 버튼이
없어 눈에 보이는 깜박임은 없지만 호출은 성공합니다.

```ts
await windows.setAlwaysOnTop({ view: "main", alwaysOnTop: true });
await windows.requestAttention({ view: "main", mode: "continuous" });
const mode = await windows.getTitlebar({ view: "main" });
```

설정 작업과 attention 작업은 null, 조회는 boolean 또는 titlebar 모드를 반환합니다. 각 작업은 같은 이름의
`windows.<작업>` 권한이 필요하며 화면에는 `plugin.windows.<작업>` command 권한도 필요합니다.
창의 수명과 대상 접근 검사, 취소 처리는 기존 창 작업과 같습니다. 닫힌 창은 `INVALID_ARGUMENT`,
네이티브 실패는 `INTERNAL`입니다. macOS는 attention 작업을 포함한 이 작업들과 세 생성 옵션을
기본값을 명시한 경우에도 `UNSUPPORTED`로 거부합니다. 재생성은 실행 중 설정과 attention 상태를
이어받지 않고 선언과 생성별 옵션으로 시작합니다.

## WebView audio

Windows의 `getWebViewAudioState({ view, windowId? })`는 현재 창의 WebView에서
`{ muted, playing }`을 조회합니다. `setWebViewAudioMuted({ view, windowId?, muted })`는
음소거를 설정하고 null을 반환합니다. `muted`는 boolean이며 자동 재생이나 장치 권한을
변경하지 않습니다. `playing`은 WebView2가 보고한 문서의 audio 재생 상태입니다.
음소거된 문서도 재생 중일 수 있으며 이 값은 물리 장치의 출력 여부를 확인하지 않습니다.

```ts
await windows.setWebViewAudioMuted({ view: "main", muted: true });
const { muted, playing } = await windows.getWebViewAudioState({ view: "main" });
```

권한은 각각 `windows.getWebViewAudioState`와 `windows.setWebViewAudioMuted`이며 화면은
해당 command 권한도 필요합니다. 기존 창 대상 선택과 windowId 수명 검사를 유지합니다.
음소거는 해당 WebView controller의 설정으로, 문서 탐색은 유지하고 창 재생성은 초기화합니다.
닫힌 창은 `INVALID_ARGUMENT`, 생성 중인 WebView는 `BUSY`, 서비스가 없는 플랫폼은
`UNSUPPORTED`입니다. 네이티브 읽기와 쓰기 실패는 `INTERNAL`입니다.
상태 변경 이벤트와 실제 audio 장치의 재생 검증은 아직 제공하지 않습니다.

## 설정과 권한

대상 창은 [app.windows](/reference/configuration/)에 정의합니다.
`view`는 화면과 정책을 선언한 ID입니다. `instances`의 기본값은 `"single"`이며
`"multiple"`과 `maxInstances`를 선언하면 같은 뷰에서 여러 창을 생성할 수 있습니다.
`startup: false`로 설정하면 `windows.create`로 열 때까지 생성하지 않습니다.
호출 인자로 임의 URL이나 새 정책을 전달할 수 없습니다.

Windows의 `create`와 `recreate`는 `{ view, options? }`를 받습니다. options에는
`title`, 부분 `window` 크기와 제약 및 초기 배치, `visible`, `showWhenReady`를 지정할 수 있습니다.
생략한 값은 선언값을 사용합니다. 크기는 정수 200–4096이며 병합한 min > max는
기존 창을 닫기 전에 `INVALID_ARGUMENT`로 거부합니다. 초기 크기는 최종 제약 안으로 보정합니다.
제약의 `null`은 해당 제약을, `showWhenReady: null`은 자동 표시를 이번 생성에서 해제합니다.
제목은 1–1024자이며 NUL을 허용하지 않습니다. options는 선언을 변경하지 않으며
옵션 없는 다음 재생성은 원래 선언으로 돌아갑니다. home, 프로필, startup과 임의 ID는 허용하지 않습니다.
macOS는 `title`, `window`의 크기와 크기 제약, `contentProtection`, `visible`, `showWhenReady`만 받습니다.
`window`의 `x`, `y`, `center`, `useContentSize`, `preventOverflow`, `titlebar`, `alwaysOnTop`,
`skipTaskbar`, `focusable`, `maximized`, `fullscreen`을 지정하면 기존 창을 닫기 전에
`UNSUPPORTED`로 거부합니다. macOS에서 `createInstance`와 `recreateInstance`는 사용할 수 없습니다.

`options.window`의 `x`, `y`, `center`, `useContentSize`, `preventOverflow`는
[초기 창 설정](/reference/configuration/#app)과 같은 단위와 작업 영역 계약을 사용합니다.
startup, create, recreate, createInstance와 recreateInstance에 모두 적용합니다.
`options.window.focusable`도 선언과 병합하는 boolean이며 기본은 `true`입니다.
`false`인 Windows 창은 활성화 없이 표시하고 사용자 클릭 및 호스트의 새 전경 활성화 요청을 차단합니다.

`maximized`, `fullscreen`도 boolean이며 기본은 `false`입니다. 초기 일반 영역을 설정한 뒤
최대화, 전체화면 순서로 적용합니다. 둘 다 켜면 전체화면 해제 뒤 최대화 상태로 돌아갑니다.
`visible: false`와 `showWhenReady`의 숨김 생성도 유지합니다. 초기 전체화면 해제는 현재 표시 상태를
유지하며 선언이나 다음 생성의 옵션을 바꾸지 않습니다. macOS는 `maximized`와 `fullscreen`을 `UNSUPPORTED`로 거부하지만 `visible`과 `showWhenReady`는 적용합니다.
필드별로 선언과 병합한 결과에서 x/y가 한 축만 있거나 `center: true`와 좌표가 함께 있으면
`INVALID_ARGUMENT`입니다. 선언의 한 축만 바꾸는 것은 나머지 축이 선언에 있을 때 허용합니다.
선언 좌표를 지우려면 `{ x: null, y: null }`, center를 해제하려면 `{ center: false }`로 지정합니다.
작업 영역과 최소 content 크기의 충돌도 슬롯 및 프로필 예약이나 기존 창 종료 전에 거부합니다.
검증 이후 디스플레이 구성이 바뀌는 OS 경쟁은 생성 실패로 처리하며 이전 창 복원은 보장하지 않습니다.

```ts
await windows.create({ view: "editor", options: {
  title: "새 문서", visible: false,
  window: { width: 1000, minWidth: null, center: true, preventOverflow: true }, showWhenReady: "sdk",
} });
```

같은 뷰의 열린 창에 다시 `create`하면 `BUSY`이며 기존 창과 세션은 유지됩니다.
기존 창을 표시하려면 `show`, 이전 세션을 정리하고 설정대로 다시 만들려면 `recreate`를 사용하세요.

뷰마다 생성 정의 하나만 선언하며 중복 view는 시작 전에 거부합니다.
Windows 선언은 0–128개입니다. 빈 선언은 임의 창 생성 권한이 아닙니다.
같은 뷰의 모든 창은 같은 UI 자산과 정책을 사용하며 각 창은 별도 windowId와 연결 세션을 가집니다.
새 창은 생성 요청자의 정책을 복사하지 않고 대상 뷰의 정책을 사용합니다.

`instances: "multiple"`은 정수 1–128의 `maxInstances`를 요구합니다. 앱 전체에서는
활성, 예약 및 정리 중인 인스턴스가 최대 128개입니다. 한도에 닿으면 `BUSY`이며
창을 닫았어도 네이티브와 프로필 정리가 끝날 때까지 슬롯을 사용합니다.
startup은 multiple에서도 시작 창 하나만 만듭니다.
기존 create/recreate는 single에서만 사용하고 multiple에서는 `INVALID_ARGUMENT`입니다.
createInstance와 recreateInstance는 single에서도 사용할 수 있으며 ID를 직접 반환합니다.

```ts
const first = await windows.createInstance({ view: "editor", options: { title: "문서 A" } });
const second = await windows.createInstance({ view: "editor", options: { title: "문서 B" } });
await windows.show({ view: "editor", windowId: second.windowId });
const replacement = await windows.recreateInstance({ view: "editor", windowId: first.windowId });
```

제어와 상태 입력에는 `{ view, windowId?, ... }`를 사용합니다. view는 권한 대상이며
windowId는 실제 창을 선택합니다. single에서는 ID를 생략할 수 있습니다.
multiple에서는 현재 창이 하나여도 반드시 ID를 전달합니다. 다른 뷰에 속한 ID는
`INVALID_ARGUMENT`입니다. 재생성은 새 ID를 발급하고 이전 ID의 제어는 거부합니다.
닫힌 ID의 getById는 null이며 허용한 view의 isDestroyed는 true입니다.
getCurrent는 인증된 호출자 세션의 창을 반환하고 백엔드 호출은 null입니다.
macOS도 네이티브 창을 만들거나 재생성할 때마다 새 `windowId`를 발급합니다.

선언의 `profile` 기본값은 `"shared"`입니다. 같은 뷰의 창은 하나의 WebView2 환경과
영속 웹 저장소를 공유하고 controller와 IPC 세션은 별도로 소유합니다. 창 하나를 닫아도
다른 창은 계속 실행됩니다. `"isolated"`는 창마다 임시 프로필을 만들고 재생성에서는
저장소를 유지합니다. 최종 종료와 실패 뒤 정리하며 새 생성과 앱 재실행에서는 복원하지 않습니다.
잠긴 파일은 삭제할 때까지 재시도하며 정리 중인 인스턴스는 계속 상한에 포함합니다.
3초 뒤에도 삭제하지 못하면 진단을 남기고 소유 기록을 유지합니다. 앱 종료 기한을
넘기면 정리 실패로 처리합니다. 다음 시작에는 소유 프로세스가 종료된 이전 임시
폴더를 제한된 개수만 정리하며 다시 열지 않습니다.
앱 이벤트를 view 대상으로 발행하면 해당 뷰의 구독한 모든 창에 전달합니다.
windows.changed는 변경된 창의 문서에만 전달합니다.
macOS는 새 인스턴스 API, multiple과 isolated 선언을 `UNSUPPORTED`로 거부합니다.

뷰 명령은 해당 뷰의 `host.permissions`, setup은 `backend.permissions`에 권한을 허용합니다.
각 메서드의 완전한 작업 이름을 허용합니다. 허용된 작업은 앱에 선언된 모든 창을 대상으로 합니다.
특정 창의 제어를 제한하려면 앱 명령에서 검사하고 화면에는 그 명령만 허용합니다.
생략한 작업은 거부합니다. 조회를 허용해도 생성이나 제어 권한은 생기지 않습니다.

```json
{
  "permissions": [
    "windows.list",
    "windows.show"
  ]
}
```

`windows.list`는 앱에 선언된 모든 창 설정을 반환합니다. 제어할 뷰는 앱 설정에 정의해야 합니다.

## 메서드

### 인쇄 대화상자

Windows의 `windows.showPrintUI({ view, windowId?, kind? })`는 현재 WebView 문서의
인쇄 대화상자를 엽니다. kind는 기본값 `"browser"` 또는 `"system"`입니다.
browser는 WebView2의 미리보기와 선택 UI, system은 OS 인쇄 선택 UI를 요청합니다.
사용자가 프린터와 설정을 선택하고 인쇄를 실행합니다. 이 작업은 프린터를 지정하거나
자동으로 인쇄하지 않으며 파일 경로, silent 옵션이나 PDF 내보내기 설정을 받지 않습니다.

```ts
await windows.showPrintUI({ view: "main" });
await windows.showPrintUI({ view: "main", kind: "system" });
```

작업 권한은 `windows.showPrintUI`입니다. 화면 호출은 해당 뷰의 command 권한도
요구합니다. 창과 windowId의 기존 대상 선택 및 접근 규칙을 사용합니다.
반환값 null은 대화상자 요청이 받아들여졌다는 뜻이며 사용자의 선택, 취소 또는 인쇄
완료를 뜻하지 않습니다. 이미 인쇄 대화상자가 열렸다면 WebView2가 기존 UI를 유지합니다.
닫힌 창은 `INVALID_ARGUMENT`, WebView 생성 중에는 `BUSY`이며,
인쇄 인터페이스가 없는 이전 WebView2 런타임과 다른 플랫폼은 `UNSUPPORTED`입니다.
지원 여부는 설치된 WebView2의 인쇄 인터페이스를 조회해 확인합니다.
인쇄 완료 이벤트, 프린터 목록, silent print와 PDF 내보내기는 아직 제공하지 않습니다.

### WebView 다운로드 승인과 수명

Windows WebView 다운로드는 기본적으로 거부합니다. `windows`를 등록하지 않은 앱에도
같은 기본값을 적용합니다. 신뢰된 backend setup은 `windows.setDownloadRequestsEnabled`
작업 권한으로 `{ view, windowId?, enabled: true }`를 호출해 요청 수집을 시작합니다.
수집은 승인과 다릅니다. 각 항목은 명시적으로 승인하기 전까지 파일을 만들지 않습니다.
화면에서 호출한 앱 명령도 view 컨텍스트이므로 다운로드 API를 직접 사용할 수 없습니다.
화면 정책에 작업을 허용해도 모든 다운로드 작업은 `PERMISSION_DENIED`입니다.

| 메서드 | 추가 입력 | 결과 |
| --- | --- | --- |
| `windows.setDownloadRequestsEnabled` | `enabled: boolean` | 요청 수집 변경 뒤 `null` |
| `windows.getDownloads` | 없음 | 현재 WebView 수명의 다운로드 snapshot 배열 |
| `windows.approveDownload` | `id: string` | 해당 pending 항목 승인 뒤 `null` |
| `windows.cancelDownload` | `id: string` | pending 거부 또는 활성 다운로드 취소 뒤 `null` |
| `windows.pauseDownload` | `id: string` | 활성 다운로드 pause 요청 뒤 `null` |
| `windows.resumeDownload` | `id: string` | 재개 가능한 다운로드 resume 요청 뒤 `null` |
| `windows.forgetDownload` | `id: string` | 종료된 기록과 네이티브 참조 정리 뒤 `null` |

모든 작업은 별도 `windows.<작업>` 권한과 backend 출처를 요구합니다.
대상 선택과 닫힌 창, multiple 뷰의 windowId 규칙은 다른 창 작업과 같습니다.
macOS와 다른 플랫폼은 이 서비스를 제공하지 않으며 `UNSUPPORTED`입니다.

getDownloads는 `{ id, url, mimeType, contentDisposition, path, totalBytes, receivedBytes,
state, interruptReason, canResume, paused }`를 반환합니다. id는 해당 WebView 수명에만
유효한 불투명 UUID입니다. URL은 최종 다운로드 URI이며 redirect chain이나 frame별
initiator 정보가 아닙니다. path는 파일명을 포함한 WebView2의 기본 저장 경로입니다.
byte 수가 없거나 JavaScript 안전 정수 범위를 넘으면 해당 수치는 null입니다.
state는 `pending`, `inProgress`, `interrupted`, `completed`, `cancelled` 중 하나입니다.
interrupted의 interruptReason은 WebView2의 네이티브 코드이며 그 외에는 null입니다.

```ts
// backend setup에서 설정한 권한과 앱의 자체 승인 규칙으로 실행합니다.
await windows.setDownloadRequestsEnabled({ view: "main", enabled: true });
const items = await windows.getDownloads({ view: "main" });
for (const item of items) {
  if (item.state === "pending") {
    // 실제 앱은 URL, MIME, 저장 경로와 사용자 선택을 검사한 뒤 한 항목만 승인합니다.
    await windows.cancelDownload({ view: "main", id: item.id });
  }
}
```

앱은 setup에서 소유한 비동기 작업으로 상태를 조회하고 사용자 선택이나 접근 규칙을
검사해 항목별로 승인하거나 거부합니다. API는 앱의 승인 규칙을 대신 정하지 않습니다.
승인은 WebView2가 선택한 기본 저장 경로와 기본 다운로드 UI를 사용합니다.
호출자가 path를 전달할 수 없으며 임의 경로, 파일 덮어쓰기 규칙과 저장 대화상자는
별도 파일 접근 계약이 필요합니다. 승인 뒤 취소는 이미 기록한 파일의 롤백을 보장하지 않습니다.

요청의 문서 origin과 다운로드 URI는 모두 대상 뷰의 기존 HTTP/HTTPS origin 안에
있어야 합니다. blob/data URI를 추가로 허용하지 않습니다. popup과 redirect, 리소스 및
OS 권한의 기존 검사는 유지합니다.
multiple-automatic-downloads 권한도 계속 거부하므로 같은 페이지에서 반복한 자동 다운로드는
승인 큐에 들어오기 전에 브라우저가 차단할 수 있습니다. 이 권한의 중재는 별도 후속 작업입니다.
다운로드를 시작하는 최상위 탐색에도 기존 세션 폐기 계약을 적용합니다. 문서 교체가 없어도
SDK 연결이 종료될 수 있으므로 화면은 클라이언트를 다시 초기화해야 할 수 있습니다.
pending 항목은 30초 뒤, 새 문서 탐색 또는 요청 수집 비활성화 시 거부합니다.
백엔드가 승인한 다운로드는 문서 탐색 뒤에도 같은 창 수명에
속하며 창 종료와 재생성에서는 취소하고 참조를 정리합니다.

WebView마다 pending, 활성, 종료된 기록을 합해 최대 32개를 유지합니다.
상한을 채우면 새 요청은 즉시 거부합니다. 종료된 항목을 forgetDownload로 지우면
슬롯을 다시 사용할 수 있습니다. 완료나 명시적 취소 전의 항목은 forget이 `BUSY`이며
먼저 취소해야 합니다. WebView2가 중단된 다운로드를 자동 재개할 수 있어 현재 canResume이
false여도 참조를 유지합니다. 없는 ID와 더 이상 pending이 아닌 ID의 승인은 `INVALID_ARGUMENT`입니다.
재개할 수 없는 항목의 resume은 `BUSY`입니다. cancel은 반복해도 안전하며 완료된 항목은
완료 상태를 유지합니다. 진행률과 완료, 실패는 현재 snapshot 조회로 확인합니다.
별도 이벤트, 속도 계산, 재시작 뒤 중단 파일 복원과 업로드는 아직 제공하지 않습니다.

다운로드 metadata의 URL, MIME, Content-Disposition과 경로는 JSON 인코딩 후 합계 64 KiB까지
허용합니다. 이스케이프 문자와 UTF-8 크기도 포함합니다. 전체 retained snapshot은 항목별
상태와 숫자의 최대 크기를 예약해 512 KiB 이내로 제한하며, 만료되거나 취소된 항목도
`forgetDownload` 전까지 예산을 사용합니다. 초과하는 시작 요청은 승인 핸들을 만들기 전에
거부합니다. 승인 뒤 metadata가 초과하면 조회는 `INTERNAL`이고 마지막 안전한 snapshot을
유지합니다. `cancelDownload`는 metadata 읽기와 독립적으로 취소하며 네이티브 Cancel 실패는
항목을 보존해 재시도할 수 있습니다. `paused`는 현재 interrupted 상태의 USER_PAUSED reason에서
조회하므로 브라우저 UI로 재개해도 최신 상태를 반영합니다.

### WebView 기본 제어

Windows와 macOS의 각 창은 WebView 하나를 소유합니다. 아래 작업도 `{ view, windowId? }`로
대상을 선택하고 작업마다 별도 `windows.<작업>` 권한을 요구합니다. multiple 뷰는
windowId가 필요합니다. 닫힌 창이나 다른 뷰의 ID는 `INVALID_ARGUMENT`이며,
WebView 생성 중에는 `BUSY`입니다. macOS는 single 뷰의 제어를 지원하며
`openDevTools`는 `UNSUPPORTED`입니다.

| 메서드 | 추가 입력 | 결과 |
| --- | --- | --- |
| `windows.getWebViewState` | 없음 | `{ url, title, loading, canGoBack, canGoForward, zoomFactor }` |
| `windows.navigateWebView` | `url: string` | 탐색 시작 뒤 `null` |
| `windows.reloadWebView` | 없음 | 일반 cache를 사용하는 reload 요청 뒤 `null` |
| `windows.stopWebView` | 없음 | 탐색과 리소스 로드 중단 요청 뒤 `null` |
| `windows.goBack` | 없음 | 이동을 시작하면 `true`, 이전 항목이 없으면 `false` |
| `windows.goForward` | 없음 | 이동을 시작하면 `true`, 다음 항목이 없으면 `false` |
| `windows.setZoomFactor` | `factor: number` | 브라우저가 실제 적용한 zoom factor |
| `windows.openDevTools` | 없음 | 개발 도구 창 열기 요청 뒤 `null` |

```ts
const target = { view: "main" };
const state = await windows.getWebViewState(target);
await windows.setZoomFactor({ ...target, factor: 1.25 });
if (state.canGoBack) await windows.goBack(target);
await windows.navigateWebView({ ...target, url: "https://app.bunaway.local/settings.html" });
```

URL은 1–8192자이며 NUL을 허용하지 않습니다. HTTP/HTTPS URL만 허용하며 대상 뷰의
기존 `origins`에 있어야 합니다. 자격 증명이 포함된 URL, file/data/javascript URL과
다른 origin은 `PERMISSION_DENIED`입니다. 허용한 URL의 redirect도 기존 탐색 및 리소스
검사를 통과해야 합니다. 이 API는 정책이나 로컬 파일 접근 범위를 추가하지 않습니다.

탐색, reload와 history 이동의 결과는 시작 여부이며 문서 완료가 아닙니다.
허용한 새 문서의 탐색이 시작되면 이전 SDK 세션과 진행 중 명령을 폐기합니다.
자기 문서를 바꾸는 화면 호출은 이전 연결에서 결과를 받지 못할 수 있으므로 새 문서에서
클라이언트를 초기화하세요. 같은 문서의 fragment 이동은 기존 세션과 documentGeneration을
유지합니다. Windows와 macOS에서는 완료와 실패를 `getReadiness` 또는 `windows.readiness`로 확인합니다.
`loading`은 허용된 최상위 문서의 탐색 시작부터 해당 탐색 완료까지이며 paint나 SDK 준비를
뜻하지 않습니다. Windows의 stop 취소 완료는 기존 준비 계약의 `cancelled` 상태로 전달합니다.
macOS의 `loading`은 WKWebView가 보고한 현재 로딩 상태입니다. 완료, 실패와 중단은 모두
false가 될 수 있으므로 성공 여부나 SDK 준비를 뜻하지 않습니다. 패키지 자산 URL은
내부 전송 scheme 대신 선언한 `https://app.bunaway.local` URL로 반환합니다.
macOS는 허용한 URL의 scheme과 hostname을 정규화한 뒤 패키지 자산 경로로 변환합니다.
대문자로 작성한 scheme이나 hostname도 같은 자산을 열며 query와 fragment는 유지합니다.
WKWebView가 history cache에서 문서를 복원하면 같은 history 항목을 다시 로드해
새 SDK 세션을 만듭니다. 이전 연결과 요청을 재사용하거나 재전송하지 않습니다.

factor는 유한한 0.25–5 값입니다. 1은 100%이며 CSS zoom과 visual zoom 한도 설정이
아닙니다. Windows에서는 대상 WebView2 controller에, macOS에서는 WKWebView의
공개 `pageZoom`에 적용하고 실제 값을 반환합니다. 창 간 zoom 설정은 독립적이며
macOS의 새 창이나 재생성한 창은 1로 시작합니다.
이 API는 origin별 zoom 공유 정책을 추가하지 않습니다. 탐색에 따른 zoom 값 변화는
WebView2의 동작을 따르므로 현재 값은 다시 조회합니다.

Windows의 openDevTools는 작업 권한과 호스트의 개발 모드 설정이 모두 필요합니다.
프로덕션 호스트는 작업 권한이 있어도 `PERMISSION_DENIED`입니다.
macOS는 공개 DevTools 제어 서비스를 제공하지 않으며 `UNSUPPORTED`입니다.
DevTools 닫기, 열림 상태와 이벤트, dock 설정은 아직 제공하지 않습니다.

창 종료의 native Cancel 실패는 해당 소유자의 참조를 보존하고 UI pump가 50 ms 간격으로
35초까지 재시도합니다. 다른 창의 메시지와 정리는 계속 처리합니다. 기한이 끝나면
닫힌 소유자의 native 정리를 보류하고 `download-cleanup-timeout` 진단을 남깁니다.
관찰한 broker 종료나 앱 종료에서 다시 안전하게 정리하며, 공유 broker를 종료해 정상
창을 닫거나 실패한 cleanup을 완료로 처리하지 않습니다. 취소된 snapshot의 interruptReason은
null이며 네이티브 USER_CANCELED reason을 interrupted 상태처럼 유지하지 않습니다.

### 부모, 모달과 신뢰된 종료

이 API는 Windows에서 지원합니다. `setParent`는 사전 선언된 두 창이 열린 뒤 호출합니다.
`view`는 제어할 정책 ID이고 선택적 windowId는 자식 창을 선택합니다.
`parent`는 현재 부모의 네이티브 `windowId`입니다. 같은 뷰의 두 창도 부모 관계를 맺을 수 있습니다.
`getParent`와 `getOwner`는 같은 관계를 반환합니다. Windows의 owner를 가진 최상위 창이며
다른 창의 내용 영역에 들어가는 child HWND는 아닙니다. 자기 자신, 순환 관계, 종료된
부모 ID는 `INVALID_ARGUMENT`입니다. 관계 변경에는 `windows.setParent` 작업 권한이 필요합니다.
관계 조회 권한은 작업마다 별도로 허용하며, 특정 창의 접근 제한은 앱 명령에서 검사합니다.

`modal: true`는 부모 입력을 즉시 차단합니다. 모달 창을 숨겨도 차단은 유지합니다.
같은 부모의 여러 모달과 중첩 모달을 지원하며 마지막 모달의 HWND와 WebView 정리가
끝나면 첫 차단 직전의 enabled 상태를 복원합니다. 이전 상태가 `false`이면 계속
비활성입니다. 차단 중인 부모의 `setEnabled`는 `BUSY`입니다. 모달의 부모를 바꾸려면
먼저 `parent: null, modal: false`로 해제합니다. `isEnabled`는 실제 HWND 상태를 읽으며
표시, 활성화나 준비 완료를 뜻하지 않습니다.

일반 `close`는 자식부터 모든 닫기 확인을 검사하고 거절하면 아직 살아 있는 창과 세션을
유지합니다. 부모와 자식이 마지막 창 집합이면 `beforeQuit`도 먼저 검사합니다.
취소나 훅 오류는 종료를 확정하지 않습니다. 부모가 승인되면 직접, 간접 자식을 함께
종료하며 각 자식 세션 철회, WebView 분리, HWND 파괴와 COM 및 프로세스 정리가 끝난 뒤
부모를 정리합니다. 소유 관계를 맺은 자식의 닫기는 트레이 숨김을 적용하지 않습니다.
동시에 진행 중인 일반 닫기나 관계 변경은 `BUSY`입니다.

`destroy`의 호출 주체는 신뢰된 앱 백엔드뿐입니다. setup의 백엔드 컨텍스트에서
호출할 수 있고, 뷰에서 시작한 명령은 `windows.destroy`를 허용해도
`PERMISSION_DENIED`입니다. 백엔드에는 `windows.destroy` 작업 권한을 허용해야 합니다.
`destroy`는 닫기 확인, 트레이 숨김과 `beforeQuit`를
우회하고 대기 중인 닫기와 재생성을 중단합니다. 부모의 destroy는 자식도 종료하며
부모 종료는 그 관계로 소유한 자식의 종료 권한을 포함합니다. 마지막 창을 destroy하면
앱은 기존 정상 정리 경로로 종료합니다. 앱 프로세스를 즉시 강제 종료하는 API는 아닙니다.
`closeBehavior: "keep-alive"`에서도 마지막 창의 destroy는 앱 종료를 확정합니다.
마지막 창의 재생성에서 이전 창 정리를 기다리는 동안 destroy해도 재생성을 취소하고
앱 종료를 확정합니다. 트레이가 있는 앱에도 같은 규칙을 적용합니다.
이미 닫혔거나 생성하지 않은 선언 창에는 `true`를 반환합니다.
종료 확정 뒤 앱이 끝나 호출 컨텍스트가 철회되면 마지막 창의 destroy 응답은
`CANCELLED`일 수 있습니다. 이 경우에도 창 종료는 확정되어 다시 열리지 않습니다.
이미 실행 중인 `beforeQuit` 함수 자체를 강제로 중단하지는 않습니다. 마지막 창의
destroy 뒤 정리는 훅 완료를 기다리지 않으며 늦은 결과로 종료를 다시 시작하지 않습니다.
이미 열린 Win32 닫기 확인은 동기 대화상자입니다. 그동안 큐에 들어온 destroy는
대화상자 응답 뒤 처리하며 추가 닫기 확인을 띄우지 않습니다.

```ts
// 신뢰된 백엔드 setup에서 사용합니다.
const parent = await windows.getReadiness({ view: "main" });
await windows.create({ view: "dialog" });
await windows.setParent({ view: "dialog", parent: parent.windowId, modal: true });
// 사용자가 거절할 수 있는 닫기입니다.
await windows.close({ view: "dialog" });
```

생성 완료는 기존대로 WebView 설정 완료입니다. 문서와 SDK 준비는 `getReadiness`와
`windows.readiness`로 구분합니다. 살아 있는 자식의 `recreate`와 `recreateInstance`는 부모 수명을 보존하고
새 자식 ID와 세션을 만듭니다. 기다리는 동안 부모가 종료되면 `CANCELLED`로 끝나며
같은 뷰의 새 부모에 자동으로 연결하지 않습니다. 닫힌 자식의 `create`는 소유 관계가
없는 새 창을 만듭니다. 생성 취소나 오류는 확인을 우회해 부분 자원을 정리합니다.
`close`와 `destroy`의 응답은 종료 확정 여부이며 비동기 네이티브 정리 완료를 뜻하지 않습니다.

| `windows.setCloseConfirmation` | `{ view, windowId?, message: string \| null }` | `Promise<null>`. 창을 닫기 전에 표시할 확인 메시지 설정. 문자열은 1–1024자, NUL 금지. `null`이면 확인 해제 |
| `windows.close` | `{ view, windowId? }` | `Promise<boolean>`. 닫기 승인 시 `true`, 확인이나 앱 종료를 취소하거나 트레이로 숨기면 `false`. 정리 완료를 기다리지는 않음 |
| `windows.respondClose` | `{ view, windowId?, requestId: number, allow: boolean }` | `Promise<null>`. 대기 중인 [닫기 요청](#닫기-요청)에 답함. 백엔드 또는 질문을 받은 창 자신의 문서만 호출할 수 있고 다른 호출자는 `PERMISSION_DENIED`. Windows와 macOS에서 지원 |

크기 제약과 `setSize`의 너비, 높이는 96 DPI 기준 논리 픽셀입니다. Windows가 현재 창의 DPI에 맞춰 실제 픽셀 크기로 변환합니다. 사용자 크기 조절, 최대화와 복원에도 제약을 적용합니다. 제약보다 작은 초기 크기와 `setSize` 값은 최소 크기로, 큰 값은 최대 크기로 보정합니다. 최소값이 최대값보다 크거나 값이 정수가 아니거나 200–4096 범위를 벗어나면 `INVALID_ARGUMENT`이며 기존 제약은 바뀌지 않습니다.
`setMinSize`와 `setMaxSize`는 지정한 쌍을 각각 교체하고 반대쪽 제약은 유지합니다. `setSizeConstraints`는 네 축 제약 전체를 교체하므로 전달하지 않은 축은 해제됩니다. 한 축에만 제약을 둘 수 있습니다.
제약의 기본값은 모두 `null`입니다. 앱의 제약을 해제해도 운영체제의 기본 크기 조절 범위는 유지됩니다.
실행 중 제약을 변경하면 현재 창도 새 범위 안으로 보정합니다. 최대화나 최소화 상태에서는 창 표시 상태를 유지하며 복원 크기에도 새 범위를 적용합니다. 전체화면 중에는 크기 제약 적용을 보류하고 설정 변경은 저장합니다. 전체화면을 해제하면 새 제약이 적용됩니다. 전체화면 상태에서 `setSize`나 위치를 바꾸면 `INVALID_ARGUMENT`이므로 먼저 전체화면을 해제하세요.
최대화된 창의 제약을 바꾸거나 해제하면 현재 모니터의 작업 영역과 새 제약으로 크기를 다시 계산합니다. 이 과정에서 창을 활성화하거나 숨긴 창을 표시하지 않으며, 다른 창에서 입력 중인 포커스를 유지합니다. 여러 모니터의 크기나 DPI가 달라도 대상 모니터를 기준으로 적용합니다.
최대화 상태에서 DPI가 변경되면 복원할 논리 크기는 유지하고 현재 최대화 크기를 다시 계산합니다.
전체화면을 해제하면 진입 전의 숨김 여부도 복원합니다. 숨긴 창은 복원 중에도 표시하거나 활성화하지 않습니다. 일반, 최소화와 최대화 상태에서 숨긴 창의 크기 제약이나 DPI가 바뀌어도 다른 창의 입력 포커스를 유지합니다.
전체화면 중 DPI가 변경되면 Windows가 제안한 위치로 대상 모니터를 선택하고 그 모니터의 실제 화면 영역을 채웁니다. 숨김 여부와 해제 시 복원할 크기는 유지합니다.
생성 완료는 WebView 준비를 뜻합니다. 웹 문서의 클라이언트 초기화 완료까지 기다리지는 않습니다.
아래 준비 조회와 이벤트로 네이티브 창, 웹 문서, SDK의 완료를 각각 확인합니다.

macOS는 뷰마다 독립된 임시 WebKit 프로필을 사용합니다. 같은 뷰를 재생성할 때는
프로필을 유지하고 앱 종료 후에는 남기지 않습니다. `focus`는 창을 표시하고 앱 활성화를
요청하며, `isFocused`는 앱이 활성 상태이고 해당 창이 key window인지 확인합니다.
`show`는 창을 표시하고 key window 전환을 요청합니다. 운영체제가 앱 활성화를 거절할
수 있으므로 포커스가 필요하면 `focus`의 결과를 처리하세요. macOS의 `close`는 닫기를
승인하며, 마지막 열린 창이면 기본 `desktop.closeBehavior: "quit"`에 따라 `beforeQuit` 승인 뒤 앱을 종료합니다.
`"keep-alive"`는 앱을 유지합니다. `desktop`은 트레이와 `"hide"`를 제외하고 지원합니다.
닫기 확인(`setCloseConfirmation`)은 아직 지원하지 않습니다. 아래 상태 변경, 크기와 닫기 확인 설명은 Windows의 동작입니다.
[닫기 요청](#닫기-요청)과 [창 수명 이벤트](#창-수명-이벤트)는 macOS에서도 같은 규칙으로 동작합니다.

## 창 식별자 조회

Windows의 네 탐색 메서드는 `WindowIdentity`인 `{ windowId, viewId }` 또는 `null`을 반환합니다.
`viewId`는 `app.windows`에 선언한 정책 뷰이며 뷰마다 창 하나를 유지합니다.
`windowId`는 `getSnapshot`과 같은 불투명 네이티브 수명 ID입니다. HWND나 `viewId`로
만들거나 추측하지 말고 반환된 값을 사용합니다.

같은 네이티브 창의 문서 탐색과 SDK 세션 교체는 `windowId`를 유지합니다. 닫았다 다시
생성하거나 `recreate`로 네이티브 창을 바꾸면 새 ID를 발급합니다. `getById`는 알 수 없는 ID와
이전 ID에 `null`을 반환합니다. 닫힌 창, 생성 전 창과 API 생성 또는 재생성 중인 창도
탐색 결과에서 제외합니다. 시작 창처럼 API 생성 작업이 없는 경우 HWND가 만들어진 뒤에는
WebView 준비 전에도 식별할 수 있습니다.

`getCurrent`는 입력으로 뷰를 받지 않으며 호스트가 인증한 `view:<viewId>` 출처를 사용합니다.
백엔드 호출에는 `null`, 잘못된 출처에는 `PERMISSION_DENIED`를 반환합니다.
`getFocused`는 OS 전경 창이 이 앱의 창일 때만 그 식별자를 반환합니다.
외부 앱이 전경이거나 전경 창이 없으면 `null`입니다.
`getLastActive`는 이 호스트에서 마지막으로 실제 활성화를 받은 창을 반환하며 기록이 없으면 `null`입니다.

네 탐색 메서드는 각각 자신의 작업 권한을 확인합니다. 권한이 없으면 `PERMISSION_DENIED`입니다.
조회 대상은 앱에 선언된 창이며 닫혔거나 교체 중인 창은 반환하지 않습니다.

마지막 활성 기록은 OS가 창을 활성화할 때만 갱신합니다. 비활성화 메시지, 문서 탐색과 조회
자체는 기록을 바꾸지 않습니다. 해당 네이티브 창을 파괴하면 기록을 삭제하며 이전 활성 창으로
되돌리지 않습니다. 다른 창을 파괴해도 기록을 유지합니다. 다만 blur, 종료나 숨김 과정에서 OS가
다른 앱 창을 실제로 활성화하면 그 활성화를 새로 기록합니다.
기록은 이 호스트 실행에만 유지하며 앱 종료 뒤에는 보존하지 않습니다.

macOS도 같은 다섯 조회(`getById`, `getCurrent`, `getFocused`, `getLastActive`, `listInstances`)를
제공합니다. 네이티브 창을 만들거나 재생성할 때마다 새 `windowId`를 발급하며 문서 탐색은 ID를
유지합니다. `getFocused`는 앱이 활성 상태일 때 key window를, `getLastActive`는 마지막으로
key window가 된 창을 반환하고 그 창을 닫으면 기록을 지웁니다. key window가 닫힐 때 AppKit이
다른 창을 key window로 바꾸면 그 창이 새 기록입니다. macOS는 뷰마다 창 하나만 지원하므로
`listInstances`는 열린 뷰마다 한 항목을 선언 순서로 반환하며 `createInstance`와
`recreateInstance`는 사용할 수 없습니다.

조회는 창 생성, 표시, 포커스나 활성화를 요청하지 않습니다. `getById`의 `windowId`는
1~128자의 영문, 숫자, `_`, `.`, `:`, `-` 문자열이며 잘못된 입력은 `INVALID_ARGUMENT`입니다.
호스트 종료와 호출 취소는 `CANCELLED`입니다. 식별자 추적을 제공하지 않는 플랫폼은
`UNSUPPORTED`, 네이티브 조회 실패는 `INTERNAL`을 반환합니다.

```ts
const current = await windows.getCurrent();
if (current) {
  const sameLifetime = await windows.getById({ windowId: current.windowId });
  const normal = await windows.isNormal({ view: current.viewId });
}
const focused = await windows.getFocused();
const lastActive = await windows.getLastActive();
const destroyed = await windows.isDestroyed({ view: "editor" });
```

## 표시와 활성 창 전환

다음은 Windows의 계약입니다. `blur`와 `activate`는 macOS에서 `UNSUPPORTED`이며,
macOS의 `showInactive`는 아래에서 따로 설명합니다. 여기서 활성 창과 포커스된 창은 `isFocused`와 같은 OS 전경 창을
뜻합니다. 창 안의 입력 요소로 키보드 포커스를 옮기는 API는 아닙니다.
API 표의 활성화 요청은 기본 `focusable: true` 기준입니다.
`false`에서는 [활성화 허용](#활성화-허용)의 비활성 표시와 상태 변경 계약을 적용합니다.

| API | 일반 창 | 숨긴 창 | 최소화한 창 | 최대화한 창 |
| --- | --- | --- | --- | --- |
| `show` | 표시하고 활성화 요청 | 숨김 해제하고 활성화 요청. 저장된 상태 유지 | 최소화 상태를 유지하며 표시 | 최대화 유지하며 표시하고 활성화 요청 |
| `showInactive` | 상태와 포커스 유지 | 숨김만 해제. 일반, 최소화 또는 최대화 상태 유지 | 최소화 유지하며 표시 | 최대화 유지하며 표시 |
| `hide` | 숨김 | 그대로 유지 | 최소화 상태를 보존하며 숨김 | 최대화 상태를 보존하며 숨김 |
| `focus` | 활성화 요청 | 표시하고 활성화 요청. 최소화했다면 복원 | 최소화 전 일반 또는 최대화 상태로 복원하고 활성화 요청 | 최대화 유지하며 활성화 요청 |
| `activate` | 전경 전환 요청 | 표시하지 않고 `false` | 복원하지 않고 `false` | 최대화 유지하며 전경 전환 요청 |
| `blur` | 활성 창이면 다음 허용 창으로 전환 | 그대로 유지하며 이미 비활성이면 `true` | 그대로 유지하며 이미 비활성이면 `true` | 최대화 유지하며 다음 허용 창으로 전환 |

`show`의 `null`은 표시 완료이며 포커스 획득을 보장하지 않습니다. `showInactive`는
활성화를 요청하지 않고 현재 입력 창과 그 안의 키보드 포커스를 유지합니다. 이미
표시된 창에 반복 호출해도 비활성화하거나 복원하지 않습니다. 최소화한 창도
`isVisible`은 `true`일 수 있으며 내용을 표시하려면 별도로 복원해야 합니다.
`hide`는 창과 WebView, 세션을 유지합니다. 활성 창을 숨기면 Windows가 다른 창을
선택할 수 있으며 다음 창을 지정하는 계약은 아닙니다.

`activate({ view })`의 대상은 앱 설정에 선언하고 이미 열린 창입니다. 임의 HWND,
다른 앱의 창이나 마지막 활성 창을 지정할 수 없습니다. 숨긴 창을 표시하거나
최소화한 창을 복원하려면 `focus`를 사용합니다. 표시된 비최소화 대상에는 호출 끝에
관찰한 전경 여부를 반환합니다. Windows가 전경 전환을 거부해 대상이 전경을 얻지
못하면 `false`이고 기존 표시 상태를 유지합니다. 이미 해당 창이 전경이면 `true`입니다.
기존 `focus`는 포커스를 얻지 못하면 `BUSY`입니다. 이 경우에도 먼저 적용한 표시와
최소화 복원은 되돌리지 않습니다.

`blur({ view })`는 숨긴 창이나 최소화한 창을 변경하지 않고 실제 비활성 여부를
반환합니다. 이미 비활성인 창도 변경 없이 `true`입니다. 표시된 비최소화 활성 창이면
`app.windows` 배열 순서에서 자신을 제외한 첫 번째 적격 창을 선택합니다. 후보는
앱에 선언된 열린 창 중 준비가 완료되고,
실패하거나 재생성 중이 아니며, 표시된 비최소화 창입니다. 최대화된 창도 후보입니다.
전환 후 원래 대상이 비활성이면 `true`, 후보가 없거나 Windows가 거부해 원래 대상이
계속 전경이면 `false`입니다. 첫 후보의 전환이 거부돼도 다음 후보로 재시도하지 않습니다.
다른 앱의 창을 고르거나 권한 없는 창을 활성화하지 않으며, 대상의 크기와 표시 상태,
세션은 유지합니다. 다음 창을 직접 지정하려면 `activate`를 호출하세요.

세 API는 각각 windows.showInactive, windows.activate, windows.blur 작업 권한이 필요합니다.
`blur`의 후보에도 동일한 호출 컨텍스트의 권한을 적용하고 backend 권한을 추가하지
않습니다. 작업 권한이 없으면 `PERMISSION_DENIED`, 허용된 미선언 뷰나 닫힌 창은
`INVALID_ARGUMENT`, 재생성 중인 대상은 `BUSY`입니다. OS가 요청한 표시 상태를
적용하지 못하거나 네이티브 조회가 실패하면 `INTERNAL`입니다.

Windows는 [전경 전환을 제한](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)합니다.
결과는 반환 시점의 관찰이며 이후 사용자 입력으로 달라질 수 있습니다.
강제 전경 전환이나 제한 우회, 입력 재전송은 하지 않습니다.
`windows.changed`는 실제 표시와 전경 상태가 바뀐 창에서만 발행합니다.
성공한 전환에서는 이전 창의 `blur`와 새 창의 `focus`가 각각 자기 뷰에 전달됩니다.
서로 다른 창의 이벤트 사이에는 전역 순서를 보장하지 않습니다. 거부나 반복 호출에서
상태가 바뀌지 않으면 이벤트를 만들지 않습니다. 조회한 snapshot의 상태와 revision은
동일한 관찰을 사용합니다.

macOS의 `showInactive`는 `orderFront:`로 창을 표시하며 key window 전환이나 앱 활성화를
요청하지 않습니다. 최소화한 창은 최소화 상태로 남습니다.

```ts
await windows.showInactive({ view: "editor" });
const activated = await windows.activate({ view: "editor" });
const blurred = await windows.blur({ view: "editor" });
```


## 창 준비

Windows의 `windows.readiness`는 준비 단계가 바뀔 때 현재 `WindowReadiness`를 전달합니다.
`windows.getReadiness({ view })`도 같은 형태를 반환합니다. 준비 조회 자체는 기다리지 않습니다.

```ts
type WindowReadiness = {
  windowId: string;
  viewId: string;
  documentGeneration: number;
  revision: number;
  nativeCreated: boolean;
  document: "pending" | "ready" | "failed" | "cancelled";
  sdk: "pending" | "ready" | "failed" | "cancelled";
  error: WireError | null;
};
```

| 단계 | 정확한 완료 조건 |
| --- | --- |
| 네이티브 창 | HWND 생성과 초기 크기, 제약 적용, 기존 `windowId` 발급 완료. 최초 이벤트는 `nativeCreated: true`, `revision: 0`. WebView2 생성 전 발행 |
| 웹 문서 | 허용한 최상위 탐색의 현재 NavigationId에 대한 WebView2 `NavigationCompleted`가 성공. iframe, 이전 탐색의 늦은 완료와 SDK 협상은 포함하지 않음 |
| SDK | 현재 세션에서 클라이언트가 서버 hello를 검증하고 협상을 수락한 뒤 보낸 준비 확인을 호스트가 수신. `client.ready`도 이 확인을 전송한 뒤 완료 |

SDK가 웹 문서보다 먼저 준비될 수 있습니다. 각 단계의 이벤트는 별도로 발생합니다.
문서 완료는 브라우저 탐색 완료이며 이미지 첫 프레임, 앱 데이터 로드와 UI 초기화 성공을 보장하지 않습니다.
SDK 완료도 앱 초기화 완료를 뜻하지 않습니다. 앱의 필요한 비동기 작업을 완료한 뒤 창을 표시하거나 splashscreen을 전환하세요.

수신 뷰에는 `events: ["windows.readiness"]`와 `windows.getReadiness` 작업 권한이 모두 필요합니다.
자기 창뿐 아니라 허용된 다른 창의 준비도 구독합니다. 권한이 없는 대상 창의 상태는 보내지 않습니다.
이벤트의 `source`는 `"native"`, `target`은 실제 수신 뷰이며 payload의 `viewId`는 준비된 창의 뷰입니다.
백엔드는 `getReadiness`로 조회합니다. 이벤트는 이력이나 재전송을 제공하지 않습니다.
구독에 실패하면 오류를 처리하고, 구독에 성공한 뒤 `getReadiness`로 이미 완료된 단계를 확인합니다.
조회와 이벤트를 합칠 때 현재 `windowId`를 기준으로 삼고 같은 창에서는 더 큰 `revision`만 적용합니다.

허용된 새 최상위 탐색은 이전 세션을 폐기하고 문서와 SDK를 `pending`으로 초기화합니다.
진행 중이던 이전 준비는 새 `documentGeneration`으로 대체되므로 해당 세대를 기다리던 작업을 취소합니다.
같은 NavigationId의 리디렉션은 세대를 다시 초기화하지 않습니다. 같은 문서의 fragment 변경도 상태를 유지합니다.
시작부터 거부된 외부 탐색은 현재 문서 준비를 유지합니다. 허용된 탐색 중 외부 리디렉션을 거부하면 그 준비는 취소됩니다.
SDK 연결 종료는 문서 상태를 유지하고 SDK를 `cancelled`로 바꿉니다. 명시적 새 연결의 SDK 준비는 다시 `pending`에서 시작합니다.
`documentGeneration`은 기존 세션 경계의 세대이므로 문서 교체 외에 세션 폐기 때도 증가합니다.
재생성은 새 `windowId`, `revision: 0`과 초기 준비 상태를 사용합니다. 이전 세션의 확인과 늦은 탐색 완료는 새 준비를 완료하지 않습니다.

탐색 실패는 `document: "failed"`, 네이티브 탐색 취소는 `"cancelled"`이고 아직 완료되지 않은 SDK 준비도 취소합니다.
이미 협상을 확인한 SDK는 세션이 살아 있는 동안 `ready`를 유지하지만 문서 준비 실패로 자동 표시와 전환은 차단됩니다.
SDK 협상 실패, 세션 오류와 기한 초과는 `sdk: "failed"`입니다. `error`는 가장 최근 준비 또는 세션 오류를 담습니다.
문서와 SDK가 각각 실패했으면 두 상태와 마지막 오류를 함께 확인합니다. 새 탐색은 오류를 지웁니다.
SDK 재연결은 문서가 실패 또는 취소 상태이면 마지막 오류를 유지하고, 그 외 상태이면 이전 오류를 지웁니다.
문서와 아직 시작하지 않은 SDK 준비는 탐색 시작 후 각각 30초를 기다립니다.
SDK 세션이 시작되면 그 세션의 준비 확인 기한은 10초입니다. 문서 기한과 독립적으로 검사합니다.
늦은 완료는 실패를 성공으로 바꾸지 않습니다. 새 탐색이나 명시적 새 SDK 연결로 다시 준비합니다.
WebView2 자체 생성 실패는 기존 호스트 시작 오류 계약을 따릅니다. 앱 종료 중에는 이벤트 전달이 보장되지 않습니다.
WebView 생성자가 실패해 HWND를 바로 회수한 시도는 생성 호출 오류로 확인하며 조회 상태에 남기지 않습니다.
창 닫기와 앱 종료는 준비를 취소하고 지연된 자동 표시를 막습니다. 생성된 적 없는 창은 조회 시 `INVALID_ARGUMENT`입니다.
닫힌 창의 마지막 준비 결과는 재생성 전까지 조회할 수 있습니다.
새 창 생성 요청을 WebView2 준비 중 취소하면 그 요청이 만든 창을 닫습니다.
재생성에서 이전 창의 닫기가 이미 확정되었다면 기존 세션 취소와 관계없이 교체를 마칩니다.

`visible: false`는 창을 숨긴 채 생성하고 유지합니다. 준비 중에 순간 표시하거나 포커스를 가져오지 않습니다.
`showWhenReady: "document"`는 문서가, `"sdk"`는 문서와 SDK가 모두 준비된 뒤 한 번 표시합니다.
이후 숨기거나 탐색해도 자동으로 다시 표시하지 않습니다. 재생성하면 선언한 옵션을 새 창에 다시 적용합니다.
명시적 `show`, `focus`와 표시를 동반하는 상태 제어는 준비 전에도 창을 표시할 수 있습니다.
자동 표시 시점부터는 일반 `show`와 같은 Windows 활성화 동작입니다. `focusable: false`이면 비활성 표시를 사용합니다.

`completeSplashscreen({ view: "main", splash: "splash" })`는 windows.completeSplashscreen 작업 권한을 먼저 검사합니다. 두 창은 앱 설정에 선언해야 합니다.
주 창이나 백엔드에서 호출해야 합니다. splash 창에서 호출하면 세션이 닫히기 전에 `INVALID_ARGUMENT`를 반환하며 창은 전환하지 않습니다.
서로 다른 열린 창이어야 하며 주 창의 문서와 SDK가 모두 준비되지 않았으면 `BUSY`입니다.
splash 창이 주 창의 직접 또는 간접 부모이면 `INVALID_ARGUMENT`이며 두 창을 변경하지 않습니다.
전환 전에 주 창의 소유 관계를 해제하거나 splash 창을 주 창의 자식으로 설정하세요.
앱은 데이터와 UI 초기화를 끝낸 뒤 이 API를 호출해 앱 준비를 알립니다.
주 창을 먼저 표시하고 splash 창의 닫기를 확정하므로 전환 중 마지막 창 종료 규칙을 실행하지 않습니다.
닫기 확인을 거절하면 주 창은 표시된 상태이고 splash 창도 유지하며 `false`를 반환합니다.
전환에서는 splash 창을 트레이로 숨기지 않고 닫습니다. `beforeQuit`는 실행하지 않습니다.
isolated splash의 임시 프로필도 최종 종료로 정리하며 다시 생성하면 새 프로필을 사용합니다.
그 뒤 마지막 주 창의 일반 닫기는 기존 종료 취소와 트레이 규칙을 따릅니다.
요청을 실행하기 전 취소하면 전환하지 않습니다. 이미 표시와 닫기를 확정한 뒤에는 그 변경을 되돌리지 않습니다.
macOS도 `getReadiness`와 `windows.readiness`를 같은 형태와 권한으로 제공합니다.
웹 문서 완료는 WKWebView 메인 프레임의 탐색 완료이고, 탐색 취소와 정책에 따른 중단은
`"cancelled"`입니다. SDK 완료는 승인된 세션의 준비 확인이며 문서와 SDK의 기한,
닫힌 창의 마지막 결과 보존, 창 닫기와 앱 종료의 `CANCELLED`("Window closed."
또는 "App shutdown."), 생성 실패의 `INTERNAL`, 생성 기한 초과의 `TIMEOUT`은 Windows와 같습니다.
`visible: false`와 `showWhenReady`로 숨겨서 생성한 창은 준비 중에 앞으로 나오거나 key window가
되거나 앱을 활성화하지 않습니다. 준비 조건을 만족하면 최초 표시와 같이 key window 전환과
앱 활성화를 요청해 한 번 표시합니다. macOS의 splashscreen 전환은 아직 지원하지 않습니다.

## 활성화 허용

`focusable: false`는 Windows의 [WS_EX_NOACTIVATE](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles)를 사용합니다.
해당 창은 사용자 클릭으로 활성화되지 않고 `show`는 비활성 표시를 사용합니다. `focus`는 새 활성화나
복원을 요청하지 않으며 이미 전경 창이면 성공, 아니면 `BUSY`입니다. `activate`도 새 활성화를 요청하지 않고
현재 전경 여부를 반환합니다. `blur` 후보에서는 이 창을 제외합니다. 설정 변경은 현재 전경 창을 강제로
비활성화하지 않으므로 `isFocusable: false`와 `isFocused: true`가 함께 관찰될 수 있습니다.
최소화, 최대화와 복원 API 및 해당 네이티브 버튼도 활성화를 요청하지 않습니다.
`desktop.show()`와 트레이 Open, 두 번째 실행의 표시 요청은 숨긴 창을 표시하고 최소화된 창을
복원합니다. `focusable: false`이면 전경 활성화를 요청하지 않으며 최소화 전 최대화 상태도 유지합니다.
이미 전경 창인 창을 최소화하면 OS는 다른 창으로 전경을 옮길 수 있습니다.
Windows 기본 동작상 이 스타일의 창은 작업 표시줄에 나타나지 않습니다. 작업 표시줄 강제 표시 옵션은 아직 없습니다.
표시, 위치와 크기를 유지하며 전체화면에서도 설정을 변경하고 유지합니다. 재생성은 선언 또는 생성 옵션으로 돌아갑니다.
trusted Win32 코드의 직접 활성화까지 막는 보안 경계는 아닙니다. setter/getter에는 각각의 operation 권한이 필요하며
닫힌 창은 `INVALID_ARGUMENT`입니다. macOS는 선언된 초기 focusable을 `UNSUPPORTED`로 거부합니다.

## 조회 단위와 좌표

조회의 `unit`은 `"physical" | "logical"`이며 기본값은 `"physical"`입니다. `dpi`는 해당 조회에 사용한 대상 창의 DPI입니다.
`setSize`는 계속 내용 영역의 96 DPI 논리 픽셀을 받고, `setPosition`은 창 바깥쪽 왼쪽 위의 화면 물리 픽셀을 받습니다.
`minimizable`, `maximizable`, `closable`의 기본값은 `true`입니다. 각 setter와 getter는 해당 이름의
operation 권한을 따로 요구하며 닫힌 창은 `INVALID_ARGUMENT`입니다. 최소화와 최대화 버튼 설정은
실제 일반 창 스타일을 조회하고 전체화면 중에는 복원할 스타일을 변경합니다.
`closable: false`는 닫기 버튼을 비활성화하고 시스템 메뉴, Alt+F4, WM_CLOSE와 렌더러의 닫기 요청을
막습니다. `isClosable`은 이 호스트 설정을 반환합니다. 전체화면 중의 변경도 유지하고 해제할 때
닫기 버튼에 반영합니다. 표시, 위치, 크기와 포커스를 유지하며 재생성하면 기본값으로 돌아갑니다.
프로그램의 `minimize`, `maximize`, `close`, `recreate`와 trusted `destroy`는 계속 사용할 수 있고
일반 close의 확인, 종료 취소와 부모 순서도 유지합니다. 렌더러 실패와 강제 호스트 정리는 이 설정으로 막지 않습니다.
이 설정은 프로그램의 권한이나 창 종료 정책을 대체하지 않습니다. fullscreenable은 아직 제공하지 않습니다.

`setTitle`은 지정한 창 수명의 제목만 변경합니다. 선언, 다른 인스턴스와 앱 이름을 바꾸지 않으며
재생성에서는 선언 또는 해당 생성의 `options.title`로 돌아갑니다. 표시, 크기와 포커스 상태를 유지합니다.
닫기 확인 대화상자의 caption도 현재 창 제목을 사용합니다. `getTitle`은 캐시 대신 실제 HWND를 읽으며
신뢰된 네이티브 코드가 빈 제목을 적용하면 빈 문자열을 반환합니다. 외부 코드가 지원 길이를 넘기는
제목을 적용했거나 OS 조회가 실패하면 `INTERNAL`입니다. 변경과 조회 권한은 각각 `windows.setTitle`,
`windows.getTitle`이며 닫힌 창은 `INVALID_ARGUMENT`입니다. 실행 중 icon 변경은 아직 제공하지 않습니다.
`resizable`과 `movable`의 기본값은 `true`입니다. 이 설정은 사용자 테두리, 제목 표시줄과
시스템 메뉴 조작에 적용하며 프로그램의 크기, 위치, 최대화와 전체화면 API는 계속 허용합니다.
`setResizable`은 일반 복원 창의 content 크기와 기존 크기 제약, 표시와 활성화 상태를 유지합니다.
정수 배율이 아닌 DPI에서도 기존 content의 물리 픽셀 수를 유지합니다. 논리 단위 조회의 반올림은 그대로 적용합니다.
테두리 두께가 바뀌면 outer 크기가 달라질 수 있습니다. 전체화면 중의 변경은 저장된 일반 창
스타일에 적용하고 전체화면을 해제할 때 반영합니다. `isResizable`도 이 일반 창 설정을 반환합니다.
`movable: false`여도 Windows의 DPI, 디스플레이 변경에 따른 위치 보정은 허용합니다.
각 설정과 조회는 해당 이름의 operation 권한을 따로 요구합니다. 닫힌 창은 `INVALID_ARGUMENT`입니다.
`center`는 `monitorId`를 생략하면 현재 창에 가장 가까운 모니터의 작업 영역을 사용하며 작업 표시줄 영역을 제외합니다.
`monitorId`는 모니터 조회 결과의 `id`입니다. 호출하는 시점에 연결된 모니터 목록에서 찾으며,
연결되지 않았거나 분리된 ID는 `INVALID_ARGUMENT`입니다. 이때 주 모니터나 현재 모니터로 대체하지 않고
창도 움직이지 않습니다. 모니터 열거에 실패하면 `INTERNAL`입니다.
창 크기, 표시, 최소화, 최대화와 포커스 상태를 유지합니다. 최소화나 최대화 중에는 복원할 일반 창의 위치만 바꿉니다. 이는 같은 DPI의 모니터에서의 동작이며, DPI가 다른 모니터는 아래 설명을 따릅니다.
작업 영역보다 큰 창도 크기를 바꾸지 않고 중앙에 배치합니다. 전체화면에서는 `INVALID_ARGUMENT`입니다.
DPI가 다른 모니터로 옮기면 Windows가 창 크기를 바꿀 수 있습니다. 일반 창은 배치 뒤 DPI 변경으로 크기가 바뀌었으면
숨김 여부와 관계없이 같은 작업 영역에서 바뀐 크기로 한 번 더 중앙에 배치합니다. 그 두 번째 이동에서 크기가 다시 바뀌면
운영체제의 DPI 처리를 따르므로 정확히 중앙이 아닐 수 있습니다. 최소화나 최대화 중에는 복원할 일반 영역을 배치하고
그 크기가 바뀌었으면 같은 방식으로 한 번 더 배치합니다. 다만 DPI가 다른 모니터를 지정하면 최대화 창의 위치와
복원 뒤 크기, 위치는 Windows의 DPI 처리를 따르며 실제 다중 모니터에서는 아직 검증하지 않았습니다.
`getOuterBounds`로 결과를 확인하고, 최소화나 최대화 중에는 `getNormalBounds`로 확인합니다.
권한은 `windows.center` 하나입니다. 이 호출은 모니터 정보를 반환하지 않고, `windows.getMonitor`나
전체화면처럼 창 기준의 모니터 선택도 해당 창 작업의 권한으로 동작하므로 모니터 조회 권한을 따로 요구하지 않습니다.
macOS에서는 `center` 자체를 지원하지 않아 `monitorId` 유무와 관계없이 `UNSUPPORTED`입니다.
따라서 `setSize` 뒤에는 `getContentSize({ view, unit: "logical" })`, `setPosition` 뒤에는 `getOuterPosition({ view })`으로 결과를 확인합니다.
제약에 따른 크기 보정과 운영체제의 배치 결과를 반환합니다.

내용 영역은 제목 표시줄과 테두리를 제외한 Win32 client 영역입니다. 바깥 영역은 제목 표시줄과 보이지 않는 크기 조절 테두리까지 포함합니다.
두 위치 모두 기본 모니터 왼쪽 위 `(0, 0)`을 원점으로 하는 가상 화면 좌표이며, 왼쪽이나 위에 놓인 모니터에서는 음수가 가능합니다.
내용 위치도 화면 좌표이므로 내용 영역 내부의 `(0, 0)`을 반환하지 않습니다. bounds의 오른쪽과 아래쪽 경계는 각각 `x + width`, `y + height`이며 해당 경계 픽셀은 영역에 포함하지 않습니다.

일반 상태에서는 현재 크기와 위치를 반환합니다. 숨긴 창도 현재 상태의 geometry를 조회하며 조회로 표시하거나 활성화하지 않습니다.
최대화 상태에서는 실제 최대화 영역을 반환합니다. 최소화 상태에서는 Win32의 최소화 위치와 client 크기를 그대로 반환하므로 음수의 화면 밖 위치나 0 크기가 나올 수 있습니다.
복원할 영역이 필요하면 `getNormalBounds`를 사용합니다. 전체화면에서는 현재 모니터를 채운 영역을 조회합니다.

`getNormalBounds`는 최대화나 최소화 전 일반 창의 바깥 영역입니다. Windows의 작업 영역 좌표를 화면 좌표로 보정하므로 작업 표시줄이 위나 왼쪽에 있어도 `setPosition`과 같은 원점을 사용합니다.
일반 창을 생성하거나 이동할 때 확인한 모니터를 복원 좌표 보정에 사용합니다. 작업 표시줄이 있는 모니터 경계에 창이 걸쳐 있어도 화면 위치를 반환합니다. 최대화한 창을 다른 모니터로 옮겨도 복원 위치가 원래 모니터에 남아 있다면 그 모니터의 작업 영역 오프셋을 적용합니다. 전체화면 중에도 저장된 복원 영역을 사용합니다.
최소화가 최대화 상태로 복원될 예정이어도 normal bounds는 일반 상태의 영역을 뜻합니다.
전체화면이 아닌 창에서 보존한 모니터가 분리되면 디스플레이 변경 메시지와 조회 시 복원 rectangle에 가장 가까운 유효 모니터로 좌표를 보정합니다. 분리 중에 조회하지 않아도 재연결 후 Windows가 옮긴 복원 위치를 유지합니다. 조회로 창의 위치나 표시 상태를 바꾸지는 않습니다.
전체화면에서는 원래 모니터의 화면 영역도 보존합니다. 핸들이 무효이면 이 화면 영역에 가장 가까운 유효 모니터를 찾으므로 같은 위치에 재연결된 모니터의 핸들이 바뀌어도 이후 조회는 다시 그 모니터의 작업 영역 오프셋을 사용합니다.
전체화면에서는 진입 전에 저장한 일반 위치와 크기를 조회합니다. 조회 시 현재 창 DPI와 현재 크기 제약으로 복원 크기를 계산하며 저장된 복원 상태는 변경하지 않습니다.
전체화면 해제는 저장된 일반 위치뿐 아니라 진입 전 최소화, 최대화와 숨김 상태도 복원하므로 해제 직후 현재 bounds가 normal bounds와 다를 수 있습니다.
모니터의 작업 영역, DPI나 크기 제약이 다시 바뀌면 실제 복원 결과도 바뀔 수 있습니다.

## DPI 변환

`value`는 `{ x, y }`, `{ width, height }`, `{ x, y, width, height }` 중 하나입니다. 부분적인 쌍이나 추가 필드는 거부합니다.
모든 입력은 정수이며 좌표는 -2147483648~2147483647, 크기는 0~2147483647입니다. 변환은 크기 제약을 적용하지 않으며 4096보다 큰 크기도 허용합니다.
소수, NaN, 무한대, 음수 크기와 범위 밖 입력은 `INVALID_ARGUMENT`입니다. 변환 결과가 같은 정수 범위를 넘는 경우도 `INVALID_ARGUMENT`입니다.
새 geometry 설정 API도 이 정수 범위를 사용하며 아래의 content 크기와 rectangle 경계 검사를 추가합니다. 기존 `setSize`와 `setPosition`의 입력 범위는 유지합니다.

물리 변환은 각 값에 `dpi / 96`, 논리 변환은 `96 / dpi`를 곱합니다. 위치도 화면 원점 `(0, 0)`을 기준으로 같은 배율을 적용합니다.
서로 다른 배율의 모니터를 연결한 화면 전체에 공통 논리 좌표계를 만들거나, 입력 위치가 놓인 모니터의 DPI를 선택하는 기능은 아닙니다.
대상 창이 모니터를 이동하고 DPI 변경 처리가 끝나면 이후 조회와 변환은 새 DPI를 사용합니다. 다른 호출 사이에는 DPI가 바뀔 수 있으므로 반환된 `dpi`를 함께 확인하세요.
크기, 위치와 bounds의 각 값을 가장 가까운 정수로 반올림합니다. 정확히 절반이면 양의 방향으로 반올림하며 `-0`은 `0`으로 반환합니다.
반올림 때문에 왕복 변환은 원래 값을 정확히 보존하지 않을 수 있습니다. bounds의 위치와 크기를 각각 반올림하므로 변환한 오른쪽 경계와는 1픽셀 차이가 날 수 있습니다.

명령 핸들러나 setup 안에서 다음과 같이 조회합니다.

```ts
import windows from "@bunaway/plugin-windows";

// 아래 호출은 명령 핸들러 또는 setup 내부에 둡니다.
const content = await windows.getContentSize({ view: "editor", unit: "logical" });
const outer = await windows.getOuterBounds({ view: "editor" });
const normal = await windows.getNormalBounds({ view: "editor" });
const converted = await windows.toPhysical({
  view: "editor",
  value: { width: 800, height: 600 },
});
```

모든 조회와 변환은 각각의 작업 권한과 열린 창이 필요합니다.

## 내용 위치, 바깥 크기와 bounds 설정

`setContentPosition`, `setOuterSize`, `setContentBounds`, `setOuterBounds`의 `unit`은
`"physical" | "logical"`이며 기본값은 `"physical"`입니다. 위치는 조회와 같은 화면 원점을
사용합니다. `setContentBounds`의 위치는 내용 영역 왼쪽 위이고 `setOuterBounds`는 창 바깥쪽
왼쪽 위입니다. bounds 호출은 위치와 크기를 함께 적용합니다. 위치나 크기 쌍의 일부를
생략하거나 추가 필드를 전달하면 `INVALID_ARGUMENT`입니다.

입력은 정수이며 좌표 범위는 -2147483648~2147483647, 크기 범위는 0~2147483647입니다.
논리 입력은 작업 시작 시 대상 창 DPI로 물리 픽셀로 변환합니다. 각 값을 가장 가까운 정수로
반올림하고 정확히 절반이면 양의 방향으로 반올림하며 `-0`은 `0`으로 처리합니다.
outer 크기에서는 현재 DPI의 일반 창 제목 표시줄과 테두리 크기를 빼서 content 크기를 구합니다.
이 content 크기를 논리 픽셀로 반올림한 결과가 두 축 모두 200~4096이어야 합니다.
따라서 0 크기, 테두리보다 작은 outer 크기와 이 범위를 벗어난 크기는 `INVALID_ARGUMENT`입니다.
범위 검사를 통과하면 기존 content 기준 최소 및 최대 크기 제약으로 보정합니다.
보정하지 않은 축의 물리 크기는 유지하며 보정한 축은 논리 제한값을 현재 DPI로 반올림해 적용합니다.
outer 크기는 테두리를 포함하므로 같은 숫자의 content 크기와 다릅니다.

content 위치를 outer 위치로 변환하고 크기 제약을 적용한 뒤, 물리 rectangle의 왼쪽, 위쪽,
오른쪽 `x + width`, 아래쪽 `y + height`가 모두 signed 32-bit 정수 범위에 있어야 합니다.
일반 복원 영역에 필요한 작업 영역 좌표도 같은 범위를 검사합니다. 변환 결과나 경계가
범위를 넘으면 `INVALID_ARGUMENT`이며 위치와 크기를 모두 유지합니다. 크기 제약도 바꾸지 않습니다.

일반 창에는 현재 영역을 적용합니다. 숨긴 창은 숨김 상태를 유지하고 표시하거나 활성화하지 않습니다.
최소화나 최대화 중에는 현재 표시 상태와 실제 영역을 유지하며 일반 상태로 복원할 영역만 바꿉니다.
숨긴 최소화, 최대화 창도 같은 규칙을 따릅니다. 이때 결과는 `getNormalBounds`로 확인하고
content 조회는 일반 상태로 복원한 뒤 사용하세요. 최소화 전 최대화 복원 이력은 유지하므로
`restore`가 최대화로 돌아갈 수 있습니다. 일반 영역을 바로 확인하려면 `unmaximize`를 사용합니다.
Windows는 복원 영역이 화면 전체를 벗어나면 위치를 보정할 수 있습니다.
운영체제의 배치 규칙은 [SetWindowPlacement](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowplacement)를 따릅니다.
이 동작은 기존 `setPosition`처럼 최소화나 최대화 중의 현재 outer 위치를 바꾸는 동작과 구분합니다.
전체화면에서는 네 설정을 `INVALID_ARGUMENT`로 거부하며 전체화면과 저장된 복원 영역을 유지합니다.

성공은 입력 숫자와 조회 숫자가 항상 같다는 뜻이 아닙니다. 반올림, 크기 제약, 모니터 이동 중
DPI 변경과 운영체제 배치를 반영한 실제 영역은 같은 단위의 조회로 확인합니다.
`windows.changed`의 bounds는 항상 현재 물리 outer 영역이며 `getOuterBounds`와 같습니다.
bounds 설정 중의 중간 위치와 크기는 발행하지 않고 적용 후 바뀐 `move`, `resize`를 한 관찰에
담습니다. 실제 영역이 그대로면 이벤트와 revision을 추가하지 않습니다.
최소화나 최대화 중 복원 영역만 바꿨을 때도 현재 영역이 그대로면 이벤트를 만들지 않습니다.
나중에 복원하면 실제 변경된 영역으로 이벤트를 발행합니다. 다른 OS 변경이 뒤따를 수 있으므로
이벤트와 `getSnapshot`의 windowId, revision을 함께 확인하세요.

네 설정도 각각의 작업 권한이 필요하며 권한을 먼저
검사합니다. 권한이 없으면 `PERMISSION_DENIED`, 허용된 미선언 뷰나 닫힌 창은
`INVALID_ARGUMENT`입니다. 창을 자동으로 열지 않습니다. 웹 호출의 두 번째 인자는
`signal`, `timeoutMs`를 지원하고 백엔드는 호출한 명령의 취소와 기한을 따릅니다.
작업 시작 전 취소와 종료는 `CANCELLED`로 실행을 막습니다. 시작한 동기 Win32 작업은
중간에 취소하거나 되돌리지 않으며 응답이 취소돼도 변경이 남을 수 있습니다.
네이티브 적용이나 조회 실패는 `INTERNAL`이며 OS가 이미 적용한 변경의 롤백은 보장하지 않습니다.

```ts
await windows.setContentBounds({
  view: "editor", x: 100, y: 120, width: 800, height: 600, unit: "logical",
});
const content = await windows.getContentBounds({ view: "editor", unit: "logical" });
await windows.setOuterBounds({
  view: "editor", x: -100, y: 50, width: 900, height: 700,
});
const outer = await windows.getOuterBounds({ view: "editor" });
```

## 창 상태 변경과 조회

최대화한 창을 최소화한 뒤 `restore`하면 최대화로 돌아갑니다. 일반 창을 최소화한 뒤에는 일반 크기로 돌아갑니다. `unmaximize`는 최소화 전 최대화 여부와 관계없이 일반 크기로 복원합니다. 최소화하지 않은 최대화 창에는 두 메서드 모두 일반 크기를 적용합니다. 복원 크기에는 현재 크기 제약을 적용합니다.

`toggleMaximize`는 호출 시 네이티브 최대화 여부를 기준으로 전환합니다. 최소화한 창은 현재 최대화 상태가 아니므로 최대화합니다. 이미 최소화한 창에 `minimize`, 이미 최대화한 창에 `maximize`를 다시 호출해도 해당 상태를 유지합니다.

전체화면 중에는 `minimize`, `maximize`, `unmaximize`, `restore`, `toggleMaximize`를 `INVALID_ARGUMENT`로 거부하고 전체화면과 복원 정보를 유지합니다. 먼저 `setFullscreen({ view, fullscreen: false })`로 해제하세요. 전체화면 중에도 상태 조회는 가능합니다. 전체화면과 최대화는 별개 상태이며 전체화면 진입 전 최대화 여부를 유지할 수 있습니다.

숨긴 창에 다섯 상태 변경을 호출하면 창을 표시합니다. `minimize`는 최소화된 표시 상태로 만들며 대상 창의 포커스를 요청하지 않습니다. 나머지는 대상 창의 활성화를 요청하지만 OS의 전경 전환 정책에 따라 포커스를 얻지 못할 수 있습니다. 상태 변경 성공은 포커스 획득을 보장하지 않습니다. 반드시 포커스가 필요하면 `focus`를 호출하고 실패를 처리하세요. 조회는 창을 표시하거나 포커스를 바꾸지 않습니다.

최소화, 최대화, 표시 여부와 전경 창 여부는 호출할 때 Windows에서 읽습니다. 전체화면은 해당 HWND에 적용한 호스트의 전체화면 모드입니다. `isVisible`은 다른 창에 가려졌는지나 화면 안에 있는지까지 판정하지 않습니다. 조회 결과는 그 시점의 상태이며 이후 사용자의 창 조작으로 바뀔 수 있습니다.

`isNormal`은 숨긴 창이나 포커스가 없는 창에도 `true`일 수 있습니다. `isDestroyed`는
아직 생성하지 않은 `startup: false` 뷰와 닫기가 수락된 창에도 `true`를 반환합니다.
API 생성 작업이 없고 살아 있는 HWND가 있으면 WebView 준비 전에도 `false`입니다. 이 조회는 창을 생성하거나
문서 준비를 기다리지 않습니다. 트레이로 숨기거나 닫기를 거절한 창은 destroyed가 아닙니다.

제어와 상태 조회 모두 각 작업 이름을 허용해야 합니다. windows.list만으로는
상태를 조회할 수 없습니다. 권한을 먼저 검사하며 권한이 없으면 대상의 선언 여부와 관계없이
`PERMISSION_DENIED`입니다. 허용된 미선언 뷰는 `INVALID_ARGUMENT`입니다.
`isDestroyed`를 제외한 상태 조회는 닫힌 창에 `INVALID_ARGUMENT`를 반환합니다.
API 생성 또는 재생성 중인 창은 `isDestroyed`를 포함해 `BUSY`입니다.

웹 UI에서는 두 번째 인자로 `signal`, `timeoutMs`를 사용할 수 있습니다. 백엔드 호출은 명령의 취소와 기한을 따르며 별도 취소 옵션을 전달하면 `INVALID_ARGUMENT`입니다. 네이티브 작업 시작 전 취소는 실행을 막습니다. 시작한 작업은 동기 실행하며 이후 취소는 창 상태 변경을 되돌리지 않습니다. OS가 요청한 표시 상태를 적용하지 못하거나 네이티브 조회가 실패하면 `INTERNAL`입니다.

```ts
await windows.maximize({ view: "editor" });
await windows.minimize({ view: "editor" });
await windows.restore({ view: "editor" });
const maximized = await windows.isMaximized({ view: "editor" }); // true
await windows.unmaximize({ view: "editor" });
```

## 닫기 확인과 수명

`setCloseConfirmation`은 창의 닫기 버튼, 웹 UI의 `window.close()`, `windows.close`,
열린 창의 `windows.recreate`에 같은 운영체제 확인 대화상자를 적용합니다.
기본 선택은 거절이며 거절하면 창과 세션을 유지합니다. 재생성을 거절하면 `CANCELLED`입니다.
`desktop.closeBehavior: "hide"`이면 닫기 버튼, `window.close()`와 `windows.close`는
확인 대화상자 없이 해당 창을 숨기며 세션을 유지합니다. 기본 `"quit"`에서 마지막 창을 닫을 때는
`desktop.beforeQuit`의 승인도 기다립니다. 종료가 취소되면 `windows.close`는 `false`를 반환합니다.
`"keep-alive"`에서는 닫기 확인 뒤 마지막 창도 실제로 닫고 `true`를 반환하며 앱 백엔드는 계속 실행합니다.
이 닫기는 `beforeQuit`를 호출하지 않습니다. 트레이 Quit 또는 `DesktopContext.quit()`으로 종료를 요청합니다.
`windows.recreate`는 닫기 확인을 적용하지만 트레이 숨김과 앱 종료 검사를 거치지 않습니다.
브라우저 프로세스가 종료되면 확인 없이 해당 창을 닫고 세션을 종료합니다.
저장이 끝난 뒤에 닫기를 허용하려면 아래 [닫기 요청](#닫기-요청)을 사용합니다.
요청을 구독하지 않으면 닫기 확인 메시지 외의 비동기 저장 훅은 없습니다.
확인 대화상자가 열려 있는 동안 같은 UI의 다른 Host 작업은 대기할 수 있습니다.

숨긴 창도 열린 창입니다. 기본 `"quit"`에서 마지막 열린 창의 닫기가 승인되면 앱이 종료되며, 종료 후 API로 창을
다시 만들 수 없습니다. 재생성 중에는 교체가 끝날 때까지 앱의 자동 종료를 보류합니다.
앱 종료 처리는 새 확인 대화상자를 띄우지 않습니다. 이미 열린 확인 대화상자가 있으면
닫혀야 UI 정리가 진행됩니다. 강제 종료는 확인 결과를 기다리지 않습니다.

### 닫기 요청

앱이 비동기 저장을 마친 뒤에 닫기를 허용하려면 닫히는 창의 문서가 `windows.closeRequested`를
구독하고 `windows.respondClose`로 답합니다. 구독하지 않으면 위의 닫기 확인과 종료 검사만 적용합니다.
이 흐름은 Windows와 macOS에서 같은 규칙으로 동작합니다. macOS의 사용자 닫기는 타이틀바의 닫기 버튼과
공개 `windows.close`입니다. WebView의 `window.close()`는 macOS에서 처리하지 않으므로 요청을 보내지 않습니다.
macOS는 닫기 확인 메시지를 지원하지 않아 아래의 닫기 확인 관련 설명은 Windows에만 해당합니다.

대상 창의 현재 문서가 `windows.closeRequested`를 구독했고 그 뷰에 `windows.respondClose` 작업 권한이 있으면,
사용자 닫기는 닫기 확인보다 먼저 그 창 자신의 문서에 `{ windowId, viewId, requestId }`를 보내고 답을 기다립니다.
대상은 창의 닫기 버튼, Alt+F4와 시스템 메뉴, 웹 UI의 `window.close()`, 공개 `windows.close`입니다.
`requestId`는 같은 windowId 안에서 증가하는 양의 정수입니다.

`windows.respondClose({ view, windowId?, requestId, allow })`는 `null`을 반환합니다.

- `allow: false`는 창을 유지합니다. 사용자 닫기는 아무 일도 없던 것처럼 끝나고 `windows.close`는 `false`를 반환합니다.
- `allow: true`는 그 창 자신의 닫기 확인만 건너뛰고 닫기를 계속합니다. 소유한 자식 창의 닫기 확인,
  마지막 창이면 `beforeQuit`, 닫기 자체는 기존 순서대로 실행합니다.
- 대기 중인 요청이 아닌 `requestId`는 `INVALID_ARGUMENT`("No pending close request.")입니다.
  이미 답했거나 취소된 요청, 보낸 적 없는 요청, 이전 요청에 대한 늦은 답이 해당합니다.
- 요청이 대기 중일 때 같은 창의 반복 사용자 닫기는 무시하고
  공개 `windows.close`와 `windows.recreate`는 `BUSY`로 실패하고 대기는 계속됩니다.

`respondClose`는 신뢰된 백엔드 또는 질문을 받은 창 자신의 문서만 호출할 수 있습니다. 다른 창의 문서가
호출하면 유효한 `requestId`여도 `PERMISSION_DENIED`로 실패하고 요청은 그대로 대기합니다.

요청은 답 없이 끝날 수 있으며 이때 창은 열려 있습니다. 창의 문서가 다른 곳으로 탐색하거나 세션이 철회되면,
마지막 `windows.closeRequested` 구독을 해제하면, 또는 이벤트를 전달할 수 없으면 요청을 취소합니다.
강제 닫기, 신뢰된 `windows.destroy`, 앱 종료와 세션 종료는 창을 닫고 대기를 끝냅니다.
다음 닫기는 요청을 보내지 않습니다.
대기 중이 아닐 때의 `windows.recreate`는 질문 없이 창을 닫고 다시 만듭니다.
`closeBehavior: "hide"`의 숨김, splashscreen 전환, 부모와 함께 닫히는 자식 창에도
요청을 보내지 않습니다.

대기에는 자동 기한이 없으므로 앱이 반드시 답해야 합니다. 신뢰된 `windows.destroy`와 앱 종료는 대기 중에도
진행합니다. 대기 중에 마지막 `windows.closeRequested` 구독을 해제하면 요청을 취소하고 창은 열려 있습니다.
리스너가 예외로 끝나 구독이 사라지는 경우도 같으므로 실패해도 답하도록 `try/finally`로 감싸세요.

```ts
import { createClient } from "@bunaway/client";
import windows from "@bunaway/plugin-windows";
import type { CommandsOf, EventsOf } from "@bunaway/backend";
import type app from "../../src-bunaway/app";

const client = createClient<CommandsOf<typeof app>, EventsOf<typeof app>>();
await client.ready;
const release = await client.listen("windows.closeRequested", async ({ payload }) => {
  let saved = false;
  try {
    saved = await saveDraft(); // 앱이 정의한 비동기 저장 함수입니다.
  } finally {
    // 저장이 실패해도 답해야 창이 대기 상태로 남지 않습니다.
    await windows.respondClose({
      view: "editor",
      windowId: payload.windowId,
      requestId: payload.requestId,
      allow: saved,
    });
  }
}, { onError: (error) => console.error(error.code, error.message) });
// 컴포넌트 정리에서 await release()를 호출하고 공유 클라이언트는 유지합니다.
```

구독하려면 해당 뷰의 `events`에 `"windows.closeRequested"`를, 답하려면 `commands`에
`"plugin.windows.respondClose"`와 호출 뷰의 `host.permissions`에 `"windows.respondClose"`를 추가합니다.

### 재생성

재생성은 기존 창의 크기 변경, 크기 제약, 전체화면과 확인 메시지를 초기화하고 초기 설정을 다시 적용합니다.
앱 상태와 뷰 프로필은 유지합니다. Windows의 저장 프로필과 macOS의 실행 중 임시 프로필을 구분합니다.
앱은 새 웹 문서에서 클라이언트를 초기화하고 이벤트 구독을 다시 등록해야 합니다.
자신의 창을 닫거나 재생성한 요청은 기존 세션 종료로 `CANCELLED`가 될 수 있습니다.
이미 승인한 재생성은 이전 세션이 종료되어도 새 창을 만듭니다.
이미 닫힌 창의 정리를 기다리는 생성 요청은 새 창을 만들기 전에 취소할 수 있습니다.
이 대기 중에 요청을 보낸 뷰의 세션이 종료되면 생성을 취소하고 창을 다시 열지 않습니다.

## 창 이벤트

`windows.changed`와 `windows.getSnapshot`은 현재 Windows에서만 지원합니다. `windows.lifecycle`과
`windows.closeRequested`는 Windows와 macOS에서 지원합니다.

`windows`는 `windows.changed`, `windows.readiness`, `windows.lifecycle`, `windows.closeRequested`를 등록합니다. 기존 `client.listen`과 직접 함수
`listen`으로 구독하며, 이벤트 payload 타입은 앱의 `EventsOf`에서 추론합니다.
`windows.changed`는 생성한 창의 정책 뷰에만 전달합니다. 다른 창을 제어하도록 허용해도
그 창의 changed 이벤트가 호출한 뷰로 전달되지는 않습니다. `windows.readiness`의 수신 대상은
위의 창 준비 계약을 따릅니다.

구독하려면 해당 뷰의 `events`에 `"windows.changed"`를 허용합니다. 구독 자체는
창 제어 권한을 요구하지 않습니다. 현재 상태를 조회하려면 `commands`에
`"plugin.windows.getSnapshot"`과 호출 뷰의 `host.permissions`에 `"windows.getSnapshot"`을
추가합니다. 설치와 플러그인 등록만으로 권한이 생기지 않습니다.

payload는 `{ windowId, viewId, revision, state, bounds, changes }`입니다.
`windowEvents["windows.changed"]`는 `moved`, `resized`를 포함하는 공개 payload schema입니다.
`windowId`는 네이티브 창 인스턴스마다 새로 발급하는 불투명 식별자이고,
`viewId`는 설정과 정책의 뷰 ID입니다. HWND를 공개하지 않습니다.
envelope의 `source`는 `"native"`, `target`은 수신 뷰 ID입니다.
백엔드에서 같은 스키마의 이벤트를 발행할 때는 기존 `"backend"` 출처를 유지합니다.

`state`는 `visible`, `focused`, `minimized`, `maximized`, `fullscreen`을 가집니다.
각 값은 기존 `isVisible`, `isFocused`, `isMinimized`, `isMaximized`, `isFullscreen`과
의미가 같습니다. `focused`는 WebView 내부 포커스를 포함한 OS 전경 창 여부입니다.
normal 상태는 최소화, 최대화와 전체화면이 모두 `false`인 상태입니다.
`bounds`는 기본 단위의 `getOuterBounds`와 같은 `{ x, y, width, height, dpi }`입니다.
좌표와 크기는 프레임을 포함한 물리 화면 픽셀이고, 최소화 시에는 네이티브 iconic
bounds를 반환합니다. 논리 좌표가 필요하면 기존 변환 API를 사용합니다.

`changes`는 아래 이름 중 실제로 달라진 항목만 포함하며, 같은 관찰에서는 표의 순서를
따릅니다. 빈 이벤트는 발행하지 않습니다.

| 이름 | 관찰한 전환 |
| --- | --- |
| `shown`, `hidden` | 네이티브 visible 값의 변경 |
| `focus`, `blur` | OS 전경 창 여부의 변경 |
| `unmaximize` | 최대화 상태 해제. 최소화로 바뀐 경우에도 포함 |
| `minimize` | 최소화 상태 진입 |
| `maximize` | 최대화 상태 진입 |
| `restore` | 최소화에서 복원하거나 최대화에서 일반 상태로 복원 |
| `enterFullscreen`, `leaveFullscreen` | 호스트 전체화면 상태 진입과 해제 |
| `move` | outer bounds의 x 또는 y 변경 |
| `resize` | outer bounds의 width, height 또는 DPI 변경 |
| `moved` | 네이티브 사용자 이동/크기 조절 루프 종료. 시작보다 최종 outer x 또는 y 변경 |
| `resized` | 같은 루프 종료. 시작보다 최종 outer width, height 또는 DPI 변경 |

API 호출과 사용자 조작은 같은 네이티브 관찰 경로를 사용합니다. 이벤트는 요청의
시작이 아니라 Windows가 반영한 상태를 알립니다. OS가 포커스 요청을 거부하고
상태가 바뀌지 않으면 focus 이벤트가 없습니다. 같은 값으로 반복 호출하거나
동일한 Win32 메시지가 반복되면 중복 이벤트가 없습니다. 전체화면 전환 중의
스타일과 placement 중간 상태는 보류하고 전환이 끝난 snapshot을 발행합니다.
명령 완료 응답과 이벤트 수신의 상대 순서는 보장하지 않습니다.

연속 move/resize는 관찰한 변경마다 FIFO로 전달합니다. Windows의 `WM_ENTERSIZEMOVE`와
`WM_EXITSIZEMOVE` 사이를 사용자 조작 하나로 추적하며 종료 때 실제 시작/최종 geometry가
달라진 축의 `moved`, `resized`를 순서대로 전달합니다. 이 최종 알림은 마지막 중간 관찰과
같은 bounds여도 새 revision을 사용합니다. 이동을 시작했지만 최종 geometry가 시작과 같으면
최종 알림이 없으며 반복 종료 메시지도 중복 발행하지 않습니다. 루프 밖의 geometry API에는
기존 move/resize만 발행합니다. debounce와 손실 없는 OS 입력 이력은 제공하지 않습니다. Windows가 메시지를 합치면
그 중간 좌표까지 복원할 수는 없습니다. 구독별 wire sequence는 1부터 증가하며
그 구독에서만 의미가 있습니다. `revision`은 창별 관찰 순번이고 재생성하면 0부터
다시 시작합니다. 여러 changes를 포함한 한 snapshot에는 revision 하나를 사용합니다.

네이티브 Worker의 미확인 이벤트 용량은 앱 전체 128개입니다. 포화되면 손실이 생긴
대상 세션을 `BUSY`로 종료해 요청과 구독을 정리합니다. Core의 구독별 대기 용량도
128개이고, 초과하면 그 구독을 마지막 `subscription-error`의 `BUSY`로 종료합니다.
서버 전송 대기열 포화는 기존 세션 `BUSY` 계약을 따릅니다. 취소와 종료 용량은
별도로 유지합니다. `onError`에서 오류를 처리한 뒤 연결과 구독을 다시 만들고 조회로
현재 상태를 복구하세요.

### 구독 후 현재 상태 복구

초기 이벤트와 과거 이력은 재전송하지 않습니다. UI 초기화에서 클라이언트의 준비와
실패를 처리하고, 먼저 구독한 다음 `windows.getSnapshot({ view })`을 호출합니다.
이 조회는 이벤트와 같은 식별자, revision, 상태와 bounds를 반환합니다. 조회와
버퍼에 남은 이벤트가 엇갈릴 수 있으므로 같은 windowId에서는 더 큰 revision만
적용합니다. `getSnapshot`은 상태가 바뀌지 않으면 revision을 늘리지 않습니다.

```ts
import { createClient } from "@bunaway/client";
import windows, { type WindowOutput } from "@bunaway/plugin-windows";
import type { CommandsOf, EventsOf } from "@bunaway/backend";
import type app from "../../src-bunaway/app";

const client = createClient<CommandsOf<typeof app>, EventsOf<typeof app>>();
await client.ready;
let current: WindowOutput<"windows.getSnapshot"> | undefined;
function apply(next: WindowOutput<"windows.getSnapshot">) {
  if (current?.windowId === next.windowId && current.revision >= next.revision) return;
  current = next;
  // current.state와 current.bounds로 화면을 갱신합니다.
}
const release = await client.listen("windows.changed", ({ payload }) => apply(payload), {
  onError: (error) => console.error(error.code, error.message),
});
apply(await windows.getSnapshot({ view: "main" }));
// 컴포넌트 정리에서 await release()를 호출하고 공유 클라이언트는 유지합니다.
```

구독 해제 완료 후 해당 콜백을 호출하지 않습니다. 이미 채널에 있던 이벤트도
비활성 구독 ID로는 전달하지 않습니다. 새 문서로 탐색, SDK pagehide, 세션 종료와 창 재생성은
이전 구독을 폐기합니다. 새 문서는 새 클라이언트 세션에서 구독과 조회를 다시 합니다.
같은 창의 문서 탐색은 windowId를 유지하고, 네이티브 창 재생성은 새 windowId를
발급합니다. 창의 생성과 닫힘은 아래 `windows.lifecycle`로 구독하고,
준비 단계는 위의 `windows.readiness`와 `getReadiness` 계약으로 확인합니다.
앱 종료가 시작되면 새 발행과 늦은 콜백을 차단하고, 호스트가 네이티브 observer,
HWND와 콜백을 기존 WebView 및 Worker 종료 순서에 맞춰 정리합니다.

### 창 수명 이벤트

`windows.lifecycle`은 창 인스턴스의 수명 전환을 알립니다. payload는 `{ windowId, viewId, phase }`이며
`phase`는 다음 네 값입니다.

| phase | 의미 |
| --- | --- |
| `created` | 네이티브 창과 WebView 컨트롤러가 생성됨 |
| `ready` | 그 windowId의 첫 문서가 ready가 됨. 이후 탐색은 다시 발행하지 않음. 준비 실패나 취소에서는 발행하지 않음 |
| `closed` | 닫기가 확정되어 세션을 철회함. 부모와 함께 닫히는 자식, 강제 닫기와 재생성 전의 창도 포함 |
| `destroyed` | 네이티브 창과 WebView 자원을 해제함. 항상 `closed` 뒤 |

각 phase는 windowId마다 최대 한 번, 위 순서로 발행합니다. 재생성하면 이전 windowId의 `closed`, `destroyed`와
새 windowId의 `created`, `ready`가 이어집니다. 생성 실패는 `created` 전에 끝나면 이벤트가 없습니다.
앱 종료나 세션 종료가 시작된 뒤에는 발행하지 않습니다. 닫히는 창 자신의 세션은 먼저 철회되므로
그 창의 문서는 자신의 `closed`와 `destroyed`를 받지 못하고 다른 창의 뷰가 받습니다.

수신하려면 뷰의 `events`에 `"windows.lifecycle"`을 허용하고 `host.permissions`에 `"windows.listInstances"`를
추가합니다. 열린 모든 창의 수명을 알리므로 창 목록 조회와 같은 권한이 필요합니다.
`windows.changed`와 달리 정책 뷰가 같은 창만 받는 것이 아니라 두 권한을 가진 열린 뷰 모두에게 전달합니다.
초기 이벤트와 과거 이력은 재전송하지 않으므로 구독 전에 열린 창은 `windows.list`로 확인합니다.

### 닫기 요청 이벤트

`windows.closeRequested`는 `{ windowId, viewId, requestId }`입니다. 닫히려는 창 자신의 현재 문서에만
전달하며, 그 문서가 구독하고 `windows.respondClose`를 호출할 수 있을 때만 사용자 닫기를 대기시킵니다.
흐름과 답하는 방법은 [닫기 요청](#닫기-요청)을 따릅니다.

## 작업 표시줄 진행률

Windows의 `windows.setTaskbarProgress({ view, windowId?, state, value? })`는 선택한 창의
작업 표시줄 버튼에 진행률을 설정하고 `null`을 반환합니다.
`windows.setTaskbarProgress` 권한을 독립적으로 허용해야 합니다. macOS는 `UNSUPPORTED`입니다.
다중 창의 windowId와 권한 규칙은 다른 창 제어와 같습니다.

| state | value | 동작 |
| --- | --- | --- |
| `"none"` | 허용하지 않음 | 진행률 표시를 제거합니다. |
| `"indeterminate"` | 허용하지 않음 | 전체 작업량을 알 수 없는 진행 상태입니다. |
| `"normal"` | 필수 | 일반 진행률을 설정합니다. |
| `"paused"` | 필수 | 일시 중지 상태와 진행률을 설정합니다. |
| `"error"` | 필수 | 오류 상태와 진행률을 설정합니다. |

value는 유한한 0~1의 비율이며 네이티브 호출에는 백만분의 일 단위로 반올림합니다.
1을 전달해도 표시를 자동으로 제거하지 않습니다. 작업 완료나 취소 때 `none`을 호출하세요.

```ts
await windows.setTaskbarProgress({ view: "main", state: "normal", value: 0.25 });
await windows.setTaskbarProgress({ view: "main", state: "paused", value: 0.25 });
await windows.setTaskbarProgress({ view: "main", state: "none" });
```

WebView 준비와 작업 표시줄 버튼 준비는 별개입니다. Windows가 버튼 생성 메시지를
전달하기 전에는 `BUSY`이며 설정을 저장하지 않습니다. 처음부터 숨긴 창은 `show`로 표시하고
버튼 생성 이후에 다시 호출하세요. 버튼이 없는 환경에서는 계속 `BUSY`일 수 있습니다.
호출은 창의 표시, 포커스와 최소화 상태를 바꾸지 않습니다.

성공은 ITaskbarList3의 요청 처리가 완료됐다는 뜻입니다. 그룹으로 묶인 창의 진행률 선택과
고대비 모드의 표시는 Windows가 결정하므로 창별 설정이 모두 동시에 보인다는 뜻은 아닙니다.
[Windows 작업 표시줄 상태 계약](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itaskbarlist3-setprogressstate)을 따릅니다.
Explorer가 버튼을 다시 만들면 마지막 성공 설정을 다시 적용합니다. 이 비동기 복원에 실패하면
진단을 기록하며 앱이 명시적으로 다시 호출할 수 있습니다. HWND 파괴와 창 재생성은 설정을 폐기합니다.
네이티브 실패는 `INTERNAL`이며 값과 상태 중 일부가 이미 변경됐을 수 있습니다.

## 오류

`PERMISSION_DENIED`는 대상 창 권한이 없거나 호스트가 정책상 호출을 거부한 경우입니다.
view 형식이나 입력이 잘못되면 `INVALID_ARGUMENT`입니다. 열린 창을 요구하는 작업은 닫힌 대상에도 `INVALID_ARGUMENT`를 반환합니다. 대상 창 권한을 먼저 검사하므로 설정에 없는 view의 조회나 변환은 `PERMISSION_DENIED`입니다.
동시에 같은 창을 생성하거나 재생성하는 작업은 `BUSY`입니다.
호출 수명 종료, 호출 취소와 종료 중인 작업은 `CANCELLED`입니다.
macOS는 setup 중에도 종료 시 대기 중인 Host API 호출을 `CANCELLED`로 끝내고,
완료된 setup의 정리 훅을 실행합니다.
닫기 확인을 거절하면 `windows.close`는 `false`를 반환하고 `windows.recreate`는 `CANCELLED`로 실패합니다.
생성이나 네이티브 호출 실패는 `INTERNAL`입니다.
[오류 처리](/guides/cancellation-and-errors/)도 확인하세요.

completeSplashscreen은 주 창과 splash 선언 모두 single이어야 합니다. multiple 선언은 `INVALID_ARGUMENT`입니다.


## 모니터와 커서

Windows에서 `getMonitors()`는 현재 데스크톱의 모니터 배열을, `windows.getPrimaryMonitor()`는
주 모니터를 반환합니다. `getMonitor({ view, windowId? })`는 대상 창과 가장 많이 겹치는
모니터를 반환합니다. 최소화한 창은 최소화 이전 rectangle을 사용하고 화면 밖의 창은
가장 가까운 모니터를 선택합니다. 닫힌 창과 유효하지 않은 windowId는 `INVALID_ARGUMENT`입니다.

`windows.getMonitorNearestPoint({ x, y })`와 `getMonitorNearestRect({ x, y, width, height })`는
물리 화면 좌표를 받습니다. rectangle은 가장 많이 겹치는 모니터를 우선하고 겹치지 않으면
가장 가까운 모니터를 선택합니다. 좌표는 부호 있는 32비트 정수이며 음수 원점을 허용합니다.
rectangle의 width와 height는 양수이고 오른쪽과 아래쪽 좌표도 32비트 범위 안이어야 합니다.
같은 거리 또는 겹침의 선택 순서는 Windows가 정합니다.

각 결과의 `id`는 `\\.\DISPLAY1` 같은 현재 Windows 디스플레이 장치명이고 `name`은
드라이버의 모니터 이름입니다. 이름이 없으면 id를 사용합니다. id는 HWND나 영구 하드웨어
식별자가 아니며 디스플레이 구성 변경 뒤 다시 조회해야 합니다. `windows.center({ view, monitorId })`에 이 id를 넘기면
해당 모니터의 작업 영역 중앙에 창을 배치합니다.
`bounds`와 `workArea`는 `{ x, y, width, height }` 형태의 물리 픽셀 rectangle입니다.
workArea는 작업 표시줄과 등록된 데스크톱 도구 모음을 제외한 영역입니다.
`primary`, 유효 DPI인 `dpi`, `dpi / 96`인 `scaleFactor`, 기본 방향에서 시계 반대 방향 각도인
`rotation`(0, 90, 180, 270 또는 null), 정수 Hz인 `refreshRate`를 함께 반환합니다.
드라이버가 orientation 또는 주사율을 제공하지 않거나 주사율이 기본값이면 null입니다.
분수 주사율과 영구 모니터 식별자는 제공하지 않습니다.

`getCursorPosition()`은 `{ x, y }` 물리 화면 좌표를 조회합니다. 조회는 커서를 이동하거나
창을 표시하고 활성화하지 않습니다. 창 기준 논리 좌표가 필요하면 기존
`toLogical({ view, value: point })`로 대상 창의 현재 DPI를 사용해 변환합니다.
전역 논리 데스크톱 좌표계는 정의하지 않습니다.

```ts
const displays = await windows.getMonitors();
const current = await windows.getMonitor({ view: "main" });
const nearest = await windows.getMonitorNearestRect(current.workArea);
const cursor = await windows.getCursorPosition();
```

작업마다 `windows.<작업명>` 권한이 필요하며 한 조회 권한이 다른 조회를 허용하지 않습니다.
전역 조회는 열린 창 없이도 사용할 수 있습니다. macOS에서는 이 작업들이 `UNSUPPORTED`입니다.
OS 조회 실패는 `INTERNAL`이며 구성 변경과 동시에 조회하면 실패할 수 있습니다.
`monitorSchema`는 같은 결과를 검증하는 공개 Zod 계약입니다.

### 모니터 변경 구독과 복구

`windows.getMonitorSnapshot()`은 `{ sourceId, revision, monitors, error }`를 반환합니다.
`sourceId`는 앱 호스트의 모니터 관찰 수명을 구분하는 UUID이며 창 탐색이나 재생성으로
바뀌지 않습니다. 초기 `revision`은 0이고 모니터 구성, 지표 또는 조회 오류 상태가 바뀌면
증가합니다. 같은 id의 배열 순서만 바뀌면 변경으로 처리하지 않습니다.
`monitorSnapshotSchema`는 결과를 검증하는 공개 Zod 계약입니다.
`safeParse`와 `safeParseAsync`는 잘못된 `error` 객체도 예외 대신 Zod 오류로 반환합니다.

`windows.monitorsChanged`의 payload는 `{ sourceId, revision, added, removed, changed, error }`입니다.
revision은 1 이상이며 세 배열은 모니터 id를 담습니다. 추가와 제거, 이름, 주 모니터,
bounds, workArea, DPI와 배율, rotation 또는 refreshRate 변경을 알립니다.
`monitorChangeSchema`는 이 payload의 공개 JSON Schema 계약입니다.
한 번에 관찰한 여러 변경은 하나로 합쳐질 수 있으므로 중간 상태를 모두 전달하지 않습니다.

뷰 정책의 `events`에 `windows.monitorsChanged`, `host.permissions`에
`windows.getMonitorSnapshot`을 모두 선언해야 해당 뷰에 이벤트가 전달됩니다.
조회 권한만으로 이벤트 구독이 허용되지 않으며 이벤트 허용만으로 디스플레이 정보를
받거나 조회할 수 없습니다. 구독할 때 초기 상태나 이전 이벤트를 재전송하지 않습니다.
구독을 완료한 뒤 snapshot을 조회하고, 이후 이벤트에서는 snapshot을 다시 조회하세요.
sourceId가 달라지면 기존 revision 비교를 초기화하고, 같은 sourceId에서는 더 오래된
revision의 응답을 버리세요. 탐색이나 문서 재생성 뒤에도 구독과 조회를 다시 수행합니다.

```ts
import { createClient } from "@bunaway/client";
import type { CommandsOf, EventsOf } from "@bunaway/backend";
import type { app } from "../../src-bunaway/app";
import windows, { type MonitorSnapshot } from "@bunaway/plugin-windows";

const client = createClient<CommandsOf<typeof app>, EventsOf<typeof app>>();
await client.ready;
let current: MonitorSnapshot | undefined;
async function recoverMonitors() {
  const next = await windows.getMonitorSnapshot();
  if (!current || current.sourceId !== next.sourceId || next.revision >= current.revision) {
    current = next;
    // next.error가 있으면 마지막 유효 목록과 오류 상태를 함께 표시합니다.
    console.log(next.monitors, next.error);
  }
}
const release = await client.listen("windows.monitorsChanged", () => {
  void recoverMonitors().catch(console.error);
}, { onError: console.error });
await recoverMonitors();
// 컴포넌트 정리 시 await release()를 호출합니다.
```

디스플레이 조회가 실패하면 snapshot의 `error`는 `INTERNAL`이고 `monitors`는 마지막
유효 목록을 유지합니다. 최초 조회부터 실패하면 목록은 비어 있습니다. 오류 진입과
정상 복구도 revision과 이벤트를 갱신하며 같은 오류 상태의 반복 조회는 이벤트를
추가하지 않습니다. 오류 원본과 네이티브 핸들은 payload에 노출하지 않습니다.
변경 이벤트는 Windows 디스플레이와 설정 알림에 따라 관찰하며 주기적으로 조회하지 않습니다.
물리 모니터 제거와 연결, 혼합 DPI 및 회전의 수동 검증은 별도로 남아 있습니다.
