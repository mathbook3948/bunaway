```ts
capabilities(): Promise<Capabilities>
```

앱 백엔드에서 현재 플랫폼 기능 정보를 조회합니다.
UI에서는 [capabilities](/reference/plugins/capabilities/)를 사용합니다.

```ts
import { capabilities } from "@bunaway/plugin-capabilities";

const support = await capabilities();
```

## 응답 필드

| 필드 | 필수 | 값, 제약 |
| --- | --- | --- |
| `name` | 예 | 영숫자, `_ . : -`, 1–128자 |
| `support` | 예 | supported, experimental, unsupported |
| `reason` | 아니요 | 문자열, 최대 1,024자 |

앱에 등록된 네이티브 플러그인 작업을 보고합니다. Windows의 창, 저장, 로그와 기능 조회는
해당 플러그인을 등록하고 어댑터를 사용할 수 있을 때 `supported`입니다.
macOS 기능 조회 어댑터는 호스트가 제공한 실행 가능 작업 목록을 그대로 반환합니다.
호스트는 등록한 작업과 실행 가능한 플랫폼 어댑터의 작업 목록을 함께 사용합니다.
어댑터 설치나 조회만으로 호출 권한을 부여하지 않습니다.
조회 결과에는 등록한 네이티브 작업을 최대 256개 포함합니다. 창 작업도 windowsPlugin을 등록한 경우에만 포함됩니다.
결과 전체에는 프로토콜의 JSON 깊이와 1 MiB 메시지 제한을 적용합니다.

## 권한 의미

support는 플랫폼 어댑터의 구현 상태입니다. OS 동의 상태 조회와 요청은 해당 기능
플러그인이 담당합니다. 이 조회는 정책 변경이나 OS 권한 요청을 실행하지 않습니다.
조회 결과와 별도로 작업 이름과 명령 호출 권한은 정책에 허용해야 합니다. 파일별 접근은 앱 명령에서 검사합니다.

`capabilities()`에는 인자가 없습니다. 명령이나 `defineApp()`으로 연결한 플러그인 setup에서 호출합니다.
capabilitiesPlugin 등록과 호출 출처의 `capabilities.get` 권한이 필요합니다. UI 직접 호출에는 `plugin.capabilities.get` 명령 허용도 필요합니다. 입력은 반드시 null입니다.
실행 범위는 [백엔드 Host API](/reference/backend/host-api/)에서 확인하세요.
잘못된 입력은 `INVALID_ARGUMENT`,
취소는 `CANCELLED`, 유효하지 않은 응답은 `INTERNAL`로 실패합니다.
