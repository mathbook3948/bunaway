```ts
storage.copyFile({ from, to }): Promise<null>
storage.move({ from, to }): Promise<null>
```

`copyFile`은 Windows와 macOS에서 지원하며 `move`는 Windows에서 지원합니다.
macOS move는 검사한 source 객체를 고정할 수 없어 이름을 바꾸기 전에 `UNSUPPORTED`로 실패합니다. `storage`를 등록하고
`storage.copyFile` 또는 `storage.move` 권한을 각각 허용합니다.
직접 화면 호출에는 해당 이름 앞에 `plugin.`을 붙인 명령 권한도 필요합니다.
이 권한은 다른 전송 작업이나 일반 읽기와 쓰기를 허용하지 않습니다.

`from`과 `to`는 [텍스트 읽기](/reference/host/storage-read-text/)와 같은 앱 지정 절대 경로입니다.
앱 명령에서 두 위치의 접근 규칙을 모두 검사하세요. 추가 필드, overwrite와 recursive 옵션은 받지 않습니다.
상위 디렉터리는 존재해야 합니다. 입력, 정규 이름, junction과 hardlink 검사는 유지합니다.

## 작은 파일 복사

`copyFile`은 일반 파일의 내용만 복사하며 상한은 4 MiB입니다.
파일 크기와 원본 핸들을 검사한 뒤 새 대상 파일을 만듭니다.
대상은 `CREATE_NEW`로 열므로 기존 파일이나 디렉터리, 링크를 덮어쓰지 않습니다.
원본과 대상의 상위 디렉터리 및 파일 핸들을 작업이 끝날 때까지 고정하고
최대 1 MiB의 재사용 버퍼로 바이트를 옮깁니다. 임의 바이트와 빈 파일을 보존합니다.

원본 크기가 상한을 넘으면 `INVALID_ARGUMENT`로 실패하며 대상을 만들지 않습니다.
복사 중 새 쓰기와 이름 변경 핸들의 접근을 차단합니다. OS와 기존 열린 핸들의 공유 규칙 때문에 실패할 수 있습니다.
앱 전체나 파일 시스템 전체의 원자적 스냅샷을 보장하지 않습니다.
복사본은 OS의 상속 ACL과 새 생성 및 쓰기 시각을 사용하며 원본의 ACL, 속성과 시각을 복제하지 않습니다.

```ts
import storage from "@bunaway/plugin-storage";

await storage.copyFile({
  from: "C:/notes/한글.txt",
  to: "C:/archive/한글.txt",
});
```

이 복사는 원자적 저장이나 crash recovery를 제공하지 않습니다.
읽기나 쓰기 실패 시에는 검사한 새 대상 핸들에만 삭제를 요청하고 원본을 유지합니다.
검사나 정리 실패, 프로세스 강제 종료에서는 빈 파일이나 일부 복사본이 남을 수 있습니다.
원본을 지우지 않으며 다른 이름으로 대상을 다시 찾아 삭제하지 않습니다.
큰 파일과 stream 복사, 디렉터리 재귀 복사는 후속 작업입니다.

## 같은 parent의 이름 변경

`move`는 파일 또는 일반 디렉터리의 검사한 핸들을 같은 parent의 새 이름으로 변경합니다.
`NtSetInformationFile`의 `FileRenameInformation`에 source 핸들과 새 leaf 이름을 전달합니다.
`RootDirectory`는 NULL이고 `ReplaceIfExists`는 false입니다. source와 모든 parent의
쓰기 및 삭제를 차단하는 핸들을 유지하며 경로를 다시 열거나 복사 후 삭제로 전환하지 않습니다.

디렉터리 이름 변경은 자식을 읽거나 링크를 따라가지 않고 디렉터리 자체에 적용합니다.
자식의 이후 저장 작업에는 기존의 경로와 링크 검사가 적용됩니다.
source와 destination이 같거나 source의 하위 경로로 이동하면 `INVALID_ARGUMENT`입니다.
다른 parent 또는 볼륨으로의 이동은 `UNSUPPORTED`이며 source를 그대로 둡니다.
같은 parent에서도 파일 시스템이나 열린 핸들의 제약 때문에 실패할 수 있습니다.

다른 parent로의 네이티브 이동은 대상 디렉터리를 쓰기 접근으로 다시 엽니다.
이는 parent의 junction 변경을 차단하는 현재의 공유 제한과 충돌합니다.
parent 공유 제한을 완화하지 않으며, 다른 parent 이동은 안전한 별도 설계가 필요한 후속 작업입니다.
[Windows rename 구조의 규칙](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)을 따릅니다.

## 실패와 취소

입력, 없는 대상 또는 parent, 기존 destination과 복사 상한 위반은 `INVALID_ARGUMENT`,
정책과 OS 접근 또는 경로 거부는 `PERMISSION_DENIED`입니다.
공유 위반과 일반 I/O 또는 정리 실패는 `INTERNAL`일 수 있습니다.
전송에 필요한 source 읽기 및 삭제 권한, destination 생성 권한과 OS 상속 ACL은 작업별로 적용합니다.

모든 작업은 I/O Worker에서 실행하며 Promise를 반환합니다.
두 번째 인자의 signal과 deadline은 [호출 취소와 기한](/reference/client/invoke/)을 따릅니다.
처리 전 취소는 작업을 막지만 시작한 동기 OS 작업을 중간에 끊거나 되돌리지 않습니다.
timeout이나 연결 종료 후에도 전송이 완료됐을 수 있습니다. 재시도 전에 두 위치의 실제 상태를 확인하세요.
덮어쓰기, 다른 parent와 볼륨의 move 및 원자적 저장의 충돌 및 복구 계약은 후속 작업입니다.

## macOS copyFile

POSIX 정규 절대 경로를 사용하며 symlink와 여러 hardlink가 있는 일반 파일을 거부합니다.
상한은 4 MiB이며 기존 대상은 파일이나 링크의 종류와 관계없이 덮어쓰지 않습니다.
원본을 먼저 읽은 뒤 새 대상을 생성하며 동시 쓰기의 일관된 스냅샷을 보장하지 않습니다.
쓰기 실패 때 일부 대상이 남을 수 있습니다. 교체된 이름을 찾아 삭제하지 않으며
원본은 유지합니다. Windows의 새 쓰기와 이름 변경 공유 차단은 macOS에 적용되지 않습니다.
