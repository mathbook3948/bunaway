```ts
storage.readDirectory({ path }): Promise<StorageDirectoryEntry[]>
storage.readDirectoryPage({ path, after?: string, limit?: number }): Promise<StorageDirectoryPage>
storage.createDirectory({ path, recursive?: boolean }): Promise<null>
storage.directorySize({ path }): Promise<StorageDirectorySize>
storage.remove({ path }): Promise<null>
storage.removeRecursive({ path }): Promise<null>
```

`@bunaway/plugin-storage`의 작업입니다. 여섯 작업 모두 Windows와 macOS에서 제공합니다. 두 플랫폼은 같은 Node 파일 시스템 어댑터를 쓰며, `readDirectoryPage`의 동작은 Linux와 Windows에서 실행해 확인했고 macOS는 작업 목록 등록만 확인했습니다.
`storage`를 등록하고
`storage.readDirectory`, `storage.readDirectoryPage`, `storage.createDirectory`, `storage.directorySize`, `storage.remove`, `storage.removeRecursive` 권한을 각각 허용합니다.
파일 삭제 권한은 트리 삭제를 허용하지 않습니다.
직접 화면 호출에는 해당 이름 앞에 `plugin.`을 붙인 명령 권한도 필요합니다.
다른 저장 작업이나 디렉터리 작업의 권한은 서로 허용하지 않습니다.

`path`는 [텍스트 읽기](/reference/host/storage-read-text/)와 같은 앱 지정 절대 경로입니다.
두 플랫폼 모두 경로 형식만 검사하고, 목록과 생성과 용량 계산은 링크(symlink, junction)를 일반 경로처럼 따라갑니다.
macOS 경로는 `/`로 시작하는 POSIX 절대 경로이며 `/tmp` 같은 별칭도 그대로 받습니다.
경로를 알아도 접근 권한이 생기지 않습니다.
화면의 경로를 그대로 승인하기보다 앱 명령에서 대상과 접근 규칙을 정하세요.

## 직접 자식 목록

`StorageDirectoryEntry`는 `{ name: string, kind: "file" | "directory" | "link" }`입니다.
목록은 대상 디렉터리의 직접 자식만 포함하며 이름의 UTF-16 순서로 정렬합니다.
빈 디렉터리는 `[]`이고 `.`과 `..`는 제외합니다. `link`는 Windows 자식의 symlink와 junction,
macOS 자식의 symlink를 뜻하며 대상을 따라가거나 자식 파일을 열지 않습니다.
링크 판정은 디렉터리 목록과 자식의 `lstat` 중 하나라도 링크라고 하면 링크로 봅니다.
hardlink의 이름은 `file`로 관찰합니다.

FIFO, 장치, socket과 알려지지 않은 종류는 공개 결과로 표현할 수 없어 UNSUPPORTED입니다.
최대 256개 자식을 반환하며 넘으면 `INVALID_ARGUMENT`로 실패합니다.
일부 목록을 성공으로 반환하지 않습니다. 이름당 상한은 Windows 파일 이름의 255 UTF-16 code unit입니다.
이 상한은 JSON escaping을 포함한 결과가 전송 상한 안에 들어가도록 정한 값입니다.
대상이 디렉터리가 아니면 `INVALID_ARGUMENT`입니다.

디렉터리를 탐색하는 동안 다른 프로세스가 자식을 추가하거나 바꿀 수 있습니다.
목록은 원자적 스냅샷이나 이후 접근의 승인을 보장하지 않습니다.
재귀 목록은 후속 작업입니다. 256개를 넘는 디렉터리는 아래 `readDirectoryPage`로 읽습니다.

## 큰 디렉터리의 페이지 단위 목록

`StorageDirectoryPage`는 `{ entries: StorageDirectoryEntry[], next: string | null }`입니다.
`readDirectoryPage`는 이름이 `after`보다 뒤인 자식 중 앞의 `limit`개를 같은 순서와 같은 항목 규칙으로 반환합니다.
`after`를 생략하면 처음부터 읽고, `limit`의 기본값과 상한은 256입니다.
`next`가 문자열이면 그 값을 다음 호출의 `after`로 넘기고, `null`이면 목록의 끝입니다.
`after`는 존재하는 이름일 필요가 없으며, 이름의 UTF-16 순서로 비교합니다.

```ts
import storage from "@bunaway/plugin-storage";

let after: string | undefined;
do {
  const page = await storage.readDirectoryPage({ path: "C:/notes/한글", after });
  for (const entry of page.entries) {
    // entry.name, entry.kind
  }
  after = page.next ?? undefined;
} while (after !== undefined);
```

- 서버에 상태를 두지 않으므로 호출 사이에 자식이 추가되거나 지워져도 같은 이름이 두 번 나오거나 건너뛰지 않습니다. 단 커서 이름 이하로 새로 생긴 이름은 이미 지나간 페이지의 몫이라 나오지 않습니다.
- 호출마다 디렉터리를 처음부터 읽으므로 비용은 호출당 디렉터리 크기에 비례합니다. 런타임이 디렉터리의 자식 목록을 한 번에 읽으므로 메모리도 호출당 디렉터리 크기에 비례합니다.
- 페이지에 든 자식만 `lstat`합니다. 스캔 뒤 사라진 자식은 그 페이지에서 빠져 `entries`가 `limit`보다 적을 수 있으며, 이 경우에도 `next`는 이어서 읽을 위치를 가리킵니다.
- 이름이 바뀐 자식은 옛 이름과 새 이름으로 각각 한 번씩 나올 수 있습니다.
- 페이지에 FIFO, 장치, socket이 있으면 `readDirectory`와 같이 UNSUPPORTED로 실패합니다. 그 자식이 다른 페이지에 있으면 이 호출은 영향을 받지 않습니다. 실패한 페이지는 `next`를 돌려주지 않고 오류에 이름이 없으므로, 앞 페이지까지만 읽을 수 있고 그 뒤의 이름은 읽을 수 없습니다.
- 한 번의 동기 읽기라서 시작한 뒤에는 취소할 수 없습니다.
- `readDirectory`의 허용은 `readDirectoryPage`를 허용하지 않으며 그 반대도 같습니다.

## 디렉터리 생성

`recursive` 기본값은 `false`입니다. 상위 디렉터리가 없으면 `INVALID_ARGUMENT`로 실패합니다.
`true`이면 없는 상위 디렉터리를 모두 만듭니다.
대상에 이미 디렉터리가 있으면 성공하고 내용을 바꾸지 않습니다. 대상 이름이 링크이면 링크가 가리키는 디렉터리를 같은 디렉터리로 봅니다.
파일이 있으면 `INVALID_ARGUMENT`입니다.

```ts
import storage from "@bunaway/plugin-storage";

await storage.createDirectory({ path: "C:/notes/한글", recursive: true });
const entries = await storage.readDirectory({ path: "C:/notes/한글" });
```

이 작업은 파일을 만들거나 기존 ACL을 바꾸지 않습니다. Windows는 OS가 정한 상속 권한을 사용합니다.
macOS의 새 디렉터리는 0700 mode를 요청하며 OS umask와 상속 ACL이 적용됩니다.
재귀 생성 중 실패하면 이미 만든 디렉터리는 남을 수 있으며 자동으로 지우지 않습니다.

## 디렉터리 재귀 용량

`directorySize`는 디렉터리 아래의 일반 파일 크기를 모두 더해
`{ bytes, files, directories }`를 반환합니다. 세 값은 모두 `Number.MAX_SAFE_INTEGER` 이하의
정수이며 합계가 이를 넘으면 `INTERNAL`로 실패합니다.

```ts
import storage from "@bunaway/plugin-storage";

const { bytes, files, directories } = await storage.directorySize({
  path: "C:/notes/한글",
});
```

- `bytes`는 일반 파일의 논리 크기의 합입니다. 디스크 할당 크기, 압축과 sparse 파일의 실제 점유량은 반영하지 않습니다.
- `files`는 더한 일반 파일 수, `directories`는 아래에서 순회한 하위 디렉터리 수입니다. 루트 자체는 세지 않으며 빈 디렉터리는 `{ bytes: 0, files: 0, directories: 0 }`입니다.
- 하드링크는 파일 이름마다 각각 더합니다. 같은 데이터가 여러 이름으로 있으면 여러 번 계산합니다.
- symlink와 junction은 목록 작업의 `link`와 같게 따라가지 않고 크기와 개수에 더하지 않습니다. 루트 경로가 링크이면 일반 경로처럼 따라가서 대상 디렉터리를 셉니다.
- 크기는 각 항목의 `lstat`에서 읽습니다. 다른 프로세스가 쓰는 중인 파일은 OS가 아직 갱신하지 않은 크기가 보일 수 있습니다.

일부 하위 디렉터리를 열지 못하거나 항목 하나의 정보를 읽지 못하면(예: 다른 프로세스가 잠근 시스템 파일) 과소 집계를 막기 위해 작업 전체가 실패합니다. 운영체제의 접근 거부는
`PERMISSION_DENIED`, 그 밖의 열기 실패는 `INTERNAL`입니다. 탐색 중 사라진 항목과 하위 디렉터리는 건너뜁니다.
탐색 중 다른 프로세스가 파일을 추가, 삭제하거나 크기를 바꿀 수 있으므로 결과는 스냅샷이 아니며
이후 접근의 승인도 아닙니다.

비용 상한은 루트 아래에서 본 항목(파일, 디렉터리와 링크) 100,000개와 디렉터리 깊이 64입니다.
넘으면 부분 합계를 반환하지 않고 `INVALID_ARGUMENT`로 실패합니다.
루트가 없거나 디렉터리가 아니면 `INVALID_ARGUMENT`입니다.
순회는 반복 방식이며 순회 단계(디렉터리 열기 또는 항목 읽기) 32개마다 이벤트 루프에 양보합니다.
취소와 기한은 양보 사이에 처리되어 다음 순회 단계에 반영되며, 취소되면 부분 합계 없이 `CANCELLED`로 끝납니다.
순회 중 어댑터 해제를 시작하면 순회는 `CANCELLED`로 끝납니다.
큰 트리를 순회하면 같은 I/O Worker에서 실행되는 모든 호출의 응답이 그만큼 늦어집니다.

## 파일과 빈 디렉터리 삭제

`remove`는 파일 하나 또는 빈 디렉터리를 삭제합니다.
대상이 링크이면 링크 자체를 삭제하고 링크가 가리키는 대상은 지우지 않습니다.
없거나 비어 있지 않은 대상은 `INVALID_ARGUMENT`입니다. 트리 삭제는 `removeRecursive`가 제공하고 휴지통 이동은 제공하지 않습니다. 파일은 [opener의 `trashFile`](/reference/plugins/opener/#휴지통)로 휴지통에 보냅니다.

삭제에는 OS의 삭제 권한이 필요합니다.
다른 프로세스의 열린 핸들, readonly 속성이나 ACL 때문에 실패할 수 있습니다.

## 디렉터리 트리 삭제

`removeRecursive`는 파일 하나, 또는 디렉터리와 그 아래 모든 항목을 삭제합니다. Node `fs.rm({ recursive: true })`와
Tauri `remove({ recursive: true })`처럼 비어 있지 않은 디렉터리를 삭제하며, 없는 대상은 `INVALID_ARGUMENT`입니다.
이 작업은 `remove`와 별도 권한입니다.

```ts
await storage.removeRecursive({ path: "C:/Users/me/AppData/Local/MyApp/cache" });
```

- 구현은 Node `fs.promises.rm({ recursive: true })`입니다. 트리 안의 symlink, junction, Windows 볼륨 마운트 지점은 따라가지 않고 항목 자체만 삭제하며, 가리키는 대상은 지우지 않습니다. symlink나 junction을 `path`로 직접 주어도 링크만 삭제합니다.
- OneDrive 같은 클라우드 동기화 자리표시자 폴더를 삭제할 때의 동작은 테스트로 확인하지 않았습니다.
- hardlink는 순회에서 만난 이름만 삭제하고 같은 데이터의 다른 이름은 유지합니다.
- 삭제는 하나의 파일 시스템 호출이라 중간에 취소할 수 없습니다. 취소와 기한은 삭제를 시작하기 전에만 반영하고, 시작한 삭제는 끝까지 실행합니다.
- 항목 수와 깊이의 상한은 없습니다. 큰 트리는 같은 I/O Worker의 다른 호출을 기다리게 할 수 있습니다.
- 다른 프로세스가 삭제 공유 없이 연 파일이 있으면 `INTERNAL`로 실패할 수 있습니다.
- 원자적이지 않습니다. 실패 전에 삭제한 항목은 복구하지 않으며, 같은 호출을 다시 하면 남은 항목을 이어서 삭제합니다.

## 실패와 취소

잘못된 입력과 대상 종류, 없는 대상, 큰 목록 및 비어 있지 않은 삭제 대상은 `INVALID_ARGUMENT`,
정책과 OS 접근 거부는 `PERMISSION_DENIED`입니다.
공유 위반과 일반 OS 및 결과 실패는 `INTERNAL`일 수 있습니다.

모든 작업은 I/O Worker에서 실행하고 Promise를 반환합니다.
두 번째 인자의 signal과 deadline은 [호출 취소와 기한](/reference/client/invoke/)을 따릅니다.
처리 전 취소는 작업을 막으며 이미 시작한 동기 OS 호출은 중간에 끊지 않습니다.
`directorySize`는 순회를 시작한 뒤에도 취소와 기한을 따릅니다. 취소는 다음 양보 뒤에 반영되고 그 사이 최대 31단계의 동기 OS 호출은 끊지 않습니다.
완료 여부가 불명확한 생성이나 삭제는 실제 상태를 다시 확인하세요. 이미 완료한 변경은 되돌리지 않습니다.
