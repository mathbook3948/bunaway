```ts
storage.readDirectory({ path }): Promise<StorageDirectoryEntry[]>
storage.createDirectory({ path, recursive?: boolean }): Promise<null>
storage.remove({ path }): Promise<null>
```

`@bunaway/plugin-storage`의 Windows 작업입니다. `storagePlugin`을 등록하고
`storage.readDirectory`, `storage.createDirectory`, `storage.remove` 권한을 각각 허용합니다.
직접 화면 호출에는 해당 이름 앞에 `plugin.`을 붙인 명령 권한도 필요합니다.
다른 저장 작업이나 디렉터리 작업의 권한은 서로 허용하지 않습니다.

`path`는 [텍스트 읽기](/reference/host/storage-read-text/)와 같은 앱 지정 절대 경로입니다.
상위 디렉터리를 고정하고 대상의 정규 이름과 네이티브 핸들을 검사합니다.
junction, reparse point, hardlink와 별칭 거부는 유지합니다. 경로를 알아도 접근 권한이 생기지 않습니다.
화면의 경로를 그대로 승인하기보다 앱 명령에서 대상과 접근 규칙을 정하세요.

## 직접 자식 목록

`StorageDirectoryEntry`는 `{ name: string, kind: "file" | "directory" | "link" }`입니다.
목록은 대상 디렉터리의 직접 자식만 포함하며 이름의 UTF-16 순서로 정렬합니다.
빈 디렉터리는 `[]`이고 `.`과 `..`는 제외합니다. `link`는 자식의 reparse point를 뜻하며
대상을 따라가거나 자식 파일을 열지 않습니다. hardlink의 이름은 `file`로 관찰할 수 있지만
그 파일에 대한 다른 저장 작업은 기존의 hardlink 검사를 따릅니다.

목록을 구할 때 새로 경로를 열지 않습니다. 검사하고 고정한 디렉터리 핸들에
`GetFileInformationByHandleEx`를 반복 호출해 여러 네이티브 batch를 읽습니다.
최대 256개 자식을 반환하며 넘으면 `INVALID_ARGUMENT`로 실패합니다.
일부 목록을 성공으로 반환하지 않습니다. 이름당 상한은 Windows 파일 이름의 255 UTF-16 code unit입니다.
이 상한은 JSON escaping을 포함한 결과가 전송 상한 안에 들어가도록 정한 값입니다.

디렉터리를 탐색하는 동안 다른 프로세스가 자식을 추가하거나 바꿀 수 있습니다.
목록은 원자적 스냅샷이나 이후 접근의 승인을 보장하지 않습니다.
자식의 이름이나 종류가 바뀌면 다음 작업에서 다시 경로와 핸들을 검사합니다.
재귀 탐색, 큰 목록의 pagination과 디렉터리 용량 계산은 후속 작업입니다.

## 디렉터리 생성

`recursive` 기본값은 `false`입니다. 상위 디렉터리가 없으면 `INVALID_ARGUMENT`로 실패합니다.
`true`이면 없는 상위 디렉터리를 순서대로 만들고 고정하며 다음 요소를 검사합니다.
대상에 이미 일반 디렉터리가 있으면 성공하고 내용을 바꾸지 않습니다.
파일이 있으면 `INVALID_ARGUMENT`, 링크나 정규 이름 거부는 `PERMISSION_DENIED`입니다.

```ts
import { storage } from "@bunaway/plugin-storage";

await storage.createDirectory({ path: "C:/notes/한글", recursive: true });
const entries = await storage.readDirectory({ path: "C:/notes/한글" });
```

이 작업은 파일을 만들거나 ACL을 바꾸지 않습니다. OS가 정한 상속 권한을 사용합니다.
재귀 생성 중 실패하면 이미 만든 디렉터리는 남을 수 있으며 자동으로 지우지 않습니다.

## 파일과 빈 디렉터리 삭제

`remove`는 검사한 파일 또는 빈 디렉터리의 핸들에 삭제 disposition을 설정하고 핸들을 닫습니다.
검사 후 이름으로 대상을 다시 열지 않으며 검사하는 동안 대상의 이름 변경과 삭제를 막습니다.
여러 개의 hardlink나 reparse point는 삭제하지 않습니다.
없거나 비어 있지 않은 대상은 `INVALID_ARGUMENT`입니다. 재귀 삭제와 휴지통 이동은 제공하지 않습니다.

삭제에는 OS의 삭제 권한과 검사에 필요한 읽기 및 메타데이터 권한이 필요합니다.
다른 프로세스의 열린 핸들, readonly 속성이나 ACL 때문에 실패할 수 있습니다.
OS가 삭제를 보류하면 다른 열린 핸들이 닫힌 뒤 이름이 제거될 수 있습니다.

## 실패와 취소

잘못된 입력과 대상 종류, 없는 대상, 큰 목록 및 비어 있지 않은 삭제 대상은 `INVALID_ARGUMENT`,
정책과 OS 접근 또는 경로 거부는 `PERMISSION_DENIED`입니다.
공유 위반과 일반 OS 및 결과 실패는 `INTERNAL`일 수 있습니다.
실패해도 탐색과 검사에 사용한 핸들은 해제합니다.

모든 작업은 I/O Worker에서 실행하고 Promise를 반환합니다.
두 번째 인자의 signal과 deadline은 [호출 취소와 기한](/reference/client/invoke/)을 따릅니다.
처리 전 취소는 작업을 막으며 이미 시작한 동기 OS 호출은 중간에 끊지 않습니다.
완료 여부가 불명확한 생성이나 삭제는 실제 상태를 다시 확인하세요. 이미 완료한 변경은 되돌리지 않습니다.
