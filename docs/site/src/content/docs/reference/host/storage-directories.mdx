```ts
storage.readDirectory({ path }): Promise<StorageDirectoryEntry[]>
storage.createDirectory({ path, recursive?: boolean }): Promise<null>
storage.directorySize({ path }): Promise<StorageDirectorySize>
storage.remove({ path }): Promise<null>
```

`@bunaway/plugin-storage`의 작업입니다. readDirectory와 createDirectory는 Windows와
macOS에서 제공하며 directorySize와 remove는 Windows에서만 제공합니다. macOS remove는
검사한 객체 자체의 삭제를 보장할 수 없어 지원 목록에서 제외되며 UNSUPPORTED로 실패합니다.
macOS directorySize도 UNSUPPORTED로 실패합니다.
`storage`를 등록하고
`storage.readDirectory`, `storage.createDirectory`, `storage.directorySize`, `storage.remove` 권한을 각각 허용합니다.
직접 화면 호출에는 해당 이름 앞에 `plugin.`을 붙인 명령 권한도 필요합니다.
다른 저장 작업이나 디렉터리 작업의 권한은 서로 허용하지 않습니다.

`path`는 [텍스트 읽기](/reference/host/storage-read-text/)와 같은 앱 지정 절대 경로입니다.
Windows에서는 상위 디렉터리를 고정하고 대상의 정규 이름과 네이티브 핸들을 검사합니다.
junction, reparse point, hardlink와 별칭 거부는 유지합니다. macOS에서는 각 부모와 대상을
열린 descriptor 기준으로 검사하며 symlink와 비정규 경로를 거부합니다.
macOS 경로는 /private/tmp처럼 symlink 별칭이 없는 정규 POSIX 절대 경로를 사용합니다.
경로를 알아도 접근 권한이 생기지 않습니다.
화면의 경로를 그대로 승인하기보다 앱 명령에서 대상과 접근 규칙을 정하세요.

## 직접 자식 목록

`StorageDirectoryEntry`는 `{ name: string, kind: "file" | "directory" | "link" }`입니다.
목록은 대상 디렉터리의 직접 자식만 포함하며 이름의 UTF-16 순서로 정렬합니다.
빈 디렉터리는 `[]`이고 `.`과 `..`는 제외합니다. `link`는 Windows 자식의 reparse point나
macOS 자식의 symlink를 뜻하며
대상을 따라가거나 자식 파일을 열지 않습니다. hardlink의 이름은 `file`로 관찰할 수 있지만
그 파일에 대한 다른 저장 작업은 기존의 hardlink 검사를 따릅니다.

목록을 구할 때 새로 경로를 열지 않습니다. 검사한 디렉터리 핸들이나 descriptor에서 읽습니다.
macOS의 FIFO, 장치, socket과 알려지지 않은 종류는 공개 결과로 표현할 수 없어 UNSUPPORTED입니다.
최대 256개 자식을 반환하며 넘으면 `INVALID_ARGUMENT`로 실패합니다.
일부 목록을 성공으로 반환하지 않습니다. 이름당 상한은 Windows 파일 이름의 255 UTF-16 code unit입니다.
이 상한은 JSON escaping을 포함한 결과가 전송 상한 안에 들어가도록 정한 값입니다.

디렉터리를 탐색하는 동안 다른 프로세스가 자식을 추가하거나 바꿀 수 있습니다.
목록은 원자적 스냅샷이나 이후 접근의 승인을 보장하지 않습니다.
자식의 이름이나 종류가 바뀌면 다음 작업에서 다시 경로와 핸들을 검사합니다.
재귀 목록과 큰 목록의 pagination은 후속 작업입니다.

## 디렉터리 생성

`recursive` 기본값은 `false`입니다. 상위 디렉터리가 없으면 `INVALID_ARGUMENT`로 실패합니다.
`true`이면 없는 상위 디렉터리를 순서대로 만들고 고정하며 다음 요소를 검사합니다.
대상에 이미 일반 디렉터리가 있으면 성공하고 내용을 바꾸지 않습니다.
파일이 있으면 `INVALID_ARGUMENT`, 링크나 정규 이름 거부는 `PERMISSION_DENIED`입니다.

```ts
import storage from "@bunaway/plugin-storage";

await storage.createDirectory({ path: "C:/notes/한글", recursive: true });
const entries = await storage.readDirectory({ path: "C:/notes/한글" });
```

이 작업은 파일을 만들거나 기존 ACL을 바꾸지 않습니다. Windows는 OS가 정한 상속 권한을 사용합니다.
macOS의 새 디렉터리는 0700 mode를 요청하며 OS umask와 상속 ACL이 적용됩니다.
재귀 생성 중 실패하면 이미 만든 디렉터리는 남을 수 있으며 자동으로 지우지 않습니다.

## 디렉터리 재귀 용량

`directorySize`는 검사한 디렉터리 아래의 일반 파일 크기를 모두 더해
`{ bytes, files, directories }`를 반환합니다. 세 값은 모두 `Number.MAX_SAFE_INTEGER` 이하의
정수이며 합계가 이를 넘으면 `INTERNAL`로 실패합니다. 이 작업은 Windows에서만 지원합니다.

```ts
import storage from "@bunaway/plugin-storage";

const { bytes, files, directories } = await storage.directorySize({
  path: "C:/notes/한글",
});
```

- `bytes`는 일반 파일의 논리 크기(EndOfFile)의 합입니다. 디스크 할당 크기, 압축과 sparse 파일의 실제 점유량은 반영하지 않습니다.
- `files`는 더한 일반 파일 수, `directories`는 아래에서 순회한 하위 디렉터리 수입니다. 루트 자체는 세지 않으며 빈 디렉터리는 `{ bytes: 0, files: 0, directories: 0 }`입니다.
- 하드링크는 파일 이름마다 각각 더합니다. 같은 데이터가 여러 이름으로 있으면 여러 번 계산합니다. 여러 hardlink가 있는 파일은 `stat`이 거부하지만 `directorySize`는 파일을 열지 않고 목록의 크기만 더하므로 거부하지 않습니다.
- symlink, junction과 mount point처럼 이름을 다른 대상으로 돌리는 reparse point(파일과 디렉터리 모두)는 목록 작업의 `link`와 같게 따라가지 않고 크기와 개수에 더하지 않습니다.
- 클라우드 placeholder, 중복 제거와 압축(WOF) 파일처럼 이름을 돌리지 않는 reparse point 파일은 데이터가 있는 일반 파일로 보고 목록의 논리 크기를 더합니다. 이런 파일은 `stat`이 거부하지만 `directorySize`는 파일을 열지 않고 크기 메타데이터만 더하므로 허용 범위 밖 파일의 내용에 접근하지 않습니다. 합계에서 빼면 과소 집계가 되므로 포함합니다.
- 이 판정은 목록의 EaSize 필드에 담긴 reparse tag를 따릅니다. 이 필드를 채우지 않는 파일 시스템에서는 이름 대리자 디렉터리도 이름을 돌리지 않는 reparse point 디렉터리로 보여 `UNSUPPORTED`로 실패할 수 있습니다.
- 크기는 열린 디렉터리 핸들의 목록에서 읽습니다. 다른 프로세스가 쓰는 중인 파일은 OS가 아직 갱신하지 않은 크기가 보일 수 있습니다. 크기를 디렉터리 목록에서 읽으므로 hardlink의 다른 이름도 마지막으로 갱신되기 전 크기로 보일 수 있습니다.

일부 하위 디렉터리를 열지 못하면 과소 집계를 막기 위해 작업 전체가 실패합니다. 운영체제의 접근 거부는
`PERMISSION_DENIED`, 그 밖의 열기 실패는 `INTERNAL`입니다.
탐색 중 사라졌거나 다른 프로세스가 삭제를 시작해 삭제 대기 중인 하위 디렉터리는 건너뜁니다.
클라우드 폴더처럼 이름을 돌리지 않는 reparse point 디렉터리는 따라가지 않고는 내용을 셀 수 없어
건너뛰지 않고 작업 전체를 `UNSUPPORTED`로 실패시킵니다.
탐색 중 다른 프로세스가 파일을 추가, 삭제하거나 크기를 바꿀 수 있으므로 결과는 스냅샷이 아니며
이후 접근의 승인도 아닙니다. 목록을 읽은 뒤 열기 전에 하위 디렉터리가 reparse point로 교체되면
이 경합은 스냅샷 비보장 범위로 보고 조용히 건너뛸 수 있습니다.

비용 상한은 루트 아래에서 본 항목(파일, 디렉터리와 링크) 100,000개와 디렉터리 깊이 64입니다.
넘으면 부분 합계를 반환하지 않고 `INVALID_ARGUMENT`로 실패합니다.
루트가 없거나 디렉터리가 아니면 `INVALID_ARGUMENT`입니다. 루트가 링크(reparse point)이거나
hardlink가 여러 개인 파일이면 다른 저장 작업과 같이 `PERMISSION_DENIED`입니다.
순회는 반복 방식이며 현재 경로의 디렉터리 핸들만 열어 두므로 순회하는 동안 상위 디렉터리의
이름 변경과 삭제를 막습니다. 루트, 상위 디렉터리(볼륨 루트까지)와 하위 디렉터리는 모두 읽기와 쓰기 공유로 열고 삭제 공유는 허용하지 않습니다.
다른 프로세스는 순회하는 동안 이 디렉터리들을 쓰기 접근으로 열 수 있지만 이름 변경이나 삭제는 막힙니다.순회 단계(항목 묶음 읽기 또는 디렉터리 열기) 32개마다 이벤트 루프에 양보합니다. 취소와 기한은 양보 사이에
처리되어 다음 순회 단계에 반영되며, 취소 요청 뒤에도 양보 사이의 최대 31단계는 그대로 실행됩니다.
정상 완료까지는 같은 I/O Worker의 다른 호출이 이 순회가 끝나기를 기다리고, 그동안 루트와 상위
디렉터리의 고정이 유지됩니다. 큰 트리를 순회하면 같은 I/O Worker에서 실행되는 모든 호출의 응답이 그만큼 늦어집니다.
취소된 순회는 다음 양보 뒤에 핸들을 닫으므로 그 사이에 다른 호출이 시작될 수 있습니다.
성공, 실패와 취소 모두 열어 둔 핸들을 닫습니다. 작업 실패 뒤 핸들 정리도 실패하면 두 오류를
함께 담은 `INTERNAL`로 실패합니다. 순회 중 어댑터 해제를 시작하면 순회는 `CANCELLED`로 끝나고, 해제는 순회가 핸들을 모두 닫은 뒤에 완료됩니다.

## 파일과 빈 디렉터리 삭제

`remove`는 검사한 파일 또는 빈 디렉터리의 핸들에 삭제 disposition을 설정하고 핸들을 닫습니다.
이 작업은 Windows에서만 지원합니다. macOS 호출은 이름을 변경하거나 삭제하기 전에 UNSUPPORTED로 실패합니다.
검사 후 이름으로 대상을 다시 열지 않으며 검사하는 동안 대상의 이름 변경과 삭제를 막습니다.
여러 개의 hardlink나 reparse point는 삭제하지 않습니다.
없거나 비어 있지 않은 대상은 `INVALID_ARGUMENT`입니다. 재귀 삭제와 휴지통 이동은 제공하지 않습니다.

삭제에는 OS의 삭제 권한과 검사에 필요한 읽기 및 메타데이터 권한이 필요합니다.
다른 프로세스의 열린 핸들, readonly 속성이나 ACL 때문에 실패할 수 있습니다.
OS가 삭제를 보류하면 다른 열린 핸들이 닫힌 뒤 이름이 제거될 수 있습니다.

## 실패와 취소

잘못된 입력과 대상 종류, 없는 대상, 큰 목록 및 비어 있지 않은 삭제 대상은 `INVALID_ARGUMENT`,
정책과 OS 접근 또는 경로 거부는 `PERMISSION_DENIED`입니다.
공유 위반과 일반 OS 및 결과 실패는 `INTERNAL`일 수 있습니다.
실패해도 탐색과 검사에 사용한 핸들은 해제합니다.

모든 작업은 I/O Worker에서 실행하고 Promise를 반환합니다.
두 번째 인자의 signal과 deadline은 [호출 취소와 기한](/reference/client/invoke/)을 따릅니다.
처리 전 취소는 작업을 막으며 이미 시작한 동기 OS 호출은 중간에 끊지 않습니다.
`directorySize`는 순회를 시작한 뒤에도 취소와 기한을 따릅니다. 취소는 다음 양보 뒤에 반영되고 그 사이 최대 31단계의 동기 OS 호출은 끊지 않으며,
취소되면 부분 합계 없이 `CANCELLED`로 끝나고 열어 둔 핸들을 모두 닫습니다.
완료 여부가 불명확한 생성이나 삭제는 실제 상태를 다시 확인하세요. 이미 완료한 변경은 되돌리지 않습니다.
