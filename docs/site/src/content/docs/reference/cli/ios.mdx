```sh
bunaway ios sync [directory]
bunaway ios build [directory]
bunaway ios run [directory] --device <Simulator UUID>
```

macOS arm64, Xcode와 Bun 1.4.2가 필요합니다. 디렉터리를 생략하면 현재 앱을 사용합니다.
최초 동기화는 고정된 Bun iOS beta.1 XCFramework를 내려받고 SHA-256을 검사합니다.
`sync`는 웹 빌드와 `app.ts` 번들을 실행한 뒤 `ios/Bunaway.xcodeproj`를 만듭니다.
`build`는 동기화 후 arm64 Simulator용 debug 앱을 `dist/ios/Bunaway.app`에 생성합니다.
출력 교체 전에 빌드가 실패하거나 취소되면 기존 `dist/ios`를 보존합니다.
최종 앱의 `bunaway-assets/licenses/`에는 런타임의 `LICENSE.md`, `LICENSE-libffi`와
프레임워크의 `FRAMEWORK-LICENSE.txt`, `THIRD-PARTY-NOTICES.txt` 원문을 포함합니다.
`run`은 부팅된 Simulator UUID를 반드시 받으며 빌드, 설치와 시작을 수행합니다.
실행에는 Xcode 빌드 결과의 최종 bundle identifier를 사용하며 기존 실행 인스턴스를 종료한 뒤 시작합니다.
UUID는 `xcrun simctl list devices available`에서 확인합니다. 파일 변경은 감시하지 않습니다.
실행 명령의 성공은 앱 설치와 시작까지의 결과이며 SDK 초기화 성공을 보장하지 않습니다.

## 앱 설정

기존 `build.app`의 default-exported AppDefinition을 사용합니다. iOS 전용 백엔드
진입점을 작성할 필요가 없습니다. 현재 한 개의 `app.view`, HTTPS `app.home`과
`app.window`를 사용합니다. 데스크톱 창 크기는 iOS 화면 크기에 적용하지 않습니다.
`app.home`의 기본 HTTPS 포트 `:443`은 동기화할 때 제거하며 다른 포트와 인증 정보는 허용하지 않습니다.
외부 화면 탐색과 네이티브 플러그인은 지원하지 않습니다. WKWebView의 카메라와 마이크 요청은 거부합니다.
정책의 모든 host permissions와 backend permissions는 빈 배열이어야 합니다.
기본 템플릿의 저장 플러그인은 iOS 어댑터가 없어 그대로 실행할 수 없습니다.

UI 초기화에서 앱 정의로 명령과 이벤트 타입을 지정한 클라이언트를 만들고 실패를 처리하는
방식을 권장합니다. [클라이언트 생성](/reference/client/create-client/)과 동일한 SDK를
사용하며 기본 WebView bridge는 호스트가 제공합니다.

## Xcode와 Swift 코드

`ios/Bunaway.xcodeproj`를 Xcode에서 엽니다. `AppDelegate.swift`와 Xcode 프로젝트는
처음에만 생성하며 이후 동기화에서 보존합니다. `.bunaway/`는 프레임워크가 교체하는
영역이므로 수정할 Swift 코드와 설정은 이 영역 밖에 둡니다.
웹 UI 또는 앱 정의를 변경하면 `ios sync`를 다시 실행한 뒤 Xcode에서 빌드합니다.
Swift 코드만 바꾸면 Xcode에서 바로 빌드할 수 있습니다.

이전 C 래퍼를 사용한 프로젝트는 Xcode의 Compile Sources에서 `BunawayEmbed.c`를 제거하고
Objective-C Bridging Header를 `.bunaway/host/embedding.h`로 바꿉니다.
동기화는 앱이 수정하는 Xcode 프로젝트를 덮어쓰지 않으므로 이 설정은 직접 갱신합니다.

호스트의 `BunawayViewController`가 UIKit 화면과 WKWebView, Bun 연결을 소유합니다.
앱 수명 동안 같은 호스트 인스턴스를 유지합니다. 서브클래스에서 수명주기를 재정의하면
`super` 호출을 유지하세요. 메인 스레드에서 `restartBackend()`를 호출하면 기존 Core와
Worker를 종료한 뒤 새 Worker와 화면을 연결합니다. 백엔드 메모리 상태는 초기화됩니다.

호스트 구현은 Swift로 작성하며 Bun의 `embedding.h`를 브리징 헤더로 사용합니다. 별도 C 소스는 컴파일하지 않습니다.
프로젝트는 XCFramework를 Embed & Sign으로 연결합니다. 기기 또는 Simulator slice는
Xcode가 선택합니다. iOS 16 이상 arm64 기기는 Xcode의 Signing & Capabilities에서
팀과 서명을 설정한 뒤 선택하세요. CLI의 `build`와 `run`은 Simulator용입니다.
기기용 slice의 서명 없는 빌드는 확인했으며 기기 실행과 배포 서명, App Store 제출은 아직 검증하지 않았습니다.

## 웹 UI 연결

명령과 이벤트는 웹 UI에서 내장 Bun으로 로컬 WebSocket을 통해 직접 전달합니다.
Swift는 문서의 출처를 확인하고 일회용 연결 주소를 전달하며, 문서와 앱의 수명을 관리합니다.
외부 서버나 인터넷 연결은 필요하지 않습니다. CSP를 직접 설정한다면 `connect-src`에
`ws://127.0.0.1:*`를 허용해야 직접 연결을 사용할 수 있습니다.
서버 시작이나 최초 연결이 실패하면 Swift 브리지로 전환합니다. 연결이 열린 뒤 끊어지면
해당 세션을 닫고 진행 중인 요청을 실패 처리하며, 요청을 자동 재전송하지 않습니다.

## 수명과 제한

Bun entry는 한 번 시작하고 백엔드는 Worker에서 실행합니다. entry 종료,
`process.exit()`와 처리되지 않은 JS 오류는 앱도 종료합니다. Bun 시작 뒤 복구할 수 없는
제어 파이프 실패도 앱을 종료합니다. Swift와 네이티브 SDK의 stdout 로그는
제어 채널과 분리됩니다. 잘못된 문서 메시지나 전달 오류는 해당 세션만 닫습니다.
해시 이동은 같은 SDK 연결을 유지합니다. 뒤로 가기로 캐시에서 복원한 페이지는 다시 로드해
새 연결을 만들므로 이전 페이지의 JS 메모리 상태는 유지하지 않습니다.
완료되거나 다른 탐색으로 교체된 탐색의 오류는 무시합니다. 현재 탐색이 취소되거나 실패하면 문서를 닫고 `app.home`을
한 번 다시 로드합니다. 복구도 실패하면 자동 탐색을 멈추고 재시도 버튼을 표시합니다.
이때 Bun과 Core는 유지합니다. 잘못된 메시지 필드, 메시지 크기와 깊이 제한 초과,
문서 입력 큐 포화는 해당 연결만 닫습니다.
직접 연결의 송수신 버퍼가 포화되면 해당 연결을 닫습니다. fallback은 WebView 전달 완료를 기다려
응답이 쌓이는 것을 제한합니다. Core의 구독 큐가 포화되면 SDK의 `onError`로 `BUSY`를 전달합니다.
background 전환 때 문서 세션을 정리하고 foreground 복귀 때 새 문서를 연결합니다.
Bun과 Core는 유지하지만 iOS가 suspend하면 JS 작업도 실행되지 않을 수 있습니다.
SIGKILL에는 JS 종료 훅이 실행되지 않으므로 지속할 데이터는 정상 작업 중 저장하세요.

이 런타임은 JIT와 기기 자식 프로세스 실행을 지원하지 않습니다.
사용할 수 없는 기능은 [Bun 릴리스 설명](https://github.com/mathbook3948/bun/releases/tag/bun-v1.4.2-beta.1)을 확인하세요.
