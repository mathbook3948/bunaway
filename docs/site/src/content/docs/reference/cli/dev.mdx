```sh
bunaway dev [directory]
```

설정과 정책을 개발 모드로 검증하고 네이티브 도구를 준비한 뒤 앱을 실행합니다.
`dev` 설정이 있으면 외부 UI 서버를 시작하고 HTTP 준비를 기다립니다.
생성 앱 스크립트는 vanilla의 `bun run dev`, Vite 기반 템플릿의 `bun run bunaway dev`입니다.

## 파일 감시

감시 중인 파일을 저장하면 앱을 다시 빌드하고 실행합니다.
node_modules, vendor, dist, .bunaway, .git, .next, .turbo는 호스트 재시작 감시에서 제외합니다.

외부 서버가 없으면 UI 변경도 전체 앱을 재시작합니다.
외부 서버가 있으면 UI는 서버의 HMR로 갱신하고 다음 파일과 디렉터리를 감시합니다.

- `src-bunaway/`.
- `build.app`이 있는 디렉터리.
- 루트의 package.json, bun.lock, tsconfig.json.

앱 정의가 프로젝트 루트에 있으면 루트 파일만 감시하고 UI 하위 디렉터리는 제외합니다.
앱 정의에서 import한 프로젝트 내부 파일도 감시합니다. `shared/`, `services/`처럼 다른 디렉터리에 있는 전이 의존성과 JSON 파일의 변경도 앱을 재시작합니다. 성공한 검증마다 import 목록을 갱신하며, 실패하면 이전 목록을 유지합니다. 프로젝트 밖의 파일과 node_modules의 변경은 감시하지 않습니다.

## 재시작

이전 호스트가 종료된 뒤 빌드하고 새 호스트를 시작합니다.
빌드 중 파일이 다시 바뀌면 최신 변경을 빌드할 때까지 앱 실행을 미룹니다.
빌드에 실패하면 오류를 표시하고 다음 저장을 기다립니다. 이때 이전 앱도 종료된 상태로 남습니다.
백엔드만 바뀌면 외부 서버를 유지하고, 서버 설정이 바뀌면 서버도 다시 시작합니다.

앱이 다시 시작되면 새 클라이언트 연결을 사용하고 메모리 상태도 초기화됩니다.
진행 중이던 요청과 구독은 정리되며 자동으로 다시 전송되지 않습니다. 이미 저장한 파일은 그대로 남습니다.

## 종료

Ctrl+C를 누르거나 창을 닫으면 앱과 개발 서버의 자식 프로세스를 정리합니다. 서버가 종료되거나 준비 시간을 초과해도 같은 정리 과정을 거칩니다.
Windows에서 이전 앱이 40초 안에 종료되지 않으면 재시작을 중단합니다.
개발 서버는 CLI가 직접 실행합니다. 다른 서버가 같은 포트를 사용 중이면 오류가 발생합니다.

개발 산출물은 `.bunaway/<target>/`에 생성합니다. 개발 중에는 이 파일을 직접 실행하는 대신 dev 명령을 사용하세요.
배포할 앱은 build/package 명령으로 만듭니다.
