ADR 0013의 개별 플러그인 구조를 Windows에서 구현했습니다.
로컬 tarball로 설치할 수 있으며 현재 플랫폼 어댑터는 Windows만 제공합니다.
[백엔드 API](/reference/backend/host-api/)와 [PluginDefinition](/reference/backend/plugins/)을 참고하세요.

## 설치, 등록, 권한을 구분합니다

저장, 앱 로그, 기능 지원 조회는 각각 설치하는 플러그인입니다.
패키지 설치는 앱의 의존성을 준비하고, `AppDefinition.plugins` 등록은 기능을
활성화합니다. 정책에는 호출할 명령과 Host 권한, 리소스 범위를 별도로 허용합니다.
설치나 등록만으로 권한을 부여하지 않습니다.

| 패키지 | 공통 공개 export | 화면 함수 |
| --- | --- | --- |
| `@bunaway/plugin-storage` | `storage`, `storagePlugin` | `storage` |
| `@bunaway/plugin-log` | `log`, `logPlugin` | `log` |
| `@bunaway/plugin-capabilities` | `capabilities`, `capabilitiesPlugin` | `capabilities` |

새 앱 정의는 필요한 플러그인 객체를 기존 `defineApp()`에 등록합니다.
옵션이 없는 플러그인에 초기화 factory를 요구하지 않습니다.

```ts
import { defineApp } from "@bunaway/backend";

import { storagePlugin } from "@bunaway/plugin-storage";
import { memo } from "./memo/module.ts";

export default defineApp({ modules: [memo], plugins: [storagePlugin] });
```

백엔드 서비스는 `@bunaway/plugin-storage`의 `storage`를 직접 import합니다.
저장의 입력과 결과는 현재 `storage.readText`와 `storage.writeText` 계약을 유지합니다.
화면에서도 같은 패키지 경로를 import합니다. 조건부 exports가 실행 환경에 맞는
구현을 선택합니다. 화면용 구현은 공통
클라이언트의 연결과 취소를 재사용하고 백엔드 실행 코드를 포함하지 않습니다.

## 공통 기반과 기능 구현

공통 SDK와 코어는 명령, 이벤트, 상태, 호출 컨텍스트, 플러그인 등록과 종료를
담당합니다. 실제 출처와 권한 검사, 제한된 작업 큐와 승인 절차는 호스트가 담당합니다.
개별 플러그인은 공개 함수, 입력과 출력 schema, 권한 정의와 플랫폼 구현을 소유합니다.
공통 계층에 기능별 작업 목록이나 저장과 앱 로그 구현을 추가하지 않습니다.

플러그인은 공통 `host.call(contract, input)`을 사용합니다. 공통 실행 범위는 하나로
유지하고 명령의 완료, 실패와 취소 후 호출을 거부합니다. setup에서 시작한 작업은
백엔드 종료까지 유효하며 종료 시 취소됩니다. 프레임워크 자체 진단 로그는 로그
플러그인과 별개로 계속 제공됩니다.

## 정책 v1의 구조 변경

공식 배포 전까지 정책의 형식 버전은 v1로 유지합니다. 개발 중 구조를 바꾸면
기존 v1의 계약과 예제를 갱신하며, v2나 이전 개발 형식의 호환 계층을 만들지 않습니다.

`view.host`와 루트 `backend`를 `{ permissions }` 구조로 바꿉니다.
권한 항목은 식별자 문자열 또는 `{ identifier, allow?, deny? }`입니다.
저장은 `storage:read-text`, `storage:write-text`, 앱 로그는 `log:write`, 지원 조회는
`capabilities:get`을 사용합니다. 저장처럼 리소스 범위가 필요한 작업에는 allow가
필요하며 deny에 일치하는 리소스는 거부합니다.

등록하지 않은 Host operation은 `UNSUPPORTED`, 권한 밖의 작업은
`PERMISSION_DENIED`입니다. 잘못된 설정이나 scope는 시작 전에 거부합니다.
기능 지원 조회와 OS 권한 메타데이터, 앱 정책의 허용은 서로 구분합니다.

## 설치와 플랫폼 지원

필요한 플러그인의 개별 패키지만 설치합니다. 공식 플러그인은 현재 공통 SDK와 같은
정확한 릴리스 버전을 사용합니다. 등록 목록은 앱 정의의 plugins에 작성하고 필요한
권한은 policy.json에 별도로 허용합니다.

화면과 백엔드는 같은 공개 import 경로와 같은 함수를 사용합니다.
설치했어도 등록하지 않은 구현은 초기화하지 않습니다.
현재 네이티브 어댑터는 Windows만 제공합니다. `PluginDefinition.platforms`에서 현재
플랫폼을 제외하면 앱 시작 단계에서 `UNSUPPORTED`로 거부합니다. Windows 작업에
어댑터가 없으면 필요한 권한이 허용된 상태에서 호출할 때 `UNSUPPORTED`로 실패합니다.
macOS는 네이티브 권한을 정책에 포함하면 호스트가 시작을 거부합니다.

새 네이티브 플러그인은 plugin.json, src/index.ts와 src/windows.ts를 기본으로 작성합니다.
추가 폴더와 파일은 제작자가 기능의 크기에 맞춰 선택합니다.
[네이티브 플러그인 작성](/reference/tooling/native-plugins/)에서 선언과 구현 방법을 설명합니다.

## 이관과 검증

공통 호출과 등록, 정책 v1의 새 구조를 먼저 구현한 뒤 세 플러그인, Windows adapter,
개별 배포와 CLI, 템플릿을 연결합니다. 내장 API를 새 패키지로 몰래 연결하는
호환 계층은 두지 않고 예제와 import를 명시적으로 바꿉니다.

검증은 플러그인 없는 앱, 저장만 설치한 독립 앱, 미등록 호출, 뷰와 앱 간 권한 분리,
취소, 초기화 실패와 역순 종료, 파일 경계, 브라우저 번들, 실제 Windows 창 실행을
포함합니다. 현재 reference-map은 구현된 공개 API를 검사하므로 이관과 함께 갱신합니다.

상세 공개 타입과 Windows 실행 순서, 이관 완료 조건은 저장소의
[구조 계약](https://github.com/mathbook3948/bunaway/blob/main/docs/architecture/plugins.md)에
정리합니다. 결정 배경은
[ADR 0013](https://github.com/mathbook3948/bunaway/blob/main/docs/decisions/0013-optional-native-plugins.md)를
따릅니다.
