창 플러그인의 `windowEvents`는 `windows.changed`의 payload 스키마를 제공하고,
`windowSnapshotSchema`는 이벤트용 JSON Schema입니다. 작업의 입력과 출력은 Zod로 정의하며,
snapshot 작업은 같은 이벤트 계약의 검증을 재사용합니다.
`WindowEvents`는 기존 typed listen의 이벤트 맵 타입입니다. 등록과 구독 권한,
상태와 물리 bounds 및 수명 규칙은 [창 API](/reference/host/windows/)에서 설명합니다.

공식 플러그인은 다음 구조를 사용합니다. 외부 제작자는 내부 파일 구성을 선택할 수 있습니다.
`src/index.ts`와 `src/platforms/<platform>.ts`는 플러그인 빌드의 진입점과 OS 경계입니다.

```text
my-plugin/
  package.json
  src/
    index.ts       계약과 플랫폼 선언 조립, 공개 export
    contract.ts    공통 스키마, 추론한 타입과 계약 검증
    operations.ts 공유 작업의 스키마와 handler
    platforms/
      windows.ts   실제 Windows 구현과 초기화, 정리
  dist/            빌드 결과
```

공식 플러그인은 공통 스키마와 타입을 contract.ts에 모으고 플랫폼 전용 보조 파일도
platforms 아래에 둡니다. 구현에서만 쓰는 상태나 바인딩 타입은 해당 구현에 둡니다.
외부 제작자에게 같은 파일 분리를 요구하지는 않습니다.

현재 네이티브 구현은 Windows를 기준으로 작성합니다. 앱에서 설치하고 등록하는 방법은
[플러그인 API](/reference/backend/host-api/)를 참고하세요.

## 패키지 설정

플러그인 작성 도구는 `@bunaway/plugin`에서 import합니다. 호환하는 프레임워크 버전을
peerDependencies에 지정하고 개발할 때도 같은 버전을 설치합니다. 공식 플러그인은
현재 공통 SDK와 정확한 버전을 맞춥니다.
`@bunaway/` 범위 밖의 외부 플러그인은 자체 패키지 버전을 사용합니다.
예를 들어 플러그인 버전이 `1.2.3`이어도 peerDependencies의 `@bunaway/plugin`이
프레임워크 버전과 정확히 일치하면 사용할 수 있습니다.
플러그인 버전은 package.json에만 작성합니다. 빌드가 이 값을 읽어 모든 출력에 기록합니다.

```json
{
  "name": "@example/plugin-system",
  "version": "0.0.0",
  "type": "module",
  "imports": {
    "#system/*": { "types": "./dist/types/*.d.ts", "default": "./src/*.ts" }
  },
  "exports": {
    ".": { "types": "./dist/types/index.d.ts", "default": "./dist/index.js" },
    "./native/*": { "types": "./dist/types/index.d.ts", "default": "./dist/native/*.js" }
  },
  "bunaway": { "plugin": "./dist/index.js" },
  "files": ["dist"],
  "dependencies": { "zod": "4.6.5" },
  "scripts": { "build": "bunaway plugin build" },
  "peerDependencies": { "@bunaway/plugin": "0.0.0" },
  "devDependencies": {
    "@bunaway/plugin": "0.0.0",
    "@bunaway/cli": "0.0.0",
    "@types/bun": "1.4.2",
    "typescript": "7.0.2"
  }
}
```

Windows 개발 모드에서는 조건부 루트 `exports`를 사용하는 플러그인도 코드 교체 시 같은 객체를 공유합니다.
`import`와 `require`는 각각의 조건에 맞는 진입점을 유지합니다. 두 조건이 같은 파일을 가리키면 공유 번들도 하나만 생성합니다.
`null`로 차단했거나 Bun 조건에서 제공하지 않는 하위 경로는 공유 목록에서 제외합니다.
앱이 해당 경로를 실제로 import하면 빌드가 실패합니다.

`imports`는 이 패키지 안에서 사용하는 비공개 별칭입니다. 위 설정에서는
`#system/contract`, `#system/platforms/windows`처럼 src와 확장자 없이 참조합니다.
소스 빌드는 default 경로를 번들에 포함하고, 설치한 패키지의 타입 검사는 types 경로를 읽습니다.
외부 앱에 내부 파일을 exports로 공개할 필요는 없습니다. 상대 import도 빌드에서 지원합니다.

## index.ts에서 한 번 선언하기

`defineNativePlugin(definition, calls?)`은 등록과 호출에 함께 쓰는 플러그인을 반환합니다.
반환값을 바로 default export합니다. 앱은 같은 값을 plugins에 등록하고 메서드를 호출합니다.
입력과 결과의 타입은 스키마에서 추론하며 별도 등록 객체나 호출 객체를 꺼내지 않습니다.

```ts
// src/platforms/windows.ts
import { hostname } from "node:os";
import { z } from "zod";

export const windowsOperations = {
  hostname: {
    input: z.null(),
    output: z.string(),
    handler: () => hostname(),
  },
} as const;
```

```ts
// src/index.ts
import { defineNativePlugin } from "@bunaway/plugin";
import { windowsOperations } from "#system/platforms/windows";

export default defineNativePlugin({
  name: "system",
  platforms: {
    windows: { operations: windowsOperations },
  },
});
```

`NativePluginDefinition`에는 version을 작성하지 않습니다. 빌드한 definition의 version은
플러그인 package.json에서 가져옵니다. 패키지를 빌드하지 않고 원본을 직접 import하면
version은 `development`이며 앱 배포에는 빌드한 export를 사용합니다.
name은 패키지 이름과 별개인 플러그인 식별자이며 작업 이름의 접두사로 사용합니다.
두 플랫폼의 입력, 결과, handler가 모두 같으면 완성된 작업 목록 하나를 각 플랫폼의
`operations`에 지정할 수 있습니다. 작업이나 handler가 다르면 플랫폼별로 선언합니다.
initialize, dispose와 thread는 작업 목록과 별개로 각 플랫폼에 지정하므로,
공유 목록을 쓰더라도 플랫폼마다 자원 수명과 실행 스레드는 다를 수 있습니다.
operations의 키는 공개 메서드 이름입니다. 각 작업에는 input, output과 handler를
작성합니다. SDK가 만드는 `system.hostname`이
호출 이름과 정책의 권한 식별자입니다. 작업마다 독립적으로 허용하며 별도 permission
이름이나 권한 묶음을 선언하지 않습니다. 선언 오류는 함수를 만들 때 거부합니다.

`NativePluginAPI`의 메서드 이름은 operations의 키와 같습니다.
위 예제는 `system.hostname(null): Promise<string>`을 만듭니다.

```ts
import { defineApp } from "@bunaway/backend";
import system from "@example/plugin-system";

export default defineApp({ modules: [], plugins: [system] });
```

화면의 이벤트 핸들러나 백엔드 명령 안에서 같은 export를 호출합니다.

```ts
import system from "@example/plugin-system";

async function readHostname() {
  return system.hostname(null);
}
```

화면과 백엔드는 같은 index.ts와 같은 함수를 사용합니다. 화면에서는 WebView로 호출하고,
백엔드에서는 현재 명령이나 setup의 호출 권한을 유지합니다.
화면용 함수와 백엔드용 함수를 따로 작성하지 않습니다.

화면의 마지막 인자에는 `NativeInvokeOptions`로 signal과 deadline을 전달할 수 있습니다.
이 옵션은 [invoke](/reference/client/invoke/) 규칙을 따릅니다. 백엔드는 진행 중 명령의
취소와 기한을 따르며 별도 옵션을 받지 않습니다. 생성 앱은 TypeScript의 browser와 bun
조건을 각각 적용해 화면과 백엔드 타입을 검사합니다. 직접 구성하는 프로젝트도 customConditions를 환경에 맞춰 지정합니다.

`index.ts`는 플러그인의 선언 조립과 공개 export를 담당합니다.
작업 목록은 `operations.ts`나 플랫폼별 작업 선언 파일에 두고 input, output과 handler를 함께 작성합니다.
`contract.ts`에는 재사용할 값 스키마와 타입, 필요한 계약 검증을 둡니다.
스키마만 모은 공통 작업 목록을 만든 뒤 플랫폼에서 펼칠 필요는 없습니다.
편의 함수의 실제 처리는 역할에 맞는 내부 파일로 분리하고 생성한 호출 함수를 전달해서 연결합니다.
log의 수준별 호출은 logger.ts,
capabilities의 결과 이름 중복 검사는 query.ts에 둡니다.
내부 파일은 contract.ts에서 계약과 타입을 읽습니다. index.ts를 역으로 import하지 않습니다.
생성된 api를 그대로 공개하는 기능에는 추가 로직 파일이 필요하지 않습니다.
플랫폼 구현 팩터리는 직접 import합니다. 선언과 구현의 최상위 코드에서는 파일이나 DLL을 열지 않습니다.
선언을 읽는 것만으로 연결이나 플랫폼 자원을 만들지 않습니다.
플랫폼 경계는 함수, Zod 스키마와 일반 객체로 된 작업 목록을 export할 수 있으며,
이름 변경과 `export *`, default 재내보내기도 지원합니다. 빌드는 별도 Bun 프로세스에서
export 형태를 읽지만 initialize와 handler는 호출하지 않습니다. 네이티브 자원 인스턴스는 initialize에서 만듭니다.
중립 출력과 다른 OS 출력에는 작업 키와 선언 형태만 남기고, 실제 스키마와 구현은 해당 OS 출력에 보존합니다.
호출 메서드의 타입 선언에는 인자, 결과와 옵션만 포함하며 내부 상태와 handler 타입은 노출하지 않습니다.
호출 함수는 설치, 앱 등록이나 권한 부여를 대신하지 않습니다.

## Zod로 입력과 결과 정의하기

`input`과 `output`에는 Zod 4.6.5 스키마를 작성합니다. Zod는 외부 의존성으로 선언하고
CLI로 플러그인과 앱을 빌드합니다. 다른 Zod 버전은 현재 앱 빌드에서 거부합니다. 기존 `s` 함수와 JSON Schema 객체는
네이티브 작업 선언에서 사용하지 않습니다. 앱 명령과 이벤트는 기존 Schema 형식을 유지합니다.

```ts
import { z } from "zod";

const input = z.strictObject({
  level: z.enum(["debug", "info", "warn", "error"]),
  message: z.string().max(1024),
  details: z.json().exactOptional(),
});
```

`z.strictObject`는 선언하지 않은 필드를 거부하고 `z.object`는 제거합니다.
`exactOptional()`은 필드 생략을 허용합니다. 호출 인자는 `z.input<typeof input>`,
반환값은 출력 스키마의 `z.output`에서 추론합니다. 기본값과 변환도 원본 Zod의 결과를 사용합니다.
고정된 Zod 4.6.5에서 문자열의 `max`는 Unicode 코드 포인트 수를 셉니다.
예를 들어 `z.string().max(1)`은 `"😀"`를 허용합니다.

### 실행 흐름

1. 화면이나 백엔드는 작업 이름과 JSON 입력을 보냅니다.
2. 호스트가 등록을 확인하고 작업을 담당하는 Worker로 전달합니다. 입력 검사 전에 호출 컨텍스트와 작업 권한을 확인합니다.
3. 허용된 호출에 대해 SDK가 `await input.parseAsync(payload)`를 실행합니다.
4. 호스트가 실행 직전에 컨텍스트와 권한을 다시 확인하고 파싱한 값으로 어댑터를 실행합니다.
5. 어댑터가 반환하면 SDK가 `await output.parseAsync(result)`를 실행합니다.
6. 파싱한 결과를 JSON으로 돌려줍니다. 호출자는 같은 스키마로 다시 파싱하지 않습니다.

스키마와 검사 함수는 설치한 플러그인 코드에 포함합니다. manifest와 Worker 메시지에는
플러그인 식별 정보와 작업 이름만 기록하며 스키마나 함수를 직렬화하지 않습니다.
`refine`, `transform`, `when`과 record의 키 처리는 Zod가 직접 실행합니다.
SDK는 스키마 내부 검사 종류를 해석하거나 JSON Schema로 변환하지 않습니다.

입력과 결과는 파싱 전후 모두 프로토콜의 JSON, 크기, 깊이와 Unicode 제한을 지켜야 합니다.
따라서 Date, bigint, undefined, 비유한 숫자를 전송하거나 변환 결과로 반환할 수 없습니다.
동기 및 비동기 refinement와 transform을 지원합니다. 입력 파싱 실패는 `INVALID_ARGUMENT`,
출력 파싱 실패는 `INTERNAL`로 처리합니다. SDK가 검사 Promise의 완료와 실패를 기다립니다.
I/O Worker는 먼저 컨텍스트와 작업 권한을 확인합니다. 거부된 호출은 입력 검사 콜백도 실행하지 않습니다.
입력 파싱을 마친 뒤 컨텍스트와 권한을 다시 확인하고 최종 승인 직후 네이티브 작업을 동기로 실행합니다.
Windows UI는 입력 파싱 후 실행 직전에 종료 상태와 호출 컨텍스트를 다시 검사합니다.
종료가 확정됐으면 취소 패킷을 기다리지 않고 `CANCELLED`로 거부합니다.
입력 파싱 중 취소된 호출은 실제 작업을 실행하지 않습니다. 결과 파싱 중 취소된 호출의
늦은 결과는 버립니다. Windows UI와 I/O, macOS 모두 메시지 수락과 작업 완료를 분리합니다.
취소와 컨텍스트 폐기 시 요청 용량을 반환하므로 입력 검사, 비동기 실행이나 결과 검사가
끝나지 않아도 다음 호출을 처리할 수 있습니다. 이미 실행한 네이티브 작업은 되돌리지 않습니다.
검사 콜백이 예외를 던지면 해당 호출을 실패시키고 이미 시작한 다른 검사의 늦은 오류도 처리합니다.
다른 검사가 끝나지 않아도 확인된 예외를 반환하며 Worker는 다음 요청을 처리합니다.
검사 함수의 예외나 Zod 오류의 상세 내용은 호출자에게 노출하지 않습니다.

선언할 때는 스키마 객체와 등록 정보를 확인하며 검사 콜백을 실행하지 않습니다.
실제 값에 대한 검사는 호출 때 이루어집니다. 검사와 변환 콜백은 입력과 결과를 처리하는 데 사용하세요. OS 자원 접근은
어댑터에서 수명과 취소를 관리합니다. Zod 콜백 자체는 취소할 수 없으므로,
호출이 취소되어도 이미 시작한 검사는 끝날 수 있습니다.

## 편의 호출이 필요한 경우

기본 메서드를 그대로 사용하면 두 번째 인자는 생략합니다. 인자 없는 조회나 수준별 로그처럼
호출 형태를 바꾸려면 `calls`에 생성된 작업 함수를 받는 조립 함수를 전달합니다.
조립 함수는 새 객체 또는 호출 가능한 함수를 반환합니다. SDK가 내부 등록 정보를 붙이고
반환값을 동결하므로 조립 함수에서 먼저 동결하지 않습니다. import 중에는 OS 자원을 만들지 않습니다.

```ts
export default defineNativePlugin({
  name: "system",
  platforms: { windows: { operations: windowsOperations } },
}, (operations) => ({
  hostname: () => operations.hostname(null),
}));
```

이 플러그인도 같은 값을 등록하고 `system.hostname()`으로 호출합니다.
공식 플러그인의 기존 편의 함수도 이 경로를 사용하며 호출 권한과 취소 처리는 생성된 작업 함수가 유지합니다.
`_definition`, `then`, `toJSON`은 내부 등록, Promise와 JSON 처리에 사용하는 예약 이름입니다.
작업 이름이나 편의 호출 결과에 이 속성이 있으면 선언을 거부합니다.

## platforms/windows.ts에서 구현하기

### 플랫폼별 operations로 선언하는 storage 샘플

각 플랫폼의 operations에서 작업마다 input, output 스키마와 handler를 함께 선언합니다.
`defineNativeOperation<Instance>()`을 한 번 만들면 각 handler의 입력은 input 스키마에서,
context의 instance는 지정한 타입에서 추론합니다. 반환값도 output 스키마의 입력 타입과 검사합니다.
최상위 공통 operations나 contracts는 요구하지 않습니다. 공개 인터페이스는 플러그인
작성자가 정의하며 재사용할 값 스키마도 선택합니다. 기존 create 어댑터 작성 방식은 호환을 위해 유지합니다.

```ts
// src/platforms/windows.ts
import { defineNativeOperation } from "@bunaway/plugin";
import { z } from "zod";
import { storageLocationSchema } from "../contract.ts";
import type { WindowsStorage } from "./windows.ts";

const operation = defineNativeOperation<WindowsStorage>();
export const windowsOperations = {
  readText: operation({
    input: storageLocationSchema,
    output: z.string(),
    handler: (input, { instance }) => instance.readText(input),
  }),
};
```

```ts
// src/index.ts
import { defineNativePlugin } from "@bunaway/plugin";
import { windowsOperations } from "./platforms/windows.ts";
import { createStorage, disposeStorage } from "./platforms/windows.ts";

export default defineNativePlugin({
  name: "storage",
  platforms: {
    windows: {
      initialize: createStorage,
      dispose: disposeStorage,
      operations: windowsOperations,
    },
  },
});
```

이 축약 예제는 readText만 지원합니다. 실제 storage는 operations.ts의 공통 작업 목록을
두 플랫폼에서 사용하고 windows-operations.ts에서 move와 remove를 추가합니다.
index.ts는 각 작업 목록과 플랫폼별 초기화, 정리를 연결합니다.
지원 여부는 각 플랫폼 operations의 키로 판단합니다. macOS에는 move와 remove를
선언하지 않아 해당 호출이 `UNSUPPORTED`로 실패합니다.
작업 선언 모듈은 자원을 초기화하지 않습니다. OS 바인딩과 초기화, 정리는
`src/platforms/<platform>.ts`에 두므로 중립 출력과 다른 OS 출력에서 제외됩니다.
플랫폼별 operations와 기존 create 어댑터를 한 플랫폼에 혼합하면 선언 오류가 납니다.

공개 `Storage` 인터페이스는 작성자가 정의합니다. `defineNativePlugin()` 결과의 메서드는 스키마에서 추론합니다.
별도의 공개 타입이 필요하면 타입 export를 추가합니다. SDK는 모든 플랫폼에 선언한 작업 이름을 모아 api를 만들며,
같은 이름의 입력이나 결과 타입이 다르면 호출 타입에는 그 합집합을 반영합니다.
실제 입력과 출력 검증은 실행할 플랫폼의 스키마만 사용합니다.
handler 입력은 input 스키마의 `z.output`, 반환값은 output 스키마의 `z.input`입니다.
값과 Promise를 모두 반환할 수 있고 각 스키마는 호출마다 한 번 파싱합니다.
호출자는 입력 스키마의 `z.input`을 전달하고 출력 스키마의 `z.output`을 받습니다.
`thread`는 실행 위치를 정하며 기본값은 worker이고 동기 또는 비동기 여부와 무관합니다.

`NativeHandlerContext<Instance>`의 instance는 initialize가 반환한 인스턴스이고,
source는 호스트가 정한 출처입니다. 호스트의 context 실행에는 requestId, permissions와
취소를 위한 signal도 전달합니다. 직접 어댑터 호출에서는 이 세 필드가 없을 수 있습니다.
handler가 await 뒤에 부수 효과를 실행한다면 signal을 확인하거나 소유한 작업에 전달해야 합니다.

initialize는 호스트의 실행 스레드에서 동기로 호출됩니다. Promise나 thenable 반환은
타입 검사에서 거부하며 런타임에서도 어댑터 생성을 실패시킵니다. 잘못된 비동기 초기화가
이미 시작됐다면 SDK는 늦게 반환한 인스턴스에 dispose를 호출하고 초기화나 정리 실패를
호스트 진단에 기록합니다. 끝나지 않는 초기화는 취소할 수 없습니다.
인스턴스 상태가 필요할 때 initialize를 작성하며 dispose가 그 인스턴스를 정리합니다.
초기화가 실패하기 전에 획득한 자원은 initialize가 회수해야 합니다.
동시에 호출한 dispose는 진행 중인 정리를 공유하고 성공한 정리는 반복하지 않습니다.
실패하면 오류를 전달하며 다음 dispose 호출에서 다시 정리합니다. 정리 구현은 이미 해제한
자원을 건너뛰고 남은 자원을 재시도할 수 있어야 합니다. 상태와 자원이 없는 handler에는 두 함수가 필요하지 않습니다.
진행 중인 작업 때문에 자동 종료를 미뤄야 하면 `busy(instance)`로 그 상태를 보고합니다.
SDK가 기존 호스트 실행 경계에 연결하므로 작성자는 execute와 executeUI를 구현하지 않습니다.

### 기존 어댑터 작성 방식

```ts
// src/platforms/windows.ts
import { hostname } from "node:os";
import { defineNativeAdapter } from "@bunaway/plugin";
import { systemOperations } from "../contract.ts";

export const createOperations = defineNativeAdapter(systemOperations, {
  setup: () => null,
  handlers: {
    hostname: () => hostname(),
  },
  dispose() {},
});
```

`NativeEnvironment`는 호스트가 정한 dataRoot와 capabilities 목록을 제공합니다.
Windows의 `app`은 검증한 앱 ID와 재실행 경로, 인자를 제공하며 `app.supportsHiddenStart`는
검증한 desktop 트레이 설정이 숨김 시작을 허용하는지 나타냅니다. 호출자가 지정할 수 없고
값이 없으면 숨김 자동 실행 등록을 허용하지 않습니다.
`NativeAdapterFactory`는 이 환경을 받아 어댑터를 반환하는 함수 타입입니다.
팩터리의 execute는 JSON 값 또는 Promise를 반환할 수 있으며 SDK가 완료를 기다립니다.
기존 `NativeAdapter` 타입의 execute는 동기 반환 계약을 유지합니다.
SDK가 감싼 `NativePluginAdapter`의 `execute`는 파싱 완료를 기다리는 Promise를 반환합니다.
호스트용 `prepare`는 입력을 파싱한 뒤 일회성 실행 함수를 반환하므로 권한 승인 직후
동기 네이티브 실행을 시작할 수 있습니다. 어댑터 제작자가 이 준비 단계를 구현할 필요는 없습니다.
DLL, 파일 핸들과 UI 자원은 createOperations 안에서 만들고 반환한 어댑터의 dispose에서 정리합니다.
초기화가 실패하면 팩터리가 이미 만든 자원도 회수해야 합니다.
Windows 호스트의 선택적 `app`은 검증한 앱 ID와 개발 또는 배포 실행의 절대 실행 파일,
프레임워크 부팅 인자를 제공합니다. 자동 실행 어댑터는 이 정보만 등록 경로로 사용하며
호출자가 실행 파일이나 다른 앱 ID를 선택하지 못합니다. 호스트 실행 정보가 없는 환경은
해당 기능을 지원한다고 가정하지 않습니다.
목록에는 앱에 등록된 네이티브 플러그인 작업만 포함합니다. 창 제어도 `windows`를
등록한 경우에만 포함합니다. 각 작업의 `support`는 해당 패키지의 플랫폼 구현에 따라
`supported`, `experimental`, `unsupported` 중 하나입니다. OS 동의 상태는 포함하지 않습니다.
`NativeAdapter.execute(operation, input, source)`는 승인된 작업을 동기로 실행하고 JSON
결과를 반환합니다. source는 호스트가 정한 출처입니다. `dispose()`는 자원을 정리하며
`void` 또는 `Promise<void>`를 반환합니다. 실패를 호출자에게 전달하려면 공통 `BunawayError`를
사용합니다. 예외의 상세 원인을 그대로 화면에 노출하지 않습니다.

선언한 schema로 입력과 결과를 검증합니다. 입력이 schema와 다르면 `INVALID_ARGUMENT`,
결과가 schema와 다르면 `INTERNAL`을 반환합니다. 권한 거부와 안전한 실행 오류는 호출자에게 전달합니다.
화면으로 전달할 때는 결과와 요청 ID, 프로토콜 정보를 합친 응답에도 1 MiB 제한을 적용합니다.
제한을 넘으면 해당 호출에 `INTERNAL`을 반환하고 연결을 유지합니다.

호스트는 진행 중인 Host 호출과 전송 용량을 제한합니다. 여유가 없으면 새 호출을
`BUSY`로 거부합니다. 작업 전송이 한도에 도달해도 이미 접수한 작업의 승인과 취소,
종료를 처리할 용량은 별도로 유지합니다.

## 함수 맵으로 플랫폼 구현하기

`defineNativeAdapter(operations, implementation)`은 create 팩터리를 만듭니다.
implementation의 setup은 어댑터 수명의 공유 자원을 반환하고 dispose는 그 자원을 정리합니다.
handlers에는 구현한 짧은 작업 이름과 함수만 적습니다. 키에서 지원 목록을 만들므로
platforms의 operations 배열을 함께 지정하면 거부합니다. `NativeHandlerFactory.operations`는
변경할 수 없는 지원 키 목록입니다. 구현하지 않은 키는 권한 확인 후 UNSUPPORTED입니다.

`NativeHandlers`의 각 함수는 `(input, context, state)`를 받습니다. input은 Zod 파싱 결과이며
반환값은 해당 출력 schema가 받는 타입입니다. 기본값과 transform도 이 타입에 반영합니다.
`NativeCallContext`는 source, requestId, permissions와 선택적 signal을 제공합니다.
작성자가 beforeExecute를 호출할 필요는 없습니다. SDK가 입력 파싱 후 실행 직전에
호스트의 살아 있는 권한을 다시 확인하고 취소를 검사합니다. 대기나 비동기 자원을 소유한
구현은 signal을 관찰해 자원도 해제해야 합니다.

공식 플러그인은 플랫폼별 operations에 스키마와 handler를 함께 선언합니다.
기존 어댑터 작성 방식은 이전 플러그인과의 호환을 위해 사용할 수 있습니다.
앱은 같은 패키지를 설치하고 app.ts의 plugins에 등록합니다. 호스트 실행 단계를 알 필요가 없습니다.

defineNativePlugin의 events에는 기존 이벤트 JSON Schema를 작업과 함께 선언합니다.
예를 들어 `events: { "system.changed": { type: "string" } }`를 지정합니다.
`defineApp()`은 플러그인의 이벤트를 등록하고 `EventsOf`에 같은 스키마를 반영합니다.

## 플랫폼 구현 연결하기

```ts
platforms: {
  windows: {
    operations: windowsOperations,
  },
  macos: {
    operations: macosOperations,
  }
}
```

package.json의 `bunaway.plugin`은 default export한 플러그인을 읽는 진입점입니다.
`platforms`는 defineNativePlugin의 선언 안에 작성하며 별도 plugin.json은 사용하지 않습니다.
플랫폼 이름은 [공통 계약의 PLATFORMS](/reference/tooling/plugin-api/#플랫폼-이름)에 정의된 windows, macos, linux, android, ios입니다. SDK와 CLI가 각각 이 목록으로 선언을 검증합니다. 구현을 제공하는 플랫폼만 선언합니다.
이 이름을 선언해도 해당 플랫폼의 프레임워크 실행 경로가 새로 생기지는 않습니다.

`operations`에는 해당 플랫폼의 작업별 스키마와 handler를 선언합니다.
구현 내부의 파일 구성은 자유롭게 나눌 수 있습니다.
import에서 확장자를 생략해도 빌드는 실제로 해석한 파일 경로를 기준으로 같은 OS 경계를 적용합니다.
`thread`는 `worker` 또는 `ui`이며 기본값은 `worker`입니다. UI 스레드가 필요한 구현만
`thread: "ui"`를 지정합니다. 초기화, 작업 실행과 정리는 같은 스레드에서 수행합니다.
각 플랫폼 출력에는 해당 OS 구현만 포함하고 화면 출력에서는 모든 OS 구현을 제외합니다.
자원 생성은 호스트가 등록된 플랫폼의 initialize를 호출할 때 수행합니다.

기존 저수준 NativeAdapter를 직접 반환하는 구현은 호환 경로에서 `operations`에 짧은 작업 이름을
나열할 수 있습니다. 생략하면 전체 작업, 빈 배열이면 지원하는 작업이 없습니다.
중복 이름과 선언하지 않은 작업 이름은 거부합니다.
기능 지원 조회와 호출 검사는 같은 목록을 사용합니다. 플랫폼 구현이나 작업이 없으면
권한 검사 뒤 `UNSUPPORTED`를 반환합니다. 지원 여부는 권한을 부여하지 않습니다.

내부 `_definition.nativePlatforms`에는 검증한 구현 정보가 들어갑니다.
`_definition`은 열거되지 않는 읽기 전용 속성입니다. CLI와 앱 조립이 읽으며 앱 코드에서 꺼내 등록하지 않습니다.
SDK가 만든 create 함수는 열거되지 않는 속성이므로 JSON과 structured clone에는 실행 위치와 지원 작업만 전달합니다.
일반 앱 플러그인의 `platforms` 배열은 앱 시작을 제한하는 별도 계약이므로 이 맵과 혼용하지 않습니다.
개발 중 manifest와 정책 형식은 v1입니다.

## 플러그인 빌드와 배포

패키지 루트에서 `bun run build` 또는 `bunaway plugin build [directory]`를 실행합니다.
`tsconfig.json`은 src를 포함하고 Bun 타입과 JSON import를 허용해야 합니다.
다음은 최소 설정입니다.

```json
{
  "compilerOptions": {
    "target": "ES2022", "module": "Preserve", "moduleResolution": "Bundler",
    "strict": true, "noEmit": true, "allowImportingTsExtensions": true,
    "resolveJsonModule": true, "types": ["bun"],
    "rootDir": "./src", "outDir": "./dist/types"
  },
  "include": ["src/**/*.ts"]
}
```

빌드는 `dist/index.js`, `dist/types/`와 선언한 OS의 `dist/native/<platform>.js`를 만듭니다.
rootDir과 outDir은 위 별칭의 types 경로를 자체 개발 중 원본 src로 연결합니다.
생성한 선언 파일은 배포 후 같은 별칭으로 dist/types를 참조하므로 src를 배포하지 않아도 됩니다.
중립 출력의 플랫폼 팩터리는 실행을 거부하는 자리 함수로 대체합니다. 화면과 백엔드,
CLI는 이 출력에서 동일한 계약과 호출 API를 읽습니다. 호스트는 패키지의 `native/<platform>`
export를 지연 import한 뒤 등록된 플러그인의 팩터리만 호출합니다. 앱에서 네이티브 export를 직접 호출하지 않습니다.
SDK 패키지는 외부 의존성으로 유지하므로 앱의 호출 컨텍스트와 오류 타입을 공유합니다.
파일 asset import는 지원하지 않으며 빌드에서 거부합니다. 타입 검사나 번들 생성이 실패하면 기존 dist를 보존합니다.
빌드 후 dist를 포함한 패키지를 배포합니다. 앱의 화면 번들러에는 별도 플러그인을 설정할 필요가 없습니다.
개별 플러그인을 수정한 뒤에는 플러그인부터 다시 빌드합니다.

Windows CLI는 설치된 플러그인의 계약과 실행 위치를 앱 설정, 정책과 함께
`assets/manifest.json`에 기록합니다. 플러그인 구현을 불러오는 코드는
CLI의 공통 앱 모듈 생성기가 메모리에서 만들고 번들에 포함합니다. 중간 소스 파일은 쓰지 않습니다.
개발 빌드에서는 manifest와 번들을 확인할 수 있고, 배포 빌드에서는 EXE에 포함합니다.
생성 결과를 직접 수정하지 않고 원본 계약이나 플랫폼 선언을 수정한 뒤 다시 빌드합니다.

## 앱의 접근 규칙

정책은 `storage.readText` 같은 작업 이름만 허용합니다. 작업마다 입력과 출력 schema를 검증하지만,
파일별 접근이나 특정 창의 제어 같은 앱 규칙은 백엔드 앱 명령에서 검사합니다.
화면에는 해당 앱 명령만 허용하고 직접 플러그인 명령은 허용하지 않아야 이 검사를 거칩니다.
뷰에서 시작한 앱 명령도 원래 뷰의 작업 권한을 유지합니다.

예를 들어 메모 읽기는 메모 ID를 입력받아 앱에서 접근 가능 여부를 확인하고,
서버가 정한 저장 경로로 `storage.readText`를 호출합니다. 화면에 임의 파일 경로를 맡길 필요가 없습니다.
플러그인은 자체 입력 검증과 플랫폼 경로, 파일 링크, 최종 핸들 검사를 담당합니다. 저장 위치와 파일별 접근 규칙은 앱이 정합니다.

## OS 권한 요청

카메라, 위치 등의 OS 동의 상태 조회와 요청은 해당 기능의 플랫폼 구현이 담당합니다.
공통 선언에 osPermission 필드를 두거나 capabilities 결과로 동의 상태를 추정하지 않습니다.
필요하면 기능 플러그인이 별도의 조회와 요청 operation을 공개합니다.

예를 들어 카메라 플러그인을 작성하면 capture 구현 안에서 OS 동의 상태를 확인하고,
필요할 때 요청한 뒤 촬영할 수 있습니다. 호스트가 먼저 `camera.capture`의 앱 정책을
검사하므로 정책에 없는 호출은 OS 요청까지 도달하지 않습니다. 사용자가 OS 요청을
거부하면 `PERMISSION_DENIED`를 반환합니다. 카메라 플러그인은 현재 제공하지 않습니다.

OS 대화상자는 import와 어댑터 등록 중에 표시하지 않습니다. 비동기 요청이 필요한 UI
구현은 executeUI를 사용하고 signal을 관찰합니다. 취소할 수 없는 OS 요청이 이미 시작됐다면
승인 뒤 기능 실행을 이어가지 않고, 요청 완료 후 소유한 자원을 정리합니다.

## 시작과 종료

설치했어도 앱에 등록하지 않은 구현은 초기화하지 않습니다.
설치한 선언과 등록한 선언이 다르면 시작을 거부합니다. 객체 키 순서는 비교에
영향을 주지 않으며 배열 순서와 값은 비교합니다.
일반 객체와 null prototype 객체는 같은 JSON 내용이면 같은 계약으로 취급합니다. 숫자 `-0`과 `0`도 같은 값으로 비교합니다.
초기화 실패나 종료 때는 준비된 구현을 역순으로 정리합니다. 정리 실패가 있어도
나머지 구현과 플랫폼 자원 회수를 시도한 뒤 오류를 보고합니다.

공통 `invokePlugin(contract, input, options?)`은 화면 호출의 기반 함수입니다.
이 함수의 입력과 결과는 JsonValue이며 의미 검사는 실행 Worker가 담당합니다.
defineNativePlugin을 사용하면 Zod 검증, 타입 추론, 공유 연결과 호출 옵션 전달을
각 플러그인에서 다시 작성할 필요가 없습니다.

## 선택 창 제어와 UI 실행

`NativeEnvironment.windows`는 UI 실행에만 제공하는 NativeWindowServices입니다. 플러그인은 필요한 저수준 창 자원을 사용하며 공통 호스트는 특정 작업 이름을 분기하지 않습니다.

`NativeAdapter.executeUI`는 UI 작업의 비동기 실행을 지원하며 requestId와 호스트가 확인한 permissions, 선택적 signal과 호스트의 실행 직전 재검사 함수 beforeExecute를 받습니다. Windows UI와 macOS 호스트는 요청 취소, 컨텍스트 폐기와 종료 때 signal을 중단합니다. 어댑터는 취소를 관찰하고 소유한 대기와 자원을 정리해야 합니다. 동기 OS 작업은 완료한 변경을 되돌리지 않습니다. `busy`는 진행 중 작업이 있어 자동 종료를 보류해야 하는지 알립니다. I/O의 execute는 권한 확인 뒤 동기 실행 계약을 유지합니다. UI 어댑터는 STA 초기화 뒤 준비하고 역순으로 정리합니다.

`@bunaway/plugin-windows`의 windowOperations는 Zod 입력과 출력 계약입니다. isWindowOperation은 이름을 확인하며 parseWindowCall과 validateWindowCall은 입력을, validateWindowOutput은 결과를 검사합니다. 이 함수는 선택 패키지 안의 계약 도구이며 공통 프로토콜은 창 작업 목록을 소유하지 않습니다.

`windowSnapshotSchema`는 표시와 geometry 관찰, `windowReadinessSchema`는 창, 문서와 SDK 준비 상태의 스키마입니다.
`windowEvents`는 `windows.changed`와 `windows.readiness`의 선언입니다. 완료 조건, 수신 범위와 상태 복구는
[창 API](/reference/host/windows/#창-준비)를 따릅니다.

Windows UI 어댑터의 선택적 `NativeEnvironment.shortcuts`는 `NativeShortcutServices`를 제공합니다.
`createWindow`로 숨긴 메시지 창을 만들고 `destroyWindow`로 해제하며 `emit`은 기존 정책과 구독 확인 경로를 사용합니다.
전역 단축키 플러그인이 개별 등록과 메시지 창을 소유하고 호스트는 기존 UI 스레드와 앱 실행 유지 정책을 유지합니다.

Windows UI 어댑터의 선택적 `NativeEnvironment.menus`는 `NativeMenuServices`를 제공합니다.
`NativeMenuItem` 트리를 `setTrayMenu`로 연결하고 `emit`으로 정책과 구독을 확인하는 기존 네이티브 이벤트 경로에 전달합니다.
null은 트레이 메뉴 숨김이고 undefined는 tray 기본 Open/Quit 복원입니다.
트레이가 없으면 연결은 UNSUPPORTED이며 메뉴 정의 자체는 선택 플러그인이 소유합니다.

`NativeEventWaiters<T>`는 UI 어댑터가 소유하는 일회성 알림 대기입니다. 생성자에 최대 대기 수를 지정하고 `wait(signal)`로 다음 알림을 기다립니다.
`publish(value)`는 현재 대기자에게 각각 복사본을 전달하며 이력을 저장하지 않습니다.
취소와 `dispose()`는 CANCELLED, 한도 초과는 BUSY이며 어댑터 정리에서 반드시 dispose를 호출합니다.
대기 자체는 앱 실행 유지 조건을 바꾸지 않습니다. 창이 없는 앱의 백엔드는 플러그인의 wait 작업을 사용할 수 있습니다.

`NativeEnvironment.tray`는 호스트가 설정한 단일 아이콘의 NativeTrayServices입니다.
get과 getBounds, setTooltip과 setIcon, setClickBehavior, focus와 subscribe를 제공합니다. 등록한 플러그인의 initialize가 트레이 구현을 생성합니다. NativeTrayInitialization은 검증한 tooltip과 빌린 NativeTrayWindowHost, 복원과 종료 콜백을 제공합니다. NativeTrayOwner의 dispose는 실패한 자원을 보존해 재시도할 수 있어야 합니다. 호스트는 콜백 정지와 창 정리, 재시도 순서를 소유합니다.
입력은 기존 emit 경로 또는 NativeEventWaiters를 통해 전달합니다.

공유 트레이 제한은 MAX_TRAY_TOOLTIP_UNITS(UTF-16 127개), MAX_TRAY_ICO_BYTES(65,536 bytes), MAX_TRAY_WAITERS(16개)로 선언합니다.
계약과 native 자원 소유자가 같은 제한을 사용합니다.

SDK가 반환하는 `NativePluginAdapter.prepare(operation, input, source, context?)`는
입력을 한 번 파싱하고 한 번만 실행할 수 있는 함수를 반환합니다. 선택적 context는 UI와
I/O 모두 같은 취소와 실행 직전 재검사를 적용합니다. 이 단계는 호스트 통합용이며
함수 맵 작성자가 직접 호출할 필요는 없습니다.
