호스트나 런타임 어댑터를 작성할 때 사용하는 공개 API입니다.
앱 정의 작성법은 [AppDefinition](/reference/backend/app-definition/)에서 설명합니다.

## createCore

```ts
import { createCore } from "@bunaway/core";
const core = await createCore(app, services);
const session = core.openSession(hostContext, "main");
await session.receive(clientMessage);
await session.close();
await core.stop();
```

`createCore(app: AppDefinition, services: CoreServices): Promise<Core>`입니다.
`@bunaway/backend`도 같은 createCore를 재수출합니다.
이름의 유효성과 중복 여부, 예약 명령, 플러그인 의존성 및 권한을 검사합니다. setup이 끝나면 Core를 반환합니다.
초기화 실패 시 이미 등록한 정리 훅을 역순 실행합니다.

## CoreServices

| 필드 | 책임 |
| --- | --- |
| `policy` | 검증한 Policy |
| `hello` | 백엔드 협상 메시지 |
| `platform` | 현재 플랫폼 |
| `backendContext` | 호스트가 발급한 백엔드 컨텍스트 |
| `runtime` | 시간, 스케줄, 취소를 제공하는 RuntimeServices |
| `validateMessage(context, message): void` | 선택적 동기 검사. 이벤트를 큐에 넣기 전에 전송 envelope 제한 검사 |
| `send(context, message)` | 서버 메시지를 해당 전송에 FIFO로 보내기 |
| `callHost(context, call, signal)` | 원래 컨텍스트를 보존해 HostResponse 반환 |

HostContext는 호스트가 발급한 값을 사용합니다. 앱의 입력 문자열을 캐스팅한 값은 유효한 컨텍스트로 인정되지 않습니다.
send가 복구할 수 없는 오류로 실패하면 어댑터에서 전송과 세션을 닫아야 합니다.
Windows 어댑터는 모든 뷰의 서버 메시지에 공유 FIFO 대기열을 사용합니다.
미확인 데이터 128개의 수신 확인을 받으면 다음 서버 메시지를 전달합니다.
대기 서버 메시지는 16,384개로 제한하며, 대기열이 남으면 새 Host API 호출은 BUSY로 거부합니다.
이미 승인한 Host 작업의 결과는 별도 대기 용량 128개를 유지하며 같은 FIFO에서 전달합니다.
대기열까지 포화되면 해당 세션의 요청과 구독에 BUSY를 전달하고 컨텍스트를 정리합니다.
취소와 종료는 이 데이터 용량을 사용하지 않습니다. 구독별 전송 순서는 유지됩니다.

전송 envelope에 추가 크기나 깊이 제한이 있으면 `validateMessage`를 제공합니다.
이 검사는 전송하거나 큐와 세션 상태를 변경하지 않으며 실패하면 throw합니다.
코어는 모든 대상의 이벤트 검사에 성공한 뒤에만 큐와 순번을 변경합니다.
검사 실패는 발행자에게 `INVALID_ARGUMENT`로 반환하며 기존 구독과 세션을 유지합니다.
Bun 프로세스 어댑터는 context, ipc와 runtime을 포함한 전체 프레임을 실제 송신과 같은 함수로 검사합니다.

선택적 `onCommandError(command, cause)`는 핸들러의 예기치 않은 예외를 원본 그대로 받는 진단 콜백입니다. `BunawayError`로 선언한 앱 오류에는 호출하지 않습니다. 반환형은 `void` 또는 `Promise<void>`이며 응답은 콜백 완료를 기다리지 않습니다. 콜백의 throw와 rejection은 무시합니다. 원본 메시지와 스택은 신뢰된 진단 경로에서만 사용하고 WebView 응답에는 넣지 않습니다.

선택적 `onPluginError(plugin, phase, cause)`는 실패한 플러그인 이름, `"setup"` 또는 `"stop"` 단계와 원래 오류를 받습니다. 선언한 `BunawayError`도 포함합니다. 반환형은 `void` 또는 `Promise<void>`이며 콜백 완료를 기다리지 않습니다. 콜백이 throw하거나 reject해도 나머지 종료 훅을 실행합니다. 종료 훅의 실패는 진단에 전달하고, 기한 안에 정리를 마치면 `stop()`은 완료됩니다.

Windows 어댑터는 플러그인 오류를 터미널과 `plugin-failed` 진단 로그에 남깁니다. Bun 프로세스 어댑터는 stderr에 기록합니다. Windows 어댑터는 진단 로그의 쓰기 실패를 무시하고 이후 로그를 계속 처리합니다. 실패한 기록은 다시 시도하지 않습니다.
두 어댑터 모두 종료 요청을 처리하던 중 setup이 `CANCELLED`로 끝난 경우에는 정상 취소로 보고 실패 로그를 남기지 않습니다.

## RuntimeServices

| 메서드 | 반환, 계약 |
| --- | --- |
| `createCancellation()` | `CancellationController` (`signal`, `abort()`) |
| `now()` | UTC epoch 밀리초 |
| `schedule(callback, delayMs)` | 타이머 해제 함수 `Dispose` |

wire deadline은 UTC이고 실제 타이머는 어댑터의 단조 시간 기준으로 예약합니다.
CancellationSignal은 `aborted`, `addEventListener("abort", listener)`, `removeEventListener` 구조로,
DOM 전역 없이도 사용할 수 있는 AbortSignal의 부분 계약입니다.

## 세션과 종료

`core.openSession(context, viewId)`는 호스트가 검증하고 선택한 뷰의 CoreSession을 만듭니다.
요청 ID와 구독, 협상 상태는 세션마다 따로 관리합니다. 앱 state와 등록된 명령은 모든 세션이 공유합니다.

`session.receive(message): Promise<void>`는 메시지를 받아 처리 경로로 전달할 때까지 기다립니다.
명령 핸들러는 그 이후에도 실행될 수 있으며 최종 결과는 services.send로 전달됩니다.
`session.close(error?: WireError)`는 요청, 구독, 컨텍스트를 정리합니다.
`core.stop()`은 세션과 플러그인 훅을 정리하며 코어 종료 예산은 2초입니다.
취소되거나 종료된 컨텍스트에서는 핸들러가 뒤늦게 완료되더라도 Host 호출과 이벤트 발행이 거부됩니다.

## runBunApp

`@bunaway/runtime-bun`의 `runBunApp(app: AppDefinition): Promise<void>`는
stdin/stdout으로 프로세스 IPC를 연결하고 부팅부터 세션과 Host 응답 처리, 종료까지 관리합니다.
프로세스 probe와 계약 테스트에서 사용하는 어댑터입니다.
Windows와 macOS 제품 호스트는 같은 AppDefinition을 Bun에서 직접 실행하며 stdin/stdout IPC를 사용하지 않습니다.

stdout은 프로토콜 전용이므로 프로세스 진단은 다른 스트림에 출력해야 합니다.
boot의 정책, backendContext, 프레임 runtime generation, 방향을 검사합니다.
준비 이전 플러그인 setup의 Host 응답도 처리하며 예상하지 않은 EOF는 연결 실패입니다.

## bindHostAPI

`bindHostAPI(context, signal, callHost, registry): HostAPI`는 고정된 컨텍스트, 취소 신호를 Host 호출에 연결합니다.
callHost는 `(context, HostCall, CancellationSignal) => Promise<HostResponse>`입니다.
입력을 검증하고 호출 전후에 취소 여부를 확인합니다. abort가 발생하면 진행 중인 호출과 취소 중 먼저 완료된 결과를 사용합니다.
Host 오류는 그대로 전달하고 잘못된 출력이나 일반 실패는 INTERNAL로 변환합니다.
파일 접근과 권한은 이 함수 이후에도 호스트에서 검사합니다.

NativeRegistry에 앱이 등록한 네이티브 계약을 전달합니다. bindHostAPI는 호출자가 넘긴 schema 대신 이 등록 계약을 사용합니다. 현재 macOS 호스트는 네이티브 플러그인의 권한과 작업을 UNSUPPORTED로 거부합니다.

## readJsonLines

`readJsonLines(chunks: AsyncIterable<Uint8Array>): AsyncGenerator<string>`는 UTF-8 NDJSON reader입니다.
바이트 조각 사이에서 끊긴 문자, 여러 줄을 처리하고 각 줄을 문자열로 yield합니다.
잘못된 UTF-8, 빈 줄, 1 MiB 초과 프레임, 마지막 줄이 미완성인 EOF를 거부합니다.
줄의 JSON/프레임 검증은 별도로 parseProcessFrame에 맡깁니다.

## 개발 실행 helper

CLI와 호스트가 개발 실행 설정을 공유할 때 사용하는 `@bunaway/runtime-bun/development` export입니다.
개발 URL은 `http(s)://localhost` 또는 `http(s)://127.0.0.1`만 허용하며 사용자 정보와 fragment가 없어야 합니다.

| 함수 | 계약 |
| --- | --- |
| `developmentUrl(value: unknown): URL` | loopback 개발 URL을 검증하고 URL 객체를 반환합니다. |
| `developmentPolicy(policy: Policy, viewId: string \| readonly string[], url: string): Policy` | viewId와 일치하는 view의 origin을 개발 URL의 origin으로 바꾼 새 Policy를 반환합니다. viewId가 배열이면 포함된 ID에 적용합니다. |
| `verifyDevelopmentLaunch(marker, launchUrl?): string \| undefined` | 개발 산출물 marker와 `--dev-url` 값이 모두 없으면 `undefined`를 반환합니다. 둘 중 하나만 있거나 URL이 다르면 실패합니다. 두 값이 일치하면 검증한 URL의 정규화된 `href`를 반환합니다. |
| `developmentWindowHome(home, server): string` | 개발 서버 URL에 앱 home의 경로와 query를 적용한 주소를 반환합니다. 서버 URL은 loopback이어야 합니다. |
| `verifyDevelopmentToolsLaunch(marker, requested = false): boolean` | marker와 `--devtools` 요청이 모두 없으면 `false`를 반환합니다. marker가 `true`이고 요청도 있을 때만 `true`를 반환하며 나머지 조합은 실패합니다. |
| `readAppReloadRequest(value: unknown): AppReloadRequest` | CLI의 비공개 개발 IPC 요청을 검증합니다. kind는 `bunaway:reload-app`, id는 UUID 형식, sha256은 소문자 16진수 64자리여야 합니다. 다른 필드는 거부합니다. |
| `readAppReloadResult(value: unknown): AppReloadResult` | kind가 `bunaway:reload-result`인 응답의 id와 status를 검증합니다. status는 `reloaded`, `restart`, `failed` 중 하나이며 선택적 message는 4096자 이하입니다. 다른 필드는 거부합니다. |

`verifyDevelopmentLaunch`는 marker가 `{ url }` 한 필드로 구성되고 실행 옵션의 URL과 정확히 같아야 합니다.
개발자 도구도 개발 산출물과 명시적인 `--devtools` 실행 옵션을 함께 요구합니다.
앱 코드 교체 IPC는 CLI가 시작한 Windows 개발 프로세스에서만 연결합니다.
이 함수들은 요청과 응답을 검증하며 코드를 로드하거나 WebView 권한을 변경하지 않습니다.
`MAX_APP_RELOAD_MESSAGE_CHARS`는 개발 IPC 응답의 message 상한이며 값은 4096입니다.

## 실행 manifest

CLI와 Windows 호스트는 `@bunaway/runtime-bun/app-manifest`로 생성 데이터의 계약을 공유합니다.
`AppManifest`는 `format: 1`, `app`, `policy`, `plugins`, `developmentSdk`를 담습니다.
`ManifestPlugin`은 이름, 버전, native 계약, 선택적 `execution: "io" | "ui"`와
권한 범위 검사 함수의 유무를 나타내는 `authorization`을 담습니다.

| 함수 | 계약 |
| --- | --- |
| `parseAppManifest(value: unknown): AppManifest` | 형식, 플러그인 계약과 개발 SDK 모듈 경로를 검사합니다. 지원하지 않는 형식, 중복 플러그인과 잘못된 입력은 예외로 거부합니다. |
| `readAppManifest(assets: string): Promise<AppManifest>` | 지정한 실행 자산 디렉터리의 `manifest.json`을 읽고 검증합니다. 파일 읽기, JSON 해석과 검증 실패를 호출자에게 전달합니다. |

앱 설정과 정책의 세부 실행 검증은 부팅 단계의 기존 검증기가 맡습니다.
정책은 manifest의 다른 필드와 별도로 검증하므로 기존 정책의 크기와 깊이 제한을 유지합니다.
플러그인 메타데이터와 native 계약은 따로 검증하므로 기존 native 계약의 크기와 깊이 제한을 유지합니다.
이 함수들은 플러그인 실행 코드를 불러오거나 네이티브 자원을 초기화하지 않습니다.
개발 SDK 경로는 `sdk0.js`, `sdk1.cjs`처럼 생성된 모듈의 파일 이름만 허용합니다.
최종 EXE와 파일 해시를 기록하는 패키지 루트의 manifest는 별도 계약입니다.

## 창 설정 helper

CLI 설정과 검증된 패키지 부팅이 공유하는 `@bunaway/runtime-bun/window-config` export입니다.

| export | 계약 |
| --- | --- |
| `MAX_WINDOWS` | 최대 창 수인 `128`입니다. |
| `readWindowSpecs(value, policy, developmentUrl?): WindowSpec[]` | 알 수 없는 필드와 잘못된 창 설정을 거부하고 검증된 WindowSpec 배열을 반환합니다. |

`WindowSpec`은 `view`, `home`, `title`, `window: { width, height, minWidth?, minHeight?, maxWidth?, maxHeight? }`와 선택적 `startup`을 가집니다. 크기 제약 값은 96 DPI 기준 논리 픽셀의 정수 `200`부터 `4096`까지이며 `null` 또는 생략은 제한 해제를 뜻합니다. 최소값이 최대값보다 크면 설정 검증에 실패합니다.
설정에는 1개부터 `MAX_WINDOWS`개까지 창을 둘 수 있습니다. view ID는 영문자, 숫자, 밑줄, 마침표, 콜론, 하이픈으로 구성한 1자부터 128자까지의 고유한 값이어야 합니다.
제목은 NUL이 없는 1자부터 1024자까지이며 초기 너비와 높이는 정수 `200`부터 `4096`까지입니다. 초기 크기는 설정한 제약으로 보정합니다.
home은 개발 URL을 전달하면 그 origin을, 그렇지 않으면 `https://app.bunaway.local`을 사용해야 합니다. 사용자 정보와 fragment는 포함할 수 없습니다.
해당 origin은 `policy`의 같은 view에 허용되어야 합니다. 창 설정 중 하나 이상은 `startup`이 `false`가 아니어야 합니다.

## Windows 개발 호스트 제어

`@bunaway/runtime-bun/windows-control`은 Windows 호스트와 개발 CLI가 공유하는 창 제어 상수입니다.
이 경로를 가져오는 것만으로 네이티브 DLL을 로드하거나 창을 만들지 않습니다.

| export | 계약 |
| --- | --- |
| `APP_SHUTDOWN_MESSAGE` | 개발 CLI가 호스트에 정상 정리를 요청하는 Win32 메시지 번호 `0x8002`입니다. 사용자 닫기 확인, 종료 취소와 트레이 숨김을 우회하는 기존 개발 종료 경로를 사용합니다. |
| `APP_WINDOW_CLASS_PREFIX` | CLI가 대상 프로세스의 호스트 창을 찾을 때 대조하는 클래스 이름 접두어 `bunaway-bun-`입니다. 호스트도 같은 접두어로 클래스를 등록합니다. |

이 값은 프레임워크의 개발 실행 계약이며 앱의 `desktop.beforeQuit` 설정을 대신하지 않습니다.
