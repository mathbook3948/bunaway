정책은 버전 1의 `{ version, views, backend }`입니다.
세 필드가 모두 필수이며 추가 필드는 허용하지 않습니다.
정책에 선언하지 않은 권한은 거부합니다.
입문 설명과 전체 템플릿은 [창과 뷰의 정책](/concepts/views-and-policy/)에 있습니다.

## views

최대 128개입니다. 단일 창 설정은 뷰 하나를, `app.windows`는 창별로 정책에 있는 뷰를 사용합니다.
각 항목은 아래 필드를 모두 요구하며 추가 필드를 거부합니다.

| 필드 | 제약 | 의미 |
| --- | --- | --- |
| `id` | 1–128자, 영숫자, `_ . : -` | 정책 단위 ID. 파일 전체에서 중복 금지 |
| `origins` | 최대 16개, 중복 금지 | 정확한 HTTP(S) origin 문자열 |
| `commands` | 최대 256개, 중복 금지 | 정확한 앱 명령 이름 |
| `events` | 최대 256개, 중복 금지 | 정확한 이벤트 이름 |
| `host` | `permissions` 필수, `windows` 선택 | 해당 뷰에서 시작한 작업의 플러그인 권한과 창 API 대상 |

배열이 비어 있으면 그 기능은 허용하지 않습니다. 와일드카드 origin, 명령은 지원하지 않습니다.
명령, 이벤트 이름은 id와 같은 식별자 규칙입니다.
핸들러와 이벤트는 `app.ts`에 등록하고 창은 앱 설정에 정의합니다. 정책에는 사용할 수 있는 이름을 선언합니다.

## origins

`https://app.bunaway.local`이나 `https://example.com:8443`처럼 origin을 지정합니다.
경로, query, fragment, 사용자 정보 없이 origin만 지정합니다.
스키마는 소문자 호스트 형태, 최대 256자, 포트 1–5자리 패턴을 검사합니다.
현재 CLI는 정책의 HTTP origin을 거부하고 프로덕션 home의 로컬 origin을 요구합니다.
개발 서버의 정확한 loopback origin은 CLI가 개발 산출물에만 적용합니다.

권한은 요청을 보낸 뷰에 적용됩니다. 호출 데이터의 origin이나 view ID로 사용할 권한을 바꿀 수는 없습니다.

## host와 backend

두 필드는 `{ "permissions": [], "windows"?: [] }` 형식입니다. permissions는 최대 256개이며
각 항목은 권한 이름 문자열 또는 `{ identifier, allow?, deny? }`입니다.
등록되지 않은 권한과 잘못된 범위는 시작 시 `INVALID_ARGUMENT`로 거부합니다.

| 필드 | 제약 | 의미 |
| --- | --- | --- |
| `permissions` | 필수 배열, 최대 256개 | 플러그인 권한 식별자와 선택적 리소스 범위 |
| `windows` | 선택 배열, 최대 128개, 중복 금지 | 생성하거나 제어할 창의 뷰 ID. 생략하면 창 API 사용 거부 |

```json
{
  "permissions": [
    "log:write",
    { "identifier": "storage:read-text", "allow": [{ "scope": "appData", "pathPrefix": "notes" }],
      "deny": [{ "scope": "appData", "pathPrefix": "notes/private" }] }
  ],
  "windows": ["editor"]
}
```

`log:write`와 `capabilities:get`은 범위가 없는 권한입니다.
저장의 `storage:read-text`, `storage:write-text`는 allow 범위를 명시해야 합니다.
문자열만으로 저장 권한을 허용할 수 없습니다.
allow와 deny는 각각 최대 128개이며 같은 식별자의 allow를 합칩니다. 일치하는 deny가 하나라도 있으면 거부합니다.

저장 permission의 scope에는 `scope`와 `pathPrefix`만 넣습니다. scope는 appData 또는 temp입니다.
pathPrefix는 최대 256자이며 영숫자, `_`, `-` 디렉터리를 `/`로 구분합니다.
빈 문자열은 지정한 scope 전체입니다. `notes`는 notes 디렉터리 아래를 허용하며 notes-other는 포함하지 않습니다.
절대 경로, `.`과 `..`, 개행은 거부합니다. 실제 파일 접근에서도 링크와 범위를 검사합니다.

읽기와 쓰기는 각각 `storage:read-text`, `storage:write-text` permission으로 허용합니다.
저장 범위 grant에는 `access` 필드가 없습니다. 같은 permission의 allow 범위는 합쳐지고,
일치하는 deny 범위가 하나라도 있으면 거부합니다. 허용 범위 밖 경로나 링크에는 접근할 수 없습니다.

## 설정 검증과 호출 오류

정책을 수정한 뒤 `bunaway validate`로 형식을 확인합니다.
스키마를 위반하거나 ID가 중복되면 정책 파싱에 실패합니다. 허용되지 않은 기능을 호출하면 `PERMISSION_DENIED`를 반환합니다.

이 정책은 UI에서 시작한 요청과 Host API 호출에 적용됩니다. OS 권한은 운영체제에서 관리하며 신뢰된 백엔드가 직접 실행하는 Bun 코드는 이 정책으로 격리하지 않습니다.

뷰에서 시작한 명령은 해당 뷰의 host 권한을 사용하고 플러그인 setup은 backend 권한을 사용합니다.
`host.windows`와 `backend.windows`에는 제어할 창의 뷰 ID를 지정합니다. 해당 목록은
Windows 창 API의 호출 범위이며 플러그인 `permissions`와 별도로 적용됩니다.
예를 들어 `backend.permissions: []`여도 뷰에 허용한 저장 작업은 동작하지만,
플러그인 setup의 저장 작업은 거부됩니다.
이 정책은 Host API 호출에 적용합니다. 신뢰된 백엔드가 직접 사용하는 Bun API의 권한은 제한하지 않습니다.
[windows API](/reference/host/windows/)에서 명령별 권한과 결과를 확인하세요.
