`@bunaway/backend/cli`의 `defineCLI`는 신뢰된 앱 backend의 순수 인자 해석 도구입니다.
Bun의 `node:util.parseArgs`로 flag를 읽고 앱이 선언한 Zod schema로 입력을 검사합니다.
OS 작업, shell 실행, 권한 부여와 앱 종료를 수행하지 않습니다. framework CLI의 명령과는 별개입니다.

```ts
import { defineApp } from "@bunaway/backend";
import { defineCLI } from "@bunaway/backend/cli";
import { z } from "zod";

const cli = defineCLI({
  name: "memo",
  commands: {
    export: {
      description: "메모 내보내기",
      options: {
        count: { type: "string", short: "c", description: "내보낼 개수" },
        verbose: { type: "boolean", short: "v" },
      },
      schema: z.strictObject({
        values: z.strictObject({
          count: z.coerce.number().int().min(1).max(10).default(1),
          verbose: z.boolean().default(false),
        }),
        positionals: z.array(z.string()).min(1),
      }),
    },
  },
});

export default defineApp({
  modules: [],
  desktop: {
    openArguments: "raw",
    async onOpen(request) {
      const result = await cli.parse(request.argv);
      if (result.kind === "help") console.log(result.help);
      else if (result.kind === "error") console.error(result.error.message, result.error.issues);
      else if (result.command === "export") {
        console.log(result.data.values.count, result.data.positionals);
        // 앱에서 실제 대상 파일과 출력 위치의 접근 규칙을 검사한 뒤 작업합니다.
      }
    },
  },
});
```

Windows의 `desktop.onOpen`은 실행 파일, Bunaway 개발 스위치와 선행 자동 실행 prefix를 제거한
`OpenRequest.argv`를 초기 실행과 second-instance 모두에 제공합니다. CLI 앱은
`desktop.openArguments: "raw"`로 파일/URL 메타데이터 해석을 건너뜁니다. 이 모드에서는
`https://`나 `file:relative.txt`도 원래 argv 문자열로 훅에 도달하며 `files`와 `urls`는 빈 배열입니다.
앱의 Zod schema가 실제로 URL이나 파일 입력을 요구하는지 검사합니다. `request.files`나
`request.urls`로 CLI 옵션을 해석하지 않습니다. 파서는 자동으로 `process.argv`를 읽지 않습니다.
순수 parser는 다른 Bun backend에서도 명시적인 argv와 함께 사용할 수 있습니다.
raw 모드에서도 `launchReason`과 숨김 자동 실행의 표시 상태 규칙은 유지합니다.

## 선언과 help

`CLIDefinition`은 `name`과 root command 또는 group입니다. `CLIGroup`의 `commands`에
중첩 group이나 leaf `CLICommand`를 선언합니다. subcommand 이름은 flag보다 먼저 옵니다.
예를 들어 `memo docs export --count=3 -- -draft.txt`는 `docs export`를 선택합니다.
group에는 flag를 선언하지 않으며 root에서 하위 명령으로 flag를 상속하지 않습니다.

leaf의 `options`는 이름별 `CLIOption`입니다. `type`은 `string` 또는 `boolean`, `short`는
선택적인 영문 한 글자이며 `multiple: true`는 반복 값을 배열로 모읍니다. `description`은
help에 표시합니다. `help`와 `h` alias는 예약했습니다. group과 option의 이름은 소문자 영문으로
시작하는 최대 64자의 영문, 숫자와 하이픈입니다. flag 이름은 대소문자를 구별합니다.

`--name=value`, `--name value`, short alias와 boolean 조합은 Bun `parseArgs`를 따릅니다.
반복 가능한 옵션은 배열이며 일반 옵션을 반복하면 마지막 값을 사용합니다. `--` 뒤는 원래
순서의 위치 인자입니다. 음수 등 하이픈으로 시작하는 string 값은 `--count=-1`처럼 지정합니다.

`schema`는 `{ values, positionals }`를 한 번 검사하는 Zod schema입니다. defaults, 숫자 변환,
필수 위치 인자와 앱의 검사를 schema에 선언합니다. 동기 및 비동기 transform/refinement를
지원하며 반환한 `data`는 schema의 출력 타입입니다. args와 선언 tree는 snapshot으로 보관하지만
Zod schema 자체는 앱이 소유합니다.

`cli.help()`는 root help를, `cli.help(["docs", "export"])`는 선택한 경로의 help를 문자열로
반환합니다. 잘못된 help 경로는 `TypeError`입니다. group에서 인자가 없거나 `--help`/`-h`만
지정하면 해당 group의 help입니다. leaf에서 help는 CLI 문법 검사 후 business schema를 실행하지
않고 반환합니다. 알 수 없는 flag와 help를 함께 지정하면 문법 오류입니다.

## 결과와 오류

`cli.parse(argv)`는 `Promise<CLIResult<CLIMatch<typeof definition>>>`입니다.

| kind | 필드와 의미 |
| --- | --- |
| `match` | `command`는 공백으로 이어 붙인 subcommand 경로이며 root leaf는 빈 문자열입니다. `data`는 선택한 schema의 출력입니다 |
| `help` | `command`, `help` 문자열. 출력과 종료는 앱이 결정합니다 |
| `error` | `command`, 해당 경로의 `help`, `error: { code, reason, message, issues }` |

오류 `code`는 `INVALID_ARGUMENT`입니다. `reason: "arguments"`는 잘못된 argv, 알 수 없는
subcommand/flag와 빠진 flag 값입니다. `reason: "schema"`는 Zod 검사 실패나 콜백 예외입니다.
`issues`는 `{ path: string[], message }[]`이며 schema 검사 문제를 반환합니다. 콜백 예외는
일반 오류로 반환합니다. Bun 문법 오류와 앱의 schema 오류 메시지는 앱이 출력하거나 전달할
정보이므로 민감한 argv를 로그나 화면에 노출할지는 앱이 결정합니다.

입력은 최대 256개 인자, 인자당 4096 UTF-16 code units와 JSON UTF-8 합계 64 KiB입니다.
NUL, 잘못된 UTF-16과 sparse 배열을 거부합니다. tree는 최대 8단계와 128개 node, 명령별 옵션은
64개입니다. cycle, 중복 short alias, 예약 이름, 잘못된 선언은 생성 시 `TypeError`입니다.
실패한 parse 이후에도 다음 실행의 argv를 처리할 수 있습니다.

파서는 앱을 종료하거나 open-request queue를 바꾸지 않습니다. `onOpen`은 async schema 완료를
기다리므로 오래 걸리는 검사는 뒤의 열기 요청도 지연합니다. parser 자체의 취소/timeout은 아직
없으며 앱이 callback과 작업 수명을 관리합니다. 자세한 lifecycle은 [앱 정의](/reference/backend/app-definition/)를 따릅니다.
