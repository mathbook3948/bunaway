핸들러와 플러그인 setup에는 `{ app, signal, host, state, events }`가 전달됩니다.
명령의 컨텍스트는 요청이 끝날 때까지 유효합니다. setup의 컨텍스트는 앱 백엔드가 종료될 때까지 사용합니다.

| 필드 | 역할 |
| --- | --- |
| `app` | 앱 이름, 식별자, 버전과 런타임 버전을 담은 읽기 전용 정보 |
| `signal` | 취소, 기한, 세션 종료를 관찰하는 신호 |
| `host` | 원래 출처의 권한에 묶인 Host API |
| `state` | 공통 앱 메모리 상태 저장소 |
| `events` | 선언된 이벤트 발행자 |

## app

`ctx.app`은 앱 자신의 메타데이터인 `AppInfo`입니다. 동결된 객체이며 모든 명령과 플러그인 setup이 같은 값을 받습니다.
권한이 필요 없고 호출 비용도 없습니다. 값은 Core가 시작될 때 한 번 정해지므로
실행 중에 바뀌지 않습니다. 예를 들어 앱이 실행되는 동안 WebView2가 업데이트돼도 `webview`는 시작 시점의 버전을 유지합니다.

| 필드 | 타입 | 출처 |
| --- | --- | --- |
| `name` | `string` | 앱 설정의 `title`. 패키지 manifest에 `title`이 없으면 `appId` |
| `identifier` | `string` | 앱 설정의 `appId` |
| `version` | `string \| null` | 앱 package.json의 `version` |
| `isPackaged` | `boolean` | 빌드된 컴파일 앱이면 `true`, 개발 실행이면 `false` |
| `paths` | `{ package, executable, resources } \| null` | 앱의 파일 시스템 위치. 아래 표 참고 |
| `runtime.framework` | `string \| null` | 빌드 시점의 bunaway 프레임워크 버전 |
| `runtime.bun` | `string` | 백엔드를 실행하는 Bun의 `Bun.version` |
| `runtime.webview` | `string \| null` | 플랫폼 WebView 엔진 버전 |

`identifier`는 런타임 앱 ID이며 패키징 설정의 `bundle.identifier`와 다른 값입니다.
`version`은 빌드가 패키지 manifest에 기록한 앱 package.json의 버전입니다.
`bundle.release.version`으로 설치 프로그램 버전을 바꿔도 `version`은 달라지지 않습니다.
Android와 iOS는 빌드할 때 이름, 식별자, 버전, 프레임워크 버전을 백엔드 번들에 포함합니다.

`version`과 `runtime.framework`는 패키지 manifest에 `app.version`이나 `framework.version`이 없으면 `null`입니다(빌드는 앱이나 프레임워크 `package.json`에 버전이 없을 때 이 필드를 생략합니다).
Windows는 `manifest.json` 파일 자체가 없어도 두 값이 `null`이지만, macOS는 `manifest.json`이 반드시 있어야 시작합니다.
경로를 제외한 모든 문자열 필드는 비어 있지 않아야 하며 1024 UTF-16 코드 유닛 이하입니다. 빌드는 `title`과 `version`이 이 조건을 어기면 실패합니다.

### isPackaged와 paths

`paths`의 세 값은 모두 절대 경로입니다. 길이는 제한하지 않고 운영체제 한도를 따릅니다. 경로에는 사용자 이름이 들어갈 수 있으므로
로그나 UI로 보낼 때 앱이 노출 여부를 정하세요.

| 필드 | Windows 패키지 실행 | Windows 개발 실행 | macOS 패키지 실행 |
| --- | --- | --- | --- |
| `paths.package` | 실행 파일이 있는 폴더 | 빌드 출력 디렉터리 | `Contents/Resources` |
| `paths.executable` | `<appId>.exe`의 실제 경로 | 버전이 고정된 `bun.exe`의 실제 경로 | 실행 파일의 실제 경로 |
| `paths.resources` | 실행 파일이 있는 폴더 | 빌드 출력 디렉터리(`package`와 같음) | `Contents/Resources` |

`resources`는 앱과 함께 배포된 디스크 파일이 놓이는 디렉터리입니다(Tauri `resource_dir`의 Windows 동작과 같습니다).
Windows 패키지는 manifest와 웹 assets를 실행 파일에 임베드하므로 이 폴더에는 앱 assets가 없고 실행 파일, `WebView2Loader.dll`, `licenses` 같은 배포 파일만 있습니다.
Electron의 `process.resourcesPath`와 달리 `app.asar`가 놓이는 위치가 아닙니다.

macOS 개발 실행은 `--package`로 지정한 디렉터리를 `package`와 `resources`로 쓰고 `executable`은 Bun 실행 파일입니다.
Android, iOS와 `runBunApp`은 파일 시스템 패키지를 노출하지 않으므로 `paths`가 `null`이고, 모바일은 번들된 앱이라 `isPackaged`가 `true`입니다.

`runtime.webview`는 플랫폼마다 다음과 같이 정해집니다.

| 플랫폼 | `runtime.webview` |
| --- | --- |
| Windows | 설치된 WebView2 런타임 버전. 앱 시작 때 조회합니다. |
| macOS | 시스템 WebKit 프레임워크의 `CFBundleShortVersionString`, 없으면 `CFBundleVersion` |
| Android, iOS | 항상 `null` |

Windows나 macOS에서 버전 조회가 실패해도 앱은 시작되고 `runtime.webview`만 `null`이 됩니다.
호스트 로그에는 `webview-version-unavailable` 항목이 남습니다.

`ctx.app`은 백엔드에서만 사용합니다. UI에서 확인하려면 앱이 직접 명령을 만들어 `ctx.app`을 반환합니다.
별도의 내장 명령은 없습니다.

```ts
import { command } from "@bunaway/backend";

const appInfo = command({
  input: { type: "object", additionalProperties: false },
  output: {
    type: "object",
    properties: {
      name: { type: "string" },
      version: { anyOf: [{ type: "string" }, { const: null }] },
      webview: { anyOf: [{ type: "string" }, { const: null }] },
    },
    required: ["name", "version", "webview"],
    additionalProperties: false,
  },
  handle(_input, ctx) {
    return {
      name: ctx.app.name,
      version: ctx.app.version,
      webview: ctx.app.runtime.webview,
    };
  },
});
```

운영체제의 종류와 버전 같은 환경 정보는 `ctx.app`이 아니라 [os 플러그인](/reference/plugins/os/)이 제공합니다.

## signal

`CancellationSignal`은 표준 AbortSignal의 `aborted`와 abort 리스너 등록, 해제 부분입니다.
요청이 취소돼도 핸들러의 일반 Promise는 강제로 멈추지 않습니다.
긴 루프나 외부 작업은 신호를 확인하고 자신이 가진 자원을 정리해야 합니다.
명령이 완료된 뒤에는 같은 context로 Host API를 호출하거나 이벤트를 발행할 수 없습니다.

## host.call

저장과 로그, 기능 조회는 [개별 플러그인 API](/reference/backend/host-api/)를 사용합니다.
플러그인 작업을 직접 호출할 때는 `context.host.call(contract, input)`에 등록된
HostOperationContract를 전달합니다. contract에는 name, input과 output schema가
필수이며 결과 타입은 output schema에서 추론됩니다. 정책은 contract의 name에 해당하는 작업 이름을 허용합니다.
창 제어도 선택 플러그인의 계약이나 `@bunaway/plugin-windows`의 `windows` API로 호출합니다. 문자열 작업 이름을 직접 전달하는 호출은 지원하지 않습니다. 메서드와 권한은 [windows 레퍼런스](/reference/host/windows/)에 있습니다.

뷰에서 호출한 명령은 그 뷰의 Host 정책을 사용합니다. 백엔드 setup은 `policy.backend`를 사용합니다.
호출할 작업에 맞는 입력을 전달해야 하며 작업 권한이나 OS 접근 권한이 없으면 실패합니다. 파일별 접근 규칙은 앱 명령에서 검사합니다. 요청이 취소되면 Host API 호출도 취소됩니다.

## 상태와 이벤트

`state`는 앱 백엔드 전체가 공유하는 저장소입니다.
`events`로 이벤트를 발행하면 수신 권한이 있는 뷰의 활성 구독에 전달됩니다.
[상태](/reference/backend/state/)와 [이벤트 발행](/reference/backend/events/)을 참고하세요.

Host 정책은 context.host를 사용하는 호출에 적용합니다. 백엔드에서 직접 Bun API를 호출하는 코드는 이 정책으로 제한되지 않습니다.
