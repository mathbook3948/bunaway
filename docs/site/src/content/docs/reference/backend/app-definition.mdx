앱 진입점은 AppDefinition을 default export합니다. CLI의 `build.app`이 이 파일을 선택합니다.
생성 템플릿은 `@bunaway/backend`의 `defineApp()`으로 기능 모듈을 조립합니다.

```ts
import { defineApp } from "@bunaway/backend";

import { message } from "./message/module.ts";

export const app = defineApp({ modules: [message] });
export default app;
```

`modules`는 필수 배열이며 `[]`도 허용합니다. 각 모듈은 `name`, `commands`, `events`를 가집니다.
선택적으로 `commands`, `events`, `state`, `plugins`, `desktop`을 함께 전달할 수 있습니다.
모듈 작성법은 [defineModule](/reference/backend/module/)에서 설명합니다.

`defineApp()`은 모듈과 직접 등록한 명령, 이벤트를 합친 AppDefinition을 즉시 반환합니다.
명령과 이벤트는 각각 최종 이름의 중복을 검사하며 플러그인의 등록 이름도 함께 검사합니다.
중복 이름, 잘못된 이름, 예약 명령은 `INVALID_ARGUMENT`로 실패합니다.
앱 객체와 조립한 명령, 이벤트 목록 및 플러그인 배열은 동결합니다. 플러그인 setup은 앱 실행 시 처리합니다.

등록한 명령과 플러그인 setup에서 [storage, log, capabilities](/reference/backend/host-api/)를
바로 사용할 수 있습니다. 명령은 원래 뷰, setup은 백엔드의 Host 권한으로 실행됩니다.

명령과 플러그인은 공개 타입에 맞는 객체나 클래스 인스턴스로 등록할 수 있습니다.
명령의 입력과 출력 규칙은 클래스 getter로 정의해도 적용됩니다.
플러그인의 이름과 버전, 의존성, 지원 플랫폼과 필요한 권한, 명령과 이벤트 목록도 유지됩니다.

기존 객체형 앱 정의도 지원합니다.
네이티브 플러그인은 `defineApp()`의 `plugins`에 default export를 전달해 등록합니다.

```ts
import type { AppDefinition } from "@bunaway/backend";
export default {
  commands: {},
  events: {},
  state: { count: 0 },
} satisfies AppDefinition;
```

## 필드

| 필드 | 필수 | 의미 |
| --- | --- | --- |
| `commands` | 예 | 이름 → `CommandDefinition` 레지스트리 |
| `events` | 예 | 이름 → payload `Schema` 레지스트리 |
| `state` | 아니요 | 초기 JSON 메모리 상태. 생략 시 빈 상태 |
| `plugins` | 아니요 | 플러그인 정의 배열. 생략 시 없음 |
| `desktop` | 아니요 | Windows 앱 열기, 종료 취소와 트레이 설정. 생략 시 마지막 창 닫기로 종료 |

명령 이름과 이벤트 이름은 각각 앱과 모든 플러그인에서 공유합니다.
동일 이름을 덮어쓰거나 중복 등록할 수 없습니다.
명령, 이벤트 이름은 1–128자의 영숫자, `_ . : -`입니다.
`plugin.` 접두사는 네이티브 플러그인 명령에 예약되어 있습니다. 앱 명령에는 사용할 수 없습니다.

## 정책과 실행

등록한 명령과 이벤트를 뷰에서 사용하려면 그 뷰의 `commands`와 `events`에도 이름을 추가합니다.
모든 플러그인의 setup이 끝나면 앱이 명령을 처리할 준비가 됩니다.
이름이 중복되거나 예약 이름을 사용하면 시작에 실패합니다. 플러그인의 의존성이나 플랫폼, 필요한 권한이 맞지 않아도 실패합니다.

CLI는 작성한 설정과 정책을 검사합니다. 호출할 명령의 권한은 개발자가 정책에 적습니다.
앱 시작은 프레임워크가 처리하므로 앱 정의를 default export하면 됩니다.

## 타입

`CommandsOf<typeof app>`는 앱에 직접 선언한 명령과 정적으로 나열한 기능 모듈의 input/output을,
`EventsOf<typeof app>`는 해당 이벤트와 정적으로 나열한 플러그인의 이벤트 payload를 추론합니다.
객체형 앱 정의에서 플러그인 이벤트 타입을 추론하려면 `plugins` 배열에
`as const`를 붙여 등록 목록을 tuple로 유지합니다. `defineApp()`에 배열을 직접 전달하면
별도 지정 없이 tuple로 추론합니다. 일반 배열로 선언한 플러그인 목록의 이벤트는
`EventsOf`에 포함하지 않습니다.
플러그인 명령까지 합친 전체 명령 목록의 자동 타입 생성은 현재 제공하지 않습니다.
[타입과 스키마](/guides/types-and-validation/)에서 클라이언트 연결 예시를 확인하세요.

## 데스크톱 앱 동작

트레이를 사용하려면 @bunaway/plugin-tray 설치와 tray 등록이 필요합니다.

Windows와 macOS Bun 호스트에서 제공합니다. macOS는 트레이를 지원하지 않으므로 `tray`와
`closeBehavior: "hide"`를 지정하면 `UNSUPPORTED`로 시작에 실패합니다. 아래 예시의 트레이와 `"hide"`는 Windows 전용입니다.
macOS에서 지원하는 `closeBehavior`는 `"quit"`(기본)과 `"keep-alive"`입니다.

```ts
import { defineApp } from "@bunaway/backend";
import tray from "@bunaway/plugin-tray";

let hasUnsavedWork = false;
export default defineApp({
  modules: [],
  plugins: [tray],
  desktop: {
    closeBehavior: "hide",
    tray: { tooltip: "Memo" },
    async onOpen(request, desktop) {
      console.log(request.source, request.urls, request.files);
      // 앱에서 URL과 파일 입력을 검증한 뒤 필요한 문서를 엽니다.
      await desktop.show();
    },
    beforeQuit(reason) {
      // 앱의 저장 상태나 비동기 확인 화면 결과로 종료 여부를 결정합니다.
      console.log(reason);
      return !hasUnsavedWork;
    },
  },
});
```

| DesktopOptions 필드 | 기본값 | 동작 |
| --- | --- | --- |
| `closeBehavior` | `"quit"` | 마지막 창 닫기로 종료를 요청합니다. `"hide"`는 해당 창을 숨기며 트레이가 필요합니다. `"keep-alive"`는 마지막 창을 실제로 닫아도 앱을 유지합니다. macOS는 `"hide"`를 `UNSUPPORTED`로 거부합니다 |
| `tray` | 없음 | `{ tooltip: string }`. tooltip은 1~127자의 NUL 없는 문자열입니다. macOS는 `UNSUPPORTED`로 거부합니다 |
| `openArguments` | `"files-and-urls"` | `"raw"`는 파일/URL 메타데이터 해석 없이 원래 argv를 전달하며 `files`와 `urls`는 빈 배열입니다 |
| `onOpen` | 없음 | `(request: OpenRequest, context: DesktopContext) => void \| Promise<void>` |
| `onOpenUrls` | 없음 | `(urls: readonly string[], context: DesktopContext) => void \| Promise<void>`. 파일과 URL을 `file:` URL을 포함한 절대 URL로 받습니다 |
| `onReopen` | 없음 | macOS 전용. `(event: ReopenEvent, context: DesktopContext) => void \| Promise<void>`. Dock 아이콘 클릭 같은 재활성화 요청을 받습니다 |
| `onReady` | 없음 | `(context: DesktopContext) => void \| Promise<void>` |
| `onAllWindowsClosed` | 없음 | `(context: DesktopContext) => void \| Promise<void>` |
| `beforeQuit` | 없음 | `(reason: QuitReason) => boolean \| void \| Promise<boolean \| void>` |
| `onWillQuit` | 없음 | `(reason: ShutdownReason) => void \| Promise<void>` |
| `onQuit` | 없음 | `(reason: ShutdownReason) => void \| Promise<void>` |

같은 앱 데이터 디렉터리는 한 앱 인스턴스만 사용합니다. 두 번째 실행의 인자와 작업 디렉터리를
기존 앱으로 전달하고 두 번째 실행은 종료합니다. 앱 시작 중 받은 요청도 준비 후 순서대로 처리합니다.
열기 요청은 최대 256개 인자와 64 KiB의 JSON을 받으며 전달 실패, 큐 초과는 두 번째 실행의 오류입니다.
접수 성공은 앱에서 문서를 성공적으로 열었다는 뜻은 아닙니다.

| OpenRequest 필드 | 의미 |
| --- | --- |
| `source` | `"initial"` 또는 `"second-instance"` |
| `launchReason` | `"manual"` 또는 `"autostart"`. 예약 실행 인자로 지정한 모드이며 Windows 실행 출처를 인증하지 않음 |
| `argv` | 프레임워크 시작 인자를 제거한 앱 인자 배열. 순서와 원래 문자열을 유지합니다 |
| `cwd` | 실행기를 호출한 작업 디렉터리 |
| `urls` | scheme을 가진 URL 배열. 파일 URL은 `files`에 포함합니다 |
| `files` | 호출자의 작업 디렉터리를 기준으로 해석한 절대 파일 경로 배열 |

`--` 이전에 `-`로 시작하는 인자는 파일 목록에서 제외합니다. `--` 뒤는 위치 인자로 처리합니다.
URL과 파일은 앱이 검증할 입력입니다. 전달받은 경로는 Host API의 저장 권한을 추가하지 않습니다.
파일 URL은 Windows의 절대 경로를 가리켜야 합니다. 인코딩된 경로 구분자나 NUL을 포함한
파일 URL은 열기 요청 처리에 실패하며, 진단을 남긴 뒤 다음 요청을 처리합니다.
CLI 옵션과 subcommand를 처리하는 앱은 `desktop.openArguments: "raw"`를 설정하고
[앱 CLI 인자](/reference/backend/cli/)의 `defineCLI`로 `request.argv`를 검사합니다.
기본 `"files-and-urls"` 모드의 URL 오류는 훅 호출 전에 요청을 실패시킵니다. raw 모드는
파일 열기나 URL 검증을 수행하지 않으며 문자열의 의미는 앱의 parser와 schema가 결정합니다.
macOS 호스트는 앱 실행 인자를 받지 않습니다. macOS의 `onOpen`은 시작할 때 한 번만 호출하며 `argv`는 `[]`,
`cwd`는 프로세스의 작업 디렉터리, `files`와 `urls`는 빈 배열입니다. OS의 파일과 URL 열기는
`onOpenUrls`로 받습니다.
`onOpen`은 초기 실행을 먼저 처리하고 이후 요청을 순서대로 처리합니다.
열기 훅이 실패하면 진단을 남기고 다음 요청을 처리합니다.
훅이 완료되지 않으면 뒤의 요청도 대기하므로 앱에서 오래 걸리는 작업의 수명을 관리합니다.
초기 `onOpen`은 앱 준비 뒤 호출되며 웹 UI의 구독 완료까지 기다리지는 않습니다.

### 파일과 URL 열기: onOpenUrls

`onOpenUrls(urls, context)`는 앱이 열도록 요청받은 파일과 URL을 요청 순서대로 받습니다. 파일은 절대 경로를
정규화한 `file:` URL로, 나머지는 정규화한 절대 URL로 전달합니다. 빈 목록으로는 호출하지 않으며 배열은
수정할 수 없습니다. 같은 입력을 `onOpen`의 `argv`로 받는 것이 아니므로 `OpenRequest`의 의미는 바뀌지 않습니다.

| 플랫폼 | 입력 | 비고 |
| --- | --- | --- |
| Windows | 초기 실행과 두 번째 실행의 인자 | `openArguments: "files-and-urls"`일 때만 호출합니다. `"raw"`는 인자를 해석하지 않으므로 호출하지 않습니다 |
| macOS | Finder, `open` 명령, URL scheme 요청 | `openArguments`와 무관합니다. 현재 패키징은 Info.plist에 `CFBundleURLTypes`와 `CFBundleDocumentTypes`를 만들지 않으므로, 설치된 앱이 사용자 정의 URL scheme이나 문서 열기를 운영체제에서 받으려면 이 항목을 Info.plist에 직접 추가해야 합니다 |

한 번의 Windows 실행에서는 `onOpen(request)`을 먼저 호출하고, URL이 있으면 `onOpenUrls`를 이어서
호출합니다. `onOpen`이 실패해도 `onOpenUrls`는 호출합니다. 인자의 URL이 잘못되어 요청이 실패하면 둘 다
호출하지 않습니다. 같은 파일이나 URL이 `onOpen`의 `argv`와 `onOpenUrls`에 모두 전달되므로 Windows에서 두 콜백을 함께 등록했다면 한쪽에서만 처리하세요. macOS에서 앱이 준비된 뒤 요청을 받으면 앱을 먼저 표시한 뒤 `onOpenUrls`를 호출합니다.
macOS의 URL은 호스트가 검증합니다. 한 요청이 항목 256개 또는 64 KiB를 넘으면 요청 전체를 거부하고,
잘못된 URL, 로컬이 아닌 호스트의 파일 URL, 인코딩된 경로 구분자(`%2F`)나 NUL을 포함한 항목은 진단을
남기고 제외합니다.

`onReady`, `onOpen`과 같은 큐에서 순서대로 실행하며 훅이 실패하면 진단을 남기고 앱은 계속 실행합니다.
앱이 준비되기 전에 도착한 macOS의 요청은 호스트가 최대 64개까지 보관했다가 전달하므로, 별도의 초기 URL
조회 없이 이 훅 하나로 처리하면 됩니다. 순서는 `onReady`, 초기 `onOpen`, 초기 실행의 `onOpenUrls`, 보관한
요청, 이후 요청입니다. 보관한 요청은 앱을 표시하지 않습니다. 시작 전에 종료가 확정되면 보관한 요청은
버립니다. URL과 파일은 앱이 검증할 입력이며 Host API의 저장 권한을 추가하지 않습니다.

```ts
desktop: {
  async onOpenUrls(urls, desktop) {
    // 파일은 file: URL로 옵니다. 허용한 scheme만 처리하고 나머지는 무시합니다.
    const allowed = ["file:", "myapp:"];
    for (const url of urls) {
      const parsed = URL.parse(url);
      if (parsed && allowed.includes(parsed.protocol)) await openDocument(parsed);
    }
    await desktop.show();
  },
},
```

### 재활성화: onReopen (macOS)

`onReopen({ hasVisibleWindows }, context)`는 Dock 아이콘 클릭처럼 운영체제가 실행 중인 앱의 재활성화를
요청할 때마다 호출합니다. `ReopenEvent.hasVisibleWindows`는 요청 시점에 표시 중인 창이 있었는지 나타냅니다.

- 등록하지 않으면 표시 중인 창이 없을 때 `show()`와 같게 처리하고, 창이 있으면 아무것도 하지 않습니다.
- 등록하면 호스트는 창을 표시하지 않으며 앱이 결정합니다. 예를 들어 `context.show()`를 호출합니다.
  앱이 준비되기 전의 요청은 시작 창이 이미 열리는 중이므로 버립니다.
- 앱이 `onReopen`을 실행하는 동안 또는 앞선 열기 요청을 처리하는 동안 재활성화가 이어지면 연속한 요청은
  하나로 합치고 가장 최근의 `hasVisibleWindows`로 한 번만 호출합니다.

Windows는 이 훅을 호출하지 않습니다. Windows에서 앱을 다시 실행하면 두 번째 실행으로 `onOpen`과
`onOpenUrls`가 호출됩니다. 훅은 `onOpen`과 같은 큐에서 실행하며 실패하면 진단을 남기고 앱은 계속 실행합니다.

| DesktopContext 메서드 | 결과 |
| --- | --- |
| `show(): Promise<void>` | 살아 있는 창을 모두 복원합니다. 열린 창이 없으면 첫 사전 선언 창을 생성합니다. 선언이 비어 있으면 아무 창도 만들지 않습니다 |
| `hide(): Promise<void>` | 트레이가 있으면 살아 있는 창을 모두 숨깁니다. 없으면 오류로 실패합니다 |
| `quit(): Promise<boolean>` | 종료 검사가 승인되면 `true`, 취소하거나 검사에 실패하면 `false` |

`show()`는 표시 요청의 접수를 기다립니다. 새 창의 문서와 SDK 준비까지 기다리지 않습니다.
두 번째 실행을 받으면 같은 표시 요청을 접수한 뒤 `onOpen`을 호출합니다.
[숨김 자동 실행](/reference/plugins/autostart/#로그인-실행-구분과-숨김-시작)의 두 번째 요청은
현재 표시 상태를 유지한 채 `onOpen`을 호출합니다.
숨김은 창, WebView, 세션과 앱 상태를 유지하므로 백엔드 작업도 계속 실행됩니다.
트레이를 클릭하거나 메뉴의 Open을 선택하면 창을 복원합니다. 숨기기 전의 최대화 상태를 유지하며,
최소화된 창은 복원합니다. Quit은 종료 검사를 거칩니다.
열린 창이 없으면 Open은 첫 선언의 `startup` 값과 관계없이 그 창을 생성해 표시합니다.
다른 창은 자동 생성하지 않으며 `app.windows: []`이면 아이콘과 Quit만 사용합니다.
이 표시 요청은 `visible`과 `showWhenReady`의 자동 표시 조건을 기다리지 않고 창을 표시합니다.
반복 표시 요청은 합치고 이전 WebView 정리와 진행 중인 창 API 작업이 끝난 뒤 생성합니다.

시작 창이 없으면 트레이 또는 `closeBehavior: "keep-alive"`를 반드시 지정합니다.
백엔드 타이머나 `beforeQuit`, `onOpen` 훅만으로는 이 조건을 충족하지 않습니다.
트레이는 시작 창이 없어도 앱을 유지하지만 마지막 창의 닫기 규칙을 바꾸지는 않습니다.
트레이와 기본 `"quit"`를 함께 쓰면 나중에 만든 마지막 창을 닫을 때 종료를 요청합니다.
`"keep-alive"`로 닫은 창은 HWND, WebView와 세션을 정리하고 앱 상태와 백엔드는 유지합니다.
이때 마지막 창 닫기는 종료 요청이 아니므로 `beforeQuit`를 호출하지 않습니다.
명시적 종료는 트레이 Quit 또는 `onOpen`에서 받은 `DesktopContext.quit()`으로 요청합니다.
트레이 없는 상주 앱은 앱이 완료할 수 있는 종료 경로를 구현해야 합니다.
설정과 지연 생성 예시는 [창 없는 시작](/guides/windows/#창-없는-시작)을 따릅니다.

`QuitReason`은 마지막 창의 닫기 `"last-window"`, 트레이 Quit `"tray"`,
`DesktopContext.quit()`의 `"api"`, macOS의 Quit 명령 `"quit-command"`입니다.
`"quit-command"`는 앱 메뉴의 Quit과 Cmd+Q, Dock의 Quit을 포함하며 Windows에서는 발생하지 않습니다.
`QuitReason`을 `switch`로 빠짐없이 처리하는 앱은 이 값도 처리해야 합니다.
macOS의 최소 앱 메뉴에는 "Quit 프로세스이름"(Cmd+Q) 항목만 있습니다.
macOS에서 `beforeQuit`가 `false`를 반환하면 열린 창과 세션을 모두 유지합니다.
기본 `"quit"`에서 마지막 창은 `beforeQuit`가 승인할 때까지 열려 있습니다.
`beforeQuit`가 `false`를 반환하거나 예외를 던지면
창과 세션을 유지하고 종료를 취소합니다. 동시 종료 요청은 같은 검사 결과를 사용합니다.
반환값이 `true` 또는 `undefined`이면 기존 종료 절차와 플러그인 StopHook을 실행합니다.
기본 `"quit"`에서는 공개 [windows API](/reference/host/windows/)로 마지막 창을 닫을 때도 종료 검사를 거칩니다.
창의 `recreate`는 앱 종료를 요청하지 않으며 트레이 숨김 대신 창을 다시 만듭니다.
`quit()`의 `true`는 종료 승인 결과이며 모든 자원이 이미 정리됐다는 뜻은 아닙니다.
종료 훅에는 자동 기한이 없으며 앱이 완료해야 합니다. 강제 종료, 호스트 실패, SIGINT, SIGTERM은 취소할 수 없습니다.
`bunaway dev`의 재시작과 CLI 종료도 `beforeQuit`와 숨김 설정을 우회하고 플러그인 StopHook과 자원 정리를 실행합니다.
창이 없는 상주 앱과 트레이 앱에도 적용합니다. OS 강제 종료는 StopHook 실행을 보장하지 않습니다.

### 수명주기 훅의 호출 시점

| 훅 | 호출 시점 | 비고 |
| --- | --- | --- |
| `onReady` | 코어와 백엔드가 준비되고 시작 창의 네이티브 생성을 시작한 뒤 한 번 | 문서나 SDK 준비를 뜻하지 않습니다. `onOpen`과 같은 큐에서 초기 `onOpen`보다 먼저 실행하며 초기 `onOpen`은 `onReady`가 끝난 뒤 시작합니다 |
| `onOpenUrls` | 초기 `onOpen` 뒤, 이후 파일과 URL 열기 요청마다 | 빈 목록으로는 호출하지 않습니다. 준비 전에 도착한 macOS 요청은 초기 실행의 `onOpenUrls` 뒤에 도착 순서대로 전달합니다 |
| `onReopen` | macOS의 재활성화 요청마다 | Windows는 호출하지 않습니다. 준비 전 요청은 버립니다 |
| `onAllWindowsClosed` | 앱이 계속 실행되는 중에 열린 창이 0개가 될 때마다 | `"keep-alive"`나 트레이 앱이 대상입니다. 종료 중이거나 승인된 마지막 창 닫기로 종료할 때, 창 없이 시작했을 때는 호출하지 않습니다 |
| `beforeQuit` | 종료 요청마다 | 종료를 취소할 수 있는 유일한 훅입니다. 자동 기한이 없습니다 |
| `onWillQuit` | 종료가 확정된 직후 한 번 | 코어 정지, 플러그인 StopHook과 창 정리보다 먼저 실행합니다. 결과를 무시하며 종료를 취소하지 못합니다. 이때 웹 UI는 더 이상 응답을 받지 못합니다 |
| `onQuit` | 코어와 Worker 정지 뒤 호스트가 반환하기 직전에 한 번 | 세션 종료에서는 호출을 보장하지 않습니다 |

`ShutdownReason`은 `QuitReason`에 `"window-destroyed"`, `"session-end"`, `"interrupted"`를 더한 값입니다.
`"window-destroyed"`는 [신뢰된 `windows.destroy`](/reference/host/windows/#부모-모달과-신뢰된-종료)로
마지막 창을 파괴했을 때, `"interrupted"`는 `bunaway dev`의 종료 요청이나 SIGINT, SIGTERM일 때,
`"session-end"`는 Windows 로그오프와 시스템 종료, macOS 로그아웃, 재시작과 시스템 종료일 때입니다.
macOS에서 사용자 결정 없이 마지막 창이 사라지는 창 생성 실패도 `"window-destroyed"`입니다.
`onWillQuit`과 `onQuit`에는 처음 확정된 종료 원인 하나를 전달합니다.

`onReady`, `onAllWindowsClosed`, `onWillQuit`과 `onQuit`이 예외를 던지거나 거부하면 진단을 남기고
앱은 실행이나 종료를 이어 갑니다. `onWillQuit`과 `onQuit`은 각각 최대 3초까지만 기다립니다.
기한이 지나면 진단을 남기고 종료를 계속하므로 이 두 훅에서는 짧은 정리 작업만 합니다.
`onWillQuit`은 Host API 범위 밖에서 실행하므로 이 훅 안에서 창이나 클립보드 같은 호스트 작업을 직접 부르면
`INVALID_ARGUMENT`로 실패합니다. 앞서 명령이나 플러그인 `setup`이 시작한 작업은 종료가 확정된 시점부터
(`onWillQuit` 실행 중 포함) `CANCELLED`로 실패합니다. 상태 저장과 앱 자원 정리처럼 앱 내부 작업만 합니다.
`onReady`, `onOpen`, `onOpenUrls`, `onReopen`, `onAllWindowsClosed`, `beforeQuit`도 Host API 범위 밖에서 실행합니다. 호스트 API는 명령이나
플러그인 `setup`(과 그 안에서 시작한 작업)에서 부르고, 훅에서는 인자로 받는 `DesktopContext`의 `show`, `hide`, `quit`만 사용합니다.
호스트 실패(시작 실패, UI Worker 중단)에서는 두 훅을 호출하지 않습니다.

### 세션 종료

Windows와 macOS에서 로그오프, 재시작과 시스템 종료는 취소할 수 없는 종료입니다. 대화상자를 표시하지 않고
`beforeQuit`를 호출하지 않으며 대기 중인 `beforeQuit`의 거부도 무시합니다. 호스트는 시스템 종료를
차단하지 않습니다. 대기 중인 닫기 확인과 [닫기 요청](/reference/host/windows/#닫기-요청)도 버립니다.
`onWillQuit("session-end")`과 플러그인 StopHook은 약 4초 안에 끝나야 하며 두 단계가 이 시간을 나눠 씁니다.
`onWillQuit`이 3초를 쓰면 StopHook에는 1초가 남습니다. 그 뒤에는 운영체제가
프로세스를 끝낼 수 있으므로 `onQuit`과 네이티브 정리를 보장하지 않습니다.
다른 앱이 종료를 취소하면 앱은 계속 실행합니다. 중요한 데이터는 사용자가 작업하는 동안 저장합니다.
macOS도 약 4초 안에 `onWillQuit`과 StopHook이 끝나면 곧바로, 아니면 4초 뒤 종료 요청에 답하고
앱을 로그아웃에서 막지 않습니다. 이후 시스템이 프로세스를 끝내므로 `onQuit`은 호출되지 않을 수 있습니다.
`onOpen`과 나머지 수명주기 훅은 앱 수명주기 콜백입니다. 명령이나 플러그인 setup의 Host 호출 컨텍스트를
자동으로 제공하지 않으므로 `storage`, `log`, `capabilities` 직접 호출의 실행 범위로 사용하지 않습니다.

Windows GUI 실행 파일에 URL과 파일 경로를 인자로 전달할 수 있습니다.
실행기를 호출하는 명령줄은 Windows와 호출한 셸의 길이 제한을 따릅니다.
앱 실행 파일은 앱 종료까지 유지되며 `-Wait`도 앱 인자로 그대로 전달합니다.
`-Wait`와 `-draft.txt`처럼 하이픈으로 시작하는 인자도 그대로 전달할 수 있습니다.
OS의 URL scheme과 파일 확장자 등록은 아직 제공하지 않습니다.
별도로 등록한 열기 명령이 앱 실행기에 인자를 전달하면 같은 `onOpen`으로 처리하고, 파일과 URL은 `onOpenUrls`로도 받습니다.
