앱 진입점은 AppDefinition을 default export합니다. CLI의 `build.app`이 이 파일을 선택합니다.
생성 템플릿은 `@bunaway/backend`의 `defineApp()`으로 기능 모듈을 조립합니다.

```ts
import { defineApp } from "@bunaway/backend";

import { message } from "./message/module.ts";

export const app = defineApp({ modules: [message] });
export default app;
```

`modules`는 필수 배열이며 `[]`도 허용합니다. 각 모듈은 `name`, `commands`, `events`를 가집니다.
선택적으로 `commands`, `events`, `state`, `plugins`, `desktop`을 함께 전달할 수 있습니다.
모듈 작성법은 [defineModule](/reference/backend/module/)에서 설명합니다.

`defineApp()`은 모듈과 직접 등록한 명령, 이벤트를 합친 AppDefinition을 즉시 반환합니다.
명령과 이벤트는 각각 최종 이름의 중복을 검사하며 플러그인의 등록 이름도 함께 검사합니다.
중복 이름, 잘못된 이름, 예약 명령은 `INVALID_ARGUMENT`로 실패합니다.
앱 객체와 조립한 명령, 이벤트 목록 및 플러그인 배열은 동결합니다. 플러그인 setup은 앱 실행 시 처리합니다.

등록한 명령과 플러그인 setup에서 [storage, log, capabilities](/reference/backend/host-api/)를
바로 사용할 수 있습니다. 명령은 원래 뷰, setup은 백엔드의 Host 권한으로 실행됩니다.

명령과 플러그인은 공개 타입에 맞는 객체나 클래스 인스턴스로 등록할 수 있습니다.
명령의 입력과 출력 규칙은 클래스 getter로 정의해도 적용됩니다.
플러그인의 이름과 버전, 의존성, 지원 플랫폼과 필요한 권한, 명령과 이벤트 목록도 유지됩니다.

기존 객체형 앱 정의도 지원합니다.

```ts
import type { AppDefinition } from "@bunaway/backend";
import { windowsPlugin } from "@bunaway/plugin-windows";
export default {
  commands: {},
  events: {},
  state: { count: 0 },
  plugins: [windowsPlugin] as const,
} satisfies AppDefinition;
```

## 필드

| 필드 | 필수 | 의미 |
| --- | --- | --- |
| `commands` | 예 | 이름 → `CommandDefinition` 레지스트리 |
| `events` | 예 | 이름 → payload `Schema` 레지스트리 |
| `state` | 아니요 | 초기 JSON 메모리 상태. 생략 시 빈 상태 |
| `plugins` | 아니요 | 플러그인 정의 배열. 생략 시 없음 |
| `desktop` | 아니요 | Windows 앱 열기, 종료 취소와 트레이 설정. 생략 시 마지막 창 닫기로 종료 |

명령 이름과 이벤트 이름은 각각 앱과 모든 플러그인에서 공유합니다.
동일 이름을 덮어쓰거나 중복 등록할 수 없습니다.
명령, 이벤트 이름은 1–128자의 영숫자, `_ . : -`입니다.
`plugin.` 접두사는 네이티브 플러그인 명령에 예약되어 있습니다. 앱 명령에는 사용할 수 없습니다.

## 정책과 실행

등록한 명령과 이벤트를 뷰에서 사용하려면 그 뷰의 `commands`와 `events`에도 이름을 추가합니다.
모든 플러그인의 setup이 끝나면 앱이 명령을 처리할 준비가 됩니다.
이름이 중복되거나 예약 이름을 사용하면 시작에 실패합니다. 플러그인의 의존성이나 플랫폼, 필요한 권한이 맞지 않아도 실패합니다.

CLI는 작성한 설정과 정책을 검사합니다. 호출할 명령의 권한은 개발자가 정책에 적습니다.
앱 시작은 프레임워크가 처리하므로 앱 정의를 default export하면 됩니다.

## 타입

`CommandsOf<typeof app>`는 앱에 직접 선언한 명령과 정적으로 나열한 기능 모듈의 input/output을,
`EventsOf<typeof app>`는 해당 이벤트와 정적으로 나열한 플러그인의 이벤트 payload를 추론합니다.
객체형 앱 정의에서 플러그인 이벤트 타입을 추론하려면 위 예제처럼 `plugins` 배열에
`as const`를 붙여 등록 목록을 tuple로 유지합니다. `defineApp()`에 배열을 직접 전달하면
별도 지정 없이 tuple로 추론합니다. 일반 배열로 선언한 플러그인 목록의 이벤트는
`EventsOf`에 포함하지 않습니다.
플러그인 명령까지 합친 전체 명령 목록의 자동 타입 생성은 현재 제공하지 않습니다.
[타입과 스키마](/guides/types-and-validation/)에서 클라이언트 연결 예시를 확인하세요.

## 데스크톱 앱 동작

현재 Windows Bun 호스트에서 제공합니다. macOS의 현재 런타임에 `desktop`을 지정하면
`UNSUPPORTED`로 시작에 실패합니다.

```ts
import { defineApp } from "@bunaway/backend";

let hasUnsavedWork = false;
export default defineApp({
  modules: [],
  desktop: {
    closeBehavior: "hide",
    tray: { tooltip: "Memo" },
    async onOpen(request, desktop) {
      console.log(request.source, request.urls, request.files);
      // 앱에서 URL과 파일 입력을 검증한 뒤 필요한 문서를 엽니다.
      await desktop.show();
    },
    beforeQuit(reason) {
      // 앱의 저장 상태나 비동기 확인 화면 결과로 종료 여부를 결정합니다.
      console.log(reason);
      return !hasUnsavedWork;
    },
  },
});
```

| DesktopOptions 필드 | 기본값 | 동작 |
| --- | --- | --- |
| `closeBehavior` | `"quit"` | 마지막 창 닫기로 종료를 요청합니다. `"hide"`는 해당 창을 숨기며 트레이가 필요합니다. `"keep-alive"`는 마지막 창을 실제로 닫아도 앱을 유지합니다 |
| `tray` | 없음 | `{ tooltip: string }`. tooltip은 1~127자의 NUL 없는 문자열입니다 |
| `onOpen` | 없음 | `(request: OpenRequest, context: DesktopContext) => void \| Promise<void>` |
| `beforeQuit` | 없음 | `(reason: QuitReason) => boolean \| void \| Promise<boolean \| void>` |

같은 앱 데이터 디렉터리는 한 앱 인스턴스만 사용합니다. 두 번째 실행의 인자와 작업 디렉터리를
기존 앱으로 전달하고 두 번째 실행은 종료합니다. 앱 시작 중 받은 요청도 준비 후 순서대로 처리합니다.
열기 요청은 최대 256개 인자와 64 KiB의 JSON을 받으며 전달 실패, 큐 초과는 두 번째 실행의 오류입니다.
접수 성공은 앱에서 문서를 성공적으로 열었다는 뜻은 아닙니다.

| OpenRequest 필드 | 의미 |
| --- | --- |
| `source` | `"initial"` 또는 `"second-instance"` |
| `argv` | 실행기에 전달한 앱 인자 배열. 순서와 원래 문자열을 유지합니다 |
| `cwd` | 실행기를 호출한 작업 디렉터리 |
| `urls` | scheme을 가진 URL 배열. 파일 URL은 `files`에 포함합니다 |
| `files` | 호출자의 작업 디렉터리를 기준으로 해석한 절대 파일 경로 배열 |

`--` 이전에 `-`로 시작하는 인자는 파일 목록에서 제외합니다. `--` 뒤는 위치 인자로 처리합니다.
URL과 파일은 앱이 검증할 입력입니다. 전달받은 경로는 Host API의 저장 권한을 추가하지 않습니다.
파일 URL은 Windows의 절대 경로를 가리켜야 합니다. 인코딩된 경로 구분자나 NUL을 포함한
파일 URL은 열기 요청 처리에 실패하며, 진단을 남긴 뒤 다음 요청을 처리합니다.
`onOpen`은 초기 실행을 먼저 처리하고 이후 요청을 순서대로 처리합니다.
열기 훅이 실패하면 진단을 남기고 다음 요청을 처리합니다.
훅이 완료되지 않으면 뒤의 요청도 대기하므로 앱에서 오래 걸리는 작업의 수명을 관리합니다.
초기 `onOpen`은 앱 준비 뒤 호출되며 웹 UI의 구독 완료까지 기다리지는 않습니다.

| DesktopContext 메서드 | 결과 |
| --- | --- |
| `show(): Promise<void>` | 살아 있는 창을 모두 복원합니다. 열린 창이 없으면 첫 사전 선언 창을 생성합니다. 선언이 비어 있으면 아무 창도 만들지 않습니다 |
| `hide(): Promise<void>` | 트레이가 있으면 살아 있는 창을 모두 숨깁니다. 없으면 오류로 실패합니다 |
| `quit(): Promise<boolean>` | 종료 검사가 승인되면 `true`, 취소하거나 검사에 실패하면 `false` |

`show()`는 표시 요청의 접수를 기다립니다. 새 창의 문서와 SDK 준비까지 기다리지 않습니다.
두 번째 실행을 받으면 같은 표시 요청을 접수한 뒤 `onOpen`을 호출합니다.
숨김은 창, WebView, 세션과 앱 상태를 유지하므로 백엔드 작업도 계속 실행됩니다.
트레이를 클릭하거나 메뉴의 Open을 선택하면 창을 복원합니다. 숨기기 전의 최대화 상태를 유지하며,
최소화된 창은 복원합니다. Quit은 종료 검사를 거칩니다.
열린 창이 없으면 Open은 첫 선언의 `startup` 값과 관계없이 그 창을 생성해 표시합니다.
다른 창은 자동 생성하지 않으며 `app.windows: []`이면 아이콘과 Quit만 사용합니다.
이 표시 요청은 `visible`과 `showWhenReady`의 자동 표시 조건을 기다리지 않고 창을 표시합니다.
반복 표시 요청은 합치고 이전 WebView 정리와 진행 중인 창 API 작업이 끝난 뒤 생성합니다.

시작 창이 없으면 트레이 또는 `closeBehavior: "keep-alive"`를 반드시 지정합니다.
백엔드 타이머나 `beforeQuit`, `onOpen` 훅만으로는 이 조건을 충족하지 않습니다.
트레이는 시작 창이 없어도 앱을 유지하지만 마지막 창의 닫기 규칙을 바꾸지는 않습니다.
트레이와 기본 `"quit"`를 함께 쓰면 나중에 만든 마지막 창을 닫을 때 종료를 요청합니다.
`"keep-alive"`로 닫은 창은 HWND, WebView와 세션을 정리하고 앱 상태와 백엔드는 유지합니다.
이때 마지막 창 닫기는 종료 요청이 아니므로 `beforeQuit`를 호출하지 않습니다.
명시적 종료는 트레이 Quit 또는 `onOpen`에서 받은 `DesktopContext.quit()`으로 요청합니다.
트레이 없는 상주 앱은 앱이 완료할 수 있는 종료 경로를 구현해야 합니다.
설정과 지연 생성 예시는 [창 없는 시작](/guides/windows/#창-없는-시작)을 따릅니다.

`QuitReason`은 마지막 창의 닫기 `"last-window"`, 트레이 Quit `"tray"`,
`DesktopContext.quit()`의 `"api"`입니다. `beforeQuit`가 `false`를 반환하거나 예외를 던지면
창과 세션을 유지하고 종료를 취소합니다. 동시 종료 요청은 같은 검사 결과를 사용합니다.
반환값이 `true` 또는 `undefined`이면 기존 종료 절차와 플러그인 StopHook을 실행합니다.
기본 `"quit"`에서는 공개 [windows API](/reference/host/windows/)로 마지막 창을 닫을 때도 종료 검사를 거칩니다.
창의 `recreate`는 앱 종료를 요청하지 않으며 트레이 숨김 대신 창을 다시 만듭니다.
`quit()`의 `true`는 종료 승인 결과이며 모든 자원이 이미 정리됐다는 뜻은 아닙니다.
종료 훅에는 자동 기한이 없으며 앱이 완료해야 합니다. 강제 종료, 호스트 실패, SIGINT, SIGTERM은 취소할 수 없습니다.
`bunaway dev`의 재시작과 CLI 종료도 `beforeQuit`와 숨김 설정을 우회하고 플러그인 StopHook과 자원 정리를 실행합니다.
창이 없는 상주 앱과 트레이 앱에도 적용합니다. OS 강제 종료는 StopHook 실행을 보장하지 않습니다.

`onOpen`과 `beforeQuit`는 앱 수명주기 콜백입니다. 명령이나 플러그인 setup의 Host 호출 컨텍스트를
자동으로 제공하지 않으므로 `storage`, `log`, `capabilities` 직접 호출의 실행 범위로 사용하지 않습니다.

Windows GUI 실행 파일에 URL과 파일 경로를 인자로 전달할 수 있습니다.
실행기를 호출하는 명령줄은 Windows와 호출한 셸의 길이 제한을 따릅니다.
앱 실행 파일은 앱 종료까지 유지되며 `-Wait`도 앱 인자로 그대로 전달합니다.
`-Wait`와 `-draft.txt`처럼 하이픈으로 시작하는 인자도 그대로 전달할 수 있습니다.
OS의 URL scheme과 파일 확장자 등록은 아직 제공하지 않습니다.
별도로 등록한 열기 명령이 앱 실행기에 인자를 전달하면 같은 `onOpen`으로 처리합니다.
