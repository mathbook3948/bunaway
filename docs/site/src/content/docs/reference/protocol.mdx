전송이나 호스트, 테스트 어댑터를 작성할 때 사용하는 `@bunaway/protocol`의 메시지 규약과 공개 API입니다.
앱의 명령 호출과 이벤트 구독은 [Client SDK](/reference/client/create-client/)를 사용합니다.

## WebView 메시지

모든 메시지에 `kind`, `protocol: { major, minor }`가 있습니다.
아래 필드 중 `deadline`만 선택적입니다. 선언하지 않은 메시지 필드는 거부합니다.

| kind | 방향 | 나머지 필드 |
| --- | --- | --- |
| `hello` | 양쪽 | `features`, `buildId` |
| `sdk-ready` | UI → 호스트 또는 코어 | 추가 필드 없음. 협상한 SDK 준비 확인이며 응답 없음 |
| `invoke` | UI → 코어 | `id`, `command`, `payload`, `deadline?` |
| `cancel` | UI → 코어 | `id`: 취소할 요청 ID |
| `listen` | UI → 코어 | `id`, `event` |
| `unlisten` | UI → 코어 | `id`, `subscriptionId` |
| `close` | UI → 호스트 또는 코어 | 추가 필드 없음. 세션 종료 알림이며 응답 없음 |
| `result` | 코어 → UI | `id`, `payload` |
| `error` | 코어 → UI | `id`, `error` |
| `event` | 코어 → UI | `subscriptionId`, `source`, `target`, `event`, `sequence`, `payload` |
| `subscription-error` | 코어 → UI | `subscriptionId`, `error` |

ID, 명령, 이벤트, feature 이름은 1–128자 `[A-Za-z0-9_.:-]`입니다.
features는 중복 없는 최대 256개 배열입니다. 버전의 각 숫자는 0–65,535 정수입니다.
deadline은 0–Number.MAX_SAFE_INTEGER 정수인 UTC epoch 밀리초입니다.
event sequence는 구독마다 1부터 증가합니다. source는 발신 뷰 ID 또는 `backend`입니다.
target은 실제로 전달받는 뷰 ID입니다. 내부 HostContext 식별자는 공개 이벤트에 포함되지 않습니다.

listen 결과의 payload는 `{ subscriptionId }`입니다. unlisten 결과는 `null`입니다.
WebView 전송을 닫으면 `close`를 보냅니다. 호스트는 메시지의 발신 문서를 확인하고 해당 세션을 철회해 진행 중 요청과 구독을 정리합니다.
협상 완료 전에도 열린 세션을 닫을 수 있으며, 반복된 종료 알림은 무시합니다. 다른 문서나 세션을 지정하는 필드는 허용하지 않습니다.
listen 성공 응답에서 비어 있지 않은 문자열 subscriptionId를 얻을 수 없으면 프로토콜 위반입니다.
클라이언트는 `INTERNAL` 오류로 연결을 닫고 진행 중 요청과 활성 구독을 모두 정리합니다.
취소되거나 호스트 기한이 지난 listen의 늦은 성공 응답도 같은 검사를 받습니다.
늦은 결과, 취소, 구독 오류의 처리 계약은 [listen](/reference/client/listen/)과 [취소 가이드](/guides/cancellation-and-errors/)를 따릅니다.

## 파싱과 직렬화

```ts
import { parseMessage, serializeMessage } from "@bunaway/protocol";
const text = serializeMessage({
  kind: "invoke", protocol: { major: 1, minor: 0 },
  id: "request-1", command: "message.read", payload: null,
});
const message = parseMessage(text);
```

| 헬퍼 | 입력 → 반환 | 추가 검사 |
| --- | --- | --- |
| `parseMessage` / `serializeMessage` | 문자열 ↔ Message | messageSchema, 크기, 깊이 |
| `parsePolicy` | 문자열 → Policy | policySchema와 중복 view ID |
| `parseBootstrap` | 문자열 → Bootstrap | bootstrapSchema와 내부 정책 view ID |
| `parseHostCall` / `serializeHostCall` | 문자열 ↔ HostCall | hostCallSchema |
| `parseHostResponse` / `serializeHostResponse` | 문자열 ↔ HostResponse | hostResponseSchema |
| `parseProcessFrame` / `serializeProcessFrame` | 문자열 ↔ ProcessFrame | processSchema와 boot 내부 정책 |
`NativeRegistry(plugins, options?)`는 계약을 복사하고 작업과 permission 중복을 검사합니다.
기본 `mode: "runtime"`은 실제 앱에 등록된 계약에 적용하며 전체 operation과 permission을
각각 최대 256개로 제한합니다. `mode: "catalog"`은 설치된 패키지 전체를 검사할 때만
사용합니다. 이 모드는 여러 플러그인의 합계 제한만 건너뛰고 각 플러그인의 개별 제한,
계약 및 이름 검증은 유지합니다. CLI는 설치 catalog와 정책 참조를 이 모드로 검사하고,
앱 실행과 Host 호출에는 기본 runtime 모드를 사용합니다.

`NativeRegistryOptions`의 `mode`는 `runtime` 또는 `catalog`입니다. `validateCall`과
`validateOutput`은 등록 schema로 검사하며 `validatePolicy`는 permission 이름과 범위를
검사합니다. `allowed(source, call, matches)`는 deny 우선으로 allow 범위를 평가합니다.

공통 프로토콜은 작업 목록을 기본 등록하지 않습니다. 창 제어도 개별 플러그인의 NativePluginContract로 등록하고 검증합니다. 창 제어 계약과 앱에서 사용하는 API는 [windows 레퍼런스](/reference/host/windows/)에 있습니다.

```ts
type NativeRegistryOptions = { mode?: "runtime" | "catalog" };
type HostOperationContract<I, O> = {
  name: string;
  input: I;
  output: O;
  permission: string;
  osPermission?: "not-required";
};
```

`osPermission: "not-required"`는 OS 권한이 필요 없는 작업을 표시하며, 기능 조회에서
OS 권한 메타데이터로 전달됩니다.

입력이 잘못되면 `ProtocolError`가 발생합니다. parse와 serialize는 스키마를 검증하고 JSON 스냅샷을 만듭니다.
원문과 직렬화 결과의 UTF-8 크기는 최대 1 MiB, 깊이는 최대 64입니다.
serialize는 getter나 toJSON을 실행하지 않으며 그런 객체를 입력하면 거부합니다.

## 버전 협상

`PROTOCOL_VERSION`과 `PROCESS_IPC_VERSION`은 각각 `{ major: 1, minor: 0 }`입니다.
`negotiateProtocol(localHello, remoteHello)`는 hello를 검증한 뒤 `{ protocol, features }`를 반환합니다.
major가 다르면 `UNSUPPORTED` 오류가 발생합니다. 같으면 두 minor 중 작은 값과 공통 feature를 정렬해 반환합니다.
buildId는 버전 협상에 사용하지 않습니다.
클라이언트의 `ready`는 협상 결과에 상대 buildId를 더합니다.

`SDK_READY_FEATURE`의 값은 `"sdk-ready"`입니다. Windows 호스트와 기본 WebView 클라이언트는
hello의 features에 이 값을 선언합니다. 양쪽이 협상한 경우 SDK는 서버 hello를 검증한 뒤
`{ kind: "sdk-ready", protocol }`을 보내고 전송 접수 후 `ready`를 완료합니다.
전송 실패나 준비 기한 초과는 `ready`를 실패시키고 연결을 정리합니다.
명시적 transport 클라이언트도 이 기능을 쓰려면 자신의 hello.features에 값을 추가합니다.
한쪽이 선언하지 않으면 이전 hello 계약을 유지하며 준비 확인을 보내지 않습니다.
이 경우 Windows의 별도 SDK 준비 상태는 자동으로 완료되지 않습니다.
호스트는 현재 발신 문서와 협상된 세션에서만 확인을 받고, 협상 전이나 협상하지 않은 확인은 거부합니다.
Windows 호스트는 준비 확인을 UI Worker에서 처리하므로 Worker 전송 대기열이 가득 차도 확인을 받습니다.
같은 세션의 중복 확인은 새 완료 이벤트를 만들지 않습니다. 요청 ID나 새 호출 컨텍스트를 발급하지 않습니다.
준비 확인은 명령 권한이나 이벤트 구독 권한을 바꾸지 않습니다.

## HostCall과 HostResponse

HostCall은 `{ operation, payload }`입니다. 전송은 JSON envelope를 검증합니다.
창 제어를 포함한 모든 등록 플러그인 작업은 플러그인 계약으로 입력과 결과를 검사합니다. 응답은 `{ kind: "result", payload }` 또는
`{ kind: "error", error }`입니다.
네이티브 플러그인 화면 명령은 `plugin.<작업 이름>`입니다.
WebView invoke의 command와 Host operation은 별도의 이름 공간, 권한 검사입니다.

## Bootstrap

`entrypoint`, `buildId`가 필수이며 `policy`, `backendContext`는 스키마에서 선택적입니다.
실제 Bun 프로세스 런타임은 시작에 policy와 backendContext를 요구합니다.
Bootstrap은 호스트가 생성해 런타임에 전달하는 부팅 정보입니다.

## 프로세스 프레임

모든 프레임에는 `ipc: { major: 1, minor: 0 }`, `runtime: { id, generation }`, `kind`가 있습니다.
Bun 자식 프로세스 경로는 UTF-8 NDJSON을 사용합니다.
runtime identity, generation, context는 신뢰된 호스트가 발급합니다.

| kind | 나머지 필드 | 역할 |
| --- | --- | --- |
| `boot` | `payload: Bootstrap` | 앱 부팅 |
| `hello` | `payload: Hello` | 프로세스 협상 |
| `ready` | `pid`, `bunVersion`, `revision` | 등록, 플러그인 준비 완료 |
| `web` | `context`, `payload: Message` | 특정 세션의 웹 메시지 |
| `host-request` | `context`, `requestId`, `operation`, `payload` | 권한에 묶인 Host 호출 |
| `host-response` | `context`, `requestId`, `payload: HostResponse` | Host 호출 결과 |
| `host-cancel` | `context`, `requestId` | Host 요청 취소 |
| `revoke` | `context` | 컨텍스트 회수 |
| `session-open` | `context`, `viewId` | 호스트가 세션 개설 |
| `shutdown` | 없음 | 종료 요청 |
| `stopping` | 없음 | 정리 시작 알림 |
| `fatal` | `error` | 복구 불가능한 실패 |

스키마가 JSON 구조를 검증한 뒤 런타임이 발급자 identity와 프레임 방향을 추가로 검사합니다.
WebView에서 위조한 host-request나 session-open은 권한을 가진 호스트 프레임으로 인정되지 않습니다.
Windows와 macOS Bun FFI 경로는 같은 프로세스의 Worker 연결에 같은 앱과 코어 계약을 적용합니다. 프로세스 IPC는 이전 probe와 어댑터 계약 검사를 위한 경로입니다.

## 공개 스키마 객체

`messageSchema`, `errorSchema`, `policySchema`, `bootstrapSchema`, `hostResponseSchema`,
`hostCallSchema`, `processSchema`를 export합니다. native 어댑터도 이 구조를 기준으로 검증합니다.
사용자 명령 payload 스키마 작성은 [Schema 레퍼런스](/reference/schema/)를 참고하세요.
