```ts
client.capabilities(): Promise<Capabilities>
capabilities(): Promise<Capabilities>
```

현재 플랫폼에서 사용할 수 있는 기능과 OS 권한 상태를 반환합니다.
UI에서 재사용하는 클라이언트의 `client.capabilities()`로 조회하며 연결 준비를 기다립니다.
직접 import한 `capabilities`도 같은 기본 연결을 사용하는 함수 API로 계속 지원합니다.

## 정책과 사용법

호출할 뷰의 `commands` 배열에 `bunaway.capabilities`를 허용해야 합니다. 기본 메시지 템플릿에는 이 권한이 없으므로 다음처럼 추가합니다.

```json
{ "commands": ["message.read", "message.save", "bunaway.capabilities"] }
```

```ts
// UI 초기화 때 만든 client를 재사용합니다.
const features = await client.capabilities();
const read = features.find((feature) => feature.name === "storage.readText");
console.log(read?.support, read?.permission);
```

위 JSON의 commands를 기존 뷰 객체에 추가합니다. 나머지 필수 정책 필드는 유지합니다.

## 결과

`name`, `support`, `permission`, 선택적 `reason`을 가진 배열입니다.
`support`는 `supported`, `experimental`, `unsupported` 중 하나입니다.
`permission`은 `granted`, `denied`, `prompt`, `not-required`, `unknown` 중 하나입니다.

## 의미와 실패

`support`는 플랫폼의 구현 상태이고 `permission`은 OS 권한 상태입니다.
실제 Host API 호출은 뷰 정책도 검사합니다. `permission: "not-required"`인 파일 작업도 허용된 저장 범위 안에서 실행합니다.
앱 WebView가 없는 환경은 `UNSUPPORTED`, 정책 미허용은 `PERMISSION_DENIED`, 잘못된 기능 응답은 `INTERNAL`로 실패합니다.
조회는 현재 상태만 반환하며 OS 권한 요청이나 정책 변경은 실행하지 않습니다.

백엔드에서 조회하려면 [capabilities.get](/reference/host/capabilities-get/)을 사용합니다.
