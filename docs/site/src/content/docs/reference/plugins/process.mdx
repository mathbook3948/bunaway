기본 export(`default`)를 `processes`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-process`를 설치하고 앱의 `plugins`에 `processes`를 등록합니다.
현재 Windows 10 이상과 macOS에서 제공합니다. 화면과 백엔드는 `processes.run`을 사용합니다.
Windows는 오래 실행하는 프로세스를 위한 `processes.spawn`, `read`, `write`, `closeStdin`, `kill`도
제공합니다. macOS에서 이 다섯 작업은 `UNSUPPORTED`입니다.

## 앱의 실행 규칙과 권한

`process.run` 권한은 프로세스 실행을 허용합니다. 실행 파일과 전체 인자는 앱 명령이 검사합니다.
설치와 등록은 권한을 부여하지 않습니다. 입력은 프로그램의 실행 권한과 backend 환경을 사용하므로
신뢰된 도구와 허용한 인자만 앱 명령에 연결합니다. 실행 파일 이름만 검사하고 임의 인자를 그대로
전달하면 그 프로그램이 제공하는 파일 접근이나 코드 실행도 허용할 수 있습니다.

```ts
import processes from "@bunaway/plugin-process";
import { BunawayError } from "@bunaway/protocol";

async function makeReport(year: number) {
  if (!Number.isInteger(year) || year < 2020 || year > 2100) {
    throw new BunawayError({ code: "INVALID_ARGUMENT", message: "지원하지 않는 연도입니다." });
  }
  return processes.run({
    executablePath: "C:/Program Files/Report Tool/report.exe",
    args: ["--year", String(year)],
    timeoutMs: 10000,
  });
}
```

앱 명령은 호출한 뷰의 Host 권한을 유지합니다. setup은 `backend.permissions`를 사용합니다.
앱 명령에서 실행 규칙을 검사할 때는 화면에 `plugin.process.run`을 직접 허용하지 않습니다.
직접 호출을 허용하면 해당 뷰가 모든 유효 실행 파일과 argv를 선택할 수 있습니다.
백엔드의 신뢰된 실행에는 `Bun.spawn`을 직접 사용해도 됩니다.

## 입력과 결과

`ProcessInput`은 다음 필드입니다.

| 필드 | 의미와 기본값 |
| --- | --- |
| `executablePath` | Windows는 drive로 시작하는 절대 local `.exe` 경로, macOS는 `/`로 시작하는 절대 POSIX 경로, 최대 1024자 |
| `args` | argv 문자열 배열, 기본값 `[]`, 최대 128개와 인자당 4096자 |
| `stdinBase64` | 선택적인 canonical base64 bytes(표준 알파벳, 필요한 `=` padding, padding bit 0), 최대 64 KiB, 미지정이면 입력을 제공하지 않음 |
| `maxOutputBytes` | stdout와 stderr의 합계 bytes 상한, 0부터 65536, 기본값 65536 |
| `timeoutMs` | 전체 실행과 pipe 완료의 기한, 1부터 30000ms, 기본값 30000 |

공통으로 PATH 조회, 상대 경로와 NUL을 거부합니다. Windows는 추가로 UNC share, device path, `.`/`..` 경로 구성 요소, alternate stream과
batch 파일을 거부하고, macOS는 `.`/`..`/빈 경로 구성 요소와 제어 문자(C0, DEL, C1)를 거부하며, 경로와 인자의 짝 없는 surrogate도 거부합니다(인코딩 때 U+FFFD로 바뀌어 검증한 값과 달라지기 때문입니다). 호출자가 env나 cwd를 바꾸는 입력은 없습니다. Windows의 자식은 backend의
작업 디렉터리와 Bun이 읽은 dotenv 값을 포함한 backend 환경을 상속합니다. macOS의 자식에게는 `PATH=/usr/bin:/bin`을 전달하고, 앱을 실행한 셸이나 호스트 프로세스의 변수는 전달하지 않습니다.
Windows에서 인자의 공백, 빈 문자열, Unicode, 따옴표와 backslash는
표준 argv 인용 규칙을 따르고, macOS는 각 인자를 별도의 argv 항목으로 전달합니다. shell을 시작하거나 shell 문자열을 해석하지 않습니다.
`&`, `%PATH%`, `$()`는 인자의 문자로 전달합니다. 전체 인자는 Windows UTF-16 command-line
상한, macOS는 실행 경로와 인자의 UTF-8 합계 256 KiB를 넘지 않도록 보수적으로 제한합니다. 지정한 프로그램 자체의 인자 해석은 앱이 검사합니다.

`ProcessResult`는 `{ pid, exitCode, signal, stdoutBase64, stderrBase64 }`입니다.
stdout와 stderr는 binary bytes를 base64로 반환합니다. `exitCode`는 Windows의 unsigned 32-bit
종료 코드를 반환하며 계약은 signed 32-bit 표현도 허용합니다. macOS는 프로세스의 종료 코드(0~255)를 반환합니다. 종료 코드가 0이 아니어도 정상 완료
결과로 반환합니다. `signal`은 Windows에서 `null`이고, macOS에서 자식이 signal로 종료되면 `SIGTERM` 같은 이름이며(이때 `exitCode`는 128 더하기 signal 번호) 그 외에는 `null`입니다. 출력 상한 초과는 결과를 자르지 않고
실패합니다. binary 입력은 한 번
제공하고 끝냅니다. 입력을 이어서 보내거나 출력을 흘려 받아야 하면 아래 핸들을 사용합니다.

## 오래 실행하는 프로세스(Windows)

`process.run`은 한 번의 호출이 끝나야 결과를 돌려줍니다. 로그를 흘리는 도구, 대화형 도구, 개발 서버처럼
오래 실행하는 프로세스는 `spawn`으로 시작하고 반환된 `handle`로 다룹니다. 다섯 작업은 각각 독립된
권한(`process.spawn`, `process.read`, `process.write`, `process.closeStdin`, `process.kill`)이 필요하고,
`process.run` 권한은 이를 허용하지 않습니다. 실행 파일과 전체 인자는 `run`과 같은 규칙으로 검사하며,
앱 명령이 허용한 도구에만 연결합니다.

| 작업 | 입력 | 결과 |
| --- | --- | --- |
| `spawn` | `executablePath`, `args`(`run`과 같은 검사, stdin, env, cwd, timeout 입력 없음) | `{ handle, pid }` |
| `read` | `handle`, `maxBytes`(1부터 65536, 기본값 65536), `waitMs`(0부터 10000, 기본값 0) | `{ stdoutBase64, stderrBase64, exited }` |
| `write` | `handle`, `dataBase64`(최대 64 KiB) | `{}` |
| `closeStdin` | `handle` | `{}` |
| `kill` | `handle` | `{}` |

`read`는 지금까지 쌓인 출력을 돌려줍니다. 출력이 없으면 `waitMs`까지 기다리고, 출력이 도착하거나
프로세스가 끝나면 그 즉시 돌려줍니다. `maxBytes`는 stdout와 stderr 합계의 상한이며 둘 다 데이터가
있으면 각각 절반(내림)을 보장하고 남는 몫은 읽을 때마다 번갈아 한쪽이 가져가서 한쪽이 다른 쪽을 막지 않습니다. `exited`는 프로세스가 끝나고 마지막
출력까지 돌려준 읽기에서 `{ exitCode, signal }`로 한 번 나오며, 그때 핸들이 해제됩니다. 그 전에는
`null`입니다. Windows의 종료 상태에는 signal이 없어 `signal`은 `null`이고, `kill`로 끝낸 프로세스의
`exitCode`는 1입니다. 같은 핸들에 `read`를 동시에 부르면 `BUSY`입니다.

`write`는 모든 바이트가 파이프에 들어갈 때까지 기다립니다. 자식이 입력을 읽지 않아 파이프가 가득
차면 계속 기다리며, 취소하면 그 `write`만 취소됩니다. 이미 파이프에 들어간 일부 바이트는 되돌리지
않습니다. `write`도 같은 핸들에서 동시에 부르면 `BUSY`입니다. `closeStdin`은 진행 중인 `write`가 끝난
뒤 입력을 닫아 자식이 파일 끝을 보게 하며 반복해도 성공합니다. 입력이 닫혔거나 자식이 입력을 닫은 뒤의
`write`는 `INVALID_ARGUMENT`입니다. `kill`은 프로세스와 하위 프로세스를 모두 종료하고 반복해도
성공합니다. 종료 상태는 이어지는 `read`로 확인합니다.

출력은 이벤트가 아니라 `read`로 가져옵니다. Windows 호스트에는 플러그인이 쓸 수 있는 일반 이벤트
서비스가 없고, 이벤트는 구독한 모든 뷰에 전달되기 때문입니다. `read`는 호출한 쪽에만 출력을
전달하고 자식의 출력 파이프(8 KiB)가 배압을 그대로 적용합니다. 읽지 않으면 자식은 쓰기에서 기다리고
어댑터는 출력을 쌓지 않습니다. 대기 중인 `read`가 있는 동안 2ms 간격으로 확인하므로 아주 긴 `waitMs`를
반복해서 쓰면 그만큼 확인이 이어집니다.

핸들은 만든 호출 출처 전용입니다. 다른 출처가 쓰면 존재하지 않는 핸들과 똑같이 `INVALID_ARGUMENT`를
받아 핸들의 존재도 알 수 없습니다. 같은 출처라면 다른 호출에서도 이어서 쓸 수 있지만, 어댑터는
화면의 종료를 알지 못하므로 핸들을 직접 종료하거나 읽어 끝내는 것은 호출한 쪽의 책임입니다. 어댑터는
동시에 최대 4개의 자식을 유지하며(`run`의 8개와 별개) 종료했지만 아직 읽지 않은 자식도 셉니다. 초과하면
`BUSY`입니다. 종료한 뒤 60초 동안 읽지 않은 핸들은 해제됩니다.

각 자식은 생성 단계에서 핸들 전용 Job Object에 들어갑니다. 루트가 끝나면 남은 하위 프로세스를 종료하고,
어댑터 폐기와 앱 종료는 대기 중인 호출을 `CANCELLED`로 끝내고 모든 자식과 하위 프로세스를
종료합니다. 폐기 중 호출이 끝나는 시점이 자식 종료 완료를 뜻하지는 않습니다. `run`의 30초 timeout은 핸들에 적용되지 않으므로 오래 실행해도 되는 도구에만 연결합니다.

## 취소와 자원 정리

동시에 최대 8개의 호출을 소유합니다. Windows의 각 호출은 직접 자식과 그 하위 프로세스를 함께 소유하고, macOS는 직접 자식만 소유합니다.
초과하면 `BUSY`입니다. 화면 함수의 마지막 인자는
`NativeInvokeOptions`이며 `signal`과 `deadline`은 [invoke](/reference/client/invoke/)를
따릅니다. 백엔드는 명령의 취소와 기한을 이어받습니다.

취소나 호출 기한 초과는 공개 호출의 Promise를 먼저 거부할 수 있습니다. 이 시점에 하위 프로세스의
종료나 pipe 정리가 끝났다고 가정하지 않습니다. 어댑터는 취소 전달 이후에도 호출별 프로세스의 종료와
stdout/stderr pipe 정리를 계속 소유하며, 내부 실행 작업과 어댑터 폐기는 이 정리를 기다립니다.
플러그인 timeout과 출력 초과도 같은 종료 및 정리 경로를 사용합니다. 취소한 작업의 부수 효과는
되돌리지 않습니다. 직접 자식이 정상 종료할 때도 남은 손자 프로세스를 종료하고 pipe를 정리합니다.
실행할 프로그램은 이 foreground 수명을 따라야 합니다. 입력을 읽지 않는 자식도 취소할 수 있습니다.

각 호출은 프로세스 생성 단계에서 전용 Job Object에 들어가므로 실행과 Job 할당 사이의 틈이 없습니다.
전용 Job은 기존 호스트 Job의 하위로 유지되며 Windows 앱 종료의 전체 descendant 정리는 호스트가
담당합니다. Job 준비 실패는 프로세스를 실행하지 않습니다. 네이티브 종료나 핸들 정리 실패는
`INTERNAL`로 반환합니다. 이 플러그인은 detach, breakaway나 임의 PID kill을 제공하지 않습니다.
desktop restart와 exit는 기존 수명주기 구현이 담당합니다.

잘못된 입력은 `INVALID_ARGUMENT`, 권한 거부는 `PERMISSION_DENIED`, 미등록 작업이나 플랫폼은
`UNSUPPORTED`입니다. 실행 실패와 출력 상한 초과는 `INTERNAL`, 취소와 폐기는 `CANCELLED`,
timeout과 호출 기한 초과는 `TIMEOUT`입니다. 실행 실패의 내부 경로나 OS 오류 원문은 응답으로
노출하지 않습니다. 자식 stdout와 stderr에는 프로그램이 출력한 정보가 그대로 포함됩니다.

## macOS의 취소 범위

macOS에서 취소, timeout, 출력 초과와 어댑터 폐기는 직접 자식에게 `SIGKILL`을 보내고 자식의 종료와
stdout/stderr pipe 정리를 기다린 뒤 끝냅니다. 자식이 만든 손자 프로세스는 종료하지 않으며, 손자가
pipe를 계속 열고 있어도 호출은 pipe를 닫고 반환합니다. 손자 프로세스가 남지 않아야 하는 도구는
앱이 그 도구의 종료 방식을 직접 보장합니다. 프로세스 그룹이나 process tree 종료는 아직 제공하지 않습니다.
Windows와 같은 `ProcessInput`, `ProcessResult`, 입출력과 timeout 상한, 동시 실행 수, 오류 코드를 사용합니다. 실행 파일 경로와 인자 검증, 전체 인자 크기 상한, 자식 환경 변수, 종료 범위는 위에서 설명한 대로 플랫폼마다 다릅니다.
