기본 export(`default`)를 `power`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-power`를 설치하고 `power`를 앱의 plugins에 등록합니다.
Windows는 모든 작업을 지원합니다. macOS는 `getStatus`, `getIdleTime`, `getIdleState`와
`startBlocker`, `listBlockers`, `isBlockerActive`, `stopBlocker`를 지원하고
`getCpuSpeedLimit`와 이벤트는 `UNSUPPORTED`입니다. 다른 플랫폼은 모두 `UNSUPPORTED`입니다.
각 작업에는 `power.<작업명>` 권한이 필요합니다. 화면에서 직접 호출하면 해당
`plugin.power.<작업명>` command도 허용합니다. 등록은 권한을 부여하지 않습니다.
Windows에서 전원 작업은 UI 스레드에서 실행됩니다. 파일 선택이나 메시지 대화상자,
팝업 메뉴 루프처럼 UI 스레드를 점유하는 네이티브 모달이 열려 있는 동안
`getStatus`, `startBlocker`, `stopBlocker` 같은 호출은 모달이 끝날 때까지 대기합니다.

```ts
import power from "@bunaway/plugin-power";
// 앱 정의: plugins: [power]
const status = await power.getStatus();
const request = await power.startBlocker({ type: "display", reason: "미디어 재생 중" });
try {
  // 화면과 시스템 idle 절전 방지가 필요한 작업
} finally {
  await power.stopBlocker({ id: request.id });
}
```

## 전원 상태와 입력 idle

`power.getStatus()`는 현재 전원 상태를 반환합니다. Windows는 GetSystemPowerStatus,
macOS는 IOKit의 IOPowerSources와 NSProcessInfo 값을 읽습니다.
source는 ac, battery 또는 unknown입니다. batteryPresent와 charging은 boolean 또는 null,
batteryPercent는 0–100 또는 null, batterySaver는 boolean입니다.
remainingSeconds와 fullLifeSeconds는 OS가 추정한 초 또는 null입니다.
배터리가 없으면 percent와 수명은 null, charging은 false입니다.
알 수 없는 플래그, 백분율과 수명은 0으로 대체하지 않습니다.
0%는 알려진 빈 배터리입니다. 조회 사이 OS 상태가 바뀔 수 있습니다.

macOS에서 source는 현재 전원을 공급하는 원천(AC Power 또는 Battery Power)이며, UPS 등
그 밖의 원천이나 확인할 수 없는 경우는 unknown입니다. 배터리 항목은 내장 배터리를
기준으로 하고, 내장 배터리가 없으면 batteryPresent는 false, charging은 false,
batteryPercent는 null입니다. batteryPercent는 현재 용량과 최대 용량의 비율을 반올림한 값입니다.
batterySaver는 저전력 모드(Low Power Mode) 여부입니다. remainingSeconds는 source가
battery일 때 OS가 추정한 남은 사용 시간이며 추정할 수 없으면 null입니다.
macOS는 완충 기준 수명 추정을 제공하지 않으므로 fullLifeSeconds는 항상 null입니다.
Electron `powerMonitor.isOnBatteryPower()`는 source가 battery인 경우와 같습니다.

`power.getIdleTime()`은 현재 세션의 마지막 입력 이후 초를 내림해 반환합니다.
Electron `powerMonitor.getSystemIdleTime()`에 대응합니다.
macOS는 `CGEventSourceSecondsSinceLastEventType`으로 로그인 세션 전체의 모든 입력 종류를
기준으로 하며 4294967초를 넘으면 그 값으로 제한합니다.
Windows는 GetLastInputInfo와 GetTickCount의 DWORD tick 차이를 사용하므로 약 49.7일마다 순환합니다.
합성 입력의 tick 값과 세션에 따라 달라지며 다른 로그인 세션의 입력은 포함하지 않습니다.
`power.getIdleState({ thresholdSeconds })`는 idle 시간이 지정한 정수 초 이상이면 idle,
미만이면 active를 반환합니다. 기한 범위는 1–4294967초입니다.
화면 잠금 여부와 절전 상태는 판정하지 않습니다.

## CPU 속도 제한

`power.getCpuSpeedLimit()`은 Electron `powerMonitor.getCPUSpeedLimit()`에 대응하며
`{ speedLimitPercent }`(0–100 정수)를 반환합니다. 100이면 제한이 없습니다.
Windows `CallNtPowerInformation`의 `ProcessorInformation`이 돌려주는 논리 프로세서별
`MhzLimit / MaxMhz` 비율(%) 중 가장 낮은 값이며, `MaxMhz`가 0인 프로세서는 건너뜁니다. 비율을 계산할 수 있는 프로세서가 없으면
(일부 가상화 환경) 제한 정보가 없는 것으로 보고 100을 반환합니다.
전원 계획, 발열과 절전 정책에 따라 호출할 때마다 달라질 수 있습니다.
출력 버퍼가 작다고 보고되면 한 번 두 배로 늘려 다시 조회합니다.
OS 조회 실패와 형식이 잘못된 결과는 `INTERNAL`입니다.
입력은 `null`이며 `power.getCpuSpeedLimit` 권한이 따로 필요합니다.

```ts
const { speedLimitPercent } = await power.getCpuSpeedLimit();
if (speedLimitPercent < 100) {
  console.log(`CPU가 ${speedLimitPercent}%로 제한되어 있습니다.`);
}
```

변경 이벤트(`speed-limit-change`)는 제공하지 않으므로 필요하면 직접 조회합니다.
thermal-state는 지원하지 않습니다. Electron의 `thermal-state-change`와
`getCurrentThermalState()`는 macOS 전용 개념이고 Windows에는 대응하는 공개 API가 없습니다.
종료 관련 이벤트는 위의 `power.suspended`와 세션 잠금 이벤트가 제공하는 범위만 지원하며,
OS 종료 알림은 이 플러그인의 이벤트가 아닙니다.

## 전원 상태 변경 구독

`power.statusChanged`의 payload는 `power.getStatus()`와 같은 `PowerStatus`입니다.
화면 정책의 events에 `power.statusChanged`, host.permissions에 `power.getStatus`를 모두
허용해야 합니다. 구독한 현재 세션에만 전달합니다. 두 호출 사이의 변경을 놓치지 않도록
먼저 구독한 뒤 `getStatus()`로 초기 값을 조회합니다.

```ts
const stop = await client.listen("power.statusChanged", ({ payload: status }) => {
  console.log(status.source, status.batteryPercent, status.charging);
}, { onError(error) { console.error(error); } });
const initial = await power.getStatus();
console.log(initial.source, initial.batteryPercent, initial.charging);
// 컴포넌트 정리 때 호출합니다.
await stop();
```

Windows가 전원 상태 변경을 알리거나 절전에서 복귀하면 GetSystemPowerStatus를 다시 읽고,
직전에 알린 값과 다를 때만 이벤트를 보냅니다. 같은 값은 보내지 않습니다.
Windows가 알리지 않는 변경은 감지를 보장하지 않으며, 예를 들어 남은 시간 추정값의
작은 변화는 다음 알림이 올 때까지 반영되지 않을 수 있습니다.
macOS에서는 이 이벤트를 발생시키지 않습니다.

읽기 실패는 기존 값을 유지하고 호스트 진단에 기록합니다. 다음 알림에서 다시 시도합니다.
구독 해제와 문서 이동 뒤에는 이전 세션으로 이벤트를 보내지 않습니다. 플러그인 종료 때
네이티브 구독을 먼저 해제한 뒤 request handle과 DLL을 정리합니다.
실제 AC 연결과 분리 같은 하드웨어 전환은 수동 검증 대상입니다.

## 절전과 화면 잠금 이벤트

`power.suspended`, `power.resumed`, `power.sessionLocked`, `power.sessionUnlocked`는
Electron powerMonitor의 `suspend`, `resume`, `lock-screen`, `unlock-screen`에 대응합니다.
payload는 모두 빈 객체입니다. 권한과 구독 모델은 `power.statusChanged`와 같아서 화면 정책의
events에 받을 이벤트를, host.permissions에 `power.getStatus`를 허용해야 합니다.

```ts
const stop = await client.listen("power.sessionLocked", () => {
  console.log("화면이 잠겼습니다.");
}, { onError(error) { console.error(error); } });
// 컴포넌트 정리 때 호출합니다.
await stop();
```

suspend와 resume은 Windows 전원 브로드캐스트(`PBT_APMSUSPEND`, `PBT_APMRESUMEAUTOMATIC`)를
따릅니다. 잠금과 해제는 WTS 세션 알림(`WTS_SESSION_LOCK`, `WTS_SESSION_UNLOCK`)이며,
앱을 실행한 프로세스의 세션 잠금만 알립니다. 다른 세션의 잠금은 알리지 않습니다.
다음 이벤트 전달 전에 같은 신호가 연속으로 쌓이면 하나로 합치고, 서로 다른 신호는 받은 순서대로 보냅니다.
resume 때 `power.resumed`와 `power.statusChanged`가 함께 나갈 수 있으며 두 이벤트의 상대 순서는 보장하지 않습니다.
`power.suspended`는 절전 전에 앱이 작업을 끝낼 수 있음을 보장하지 않으며 복귀 뒤에 도착할 수 있습니다.
로그온 직후 등(예를 들어 Terminal Services가 준비되기 전) 잠금 알림 등록이 실패하면 호스트 진단에
기록하고 5초 간격으로 2분까지 다시 등록합니다. 계속 실패하면 진단을 한 번 더 남기고
`power.sessionLocked`와 `power.sessionUnlocked`는 발생하지 않습니다. 조회, blocker와
`power.suspended`, `power.resumed`는 계속 동작합니다.
구독 전의 상태는 replay하지 않으며 현재 잠금 여부를 조회하는 API는 없습니다.
macOS에서는 이 이벤트를 발생시키지 않습니다.
구독 해제와 플러그인 종료 뒤에는 이벤트를 보내지 않습니다.

## 절전과 화면 유지 요청

`power.startBlocker({ type, reason })`는 `{ id, type }`를 반환합니다.
type이 system이면 시스템 idle 절전 방지 요청을, display이면 화면 유지와 시스템 idle
절전 방지 요청을 함께 등록합니다. reason은 사용자에게 설명할 1–512 Unicode 코드 포인트
문자열이며 NUL을 허용하지 않습니다. Windows의 power request 진단과 macOS의 assertion 이름
(`pmset -g assertions`)에 표시됩니다.
예를 들어 `😀`는 한 코드 포인트이며 512개까지 허용합니다.
요청 최대 개수는 앱당 128개이고 초과하면 `BUSY`입니다.
같은 type과 reason을 반복해도 새 ID와 독립 native handle을 만듭니다.

macOS에서 system은 `PreventUserIdleSystemSleep`, display는 `PreventUserIdleDisplaySleep`
IOPMAssertion을 만듭니다. 플러그인 정리는 남은 assertion을 모두 해제합니다.

`power.listBlockers()`는 이 앱 어댑터가 등록한 `{ id, type }` 배열을 반환합니다.
`power.isBlockerActive({ id })`는 이 어댑터에 해당 요청이 등록돼 있는지 반환합니다.
`power.stopBlocker({ id })`는 해제했다면 true, 없거나 이미 해제한 ID면 false입니다.
ID는 UUID이며 native handle이 아닙니다. 조회와 stop 권한은 별도이고 같은 앱의
허용된 호출자들이 요청을 관리합니다. OS의 다른 프로세스 요청은 조회하거나 해제하지 않습니다.

블로커 조회는 앱의 등록 상태를 나타냅니다. OS가 실제로 절전을 막고 있는지 보장하지 않습니다.
사용자가 선택한 절전과 전원 정책은 유지되며 Modern Standby의 배터리 정책으로 요청이
종료될 수도 있습니다. Windows에서는 OS가 요청 count를 종료해도 stop이 handle을 정리합니다.
앱 종료와 어댑터 dispose는 모든 handle 해제를 시도합니다. public ID가 있는 요청의 해제가
실패해도 부분 활성화에서 남은 handle 정리를 함께 시도합니다. 실패를 모아 보고하고 실패한
handle은 다음 정리 시도까지 보유합니다. 남은 handle이 있으면 request를 해제하는 라이브러리(Windows는 DLL,
macOS는 IOKit)를 닫지 않습니다.
프로세스 종료에서는 OS가 남은 프로세스 자원을 회수합니다.

권한 거부는 `PERMISSION_DENIED`, 잘못된 입력은 `INVALID_ARGUMENT`, OS 조회와 요청
생성 또는 정리 실패는 `INTERNAL`입니다. 닫힌 호출 컨텍스트와 종료 후 호출은 `CANCELLED`입니다.
부분 활성화 실패는 이미 등록한 요청과 handle을 정리하며 public ID를 반환하지 않습니다.
등록과 해제는 동기 OS 호출입니다. 요청을 취소해도 이미 완료한 등록을 되돌리지 않습니다.
결과 수신 전에 취소되면 허용된 백엔드가 listBlockers로 등록 상태를 복구하거나 앱 종료의
자동 정리로 해제합니다.

실제 하드웨어의 절전/화면 timeout 검증은 후속 작업입니다. macOS는 macOS CI에서 `pmset -g assertions`에
assertion이 나타나고 stop과 정리 뒤 사라지는지 확인합니다.
[Windows PowerSetRequest 계약](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest)을 따릅니다.
