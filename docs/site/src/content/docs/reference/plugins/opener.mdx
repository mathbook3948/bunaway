기본 export(`default`)를 `opener`로 가져와 앱에 등록하고 호출합니다.

```ts
opener.openUrl(url: string, options?: NativeInvokeOptions): Promise<null>
opener.openFile(path: string, options?: NativeInvokeOptions): Promise<null>
opener.revealFile(path: string, options?: NativeInvokeOptions): Promise<null>
opener.openFileWith(path: string, app: string, options?: NativeInvokeOptions): Promise<null>
opener.openUrlWith(url: string, app: string, options?: NativeInvokeOptions): Promise<null>
opener.getUrlHandler(url: string, options?: NativeInvokeOptions): Promise<{ name: string; path: string } | null>
opener.readShortcutLink(path: string, options?: NativeInvokeOptions): Promise<ShortcutLink>
opener.writeShortcutLink(path: string, details: ShortcutDetails, operation?: "create" | "update" | "replace", options?: NativeInvokeOptions): Promise<null>
```

`@bunaway/plugin-opener`를 설치하고 앱의 `plugins`에 `opener`를 등록합니다. 세 함수는 Windows와 macOS 어댑터를 제공합니다. macOS 네이티브 실행 검증은 현재 진행 중입니다.

```ts
import { defineApp } from "@bunaway/backend";
import opener from "@bunaway/plugin-opener";

export default defineApp({ modules: [], plugins: [opener] });
```

화면이나 앱 백엔드에서 세 함수를 호출합니다.

```ts
import opener from "@bunaway/plugin-opener";

await opener.openUrl("https://example.com/search?q=한글 값");
await opener.openFile("C:/Users/me/Documents/한글 보고서.txt");
await opener.revealFile("C:/Users/me/Documents/한글 보고서.txt");
```

`openFile`은 파일을 기본 연결 앱으로 엽니다. `revealFile`은 부모 폴더에서 해당 파일 하나를 선택하도록 Windows Explorer나 macOS Finder에 요청합니다. 성공한 `null` 결과는 OS가 요청을 접수했다는 뜻입니다. 브라우저나 기본 앱의 표시와 실행 완료, 파일 읽기 완료 또는 Explorer 선택 완료를 기다리지 않습니다.

## URL 입력

`url`은 절대 HTTP 또는 HTTPS 주소여야 합니다. 입력과 정규화된 URL은 각각 최대 8,192자입니다. 호스트 이름이 유효해야 하며 제어 문자, 역슬래시, 앞뒤 공백은 허용하지 않습니다. `file:`, `javascript:`와 임의 커스텀 스킴은 거부합니다.

경로와 쿼리에 공백이나 한글을 쓸 수 있습니다. 호출할 때 URL 규칙에 따라 정규화되고, 인코딩된 주소가 브라우저로 전달됩니다.

```ts
await opener.openUrl("https://example.com/도움말?q=검색어 입력");
```

## 파일 입력

Windows의 `path`는 드라이브부터 지정한 `C:\folder\file.txt` 또는 UNC 공유를 지정한 `\\server\share\file.txt`와 같은 절대 Windows 파일 경로여야 합니다. `/`를 `\`로 바꾸고 드라이브 문자를 대문자로 바꾸며, Unicode, 한글, 파일명 중간의 공백과 쉼표를 보존합니다. 최대 길이는 259 UTF-16 코드 단위이고 각 이름은 최대 255 단위입니다. 파일이 존재해야 하며 디렉터리는 거부합니다.

상대 경로, `C:file.txt` 같은 드라이브 상대 경로, `.`과 `..`, 중복 구분자, 제어 문자, 잘못된 Unicode, 예약 장치명, 이름 끝의 점이나 공백, alternate data stream, `\\?\`와 `\\.\` 장치 경로는 거부합니다. 파일과 부모 디렉터리는 파일 시스템의 실제 이름으로 지정해야 합니다. reparse point, junction, 심볼릭 링크, 하드 링크와 8.3 별칭을 통한 접근은 허용하지 않습니다.

권한 확인 뒤 파일을 읽기 접근으로, 부모 디렉터리를 조회 접근으로 검사합니다. 파일이 없으면 `INVALID_ARGUMENT`과 `details.reason: "FILE_NOT_FOUND"`를 반환합니다. 읽기나 조회 권한이 없거나 공유 잠금과 충돌하면 `PERMISSION_DENIED`입니다. OS 요청 제출 중에는 파일과 부모 핸들을 유지해 경로 교체를 막고 성공과 실패 모두에서 해제합니다.

macOS의 `path`는 `/Users/me/Documents/보고서.txt`처럼 절대 POSIX 경로입니다.
최대 길이는 259 UTF-16 코드 단위, 각 이름은 최대 255 UTF-8 바이트입니다. 상대 경로,
빈 이름, 중복 `/`, `.`과 `..`, 제어 문자와 잘못된 Unicode를 거부합니다. 읽을 수 있는
일반 파일이어야 하며 파일과 부모의 심볼릭 링크, 하드 링크를 허용하지 않습니다.
없는 파일과 접근 거부는 같은 오류 계약을 따릅니다. POSIX descriptor는 rename을 막지
않으므로 NSWorkspace 요청 직전에 파일 identity를 다시 확인해도 경로 교체 경쟁은 남습니다.
Windows 핸들의 고정 보장과 구분해야 합니다.

```ts
await opener.openFile("/Users/me/Documents/한글 보고서.txt");
await opener.revealFile("/Users/me/Documents/한글 보고서.txt");
```

## 휴지통

`opener.trashFile(path: string, options?: NativeInvokeOptions): Promise<null>`로 기존 파일 하나를 Windows 휴지통으로 보냅니다. `opener.trashFile` 권한을 허용하며 화면에서 직접 호출하려면 `plugin.opener.trashFile` 명령도 허용합니다. 입력은 다른 파일 작업과 같은 `{ path: string }`입니다.

```ts
await opener.trashFile("C:/Users/me/Documents/삭제할 파일.txt");
```

성공한 `null`은 Windows가 휴지통의 새 항목을 반환했음을 뜻합니다. 로컬 고정 드라이브만 지원하며 UNC 공유와 이동식 드라이브는 `UNSUPPORTED`입니다. 기존 경로, 읽기 권한, 링크와 별칭 검사를 적용합니다. 디렉터리를 받지 않고 HTML 파일의 연결된 `_files` 폴더도 삭제하지 않습니다. `FOFX_RECYCLEONDELETE`로 휴지통 이동을 요청하고 삭제 직전 콜백에 휴지통 플래그가 없으면 거부합니다. 프레임워크는 이동 실패를 일반 삭제로 재시도하지 않습니다. OS 오류나 중단, 휴지통 항목을 확인할 수 없는 결과는 실패로 반환합니다. 시스템의 영구 삭제 경고를 유지하므로 OS 설정에 따라 대화 상자가 표시될 수 있습니다. 콜백 플래그는 가능한 경우 휴지통 이동을 요청하며 OS 내부 실패 경로의 결과를 사전에 증명하지 않습니다. 휴지통 비활성화, 용량 초과와 경고 UI는 아직 검증하지 않았습니다. 사후 결과를 거부해도 이미 발생한 삭제를 복구할 수는 없습니다.

부모 핸들을 유지해 부모 경로 교체를 막습니다. 파일은 이동을 위해 삭제 공유를 허용하고 삭제 직전 파일 ID, 경로와 링크를 다시 검사합니다. 마지막 검사 뒤 다른 프로세스가 파일 자체를 교체하는 경쟁까지 막지는 못합니다. 앱의 파일별 승인이 파일 ID에 원자적으로 적용된다고 가정하지 마세요. 휴지통 이동은 I/O Worker에서 실행하며 취소나 기한 초과로 이미 진행된 이동을 되돌리지 않습니다. 복원 API는 제공하지 않습니다.

## 최근 문서

Windows 셸의 최근 항목(Recent Items)에 파일을 추가하거나 목록을 지웁니다.

- `opener.addRecentDocument(path: string, options?: NativeInvokeOptions): Promise<null>`은 기존 파일 하나를 사용자의 셸 최근 항목에 추가합니다. 입력은 `{ path: string }`이고 권한은 `opener.addRecentDocument`입니다.
- `opener.clearRecentDocuments(options?: NativeInvokeOptions): Promise<null>`은 `SHAddToRecentDocs(NULL)`을 호출해 **사용자의 셸 최근 항목 전체**를 지웁니다. 이 앱이 추가한 항목뿐 아니라 다른 앱과 사용자가 만든 항목도 포함하며 앱 범위로 제한할 수 없습니다. 입력은 `{}`이고 권한은 `opener.clearRecentDocuments`입니다. 사용자 데이터를 지우므로 사용자의 명시적 동작에만 연결하세요.

화면에서 직접 호출하려면 `plugin.opener.addRecentDocument`, `plugin.opener.clearRecentDocuments` 명령도 허용합니다.

```ts
await opener.addRecentDocument("C:/Users/me/Documents/보고서.txt");
await opener.clearRecentDocuments();
```

추가는 다른 파일 작업과 같은 경로 검사와 핸들 고정을 거친 뒤 opener의 I/O STA에서 `SHAddToRecentDocs(SHARD_PATHW)`를 호출합니다. 핸들 고정은 호출이 반환될 때까지만 유지되며, 셸이 그 뒤에 파일을 읽는 시점의 교체까지 막지는 않습니다. 삭제는 `SHAddToRecentDocs(NULL)`을 호출합니다. 이 API는 결과를 반환하지 않으므로 성공은 요청을 전달했다는 뜻이며, 사용자의 최근 항목 기록 설정에 따라 항목이 표시되지 않을 수 있습니다. 이 기능이 보장하는 것은 셸 최근 항목에 대한 추가와 삭제 요청뿐입니다. 앱 전용 최근 문서나 점프 목록 연결은 보장하지 않으며, 점프 목록과의 연결은 AppUserModelID 설정이 제공된 뒤의 별도 작업입니다. 목록 조회는 지원하지 않습니다. Windows는 앱별 최근 목록을 읽는 공식 API를 제공하지 않고, Recent 폴더의 `.lnk`는 앱별로 구분되지 않기 때문입니다. macOS는 `UNSUPPORTED`입니다.

Electron과 같이 호출 뒤 프로세스에 멀티스레드 COM 아파트(MTA)가 남을 수 있으며, opener는 그 상태에서도 정상 동작합니다. opener는 자신이 초기화한 STA만 종료 때 해제합니다.

최근 문서 작업의 오류는 다음과 같습니다.

| 오류 | 의미 |
| --- | --- |
| `INVALID_ARGUMENT` | 경로가 유효하지 않거나 파일이 없음(`details.reason`은 `FILE_NOT_FOUND`) |
| `PERMISSION_DENIED` | 작업 권한 없음, 파일 접근 거부나 링크 거부 |
| `CANCELLED` | 플러그인 종료(dispose) 뒤 호출, 또는 시작 전에 이미 중단된 호출 |

호스트는 승인 전에 취소된 작업을 실행하지 않으며, 이미 중단된 호출은 셸을 부르기 전에 실패합니다. 셸 호출은 동기이며 중간에 중단할 수 없으므로 취소와 기한 초과는 이미 전달한 요청을 되돌리지 않습니다.

## 정책

화면에서 직접 호출하려면 기존 뷰의 `commands`에 `plugin.opener.openUrl`을, `host.permissions`에 `opener.openUrl`을 추가합니다.

```json
{
  "commands": ["app.help", "plugin.opener.openUrl"],
  "host": { "permissions": ["opener.openUrl"] }
}
```

명령 핸들러에서 호출하면 원래 명령의 뷰 권한을 사용합니다. 플러그인 setup에서 호출하려면 루트 `backend.permissions`에 `opener.openUrl`을 추가합니다.

```json
{
  "backend": { "permissions": ["opener.openUrl"] }
}
```

설치나 플러그인 등록만으로 권한이 생기지 않습니다. 이 권한은 URL 대상을 제한하지 않으므로 허용된 호출자는 모든 HTTP와 HTTPS 주소를 열 수 있습니다.

파일 작업에는 각각 `opener.openFile`, `opener.revealFile` 작업 권한이 필요합니다. 화면 직접 호출은 뷰의 `commands`에 `plugin.opener.openFile`, `plugin.opener.revealFile`도 추가합니다. 예를 들어 뷰의 `host`를 다음과 같이 설정합니다.

```json
{
  "permissions": [
    "opener.openFile",
    "opener.revealFile"
  ]
}
```

setup에서 호출할 때는 같은 작업 이름을 루트 `backend.permissions`에 둡니다. 파일별 접근 제한은 앱 명령에서 검사하고 화면에는 그 명령만 허용합니다. `opener.openUrl`은 파일 권한을 부여하지 않습니다.

작업 권한은 유효한 파일 경로 전체에 적용하며 연결 앱의 동작을 격리하지 않습니다. 실행 파일과 셸 바로가기도 기본 동작으로 실행될 수 있으므로 앱 명령에서 신뢰하는 파일을 정합니다. 기본 연결 변경은 지원하지 않습니다.

## URL 처리 앱 조회

`opener.getUrlHandler(url)`은 URL의 scheme에 연결된 앱을 조회합니다. 입력은 `openUrl`과 같은 규칙의 HTTP 또는 HTTPS URL `{ url: string }`이고, 결과는 표시 이름 `name`과 실행 파일 경로 `path`를 담은 객체입니다. 처리 앱이 없으면 `null`입니다. 앱을 실행하거나 URL을 열지 않습니다.

```ts
const handler = await opener.getUrlHandler("https://example.com/");
if (handler) {
  console.log(handler.name, handler.path);
}
```

Windows만 지원하며 macOS는 `UNSUPPORTED`입니다. Windows는 `AssocQueryStringW`에 `ASSOCF_IS_PROTOCOL`을 지정해 표시 이름과 실행 파일 경로를 조회합니다. 이름이나 경로 조회가 실패하거나, 빈 값이거나, 최대 32,768 UTF-16 코드 단위를 넘거나, 제어 문자를 포함하면 모두 `null`입니다. Electron과 Chromium처럼 실패 코드를 구분하지 않습니다. 오류는 입력이 잘못된 `INVALID_ARGUMENT`와 플러그인 종료 뒤 호출의 `CANCELLED`뿐입니다. 아이콘은 반환하지 않습니다. 호출은 I/O Worker에서 동기로 실행하므로 시작 전에 취소된 호출만 막고, 진행 중인 조회는 중단하지 않습니다.

실행 파일 경로가 노출되므로 권한은 `opener.getUrlHandler`이며 `opener.openUrl`과 별개입니다. 화면 직접 호출에는 `plugin.opener.getUrlHandler` 명령도 허용합니다. 연결 앱은 사용자 설정에 따라 달라지므로 결과를 기본 브라우저 판별이나 보안 판단에 쓰지 마세요.

## Windows 바로가기

`opener.readShortcutLink(path, options?)`는 Windows 바로가기 파일(`.lnk`)의 속성을 읽고, `opener.writeShortcutLink(path, details, operation = "create", options?)`는 바로가기를 만들거나 바꿉니다. Electron `shell.readShortcutLink`, `shell.writeShortcutLink`에 대응하며 Windows만 지원합니다(macOS는 `UNSUPPORTED`).

```ts
await opener.writeShortcutLink("C:\\Users\\me\\Desktop\\App.lnk", {
  target: "C:\\Program Files\\App\\app.exe",
  cwd: "C:\\Program Files\\App",
  args: "--start",
  description: "App",
  icon: "C:\\Program Files\\App\\app.ico",
  iconIndex: 0,
});
const link = await opener.readShortcutLink("C:\\Users\\me\\Desktop\\App.lnk");
```

속성은 `target`, `cwd`, `args`, `description`, `icon`, `iconIndex`입니다. 읽기 결과는 항상 여섯 속성을 모두 담고, 설정하지 않은 문자열은 빈 문자열, `iconIndex`는 0입니다. `target`, `cwd`, `icon`은 존재하지 않아도 되는 절대 Windows 경로이며(`%`로 시작하는 환경 변수 경로는 절대 경로가 아니라서 받지 않습니다), `args`는 2,048 UTF-16 코드 단위, `description`은 260 코드 단위(Shell이 보존하는 길이이며 더 긴 값은 조용히 잘리므로 거부합니다) 이하이고 제어 문자를 받지 않습니다. 읽기는 `GetPath(SLGP_RAWPATH)`로 저장된 경로를 그대로 반환하며 대상을 찾거나 실행하지 않습니다.

`operation`은 Electron과 같습니다. `create`(기본)는 새 바로가기를 쓰거나 같은 경로의 기존 바로가기를 덮어쓰고, `replace`는 기존 바로가기를 덮어쓰며 파일이 없으면 실패합니다. 두 작업은 빈 바로가기에서 시작하므로 `target`이 필요합니다. `update`는 기존 바로가기를 읽어 입력에 있는 속성만 바꿉니다(`cwd`와 `icon`에 빈 문자열을 주면 해당 속성을 비웁니다. `iconIndex`는 바뀌지 않으므로 함께 0으로 지정하세요. `target`은 비울 수 없고, 읽기 결과를 그대로 다시 쓰면 원시 경로나 빈 `target`이 검증에서 거부될 수 있습니다)(`icon`과 `iconIndex` 중 하나만 주면 다른 하나는 유지). AppUserModelID와 toast activator는 지원하지 않습니다.

경로는 `.lnk`로 끝나는 절대 경로여야 하고 부모 디렉터리는 만들지 않습니다. 파일 작업과 같은 검사를 적용합니다. 부모와 기존 파일을 핸들로 고정하고 reparse point, junction, 심볼릭 링크, 하드 링크, 8.3 별칭과 정규 철자가 아닌 경로를 `PERMISSION_DENIED`로 거부합니다. 새 파일을 만드는 `create`는 마지막 이름을 고정할 수 없어, 검사 뒤 그 이름에 링크가 생기는 경쟁은 막지 못합니다. 없는 파일과 부모는 `INVALID_ARGUMENT`와 `details.reason: "FILE_NOT_FOUND"`, 바로가기가 아닌 파일은 `INVALID_ARGUMENT`와 `details.reason: "NOT_A_SHORTCUT"`입니다(바로가기가 아닌 파일은 덮어쓰기 전에 `update`에서 거부하지만, `create`와 `replace`는 검사 없이 `.lnk` 파일을 덮어씁니다). Shell이 거부한 쓰기는 `INTERNAL`입니다. 호출은 COM 호출이 끝날 때까지 동기로 실행하므로 취소는 시작 전에만 적용합니다.

권한은 `opener.readShortcutLink`와 `opener.writeShortcutLink`이며 서로, 그리고 `openFile` 계열 권한과 별개입니다. 입력은 각각 `{ path }`와 `{ path, operation, details }`이고 결과는 속성 객체와 `null`입니다. 쓰기는 사용자가 실행할 대상을 만드는 작업이므로 앱 명령에서 경로와 대상을 제한하세요. 화면 직접 호출에는 `plugin.opener.readShortcutLink`, `plugin.opener.writeShortcutLink` 명령도 허용합니다.

## 지정 앱으로 열기

지정 앱 함수는 Windows 전용이며 macOS에서는 제공하지 않습니다. `opener.openFileWith(path, app)`과 `opener.openUrlWith(url, app)`은 지정한 Windows 실행 파일에 대상 하나를 전달합니다. `app`은 절대 `.exe` 경로여야 하며 위의 파일 경로, 실제 이름과 링크 검사 규칙을 따릅니다. 셸 명령, `.cmd`, `.bat`, `.lnk`, 별도 실행 인자는 받지 않습니다. 파일 대상은 `openFile`과 같은 검사를, URL은 `openUrl`과 같은 HTTP/HTTPS 검사를 받습니다.

```ts
import opener from "@bunaway/plugin-opener";

await opener.openFileWith("C:/Documents/한글 보고서.txt", "C:/Apps/editor.exe");
await opener.openUrlWith("https://example.com/도움말", "C:/Apps/browser.exe");
```

각각 `opener.openFileWith`, `opener.openUrlWith` 권한이 필요합니다. 화면에서 직접 호출하면 뷰의 `commands`에도 `plugin.opener.openFileWith`, `plugin.opener.openUrlWith`를 허용합니다. 기존 opener 권한은 두 작업을 허용하지 않습니다. 입력은 각각 `{ path, app }`, `{ url, app }`이고 결과는 `null`입니다.

지정 앱 경로도 현재 호출자의 권한으로 검사합니다. 파일 작업은 앱과 대상의 핸들을 함께 유지하고, URL 작업은 앱의 핸들을 유지한 채 Explorer에 요청합니다. 대상은 Windows argv 규칙으로 인코딩한 단일 인자이므로 공백, 한글과 URL fragment의 따옴표를 보존합니다. 임의 실행 파일을 지정할 수 있는 권한이므로 앱 명령에서 허용할 실행 파일과 대상을 검사하세요. 지정 앱이 대상 인자를 어떻게 처리할지는 그 앱이 결정합니다.

성공은 Explorer의 실행 요청 접수이며 지정 앱의 실행, 대상 표시나 읽기 완료를 보장하지 않습니다. 실행은 Explorer에 위임하므로 앱의 종료용 Job을 상속하지 않습니다. 기존 기본 연결은 변경하지 않으며, 이미 접수한 요청은 취소로 되돌리지 않습니다. 경로 검사와 동기 OS 오류는 아래의 공통 오류 계약을 따릅니다.

화면 호출은 `signal`과 절대 시각 `deadline`을 `options`로 전달할 수 있습니다. 호출 취소와 기한은 [invoke](/reference/client/invoke/) 규칙을 따릅니다. 백엔드 호출은 현재 명령의 취소와 기한을 이어받으며 별도 `options`를 받지 않습니다.

## 결과와 오류

`null`은 Windows Explorer가 브라우저 실행 요청을 접수했음을 나타냅니다. 실행에는 접근 가능한 Explorer 데스크톱이 필요합니다. Explorer가 브라우저를 실행하므로 브라우저는 앱의 종료용 Job을 상속하지 않고, 앱 종료나 개발 재시작 뒤에도 유지됩니다. 브라우저 프로세스나 페이지 상태는 추적하지 않으며 취소된 호출을 되돌리지 않습니다.

`openFile`도 Explorer에 실행을 위임해 기본 연결 앱이 앱의 종료용 Job을 상속하지 않게 합니다. `revealFile`은 경로를 셸 명령 문자열에 붙이지 않고 파일 식별자를 OS에 전달합니다. 접수 이후의 파일 소실, 연결 앱 부재, 앱 내부 실패와 화면 변경은 반환 결과에 포함하지 않습니다. OS 호출을 진행하는 동안 취소나 기한 초과가 발생해도 OS 작업은 반환할 때까지 계속될 수 있습니다. 파일 검사와 셸 요청은 I/O Worker에서 실행하므로 UNC 공유와 셸 확장의 응답이 느려도 이 작업이 UI Worker를 막지 않습니다. I/O Worker의 후속 작업과 정리는 OS 호출이 끝날 때까지 지연될 수 있습니다. 호스트 승인 전에 취소된 대기 작업은 실행하지 않습니다.

macOS는 NSWorkspace에 URL과 파일을 열도록 요청하고 Finder에 선택을 요청합니다.
참인 접수 결과만 `null`로 반환하며 거부되면 `INTERNAL`입니다. 기본 앱 표시, 파일 읽기,
URL 페이지 로딩과 Finder의 실제 선택 완료는 기다리지 않습니다. 파일 검사와 NSWorkspace
호출은 같은 I/O Worker에서 실행하고 각 요청의 autorelease pool을 정리합니다. 앱의 직접
자식으로 연결 앱을 실행하거나 셸 명령을 만들지 않습니다. 접수한 작업은 취소나 종료로
되돌리지 않습니다.

Host operation은 `opener.openUrl`, `opener.openFile`, `opener.revealFile`, `opener.trashFile`, `opener.addRecentDocument`, `opener.clearRecentDocuments`, `opener.getUrlHandler`, `opener.readShortcutLink`, `opener.writeShortcutLink`입니다. 입력은 URL 작업에서 `{ url: string }`, 파일 작업에서 `{ path: string }`, `opener.clearRecentDocuments`에서 `{}`입니다. `opener.readShortcutLink`는 `{ path: string }`을, `opener.writeShortcutLink`는 `{ path, operation, details }`를 받습니다. `opener.getUrlHandler`는 `{ name, path }` 또는 `null`을, `opener.readShortcutLink`는 바로가기 속성 객체를, 나머지는 `null`을 반환합니다.

| 오류 | 의미 |
| --- | --- |
| `INVALID_ARGUMENT` | URL이나 파일 경로가 유효하지 않거나 디렉터리 입력, 파일 소실. 파일 소실은 `details.reason`이 `FILE_NOT_FOUND`, `update`와 읽기 대상이 바로가기가 아니면 `NOT_A_SHORTCUT` |
| `PERMISSION_DENIED` | 작업 권한 없음, OS 파일 접근 거부, 공유 잠금 충돌, 링크나 경로 별칭 거부 |
| `UNSUPPORTED` | 현재 플랫폼이나 실행 환경에서 기능을 지원하지 않음 |
| `INTERNAL` | 파일 검사 실패, Explorer 데스크톱 접근 실패, Shell의 바로가기 쓰기 거부 또는 다른 OS 요청 실패 |
| `CANCELLED`, `TIMEOUT` | 호출이 취소되었거나 기한을 넘김 |

닫힌 앱의 플러그인 자원은 앱 종료 과정에서 정리합니다. 자세한 패키지 계약과 Windows 검증 방법은 [`@bunaway/plugin-opener` README](https://github.com/mathbook3948/bunaway/tree/main/plugins/opener)를 참고하세요.
