기본 export(`default`)를 `image`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-image`를 설치하고 `image`를 앱의 `plugins`에 등록합니다.
화면과 앱 백엔드는 같은 `image` API를 사용합니다(`image.createFromPath`만 백엔드 전용). Windows와 macOS arm64에서 제공합니다. macOS Intel은 지원하지 않습니다.

```ts
import { defineApp } from "@bunaway/backend";
import image from "@bunaway/plugin-image";

export default defineApp({ modules: [], plugins: [image] });
```

## 생성과 조회

| 함수 | 입력 | 결과 | 권한 |
| --- | --- | --- | --- |
| `image.createRGBA` | `{ width, height, rgba }` | `{ id, width, height, empty }` | `image.createRGBA` |
| `image.createBytes` | `{ mime, data }` | `{ id, width, height, empty }` | `image.createBytes` |
| `image.createDataURL` | `{ url }` | `{ id, width, height, empty }` | `image.createDataURL` |
| `image.getInfo` | `{ id, scaleFactor? }` | `{ width, height, empty, scaleFactor? }` | `image.getInfo` |
| `image.getPixels` | `{ id, scaleFactor? }` | `{ width, height, rgba }` | `image.getPixels` |

모든 함수는 Promise를 반환합니다. `id`는 opaque UUID이며 네이티브 pointer나 파일 경로가
아닙니다. 리소스는 앱 수명에 속하고 권한을 받은 화면이나 백엔드끼리 ID를 전달할 수 있습니다.
작업별 권한으로 앱 전체의 해당 image operation을 허용하며 특정 ID의 접근 제한은 앱 명령에서
검사합니다. 등록만으로 권한을 얻지 않습니다.

`width`와 `height`는 0부터 4,096까지의 정수입니다. 빈 이미지는 0×0과 빈 `rgba` 문자열만
허용합니다. 양수 크기의 `rgba`는 행을 위에서 아래로 이어 붙인 RGBA 8-bit 픽셀의 canonical
base64이며 한 픽셀은 빨강, 초록, 파랑, alpha 순서의 4바이트입니다. Premultiplied alpha를
사용하지 않으며 `width * height * 4`는 524,288바이트까지입니다. 예를 들어 512×256 이미지는
상한에 해당합니다. 사용하지 않는 base64 padding bit도 0이어야 합니다.

```ts
import image from "@bunaway/plugin-image";

const resource = await image.createRGBA({ width: 1, height: 1, rgba: "/wAAgA==" });
const info = await image.getInfo({ id: resource.id });
const pixels = await image.getPixels({ id: resource.id });
```

`mime`은 `image/png`, `image/jpeg` 또는 `image/bmp`입니다. `data`는 해당 이미지 파일의
canonical base64이며 디코딩한 파일 bytes는 600,000바이트까지입니다. 파일 경로, URI와
임의의 decoder 이름을 받지 않습니다. `url`은 같은 세 MIME의 `data:<mime>;base64,<data>`
형식만 받으며 네트워크 요청을 수행하지 않습니다. MIME과 실제 파일 형식이 다르거나 네이티브 codec이
여러 frame으로 판단한 입력, 지원 크기를 벗어난 decode 결과는 거부합니다.

bytes와 data URL은 Windows의 Windows Imaging Component 또는 macOS의 ImageIO로 디코딩합니다. 픽셀은 복사해 보유하며
색상 profile, EXIF metadata와 orientation 처리는 제공하지 않습니다. 파일 bytes의 확보는
앱이 기존 저장소 권한으로 수행합니다. 이 플러그인은 저장소 scope를 추가하지 않습니다.

## 내보내기와 해제

| 함수 | 입력 | 결과 | 권한 |
| --- | --- | --- | --- |
| `image.exportBytes` | `{ id, format, scaleFactor? }` | `{ mime, data }` | `image.exportBytes` |
| `image.exportDataURL` | `{ id, format, scaleFactor? }` | data URL 문자열 | `image.exportDataURL` |
| `image.dispose` | `{ id }` | 처음 해제하면 `true`, 이미 없으면 `false` | `image.dispose` |

`format`도 `image/png`, `image/jpeg` 또는 `image/bmp`입니다. PNG는 alpha를 보존합니다.
JPEG와 BMP는 모든 픽셀의 alpha가 255일 때만 내보냅니다. 투명 픽셀에 배경색을 임의로
적용하지 않습니다. JPEG는 플랫폼 codec의 기본 품질로 인코딩하며 픽셀 값은 손실될 수 있습니다.
빈 이미지는 픽셀 조회와 해제는 가능하지만 인코딩할 수 없습니다. encoded 결과도
600,000바이트까지이며 파일 bytes의 base64 또는 해당 data URL을 반환합니다.

```ts
try {
  const png = await image.exportBytes({ id: resource.id, format: "image/png" });
  const restored = await image.createBytes(png);
  try {
    const url = await image.exportDataURL({ id: restored.id, format: "image/png" });
  } finally {
    await image.dispose({ id: restored.id });
  }
} finally {
  await image.dispose({ id: resource.id });
}
```

앱은 최대 64개 리소스와 합계 8 MiB의 RGBA 픽셀을 보유합니다. 빈 이미지도 슬롯을
사용합니다. 상한에 도달하면 `BUSY`이며 사용하지 않는 리소스를 해제한 뒤 다시 생성할 수
있습니다. 해제 뒤 조회나 인코딩은 `INVALID_ARGUMENT`입니다. 새 리소스는 새 ID를 받습니다.
앱 종료는 모든 픽셀 버퍼와 네이티브 codec 자원을 정리하며 재시작 뒤 이전 ID를 복구하지 않습니다.

## Crop과 resize

| 함수 | 입력 | 결과 | 권한 |
| --- | --- | --- | --- |
| `image.crop` | `{ id, x, y, width, height }` | 새 `{ id, width, height, empty }` | `image.crop` |
| `image.resize` | `{ id, width, height, interpolation? }` | 새 `{ id, width, height, empty }` | `image.resize` |

두 함수는 Promise를 반환하며 소스 이미지와 분리된 새 리소스를 만듭니다. 소스의 크기,
픽셀과 ID는 바꾸지 않습니다. 결과 ID는 다른 생성과 같은 64개, 8 MiB quota를 사용하고
앱이 명시적으로 해제합니다. 요청 취소와 앱 종료의 정리도 생성과 같습니다.

`crop`의 `x`, `y`는 왼쪽 위부터 센 0 이상의 정수 픽셀 좌표이며 `width`, `height`는
1 이상의 정수입니다. 영역 전체가 소스 안에 있어야 합니다. 범위를 벗어나면
`INVALID_ARGUMENT`이며 영역을 자동으로 줄이지 않습니다. Alpha와 픽셀 값을 그대로 복사합니다.

`resize`의 출력 크기는 각각 1부터 4,096까지이고 RGBA는 524,288바이트까지입니다.
폭과 높이를 둘 다 지정하며 종횡비를 자동으로 유지하지 않습니다. `interpolation`은
`nearest` 또는 `linear`이고 생략하면 `linear`입니다. Nearest는 출력 픽셀 중심을 소스
좌표로 비례 변환한 뒤 좌표를 내림해 선택합니다. 선택한 RGBA 네 바이트를 직접 복사하므로
투명 픽셀의 RGB도 보존합니다. Linear는 Windows의 WIC scaler 또는 macOS의 CoreGraphics에서 premultiplied alpha로 보간한 다음
다시 straight RGBA로 변환해 투명 edge의 색 번짐을 방지합니다. 8-bit 변환의 반올림으로
채널 값이 달라질 수 있고 완전히 투명한 픽셀의 RGB는 0으로 정규화될 수 있습니다.
빈 이미지와 해제한 ID는 두 transform의 소스로 사용할 수 없습니다.

```ts
const cropped = await image.crop({ id: resource.id, x: 0, y: 0, width: 1, height: 1 });
try {
  const resized = await image.resize({ id: cropped.id, width: 2, height: 2, interpolation: "nearest" });
  try {
    const pixels = await image.getPixels({ id: resized.id });
  } finally {
    await image.dispose({ id: resized.id });
  }
} finally {
  await image.dispose({ id: cropped.id });
}
```

Transform은 항상 소스의 기준 표현(scale factor 1)에 적용되고 representation이 없는 독립 리소스를 반환합니다.

## Scale-factor representation

| 함수 | 입력 | 결과 | 권한 |
| --- | --- | --- | --- |
| `image.addRepresentation` | `{ id, scaleFactor, source }` | `{ representations: [{ scaleFactor, width, height }] }` | `image.addRepresentation` |
| `image.getRepresentations` | `{ id }` | `{ representations: [{ scaleFactor, width, height }] }` | `image.getRepresentations` |

`id`의 픽셀은 scale factor 1인 기준 표현입니다. `addRepresentation`은 같은 앱이 가진 다른 리소스
`source`(`id` 자신은 불가)의 픽셀을 `id`의 `scaleFactor` 표현으로 붙입니다. `scaleFactor`는 0보다 크고 4 이하인
유한 수이며 1은 기준 표현이라 쓸 수 없습니다. 같은 `scaleFactor`는 교체합니다. 표현의 폭과 높이는
기준 크기에 `scaleFactor`를 곱한 값의 내림 또는 올림이어야 하며 어긋나거나 빈 이미지가 끼면
`INVALID_ARGUMENT`입니다. 리소스당 기준 외 표현은 8개까지이고 넘으면 `BUSY`입니다.
표현의 픽셀은 소스와 같은 버퍼를 참조하지만 8 MiB 풀에는 따로 합산되며 초과하면 `BUSY`입니다.
소스를 해제해도 이미 붙인 표현은 남고, `dispose`는 표현을 함께 해제합니다.
`getRepresentations`는 기준을 포함해 `scaleFactor` 오름차순으로 돌려주며 빈 이미지는 빈 배열입니다.

`getInfo`, `getPixels`, `exportBytes`, `exportDataURL`은 선택 입력 `scaleFactor`(0 초과 4 이하,
생략하면 1)를 받아 표현을 고릅니다. 요청과 정확히 같은 표현이 있으면 그것, 없으면 요청보다 큰
표현 중 가장 작은 것, 그것도 없으면 가장 큰 표현입니다. 픽셀은 다시 샘플링하지 않으며
결과는 고른 표현의 픽셀 크기와 픽셀입니다. `getInfo`는 `scaleFactor`를 넘긴 경우 실제로 고른
`scaleFactor`도 돌려줍니다. 생략하면 기존과 같은 `{ width, height, empty }`입니다.
`crop`과 `resize`는 `scaleFactor`를 받지 않고 기준 표현에 적용합니다.

```ts
const logo1x = await image.createBytes({ mime: "image/png", data: png1x });
const logo2x = await image.createBytes({ mime: "image/png", data: png2x });
await image.addRepresentation({ id: logo1x.id, scaleFactor: 2, source: logo2x.id });
await image.dispose({ id: logo2x.id });
const info = await image.getInfo({ id: logo1x.id, scaleFactor: 1.5 }); // 2배 표현이 선택된다
```

## 파일 형식 아이콘

| 함수 | 입력 | 결과 | 권한 |
| --- | --- | --- | --- |
| `image.createFileTypeIcon` | `{ extension, size }` | 새 `{ id, width, height, empty }` | `image.createFileTypeIcon` |

`extension`은 점으로 시작하는 1~31자의 확장자(예: `.txt`)입니다. 영문자, 숫자, `_`, `-`, `+`, `~`만
허용하며 경로 구분자, NUL, 공백, `:`, 추가 점은 `INVALID_ARGUMENT`입니다. `size`는
`small`(16), `normal`(32), `large`(48) 중 하나이고 값은 100% 배율의 픽셀 크기입니다. 화면 배율이
높으면 Windows는 셸 아이콘 목록의 크기를 따라 더 큰 정사각형 이미지를 반환할 수 있으므로 실제 크기는
결과의 `width`, `height`를 사용하세요. macOS는 항상 요청한 크기의 정사각형입니다.

Windows는 셸에 등록된 확장자의 연결 아이콘을 `SHGFI_USEFILEATTRIBUTES`로 조회합니다.
디스크의 파일이나 경로를 열지 않으므로 저장소 권한이 필요하지 않고 존재하지 않는 확장자도
기본 문서 아이콘을 반환합니다. 실제 파일 경로, UNC 경로와 파일 이름은 받지 않습니다.
Electron의 `app.getFileIcon`은 실제 경로를 받아 임의 경로에 접근할 수 있지만 이 API는
확장자만 받아 접근 범위를 줄였습니다. 결과는 straight RGBA이고 alpha 채널이 없는 아이콘은
마스크로 투명도를 복원합니다. 결과 ID는 다른 생성과 같은 64개, 8 MiB quota와 명시적
`image.dispose`, 생성 취소 규칙을 따릅니다.

macOS arm64는 `NSWorkspace`의 `iconForFileType:`으로 확장자에 등록된 형식의 아이콘을 조회하고,
요청한 크기의 정사각형으로 그려 straight RGBA로 반환합니다. 파일을 열지 않으므로 저장소
권한이 필요하지 않고, 등록되지 않은 확장자도 오류 없이 아이콘을 반환합니다. 요청보다 큰
표현이 선택되면 CoreGraphics의 낮은 품질 보간으로 줄이므로 작은 크기에서는 가장자리가 다소
거칠 수 있습니다.

```ts
const icon = await image.createFileTypeIcon({ extension: ".txt", size: "normal" });
try {
  const pixels = await image.getPixels({ id: icon.id });
} finally {
  await image.dispose({ id: icon.id });
}
```

## 파일에서 만들기

| 함수 | 입력 | 결과 | 권한 |
| --- | --- | --- | --- |
| `image.createFromPath` | `{ path, maxDimension? }` | 새 `{ id, width, height, empty }` | `image.createFromPath` (백엔드 전용) |

Windows에서 PNG, JPEG, BMP 파일을 읽어 새 리소스로 만듭니다. `createBytes`의 인코딩 상한(600,000바이트)과
이미지 상한(4,096, 524,288바이트)을 넘는 사진도 읽을 수 있도록, 디코드하면서 이미지 상한 안으로
축소합니다. 결과의 긴 변은 `maxDimension`(1부터 4,096까지의 정수, 기본 4,096) 이하이고 비율을 유지하며
원본보다 키우지 않습니다. 픽셀 수가 상한을 넘으면 `width * height * 4`가 524,288바이트 이하가 되도록
더 줄입니다. 작은 `maxDimension`으로 thumbnail을 만들 수 있습니다. 축소는 premultiplied alpha에서 하므로
투명한 가장자리의 색이 번지지 않습니다. 크기를 줄이지 않는 이미지는 premultiplied 변환을 거치지 않으므로 완전히 투명한 픽셀의 색도 유지하고,
줄이는 이미지는 premultiplied로 변환하므로 그 픽셀의 RGB가 0이 됩니다. 결과는 8비트 straight RGBA입니다.

- `path`는 `C:\` 같은 로컬 드라이브의 절대 경로이며 259자까지 받습니다. UNC, `\\?\`와 `\\.\` 접두사,
  `.`와 `..`, 예약된 장치 이름, `:`(대체 데이터 스트림)과 금지 문자는 `INVALID_ARGUMENT`입니다.
  경로는 문법만 검사합니다. 링크는 따라가고 연결된 네트워크 드라이브나 네트워크 공유를 가리키는 링크도 열 수 있으므로,
  어떤 폴더의 파일을 허용할지는 앱이 정합니다([ADR 0024](https://github.com/mathbook3948/bunaway/blob/main/docs/decisions/0024-plugin-path-responsibility.md)).
- 형식은 확장자가 아니라 파일 내용으로 판별합니다. 파일은 16 MiB까지이며 열린 파일의 크기를 읽기 전에
  확인합니다. 일반 파일이 아니거나(디렉터리, 장치) 없는 파일, 지원하지 않는 형식, 여러 프레임인 파일은
  `INVALID_ARGUMENT`입니다. 가로나 세로가 16,384를 넘거나 픽셀이 64,000,000개를 넘는 파일은 픽셀을
  디코드하기 전에 헤더 크기로 거부합니다.
- 이 작업은 **백엔드 전용**입니다. 정책의 `backend.permissions`에만 허용할 수 있고, 화면의
  `host.permissions`나 `commands`(`plugin.image.createFromPath`)에 넣으면 앱을 시작하거나 빌드할 때
  거부합니다. 화면은 앱 명령이 정한 경로로 이 함수를 호출한 백엔드 명령을 거쳐 결과 ID만 받습니다.
  Electron과 Tauri는 이 기능에 경로 scope를 두지 않으며, Tauri는 프런트엔드에 권한만 주면 호출을 허용합니다.
  이 작업은 그보다 좁게 앱 백엔드만 호출할 수 있습니다.
- 결과 ID는 다른 생성과 같은 64개, 8 MiB quota와 명시적 `image.dispose`, 생성 취소 규칙을 따릅니다.
  macOS는 아직 지원하지 않습니다. 입력 검사가 Windows 드라이브 경로만 받으므로 macOS에서 POSIX 경로는 `INVALID_ARGUMENT`, 드라이브 경로는 `UNSUPPORTED`입니다.
  셸의 파일 thumbnail 캐시(`IShellItemImageFactory`)는
  사용하지 않으며 파일을 직접 디코드합니다.

```ts
// 백엔드 명령 안에서, 앱이 정한 폴더의 경로만 넘깁니다.
const thumbnail = await image.createFromPath({ path: photoPath, maxDimension: 256 });
try {
  const png = await image.exportBytes({ id: thumbnail.id, format: "image/png" });
} finally {
  await image.dispose({ id: thumbnail.id });
}
```

## 정책, 취소와 오류

화면 직접 호출은 `commands`의 `plugin.image.<operation>`과 `host.permissions`의
`image.<operation>`을 각각 허용합니다. 백엔드 명령은 호출 출처의 권한을 유지하고 setup에서의
호출은 루트 `backend.permissions`를 따릅니다. 생성 권한은 조회, export나 해제를 허용하지 않습니다.

화면의 마지막 인자는 선택적인 `NativeInvokeOptions`이며 `signal`과 절대 `deadline`을 받습니다.
백엔드는 현재 명령의 취소와 기한을 이어받습니다. 호스트가 생성 작업을 완료하기 전에
요청이 취소되면 새 ID와 픽셀 버퍼를 버리고 quota를 복원합니다. 완료한 생성은 뒤늦은
화면 취소로 되돌리지 않습니다. 받은 ID의 수명은 정상 호출 완료와 창 탐색으로 끝나지
않으며 앱이 명시적으로 해제합니다. 네이티브 codec의 동기 decode/encode를 중간에 중단하지는 않습니다. `createFromPath`는 파일 읽기와 디코드를 UI 스레드에서 동기로 실행하므로 큰 파일이나 느린 네트워크 드라이브에서는 창이 그동안 응답하지 않을 수 있습니다.
취소된 결과는 호스트가 폐기하며 이미 실행한 명시적 해제는 되돌리지 않습니다.

| 오류 | 의미 |
| --- | --- |
| `INVALID_ARGUMENT` | 잘못된 크기, base64, MIME, encoded 입력, 없는 ID, 기준 크기와 맞지 않는 표현, 지원하지 않는 export 또는 읽을 수 없는 이미지 파일 |
| `PERMISSION_DENIED` | 해당 operation 권한이 없거나 운영체제가 파일 접근을 거부함 |
| `UNSUPPORTED` | 등록하지 않은 작업이나 지원하지 않는 플랫폼 |
| `BUSY` | 리소스 수, 리소스당 표현 8개 또는 앱 픽셀 메모리 상한에 도달함 |
| `INTERNAL` | 플랫폼 codec의 native 리소스 처리나 인코딩이 실패함 |
| `CANCELLED`, `TIMEOUT` | 요청 취소, 기한 초과 또는 앱 종료 |

소유권과 실제 플랫폼 회귀 범위는 [플러그인 README](https://github.com/mathbook3948/bunaway/tree/main/plugins/image)를 참고하세요.
