기본 export(`default`)를 `notification`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-notification`은 Windows toast 표시, 실행 중 이벤트, 알림 상태 조회와 설정 페이지 열기를 제공합니다.
패키지를 설치하고 `notification`를 등록한 다음 작업별 정책 권한을 허용하세요.

```ts
import { defineApp } from "@bunaway/backend";
import notification from "@bunaway/plugin-notification";

export default defineApp({ modules: [], plugins: [notification] });
```

## 상태 조회와 설정 열기

```ts
notification.getStatus(options?: NativeInvokeOptions): Promise<NotificationStatus>
notification.openSettings(options?: NativeInvokeOptions): Promise<null>
```

앱 명령이나 플러그인 setup에서 호출하면 현재 호출 컨텍스트의 권한과 취소를 사용합니다.
백엔드 호출은 별도 취소 signal이나 기한을 받지 않으며 현재 명령의 설정을 상속합니다.

```ts
import notification from "@bunaway/plugin-notification";

const status = await notification.getStatus();
if (status.support === "supported" && status.setting === "disabledForApplication") {
  // 사용자가 설정 열기를 선택했을 때 호출합니다.
  await notification.openSettings();
}
```

`getStatus`는 신뢰된 호스트 설정의 앱 ID를 사용합니다. 호출자가 다른 앱 ID를
선택할 수 없습니다. 상태 조회에는 이 ID로 등록된 시작 메뉴 바로가기와 같은 process
AppUserModelID가 필요합니다. Windows 호스트와 설치 바로가기는 이 ID를 사용합니다.
기존 알림 상태가 있는 같은 ID를 개발과 배포에서 쓰면 같은 Windows 설정을 조회합니다.
바로가기만으로 알림 상태가 초기화되지는 않습니다. 아직 알림을 보내지 않은 앱이나 등록이 없는
개발 실행, 바로가기를 만들지 않는 설치에서는 Windows가 `UNSUPPORTED`를 반환할 수 있습니다.
조회는 바로가기, toast activator나 앱 등록을 만들지 않습니다.
상태를 초기화하기 위한 알림도 보내지 않습니다. `show`를 명시적으로 호출하면 요청한 알림을 전송하며 OS 상태가 생길 수 있습니다.

## 결과와 OS 권한

`NotificationStatus`는 `support`, `appUserModelId`, `setting`을 반환합니다.
`support`는 toast API를 사용할 수 있으면 `supported`, 해당 WinRT 클래스나 인터페이스가
없으면 `unsupported`입니다. `unsupported`일 때 `setting`은 `null`입니다.
네이티브 기능 조회 플러그인의 지원 목록은 등록된 작업의 플랫폼 구현을 나타내며
사용자 차단 상태를 대신하지 않습니다.

`NotificationSetting`은 Windows가 직접 반환한 설정을 다음 값으로 나타냅니다.

| `setting` | 의미 |
| --- | --- |
| `enabled` | 조회한 Windows 설정에서 알림을 허용함 |
| `disabledForApplication` | 사용자가 이 앱의 알림을 끔 |
| `disabledForUser` | 사용자 또는 관리자가 현재 사용자의 모든 알림을 끔 |
| `disabledByGroupPolicy` | 그룹 정책이 알림을 차단함 |
| `disabledByManifest` | Windows가 앱 manifest의 toast 사용 선언 부족을 보고함 |
| `unknown` | 현재 구현이 모르는 Windows 설정 값 |

여러 차단이 있으면 Windows가 우선순위에 따라 하나를 반환합니다. 이 결과로 더 좁은
범위의 사용자 설정을 추정하지 마세요. 조회 실패는 오류이며 `enabled`로 바꾸지 않습니다.
`enabled`는 실제 알림 표시나 클릭 후 activation 성공을 보장하지 않습니다.
집중 지원과 일시적인 화면 표시 억제 상태도 이 API로 판별하지 않습니다.

현재 Windows 데스크톱 경로에는 알림 동의 팝업을 요청하는 API가 없습니다.
사용자는 Windows 설정에서 직접 허용 상태를 바꿉니다. 플러그인은 사용자 선택이나
그룹 정책을 변경하지 않습니다.

`openSettings`는 고정된 `ms-settings:notifications` 페이지를 열도록 OS에 요청합니다.
임의 URI나 앱별 설정 경로를 받지 않습니다. 성공은 요청 접수이며 페이지가 보였거나
권한을 허용했다는 뜻이 아닙니다. 설정 화면에서 돌아오면 `getStatus`를 다시 호출하세요.
OS에 해당 페이지나 처리 앱이 없거나 요청이 거부되면 오류를 반환합니다.

## 정책과 오류

| 작업 | 입력 | 권한 |
| --- | --- | --- |
| `notification.show` | `NotificationOptions` | `notification.show` |
| `notification.clear` | `NotificationIdentity` | `notification.clear` |
| `notification.clearAll` | `null` | `notification.clearAll` |
| `notification.getStatus` | `null` | `notification.getStatus` |
| `notification.openSettings` | `null` | `notification.openSettings` |

뷰에서 직접 호출하려면 `commands`에 `plugin.notification.getStatus` 또는
`plugin.notification.openSettings`를 추가하고 `host.permissions`에 해당 작업을 허용합니다.
명령 핸들러는 원래 뷰의 권한을 사용하며 setup은 루트 `backend.permissions`를 사용합니다.
설정 열기 권한은 상태 조회 권한과 독립입니다.

- `INVALID_ARGUMENT`: 작업 입력, 텍스트, 알림 식별자 또는 호스트 앱 ID가 유효하지 않습니다.
- `PERMISSION_DENIED`: 앱 정책, Windows 상태 조회나 설정 실행 권한이 없습니다.
- `UNSUPPORTED`: 플랫폼 어댑터나 호스트 앱 정보가 없거나 Windows가 상태 조회에 필요한
  앱의 OS 알림 상태를 찾지 못했거나 MSIX에서 상태를 조회했습니다. 바로가기 등록 후에도
  첫 알림 전에는 상태가 없을 수 있습니다. 플러그인은 상태를 자동으로 만들지 않습니다.
  MSIX 앱의 패키지 식별자 연동은 아직 제공하지 않습니다.
- `INTERNAL`: WinRT 초기화, 상태 조회나 설정 열기 요청이 실패했습니다.
- `CANCELLED`, `TIMEOUT`, `BUSY`: 기존 Host API의 취소, 기한과 대기열 제한입니다.

현재 Windows x64의 unpackaged 데스크톱을 지원합니다. macOS, Linux와 모바일
어댑터는 없습니다. 기존 설치의 시작 메뉴 바로가기 선택은 유지합니다.


## Toast 표시, 교체와 제거

```ts
notification.show(input: NotificationOptions, options?: NativeInvokeOptions): Promise<NotificationResult>
notification.clear(input: NotificationIdentity, options?: NativeInvokeOptions): Promise<null>
notification.clearAll(input: null, options?: NativeInvokeOptions): Promise<null>

await notification.show({
  id: "export-done",
  title: "내보내기 완료",
  body: "결과 파일을 확인하세요.",
  data: "export:42",
  silent: true,
});
// 같은 id와 group으로 다시 show하면 이전 알림을 교체합니다.
await notification.clear({ id: "export-done" });
```

| 입력 | 기본값과 제한 |
| --- | --- |
| `id` | 필수. 영문 대소문자, 숫자, `.`, `_`, `-`로 된 1~16자 |
| `group` | `bunaway`. id와 같은 문자와 길이 제한 |
| `title` | 필수. 1~256자 |
| `body` | 빈 문자열. 최대 2048자 |
| `data` | null. 최대 2048자의 앱 문자열이며 클릭 이벤트에만 포함 |
| `silent` | false. true이면 소리 억제 |
| `suppressPopup` | false. true이면 popup 대신 알림 기록으로 전달 |
| `icon` | null. 앱 로고 대신 표시할 이미지의 로컬 절대 경로 |
| `image` | null. 본문 이미지의 로컬 절대 경로 |
| `imagePlacement` | `inline`. `hero`이면 알림 상단 큰 이미지 |
| `sound` | null. Windows 시스템 소리 이름. 아래 목록 중 하나 |
| `soundLoop` | false. `Looping.*` 소리에서만 true 가능 |

`NotificationResult`는 `{ id, group }`입니다. 성공은 OS 접수이며 표시 완료나 사용자
확인을 뜻하지 않습니다. 제목과 본문은 XML escape하며 유효하지 않은 XML 문자는 거부합니다.
임의 XML, 실행 명령이나 activation URI는 받지 않습니다.
앱 ID는 호스트가 정하며 호출자가 다른 앱의 알림을 선택할 수 없습니다.
clear는 지정한 ID/group의 popup과 기록만 지웁니다. 같은 앱의 이전 프로세스가 남긴
해당 기록도 지울 수 있습니다. 존재 여부와 무관하게 성공 결과는 null입니다.

`notification.clearAll`은 입력 `null`로 같은 앱의 popup과 알림 센터 기록을 모두 지우고
null을 반환합니다. 이번 실행이 소유한 알림을 숨긴 뒤 호스트 앱 ID 범위의 기록 전체를 제거하므로
이전 프로세스가 남긴 기록도 지우며, 다른 앱의 알림은 건드리지 않습니다. 소유 중이던 항목은
모두 해제되어 늦게 온 callback은 버려지고 64개 한도도 비워집니다. 별도의 dismissed 이벤트는
보내지 않습니다. 실패하면 소유권을 유지하므로 다시 호출할 수 있습니다. Tauri의
`removeAllActive`와 같은 범위입니다. Electron `Notification`에는 대응하는 API가 없어
Tauri 기준으로 제공하며, `clearAll` 권한은 `clear`와 독립입니다.

동시에 최대 64개의 ID/group을 소유합니다. dismissed 후에도 후속 callback을 받기 위해
소유권을 유지하므로 끝난 항목은 clear하세요. 새 ID가 한도를 넘으면 `BUSY`이며 같은 ID
교체는 가능합니다. 종료 시 이번 실행의 알림과 callback을 정리합니다. 강제 종료는
정리를 보장하지 않으므로 다음 실행에서 알려진 ID/group을 clear할 수 있습니다.
정책과 취소는 네이티브 실행 직전에 검사합니다. Windows에 이미 전달한 show는 요청 취소로
자동 회수하지 않습니다. 회수하려면 clear를 호출하세요.

## 아이콘, 이미지와 소리

```ts
await notification.show({
  id: "build-done",
  title: "빌드 완료",
  icon: "C:\\Users\\me\\app\\icon.png",
  image: "C:\\Users\\me\\app\\preview.jpg",
  imagePlacement: "hero",
  sound: "Reminder",
});
```

`icon`과 `image`는 `C:\` 형식의 로컬 드라이브 절대 경로만 받습니다. 상대 경로, UNC 경로, URL,
`..` 구간, 제어 문자, 짝 없는 surrogate와 드라이브 문자 뒤의 `:`(NTFS 대체 데이터 스트림)는
거부합니다. 확장자는 Windows toast가 지원하는 `png`, `jpg`, `jpeg`, `gif`이고 파일은 `show` 시점에 읽을 수 있는
일반 파일이며 3,000,000바이트(Microsoft 문서의 3 MB) 이하여야 합니다.
`imagePlacement: "hero"`는 `image`가 있을 때만 지정할 수 있습니다.

파일에 접근하기 전에 다음 순서로 검사합니다. 네트워크 응답 지연으로 호스트 스레드가 멈추거나
링크를 통해 네트워크 공유에 접근하는 것을 막기 위한 검사입니다.

1. `GetDriveTypeW`로 드라이브 루트를 확인하여 고정 드라이브와 RAM 디스크만 허용합니다. 네트워크,
   이동식, 광학 드라이브와 종류를 알 수 없는 드라이브는 거부합니다.
2. 드라이브 루트 아래 경로 구성요소를 위에서부터 `GetFileAttributesW`로 확인합니다. 심볼릭 링크,
   정션, 클라우드 폴더 같은 reparse point를 만나면 따라가지 않고 거부합니다. 최종 파일도 같습니다.
3. 최종 파일이 offline 또는 열 때 내려받는(recall) 속성이면 거부하여 클라우드 파일을 내려받지 않습니다.
4. 마지막에 일반 파일 여부와 크기를 확인합니다.

조건을 어기면 `INVALID_ARGUMENT`이며 오류에 경로를 담지 않습니다. 남는 한계가 있습니다.
`subst`로 만든 드라이브는 대상 경로의 종류로 보고되므로 네트워크 공유를 가리키는 `subst` 드라이브는
가려내지 못합니다. 검사와 Windows의 파일 읽기 사이에 경로가 링크로 바뀌는 경우도 막지 못합니다.
검사 뒤에 파일이 바뀌거나 지워지면 Windows가 이미지 없이 표시할 수 있습니다.
Windows가 이미지를 읽을 수 있어야 하므로 앱 실행 사용자가 읽을 수 있는 위치에 두세요.
경로는 최대 259자(MAX_PATH 260에서 종료 NUL 제외)이지만 퍼센트 인코딩한 `file:///` URI는 비ASCII 문자 때문에 훨씬 길어질 수 있습니다.
URI 길이는 따로 검사하지 않으며 Windows가 너무 긴 값을 받지 않으면 이미지 없이 표시될 수 있습니다.

`sound`는 Windows 시스템 소리 이름만 받습니다. Windows 비패키지 앱은 임의 소리 파일을
재생할 수 없습니다. 사용할 수 있는 값은 `Default`, `IM`, `Mail`, `Reminder`, `SMS`,
`Looping.Alarm`, `Looping.Alarm2`~`Looping.Alarm10`, `Looping.Call`, `Looping.Call2`~`Looping.Call10`입니다.
`soundLoop: true`는 `Looping.*` 소리에서만 가능하며 그 밖에는 `INVALID_ARGUMENT`입니다.
`soundLoop: true`이면 toast에 `duration="long"`을 함께 지정해 알림이 길게 표시되는 동안 소리를 반복합니다.
반복은 알림이 사라질 때까지 이어진다고 보장하지 않으며 Windows 설정을 따릅니다.
`silent: true`와 `sound`를 함께 지정하면 `INVALID_ARGUMENT`입니다. 소리를 켜려면 `silent`를 생략하세요.
Windows 소리 설정이나 집중 지원이 소리를 막을 수 있습니다.

## 실행 중 이벤트와 activation 범위

| 이벤트 | 데이터 |
| --- | --- |
| `notification.clicked` | `{ id, group, data }` |
| `notification.dismissed` | `{ id, group, reason }` |
| `notification.failed` | `{ id, group, hresult }` |

reason은 `userCanceled`, `applicationHidden`, `timedOut`, `unknown`입니다.
HRESULT는 unsigned 32비트 정수입니다. Show 자체가 실패하면 명령 오류로 반환하며
후속 Failed callback과 구분합니다. 표시 완료 이벤트는 만들지 않습니다.
앱 정의로 `CommandsOf`, `EventsOf`를 지정한 클라이언트에서 이벤트를 구독하세요.
뷰 정책의 `events`에 이벤트 이름을 허용하고 `host.permissions`에 `notification.show`도
허용해야 합니다. 직접 작업 호출은 `commands`에 `plugin.notification.show` 또는
`plugin.notification.clear` 또는 `plugin.notification.clearAll`과 해당 host 권한을 추가합니다. 구독 해제, 뷰 종료와 권한 거부
뒤에는 전달하지 않습니다. clear, 교체와 앱 종료 뒤 이전 객체의 callback은 버립니다.
앱이 요청한 제거에 대해 별도의 합성 dismissed 이벤트는 보내지 않습니다.

시작 메뉴 바로가기의 AppUserModelID와 process AppUserModelID가 일치해야 합니다.
플러그인은 COM activator, 바로가기나 URL handler를 등록하지 않습니다. MSIX는 아직
`UNSUPPORTED`입니다. 실행 중 받은 Activated callback만 clicked로 전달하며 자동으로
창을 표시하거나 포커스를 바꾸지 않습니다. 백엔드 이벤트 구독이나 `onOpen` 라우팅은
추가하지 않습니다. 앱 종료 후 toast 클릭으로 앱을 시작하는 cold-start activation은
지원하지 않습니다. 알림 센터의 나중 클릭과 비정상 종료 뒤 남은 알림의 activation도
보장하지 않습니다. 액션 버튼, 인라인 응답과 예약은 후속 범위입니다.
