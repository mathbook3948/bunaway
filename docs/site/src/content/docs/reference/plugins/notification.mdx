기본 export(`default`)를 `notification`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-notification`은 Windows toast 표시와 예약, 실행 중 이벤트, 알림 상태 조회와 설정 페이지 열기를 제공합니다.
패키지를 설치하고 `notification`를 등록한 다음 작업별 정책 권한을 허용하세요.

```ts
import { defineApp } from "@bunaway/backend";
import notification from "@bunaway/plugin-notification";

export default defineApp({ modules: [], plugins: [notification] });
```

## 상태 조회와 설정 열기

```ts
notification.getStatus(options?: NativeInvokeOptions): Promise<NotificationStatus>
notification.openSettings(options?: NativeInvokeOptions): Promise<null>
```

앱 명령이나 플러그인 setup에서 호출하면 현재 호출 컨텍스트의 권한과 취소를 사용합니다.
백엔드 호출은 별도 취소 signal이나 기한을 받지 않으며 현재 명령의 설정을 상속합니다.

```ts
import notification from "@bunaway/plugin-notification";

const status = await notification.getStatus();
if (status.support === "supported" && status.setting === "disabledForApplication") {
  // 사용자가 설정 열기를 선택했을 때 호출합니다.
  await notification.openSettings();
}
```

`getStatus`는 신뢰된 호스트 설정의 앱 ID를 사용합니다. 호출자가 다른 앱 ID를
선택할 수 없습니다. 상태 조회에는 이 ID로 등록된 시작 메뉴 바로가기와 같은 process
AppUserModelID가 필요합니다. Windows 호스트와 설치 바로가기는 이 ID를 사용합니다.
기존 알림 상태가 있는 같은 ID를 개발과 배포에서 쓰면 같은 Windows 설정을 조회합니다.
바로가기만으로 알림 상태가 초기화되지는 않습니다. 아직 알림을 보내지 않은 앱이나 등록이 없는
개발 실행, 바로가기를 만들지 않는 설치에서는 Windows가 `UNSUPPORTED`를 반환할 수 있습니다.
조회는 바로가기, toast activator나 앱 등록을 만들지 않습니다.
상태를 초기화하기 위한 알림도 보내지 않습니다. `show`를 명시적으로 호출하면 요청한 알림을 전송하며 OS 상태가 생길 수 있습니다.

## 결과와 OS 권한

`NotificationStatus`는 `support`, `appUserModelId`, `setting`을 반환합니다.
`support`는 toast API를 사용할 수 있으면 `supported`, 해당 WinRT 클래스나 인터페이스가
없으면 `unsupported`입니다. `unsupported`일 때 `setting`은 `null`입니다.
네이티브 기능 조회 플러그인의 지원 목록은 등록된 작업의 플랫폼 구현을 나타내며
사용자 차단 상태를 대신하지 않습니다.

`NotificationSetting`은 Windows가 직접 반환한 설정을 다음 값으로 나타냅니다.

| `setting` | 의미 |
| --- | --- |
| `enabled` | 조회한 Windows 설정에서 알림을 허용함 |
| `disabledForApplication` | 사용자가 이 앱의 알림을 끔 |
| `disabledForUser` | 사용자 또는 관리자가 현재 사용자의 모든 알림을 끔 |
| `disabledByGroupPolicy` | 그룹 정책이 알림을 차단함 |
| `disabledByManifest` | Windows가 앱 manifest의 toast 사용 선언 부족을 보고함 |
| `unknown` | 현재 구현이 모르는 Windows 설정 값 |

여러 차단이 있으면 Windows가 우선순위에 따라 하나를 반환합니다. 이 결과로 더 좁은
범위의 사용자 설정을 추정하지 마세요. 조회 실패는 오류이며 `enabled`로 바꾸지 않습니다.
`enabled`는 실제 알림 표시나 클릭 후 activation 성공을 보장하지 않습니다.
집중 지원과 일시적인 화면 표시 억제 상태도 이 API로 판별하지 않습니다.

현재 Windows 데스크톱 경로에는 알림 동의 팝업을 요청하는 API가 없습니다.
사용자는 Windows 설정에서 직접 허용 상태를 바꿉니다. 플러그인은 사용자 선택이나
그룹 정책을 변경하지 않습니다.

`openSettings`는 고정된 `ms-settings:notifications` 페이지를 열도록 OS에 요청합니다.
임의 URI나 앱별 설정 경로를 받지 않습니다. 성공은 요청 접수이며 페이지가 보였거나
권한을 허용했다는 뜻이 아닙니다. 설정 화면에서 돌아오면 `getStatus`를 다시 호출하세요.
OS에 해당 페이지나 처리 앱이 없거나 요청이 거부되면 오류를 반환합니다.

권한을 요청하는 `requestPermission` 같은 API는 없습니다. Windows 데스크톱 앱의 toast에는 동의 팝업이 없고 앱이
알림 설정을 바꿀 수도 없습니다. Electron 메인 프로세스의 `Notification`도 권한 요청 API가 없고, Tauri 알림 플러그인의 요청 호출은
데스크톱에서 팝업 없이 항상 허용으로 응답합니다. 앱은 `getStatus`로 상태를 읽고 사용자가 선택했을 때 `openSettings`를 호출하세요.

## 정책과 오류

| 작업 | 입력 | 권한 |
| --- | --- | --- |
| `notification.show` | `NotificationOptions` | `notification.show` |
| `notification.schedule` | `ScheduleOptions` | `notification.schedule` |
| `notification.listScheduled` | `null` | `notification.listScheduled` |
| `notification.takeActivations` | `null` | `notification.takeActivations` |
| `notification.cancelScheduled` | `NotificationIdentity` | `notification.cancelScheduled` |
| `notification.clear` | `NotificationIdentity` | `notification.clear` |
| `notification.clearGroup` | `{ group }` | `notification.clearGroup` |
| `notification.clearAll` | `null` | `notification.clearAll` |
| `notification.list` | `null` | `notification.list` |
| `notification.getStatus` | `null` | `notification.getStatus` |
| `notification.openSettings` | `null` | `notification.openSettings` |

뷰에서 직접 호출하려면 `commands`에 `plugin.notification.getStatus` 또는
`plugin.notification.openSettings`를 추가하고 `host.permissions`에 해당 작업을 허용합니다.
명령 핸들러는 원래 뷰의 권한을 사용하며 setup은 루트 `backend.permissions`를 사용합니다.
설정 열기 권한은 상태 조회 권한과 독립입니다.

- `INVALID_ARGUMENT`: 작업 입력, 텍스트, 알림 식별자 또는 호스트 앱 ID가 유효하지 않습니다.
- `PERMISSION_DENIED`: 앱 정책, Windows 상태 조회나 설정 실행 권한이 없습니다.
- `UNSUPPORTED`: 플랫폼 어댑터나 호스트 앱 정보가 없거나 Windows가 상태 조회에 필요한
  앱의 OS 알림 상태를 찾지 못했거나 MSIX에서 상태를 조회했습니다. 바로가기 등록 후에도
  첫 알림 전에는 상태가 없을 수 있습니다. 플러그인은 상태를 자동으로 만들지 않습니다.
  MSIX 앱의 패키지 식별자 연동은 아직 제공하지 않습니다.
- `INTERNAL`: WinRT 초기화, 상태 조회나 설정 열기 요청이 실패했습니다.
- `CANCELLED`, `TIMEOUT`, `BUSY`: 기존 Host API의 취소, 기한과 대기열 제한입니다.

현재 Windows x64의 unpackaged 데스크톱을 지원합니다. macOS, Linux와 모바일
어댑터는 없습니다. 기존 설치의 시작 메뉴 바로가기 선택은 유지합니다.


## Toast 표시, 교체와 제거

```ts
notification.show(input: NotificationOptions, options?: NativeInvokeOptions): Promise<NotificationResult>
notification.clear(input: NotificationIdentity, options?: NativeInvokeOptions): Promise<null>
notification.clearGroup(input: { group: string }, options?: NativeInvokeOptions): Promise<null>
notification.clearAll(input: null, options?: NativeInvokeOptions): Promise<null>
notification.list(input: null, options?: NativeInvokeOptions): Promise<NotificationResult[]>

await notification.show({
  id: "export-done",
  title: "내보내기 완료",
  body: "결과 파일을 확인하세요.",
  data: "export:42",
  silent: true,
});
// 같은 id와 group으로 다시 show하면 이전 알림을 교체합니다.
await notification.clear({ id: "export-done" });
```

| 입력 | 기본값과 제한 |
| --- | --- |
| `id` | 필수. 영문 대소문자, 숫자, `.`, `_`, `-`로 된 1~16자 |
| `group` | `bunaway`. id와 같은 문자와 길이 제한 |
| `title` | 필수. 1~256자 |
| `body` | 빈 문자열. 최대 2048자 |
| `data` | null. 최대 2048자의 앱 문자열이며 클릭 이벤트에만 포함 |
| `silent` | false. true이면 소리 억제 |
| `suppressPopup` | false. true이면 popup 대신 알림 기록으로 전달 |
| `timeoutType` | `default`. `never`이면 popup이 사용자가 닫을 때까지 남음. 아래 설명 참고 |
| `expiresAfterSeconds` | null. 1~604800(7일)의 정수이며 지정하면 그 시간이 지난 뒤 알림 센터에서도 자동으로 제거 |
| `icon` | null. 앱 로고 대신 표시할 이미지의 로컬 절대 경로 |
| `image` | null. 본문 이미지의 로컬 절대 경로 |
| `imagePlacement` | `inline`. `hero`이면 알림 상단 큰 이미지 |
| `sound` | null. Windows 시스템 소리 이름. 아래 목록 중 하나 |
| `soundLoop` | false. `Looping.*` 소리에서만 true 가능 |
| `actions` | 빈 배열. `{ id, label }` 버튼 목록. id는 알림 id와 같은 문자 규칙이며 중복할 수 없고 label은 1~64자 |
| `reply` | null. `{ placeholder?, buttonLabel }`. 텍스트 입력 상자와 전송 버튼을 추가. placeholder는 최대 128자, buttonLabel은 1~64자 |

`NotificationResult`는 `{ id, group }`입니다. 성공은 OS 접수이며 표시 완료나 사용자
확인을 뜻하지 않습니다. 제목과 본문은 XML escape하며 유효하지 않은 XML 문자는 거부합니다.
임의 XML, 실행 명령이나 activation URI는 받지 않습니다.
앱 ID는 호스트가 정하며 호출자가 다른 앱의 알림을 선택할 수 없습니다.
clear는 지정한 ID/group의 popup과 기록만 지웁니다. 같은 앱의 이전 프로세스가 남긴
해당 기록도 지울 수 있습니다. 존재 여부와 무관하게 성공 결과는 null입니다.

`notification.clearGroup`은 입력 `{ group }`으로 같은 앱의 해당 group에 속한 popup과 알림 센터 기록을
모두 지우고 null을 반환합니다. `group`은 `id`와 같은 식별자 규칙을 따르며 생략할 수 없습니다. 이번
실행이 소유한 해당 group의 알림을 숨긴 뒤 호스트 앱 ID 범위에서 그 group의 기록을 제거하므로 이전
프로세스가 남긴 기록도 지우고, 다른 group과 다른 앱의 알림은 건드리지 않습니다. 없는 group도 오류 없이
성공하며 소유 중이던 항목은 해제되어 늦게 온 callback은 버려집니다. 별도의 dismissed 이벤트는 보내지
않습니다. Tauri `removeActive`는 ID 목록을 받고 Electron `Notification`에는 대응하는 API가 없어, group
단위 제거는 Windows 알림 기록의 group 모델에 맞춘 확장이며 `clearGroup` 권한은 `clear`, `clearAll`과 독립입니다.

`notification.clearAll`은 입력 `null`로 같은 앱의 popup과 알림 센터 기록을 모두 지우고
null을 반환합니다. 이번 실행이 소유한 알림을 숨긴 뒤 호스트 앱 ID 범위의 기록 전체를 제거하므로
이전 프로세스가 남긴 기록도 지우며, 다른 앱의 알림은 건드리지 않습니다. 소유 중이던 항목은
모두 해제되어 늦게 온 callback은 버려지고 64개 한도도 비워집니다. 별도의 dismissed 이벤트는
보내지 않습니다. 실패하면 소유권을 유지하므로 다시 호출할 수 있습니다. Tauri의
`removeAllActive`와 같은 범위입니다. Electron `Notification`에는 대응하는 API가 없어
Tauri 기준으로 제공하며, `clearAll` 권한은 `clear`와 독립입니다.

`notification.list`는 입력 `null`로 같은 앱의 알림 센터 기록에 남은 알림의 `{ id, group }`
배열을 반환합니다. 이전 프로세스가 남긴 항목도 포함하며 다른 앱의 알림은 조회하지 않습니다.
제목, 본문과 `data`는 반환하지 않습니다. 태그가 없거나 id/group 규칙을 벗어난 항목은
`clear`로 가리킬 수 없으므로 결과에서 뺍니다. 기록이 비면 빈 배열이며 소유 중인 알림과
이벤트에는 영향이 없습니다. Tauri의 `active()`와 같은 범위입니다. Electron `Notification`에는
대응하는 API가 없어 Tauri 기준으로 제공하며, `list` 권한은 `show`, `clear`와 독립입니다.

동시에 최대 64개의 ID/group을 소유합니다. dismissed 후에도 후속 callback을 받기 위해
소유권을 유지하므로 끝난 항목은 clear하세요. 새 ID가 한도를 넘으면 `BUSY`이며 같은 ID
교체는 가능합니다. 종료 시 이번 실행의 알림과 callback을 정리합니다. 강제 종료는
정리를 보장하지 않으므로 다음 실행에서 알려진 ID/group을 clear할 수 있습니다.
정책과 취소는 네이티브 실행 직전에 검사합니다. Windows에 이미 전달한 show는 요청 취소로
자동 회수하지 않습니다. 회수하려면 clear를 호출하세요.

## 예약 알림

```ts
notification.schedule(input: ScheduleOptions, options?: NativeInvokeOptions): Promise<NotificationResult>
notification.listScheduled(input: null, options?: NativeInvokeOptions): Promise<ScheduledNotification[]>
notification.cancelScheduled(input: NotificationIdentity, options?: NativeInvokeOptions): Promise<null>

await notification.schedule({
  id: "standup",
  title: "스탠드업 5분 전",
  deliverAt: Date.now() + 10 * 60 * 1000,
});
const pending = await notification.listScheduled(null);
// [{ id: "standup", group: "bunaway", deliverAt: 1790000000000 }]
await notification.cancelScheduled({ id: "standup" });
```

`schedule`은 `show`의 입력 필드와 규칙을 그대로 받고 `expiresAfterSeconds` 대신 `deliverAt`을 받습니다.
`deliverAt`은 표시할 시각의 epoch 밀리초 정수이며 1~253402300799999(9999-12-31T23:59:59.999Z)입니다.
현재 시각 이하이면 `INVALID_ARGUMENT`입니다. 예약한 알림에는 만료 시각을 지정할 수 없어
`expiresAfterSeconds`를 보내면 거부합니다. 결과는 `show`와 같은 `{ id, group }`이며 OS가 예약을
접수했다는 뜻입니다.

예약은 Windows의 `ToastNotifier.AddToSchedule`에 맡기므로 앱이 종료돼도 남습니다. 같은 id와
group으로 다시 예약하면 이전 예약을 대체하며 새 예약이 접수된 뒤에 이전 예약을 지웁니다.
다른 group의 같은 id는 별개 예약입니다. 앱당 예약은 최대 4096개이고 새 id/group이 한도를
넘으면 `BUSY`입니다. 교체는 새 예약을 먼저 추가하므로 4096개가 찬 상태에서는 같은 id/group이어도 `BUSY`이며, 먼저 `cancelScheduled`로 비워야 합니다. 교체 중 이전 예약 제거가 실패하면 오류를 반환하고 두 예약이 함께 남을 수 있으며, 같은 id/group으로 `cancelScheduled`를 호출하면 모두 지웁니다. 반복(`interval`, `every`)은 지원하지 않는
단발 예약입니다.

`listScheduled`는 같은 앱 ID에서 아직 표시되지 않은 예약의 `{ id, group, deliverAt }` 배열을
반환합니다. 순서는 정해져 있지 않습니다. 이전 프로세스가 만든 예약도 포함하며 제목, 본문과 `data`는 반환하지
않습니다. 태그가 없거나 id/group 규칙을 벗어난 항목은 `cancelScheduled`로 가리킬 수 없으므로
결과에서 뺍니다. `cancelScheduled`는 해당 id/group의 예약을 모두 제거하고 null을 반환하며
예약이 없어도 성공합니다.

예약 알림은 앱이 소유하는 표시 알림이 아닙니다. 표시 시각이 되면 Windows가 예약한 태그와 group으로
알림 센터에 넣으므로 그 뒤에는 `list`, `clear`, `clearGroup`, `clearAll`이 적용됩니다. 반대로 `clear`, `clearGroup`, `clearAll`과 앱 종료는
예약을 취소하지 않습니다. 예약 알림에는 toast 객체 callback이 없어 `dismissed`, `failed` 이벤트는 연결되지 않습니다. 설치된 앱은 예약 알림의 클릭을 activator로 받으므로, 첫 `takeActivations` 뒤에는 `notification.clicked`, `actionInvoked`(`data: null`)로 나가고 앱이 꺼져 있었다면 `takeActivations`가 돌려줍니다. 같은 id와 group으로 `show`도 한 알림이 이번 실행에 있으면 그 항목의 `data`와 버튼 검사를 쓰고, 그 알림의 클릭이 이미 한 경로로 전달돼 중복으로 기다리는 중이면 예약 알림의 첫 클릭 하나가 중복으로 처리되어 사라질 수 있습니다.
[앱이 꺼진 뒤의 클릭](#앱이-꺼진-뒤의-클릭)을 보세요. `icon`과 `image` 파일은 예약 시점에 검사하지만 Windows가 표시 시각에 다시 읽으므로
그때까지 파일을 유지해야 합니다.

Tauri notification 플러그인의 `schedule`, `pending`, `cancel`과 같은 범위이며 반복 예약은
제외했습니다. Electron `Notification`에는 대응하는 API가 없습니다. 세 작업의 권한은 `show`와
서로 독립입니다.

검증 범위: Windows CI는 실제 WinRT로 예약, 같은 id/group 교체, 목록의 `deliverAt`, 취소, 과거 시각 거부,
약 8초 뒤의 표시 시각에 알림이 알림 센터 기록으로 들어가며 예약 목록에서 사라지는 것과 컨트롤러를
종료한 뒤 새 어댑터에서 예약이 그대로 조회되는 것을 확인합니다. 예약한 프로세스를 정상 종료한 뒤에도
새 프로세스에서 예약이 조회되고 취소되며, 알림을 표시한 적 있는 앱 ID에서 취소하지 않은 예약은 표시 시각에 알림 센터 기록으로 들어갑니다.
CI 측정에서 한 번도 알림을 표시한 적 없는 앱 ID로 예약한 알림은 표시 시각에 예약 목록에서 사라졌지만
알림 센터 기록에 들어오지 않았습니다. 같은 앱 ID로 소리와 popup을 억제한 알림을 한 번 표시하고 지운 뒤에 예약한 알림은 도착했습니다. 어느 조건이 차이를 만드는지는 나누어 확인하지 않았습니다.
강제 종료된 프로세스, 시스템 시계 변경, 절전 중 도착한 예약, 집중 지원 모드는 확인하지 않았습니다.

## 아이콘, 이미지와 소리

```ts
await notification.show({
  id: "build-done",
  title: "빌드 완료",
  icon: "C:\\Users\\me\\app\\icon.png",
  image: "C:\\Users\\me\\app\\preview.jpg",
  imagePlacement: "hero",
  sound: "Reminder",
});
```

`icon`과 `image`는 `C:\` 형식의 로컬 드라이브 절대 경로만 받습니다. 상대 경로, UNC 경로, URL,
`..` 구간, 제어 문자, 짝 없는 surrogate와 드라이브 문자 뒤의 `:`(NTFS 대체 데이터 스트림)는
거부합니다. 확장자는 Windows toast가 지원하는 `png`, `jpg`, `jpeg`, `gif`이고 파일은 `show` 시점에 읽을 수 있는
일반 파일이며 3,000,000바이트(Microsoft 문서의 3 MB) 이하여야 합니다.
`imagePlacement: "hero"`는 `image`가 있을 때만 지정할 수 있습니다.

파일에 접근하기 전에 다음 순서로 검사합니다. 네트워크 응답 지연으로 호스트 스레드가 멈추는 것을 막고
클라우드 파일을 직접 지정했을 때 내려받지 않기 위한 검사입니다.

1. `GetDriveTypeW`로 드라이브 루트를 확인하여 고정 드라이브와 RAM 디스크만 허용합니다. 네트워크,
   이동식, 광학 드라이브와 종류를 알 수 없는 드라이브는 거부합니다.
2. 파일을 `GetFileAttributesW`로 한 번 확인합니다. 디렉터리이거나 offline 또는 열 때 내려받는(recall)
   속성이면 거부합니다. 경로의 마지막이 링크이면 링크 자신의 속성을 확인하므로 링크가 가리키는 파일의
   속성은 확인하지 않습니다.
3. 마지막에 일반 파일 여부와 크기를 확인합니다.

조건을 어기면 `INVALID_ARGUMENT`이며 오류에 경로를 담지 않습니다. 남는 한계가 있습니다.
`subst`로 만든 드라이브는 대상 경로의 종류로 보고되므로 네트워크 공유를 가리키는 `subst` 드라이브는
가려내지 못합니다. 링크는 따라가며 거부하지 않고 링크 대상에는 드라이브 종류 제한도 적용하지 않으므로, 이미지를 둘 폴더는 앱이 정하고
신뢰할 수 없는 폴더의 경로를 화면에서 그대로 받지 마세요. 링크가 네트워크 공유를 가리키는 경로의 처리도 앱이
정합니다. 검사와 Windows의 파일 읽기 사이에 경로가 바뀌는 경우도 막지 못합니다.
검사 뒤에 파일이 바뀌거나 지워지면 Windows가 이미지 없이 표시할 수 있습니다.
Windows가 이미지를 읽을 수 있어야 하므로 앱 실행 사용자가 읽을 수 있는 위치에 두세요.
경로는 최대 259자(MAX_PATH 260에서 종료 NUL 제외)이지만 퍼센트 인코딩한 `file:///` URI는 비ASCII 문자 때문에 훨씬 길어질 수 있습니다.
URI 길이는 따로 검사하지 않으며 Windows가 너무 긴 값을 받지 않으면 이미지 없이 표시될 수 있습니다.

`sound`는 Windows 시스템 소리 이름만 받습니다. Windows 비패키지 앱은 임의 소리 파일을
재생할 수 없습니다. 사용할 수 있는 값은 `Default`, `IM`, `Mail`, `Reminder`, `SMS`,
`Looping.Alarm`, `Looping.Alarm2`~`Looping.Alarm10`, `Looping.Call`, `Looping.Call2`~`Looping.Call10`입니다.
`soundLoop: true`는 `Looping.*` 소리에서만 가능하며 그 밖에는 `INVALID_ARGUMENT`입니다.
`soundLoop: true`이면 toast에 `duration="long"`을 함께 지정해 알림이 길게 표시되는 동안 소리를 반복합니다.
반복은 알림이 사라질 때까지 이어진다고 보장하지 않으며 Windows 설정을 따릅니다.
`silent: true`와 `sound`를 함께 지정하면 `INVALID_ARGUMENT`입니다. 소리를 켜려면 `silent`를 생략하세요.
Windows 소리 설정이나 집중 지원이 소리를 막을 수 있습니다.

### 표시 시간과 만료

`timeoutType`은 Electron `Notification`의 같은 이름 옵션과 같은 값(`default`, `never`)을 받습니다.
`never`는 toast에 `scenario="reminder"`를 지정해 popup이 자동으로 사라지지 않고 사용자가 닫을
때까지 남게 합니다. 이 시나리오는 버튼이 있어야 하므로 `actions`나 `reply`가 없으면 시스템 닫기
버튼을 자동으로 넣고, 있으면 그 버튼을 그대로 씁니다. 자동으로 넣는 닫기 버튼은 `actions`의 5개
한도에 포함되지 않습니다. `suppressPopup: true`이면 popup이 없으므로 `timeoutType`은 효과가
없고 오류도 아닙니다.

`expiresAfterSeconds`는 Electron과 Tauri에 없는 확장으로 `ToastNotification.ExpirationTime`을
현재 시각에 지정한 초를 더한 값으로 설정합니다. 알림 센터는 그 시각이 지나면 항목을 제거합니다.
`timeoutType`, `silent`, `sound`와 자유롭게 함께 쓸 수 있습니다. 생략하면 Windows의 기본 보관
기간을 따르며, CI에서 만료를 지정하지 않은 알림의 `ExpirationTime`이 약 3일 뒤로 읽히는 것을
확인했습니다. 같은 id와 group으로 다시 `show`하면 새 알림의 값이 적용되므로
`expiresAfterSeconds`를 생략한 교체는 이전 값 대신 이 기본 보관 기간으로 돌아갑니다.

검증 범위: Windows CI는 `reminder` 시나리오와 시스템 닫기 버튼이 들어간 toast를 Windows가 받아
알림 기록에 보관하는 것과, 보관된 알림의 `ExpirationTime`이 지정한 시간에 맞는 것을 확인합니다.
popup이 실제로 사용자가 닫을 때까지 남는지와 만료 시각에 알림 센터에서 항목이 사라지는지는
화면 조작이나 대기가 필요해 자동으로 확인하지 않았습니다.

## 액션 버튼과 인라인 응답

```ts
await notification.show({
  id: "chat-42",
  title: "새 메시지",
  body: "점심 같이 먹을래요?",
  actions: [
    { id: "mute", label: "음소거" },
    { id: "open", label: "열기" },
  ],
  reply: { placeholder: "답장 입력", buttonLabel: "보내기" },
});
```

`actions`의 버튼은 Electron `Notification`처럼 알림마다 선언하고, Tauri처럼 문자열 id로
구분합니다. Electron의 `action`과 `reply` 이벤트는 하나의 `actionInvoked`로 합쳤습니다. 버튼과 응답 전송 버튼을
합쳐 최대 5개이고, 넘으면 `INVALID_ARGUMENT`입니다. `reply`를 지정하면 입력 상자와
전송 버튼이 나타납니다. Windows toast의 입력 상자는 `hint-inputId`로 연결한 버튼과 함께 선언하므로 `buttonLabel`은
필수이며 기본 문구는 없습니다. 지역화는 앱이 맡습니다. label, placeholder는 제목과
같은 XML 문자 규칙을 따르고 속성으로 escape해 넣습니다. `data`는 XML에 싣지 않습니다.

버튼이나 응답 전송 버튼을 누르면 `notification.clicked` 대신 `notification.actionInvoked`를
전달합니다. 알림 본문을 누르는 동작은 계속 `notification.clicked`입니다.
`actionId`는 누른 버튼의 id이고 응답 전송 버튼이면 null입니다. `reply`는 알림에 `reply`를
지정했다면 사용자가 입력한 문자열(비어 있으면 빈 문자열)이며, 어느 버튼을 눌러도 함께 옵니다.
지정하지 않았다면 null입니다. 응답은 사용자가 직접 입력한 신뢰할 수 없는 문자열이므로 앱이
검증하세요. 응답은 최대 2048 UTF-16 코드 단위(`data`와 같은 한도)이며 넘으면 잘라내지 않고 이벤트를
보내지 않습니다. 이 알림에 선언하지 않은 버튼 id는 이벤트를 만들지 않습니다.
같은 알림의 `actionInvoked`와 `dismissed` 사이의 순서는 보장하지 않습니다.

입력 상자를 비워 둔 채 보내면 `reply`는 빈 문자열입니다. 응답 값을 읽을 수 없으면 이벤트를 보내지 않습니다.

이 프로세스가 표시한 알림의 이벤트는 Activated callback에서 만들고, 설치된 앱에서는 Windows의 toast
activator도 같은 클릭을 알립니다. 한 번의 클릭은 한 번만 이벤트가 됩니다. 앱이 꺼진 동안의 클릭과 이전
실행이 남긴 알림의 클릭은 [앱이 꺼진 뒤의 클릭](#앱이-꺼진-뒤의-클릭)에서 설명합니다. 권한은
`notification.show`와 이벤트 정책을 따릅니다. 자동 시험은 가짜 COM 객체와 Windows의
인터페이스 메타데이터, 실제 ValueSet 읽기까지만 확인하며, 실제 버튼 클릭에서 Windows가 주는
인수 문자열은 GUI 입력이 필요해 확인하지 않았습니다.

## 실행 중 이벤트와 activation 범위

| 이벤트 | 데이터 |
| --- | --- |
| `notification.clicked` | `{ id, group, data }` |
| `notification.actionInvoked` | `{ id, group, actionId, reply, data }` |
| `notification.dismissed` | `{ id, group, reason }` |
| `notification.failed` | `{ id, group, hresult }` |

reason은 `userCanceled`, `applicationHidden`, `timedOut`, `unknown`입니다.
HRESULT는 unsigned 32비트 정수입니다. Show 자체가 실패하면 명령 오류로 반환하며
후속 Failed callback과 구분합니다. 표시 완료 이벤트는 만들지 않습니다.
앱 정의로 `CommandsOf`, `EventsOf`를 지정한 클라이언트에서 이벤트를 구독하세요.
뷰 정책의 `events`에 이벤트 이름을 허용하고 `host.permissions`에 `notification.show`도
허용해야 합니다. 직접 작업 호출은 `commands`에 `plugin.notification.show` 또는
`plugin.notification.clear`, `plugin.notification.clearGroup`, `plugin.notification.clearAll` 또는 `plugin.notification.list`와 해당 host 권한을 추가합니다. 구독 해제, 뷰 종료와 권한 거부
뒤에는 전달하지 않습니다. clear, 교체와 앱 종료 뒤 이전 객체의 callback은 버립니다.
앱이 요청한 제거에 대해 별도의 합성 dismissed 이벤트는 보내지 않습니다.

시작 메뉴 바로가기의 AppUserModelID와 process AppUserModelID가 일치해야 합니다.
MSIX는 아직 `UNSUPPORTED`입니다. 클릭을 받아도 자동으로 창을 표시하거나 포커스를 바꾸지 않습니다.
백엔드 이벤트 구독이나 `onOpen` 라우팅은 추가하지 않습니다.

## 우선순위와 고급 콘텐츠

`alarm`, `incomingCall` 시나리오 필드는 없습니다. Electron과 Tauri의 데스크톱 알림도 이런 필드를 제공하지
않습니다. 알림 센터 우선순위도 아직 없습니다. Electron의 `urgency`에 해당하는 필드이며 Tauri에는 없고, 필요해지면
추가합니다. 사용자가 닫을 때까지 남기려면 `timeoutType: "never"`, 소리를 반복하려면 `sound`의 `Looping.*`와
`soundLoop`, 알림 센터 보관 기간은 `expiresAfterSeconds`를 쓰세요.

진행률 막대와 제목, 본문 밖의 추가 텍스트 줄도 없습니다. 본문은 `body` 하나입니다. 진행률은
`windows.setTaskbarProgress`나 앱 화면으로 보이고, 끝났을 때 같은 `id`와 `group`으로 `show`해 알림을 교체하세요.
Electron에서 `toastXml`로 이런 내용을 쓰던 앱은 옮길 수 없습니다.

임의 파일 첨부 필드와 클릭 동작 종류(action type, 카테고리) 등록도 없습니다. Windows toast에 파일 첨부 개념이 없고
Electron도 첨부 전용 필드가 없으며(Windows에서는 `icon`과 `toastXml`뿐), Tauri의 `attachments`는 모바일 전용입니다.
Tauri는 데스크톱에서도 액션 종류를 먼저 등록해 알림이 참조하게 하지만, 여기서는 Electron처럼 알림마다 `actions`를 선언합니다. 보이는 이미지와 소리는 `icon`,
`image`, `sound` 필드를 쓰고, 클릭은 `notification.clicked`, `notification.actionInvoked`, `notification.dismissed`
(`show`로 표시한 알림 기준) 이벤트로 받아 처리하세요. 자세한 근거는 [ADR 0052](https://github.com/mathbook3948/bunaway/blob/main/docs/decisions/0052-notification-permission-request-and-attachments.md)에 있습니다.

## 사용자 지정 toast XML

`show`와 `schedule`은 toast XML을 받지 않습니다. `toastXml` 같은 필드는 엄격한 입력 검사에서
`INVALID_ARGUMENT`로 거부됩니다. 플러그인이 본문, 아이콘, 이미지, 소리, 버튼과 입력란을 선언된 필드에서
조립하고 모든 문자열을 이스케이프합니다.

Electron은 Windows에서 `toastXml`로 XML 전체를 직접 지정할 수 있고 Tauri 알림 플러그인에는 이 옵션이 없습니다.
bunaway는 이 옵션을 제공하지 않습니다. 임의 XML의 `launch`와 버튼 `arguments`는 플러그인이 만든 activation
인자(id, group, 액션 id) 형식이 아니라서 플러그인이 해석하지 못하고 버리므로 `notification.actionInvoked`와
앱이 꺼진 뒤의 `takeActivations` 전달이 사라집니다. 또 이미지 `src`가 로컬 파일 검사를 거치지 않고,
플러그인이 만들지 않는 `activationType="protocol"` 경로가 열립니다. 선언 필드로 표현되지 않는 내용은 필드를
추가하는 방식으로 제공합니다.

## 앱이 꺼진 뒤의 클릭

```ts
notification.takeActivations(options?: NativeInvokeOptions): Promise<TakenActivation[]>

// UI를 초기화할 때: 먼저 이벤트를 구독하고, 그다음 한 번 호출합니다.
const missed = await notification.takeActivations();
// [{ kind: "actionInvoked", id: "msg-42", group: "chat", actionId: "reply", reply: "곧 갈게요", data: null }]
```

설치된 앱(`launch.mode`가 `packaged`)에서 알림 센터의 toast를 클릭하면, 앱이 꺼져 있어도 Windows가
앱을 시작하고 그 클릭을 전달합니다. 예약 알림의 클릭도 같습니다. Electron이 Squirrel 바로가기의
AppUserModelID로 알림 클릭에 앱을 시작하는 것과 같은 방식이며, Tauri 알림 플러그인은 데스크톱에서
이 동작을 지원하지 않습니다.

- 설치 프로그램이 시작 메뉴 바로가기에 앱 ID로 정한 toast activator 클래스(CLSID)를 기록하고,
  앱은 시작할 때마다 `HKCU\Software\Classes\CLSID\{...}\LocalServer32`에 실행 파일 경로를 쓰고 그 클래스를
  등록합니다. 관리자 권한은 필요 없습니다. CLSID는 앱 ID에서 계산하므로 설치 프로그램과 플러그인이 같은
  값을 씁니다. 설치 위치를 바꾸면 다음 실행에서 경로가 고쳐집니다. 그 사이 시작하지 않은 상태의 클릭은
  앱을 시작하지 못합니다.
- 클릭은 `notification.clicked` 또는 `notification.actionInvoked`와 같은 값이지만 `data`는 항상
  `null`입니다. 활성화 인수에는 `id`, `group`, 누른 버튼만 들어가고 `data`는 싣지 않습니다. 앱은 `id`와
  `group`으로 자기 저장소에서 알림을 찾으세요. 답장 텍스트는 그대로 전달합니다.
- 앱이 구독하기 전에 도착한 클릭(앱을 시작시킨 바로 그 클릭)은 이벤트로 보내지 않고 플러그인이 최대
  16건까지 보관합니다. 가장 오래된 것부터 버립니다. `takeActivations`는 보관한 클릭을 오래된 순서로
  돌려주고 비웁니다. 첫 호출 뒤에 도착하는 클릭은 이벤트로 바로 전달하므로, 이벤트를 먼저 구독하고
  나서 한 번 호출하세요. 앱이 이 작업을 한 번도 호출하지 않으면 보관한 클릭은 받지 못합니다.
- 이 프로세스가 표시한 알림의 클릭은 그 알림의 `data`와 선언한 버튼 검사를 그대로 적용합니다.
- 활성화 인수는 같은 사용자의 다른 로컬 프로세스도 activator를 호출해 만들 수 있습니다. 형식
  (`bunaway1;<group>;<id>;<대상>`), 길이와 앱 ID가 맞지 않는 호출은 버리지만, 형식이 맞는 호출이 실제
  사용자 클릭인지는 구별하지 않습니다. 종료 상태와 이전 실행에서 온 클릭을 권한 판단이나 되돌릴 수 없는
  작업의 근거로 쓰지 마세요.
- 개발 실행(`launch.mode`가 `development`)은 activator를 등록하지 않으므로 실행 중인 프로세스가 표시한
  알림의 클릭만 받습니다. 시작 메뉴 바로가기를 만들지 않은 설치는 바로가기에 CLSID가 없어 Windows가
  꺼진 앱을 시작하지 못하고, 앱이 실행 중일 때의 클릭만 전달합니다. activator 등록이 실패하면 오류를
  로그에 남기고 알림 표시와 실행 중 클릭은 계속 동작합니다.
- 이 기능이 생기기 전에 설치한 앱을 업데이트하면, 설치 프로그램이 이 앱의 시작 메뉴 링크(대상이 현재 실행
  파일이고 CLSID가 없는 것)만 다시 만들어 CLSID를 기록하고 사용자가 바꾼 `Arguments`는 되돌려 놓습니다.
  대상이 다른 링크는 건드리지 않습니다.
- 같은 앱 ID로 띄운 개발 실행이 있거나 등록이 실패하면 클릭마다 설치된 실행 파일이 새로 시작되어 `-Embedding`을
  실행 중인 인스턴스로 넘길 수 있고, 그 클릭은 이벤트가 되지 않을 수 있습니다.
- `takeActivations`는 프로세스에서 한 번만 보관 모드를 끝냅니다. 두 번째 창이나 새로 고침한 뒤 UI가 늦게
  구독하면 그 사이의 클릭은 받지 못할 수 있으니 한 곳에서만 호출하세요.
- `LocalServer32`는 마지막으로 실행한 packaged 실행 파일이 차지합니다. 같은 앱 ID의 다른 위치 사본을 한 번 실행하면 꺼진 앱의 클릭이 그 사본을 시작하고, 사본을 지우면 설치본을 다시 실행할 때까지 시작하지 못합니다.
- perUser 설치 제거는 `HKCU` 키를 지웁니다. perMachine 제거는 다른 사용자의 `HKCU`를 지울 수 없으므로
  그 키가 남지만 지워진 실행 파일을 가리키고 바로가기도 없어 동작하지 않습니다.
- Windows가 activator가 등록된 앱에 같은 클릭을 toast 객체와 activator 양쪽으로 알릴 수 있어, 한쪽이
  먼저 전달하면 다른 쪽은 무시합니다.
- 앱이 `-Embedding` 같은 `-`로 시작하는 인수를 받을 수 있습니다. files-and-urls 모드의 `onOpen`은 이
  인수를 무시하고, raw 모드의 `onOpen.argv`에는 보입니다.

검증 범위: Linux 계약 시험은 인수 형식의 허용과 거부, 보관 한도와 `takeActivations` 전환, 살아 있는 toast와의
중복 제거를 확인합니다. Windows CI는 별도 프로세스가 COM으로 실제 activator 클래스에 연결해
`Activate`를 호출하는 경로(잘못된 호출 거부 포함), 클래스 해제, 사용자 hive의 `LocalServer32` 기록과 갱신,
설치한 바로가기에 CLSID가 기록되는 것, CLSID 없이 설치한 링크가 업데이트로 CLSID를 얻고 `Arguments`를 유지하는 것, CLSID가 있는 링크는 업데이트해도 그대로 두는 것과 perUser 제거가 키를 지우는 것을 확인합니다. 대화형 데스크톱에서
실제로 알림을 클릭해 꺼진 앱이 시작되는 것, 실제 버튼의 답장 입력, Windows가 activator가 있는 앱에서도
toast 객체 callback을 계속 보내는지, 예약 알림을 실제로 클릭하는 것은 자동으로 확인하지 못합니다. 실행 파일 이름을 바꾸는 업데이트에서는 링크 대상이 바뀐 그 업데이트에는 CLSID가 붙지 않고 다음 업데이트에 붙습니다. 링크를 지운 뒤 설치가 롤백되면 링크가 복원되지 않습니다.
