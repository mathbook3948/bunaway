기본 export(`default`)를 `network`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-network`를 설치하고 앱의 `plugins`에 `network`를 등록합니다.
현재 Windows와 macOS에서 제공합니다. 화면과 백엔드는 `network`를 사용합니다.

## 권한과 앱의 URL 규칙

`network.request`, `network.exchange`, `network.isOnline`, `network.resolveHost`와 `network.resolveProxy`는 각각 독립 Host 권한입니다. 권한은 작업 호출을
허용하고 대상 URL은 앱 명령이 검사합니다. 이 API는 Bun 네트워크 요청이므로 브라우저의
CORS 제한을 적용하지 않습니다. 승인한 Origin 목록은 앱이 작성하며 임의 Origin header는
입력으로 받지 않습니다. 뷰의 명령과 Host 권한을 통해 호출 가능한 출처를 제한합니다.

예를 들어 앱 명령의 입력에서 URL을 받은 경우 다음처럼 검사한 뒤 요청합니다.

```ts
import network from "@bunaway/plugin-network";
import { BunawayError } from "@bunaway/protocol";

async function readReport(urlText: string) {
  const url = new URL(urlText);
  if (url.origin !== "https://reports.example.com" || url.pathname !== "/daily") {
    throw new BunawayError({ code: "PERMISSION_DENIED", message: "허용하지 않은 보고서 주소입니다." });
  }
  return network.request({ url: url.href });
}
```

앱 명령은 호출한 뷰의 Host 권한을 유지합니다. setup은 `backend.permissions`를 사용합니다.
앱 명령에서 검사할 때는 화면에 `plugin.network.request` 또는 `plugin.network.exchange`를
직접 허용하지 않습니다. 직접 화면 호출을 허용하면 해당 작업의 모든 유효 URL을 호출할 수
있습니다. DNS나 IP 범위 제한이 필요한 앱은 별도 접근 규칙을 설계해야 합니다.

신뢰된 백엔드의 일반 네트워크 작업에는 Bun의 `fetch`와 `WebSocket`을 직접 사용해도 됩니다.
이 플러그인은 WebView cookie를 공유하지 않고 OS의 NTLM이나 integrated authentication을
제공하지 않습니다. proxy는 Bun이 실행 환경에서 읽는 신뢰된 설정을 따릅니다. 호출자가
proxy, TLS 검증 해제나 인증 설정을 바꾸는 입력은 없습니다.

## HTTP 요청

```ts
const result = await network.request({
  url: "https://reports.example.com/daily",
  method: "POST",
  headers: [["content-type", "application/octet-stream"]],
  bodyBase64: "AP8B",
  maxResponseBytes: 65536,
  timeoutMs: 30000,
});
```

`NetworkRequest`의 `url`은 절대 HTTP/HTTPS URL입니다. credentials, fragment, 공백과
backslash를 거부합니다. `method`는 GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS이며
기본값은 GET입니다. `headers`는 이름과 값의 쌍 배열이며 기본값은 빈 배열입니다.
header는 64개, 합계 16 KiB까지입니다. Host, Content-Length, Connection, Transfer-Encoding,
Upgrade, Proxy-Authorization, Proxy-Connection, Origin, Referer, Cookie, Accept-Encoding,
Expect와 Sec- 접두사 header는 받지 않습니다. Authorization은 앱이 직접 지정할 수 있습니다.

`bodyBase64`는 선택적인 canonical base64 bytes이며 최대 64 KiB입니다. 표준 알파벳과
필요한 `=` padding만 받고 padding이 남긴 bit가 0이 아니면 `INVALID_ARGUMENT`입니다. GET과 HEAD는 body를 받지
않습니다. `maxResponseBytes`는 0부터 65536까지이며 기본값은 65536입니다.
응답 body는 Bun이 압축을 해제한 후의 bytes를 셉니다. HEAD의 빈 body는 0 상한에서도
성공합니다. `timeoutMs`는 1부터 30000까지이며 기본값은 30000입니다.

`NetworkResponse`는 `{ status, headers, bodyBase64 }`입니다. HTTP 4xx/5xx도 응답으로
반환합니다. redirect를 자동으로 따라가지 않으며 3xx와 Location header를 반환합니다.
앱은 새 대상 URL에 접근 규칙을 적용한 뒤 별도 호출해야 합니다. 자동 재시도는 없습니다.
응답 header 상한도 64개와 16 KiB입니다. 응답이 상한을 넘으면 자르지 않고 실패합니다.
공개 stream과 progress는 아직 제공하지 않습니다.

## 신뢰된 backend의 HTTP stream 대응

Node/Electron stream 이름을 앱의 별도 구현으로 복제하지 않고 Bun의 다음 API를 사용합니다.
이 경로는 신뢰된 backend의 직접 실행이며 `network.request`의 제한된 정책 중재 응답과 구분합니다.

| 기존 역할 | Bun 대응 |
| --- | --- |
| `ClientRequest`의 method, URL, header와 body 작성 | `fetch(url, { method, headers, body, signal })` |
| `IncomingMessage`의 status와 header | 반환한 `Response.status`, `Response.headers` |
| `IncomingMessage`의 응답 stream | `Response.body`의 `ReadableStream<Uint8Array>` |
| 응답 완료까지의 timeout과 취소 | 호출자가 소유한 `AbortController` 또는 `AbortSignal.timeout` |
| 요청 body stream | `RequestInit.body`에 `ReadableStream` 전달 |

```ts
async function readChunks(url: string, signal: AbortSignal) {
  const response = await fetch(url, { signal });
  if (!response.body) return;
  for await (const bytes of response.body) {
    // 앱이 chunk 소비와 저장 위치, 총 bytes 및 progress 처리를 소유합니다.
    console.log(bytes.byteLength);
  }
}
```

직접 stream은 플러그인의 64 KiB 상한을 적용하지 않습니다. 앱이 대상 접근 규칙, 읽기 상한,
저장 위치와 취소를 소유합니다. 정책을 중재하는 공개 stream API는 후속 작업입니다.

## WebSocket 교환

```ts
const result = await network.exchange({
  url: "wss://reports.example.com/socket",
  messages: ["daily"],
  receiveCount: 1,
  timeoutMs: 30000,
});
```

`network.exchange`는 호출 하나에 소켓 하나를 소유합니다. 절대 ws/wss URL만 받으며 HTTP와
같은 URL 제약을 적용합니다. 연결 후 `messages`의 text를 순서대로 보냅니다. 최대 64개이며
UTF-8 합계 64 KiB까지입니다. send buffer가 64 KiB를 넘으면 `BUSY`로 실패합니다.
`receiveCount`는 1부터 64까지입니다. 수신 text와 binary의 합계도 64 KiB까지입니다.
이 제한은 Bun이 메시지를 전달한 뒤 적용하며 Bun 자체의 frame 메모리 상한을 바꾸지 않습니다.

결과는 `{ messages, close: { code, reason, wasClean } }`입니다. text는
`{ kind: "text", text }`, binary는 `{ kind: "binary", base64 }`로 반환합니다.
수신 개수가 채워지면 code 1000으로 close를 시작하고 close 이벤트까지 기다립니다.
상대가 먼저 닫으면 그때까지의 메시지와 실제 close 정보를 반환합니다. close handshake를
포함한 전체 교환에 timeout을 적용합니다. redirect는 따라가지 않습니다.
장기 연결 handle, 독립 send/receive, 상태 이벤트와 사용자 지정 handshake header는 아직 없습니다.

## 온라인 상태와 변경 이벤트

```ts
const online = await network.isOnline();
```

`network.isOnline()`은 boolean을 반환하며 입력이 없습니다. Windows와 macOS에서 제공합니다.
Electron `net.isOnline()`(활성 연결 유무)에 대응하며, 루프백과 link-local이 아닌 주소를
가진 동작 중인 네트워크 인터페이스가 하나라도 있으면 `true`입니다. link-local은 IPv4
169.254.0.0/16과 IPv6 fe80::/10이며, DHCP 실패 때의 자동 주소나 macOS 시스템 인터페이스(awdl,
utun, bridge)의 fe80 주소만 있는 상태는 연결로 보지 않습니다. 반면 VPN, Hyper-V, WSL, Docker 같은
가상 어댑터가 그 밖의 주소를 가지면 실제 외부 연결이 없어도 `true`입니다.
인터넷에 실제로 닿는지, 캡티브 포털 뒤에 있는지는 판단하지 않으므로 요청 실패는 별도로
처리해야 합니다. Windows는 동작 중인 어댑터의 주소 목록(GetAdaptersAddresses)에서, macOS는
getifaddrs에서 주소를 읽습니다. 읽기에 실패하면 `INTERNAL`입니다.

`network.onlineChanged`의 payload는 `{ online: boolean }`이며 값이 실제로 바뀔 때만 보냅니다.
Electron 렌더러의 `online`과 `offline` 이벤트에 대응합니다. 이벤트는 현재 Windows에서만
발생하며 macOS에서는 발생하지 않습니다. 화면 정책의 events에 `network.onlineChanged`,
host.permissions에 `network.isOnline`을 모두 허용해야 하고, 구독한 현재 세션에만 전달합니다.
먼저 구독한 뒤 `isOnline()`으로 초기 값을 조회하면 두 호출 사이의 변경을 놓치지 않습니다.

```ts
const stop = await client.listen("network.onlineChanged", ({ payload }) => {
  console.log(payload.online);
}, { onError(error) { console.error(error); } });
const initial = await network.isOnline();
// 컴포넌트 정리 때 호출합니다.
await stop();
```

Windows는 플러그인이 시작된 뒤 2초마다 상태를 다시 읽고 직전에 알린 값과 다를 때만 이벤트를 보냅니다.
시작 시점의 값은 이벤트로 보내지 않으므로 변경은 최대 2초 늦게 전달될 수 있고, 2초보다 짧은
끊김은 놓칠 수 있습니다. 시작 때 읽기에 실패해도 플러그인은 시작하며, 처음 성공한 읽기를
기준값으로 삼고 그 값은 이벤트로 보내지 않습니다. 이후 읽기 실패는 기존 값을 유지하고 호스트
로그에 기록한 뒤 다음 주기에 다시 시도합니다.
플러그인 종료 때 조회를 멈춥니다.

## 호스트 이름 조회

```ts
const { endpoints } = await network.resolveHost({
  host: "reports.example.com",
  timeoutMs: 5000,
});
// [{ address: "203.0.113.10", family: "ipv4" }, { address: "2001:db8::10", family: "ipv6" }]
```

`network.resolveHost`는 호스트 이름의 IP 주소를 조회합니다. Windows와 macOS에서 제공하며
Electron `net.resolveHost()`의 `{ endpoints: [{ address, family }] }` 결과 형태에 대응합니다.
독립 Host 권한 `network.resolveHost`가 필요합니다.

- 입력 `host`는 ASCII 호스트 이름이나 IPv4 주소입니다. 끝의 점은 허용하며 전체 253자, 레이블
  63자까지입니다. IPv4 주소는 앞자리 0이 없는 십진수 4개(`127.0.0.1`)만 받으며 `127.1`, `0x7f.1`,
  `2130706433` 같은 축약 표기와 마지막 레이블이 숫자인 이름은 거부합니다. 스킴, 포트, 경로, 사용자 정보와 IPv6 주소는 `INVALID_ARGUMENT`입니다.
  국제화 도메인 이름은 punycode(`xn--`)로 바꿔 전달합니다.
- `timeoutMs`는 1부터 30000까지이며 기본값은 30000입니다. 기한이 지나면 `TIMEOUT`입니다.
- 조회는 운영체제 리졸버(getaddrinfo)를 사용하므로 hosts 파일, 검색 접미사와 시스템 DNS
  설정을 따릅니다.
- 결과는 리졸버가 돌려준 순서를 유지하고 중복 주소는 제거합니다. 최대 64개이며 넘으면 뒤쪽을
  버립니다. `family`는 `"ipv4"` 또는 `"ipv6"`입니다.
- 이름이 없거나 리졸버가 실패하면 `INTERNAL`입니다. 실패 원인은 구분해 알려주지 않습니다.
- getaddrinfo는 중간에 멈출 수 없습니다. 취소나 기한 만료는 호출을 즉시 끝내고, 이미 시작한
  조회는 백그라운드에서 끝납니다. 그런 조회까지 포함해 동시에 진행 중인 조회가 16개이면
  새 조회는 `BUSY`입니다.

Electron의 `queryType`, `source`, `cacheUsage`, `secureDnsPolicy` 옵션은 제공하지 않습니다.
Chromium의 자체 DNS 클라이언트와 DNS-over-HTTPS 설정은 사용하지 않고 항상 시스템 리졸버를 씁니다.
이 조회는 프록시를 거치지 않으므로 프록시 뒤 환경에서 `network.request`가 접속하는 주소와
다를 수 있습니다. 프록시 경로는 아래 `network.resolveProxy`로 조회합니다.

## 프록시 경로 조회

```ts
const { entries } = await network.resolveProxy({
  url: "https://reports.example.com/daily",
});
// [{ kind: "proxy", scheme: "http", host: "proxy.corp.example", port: 8080 }, { kind: "direct" }]
```

`network.resolveProxy`는 URL이 시스템 설정에서 어떤 경로를 쓰는지 조회합니다. Windows에서만 제공하며
macOS에서는 `UNSUPPORTED`입니다. Electron `session.resolveProxy(url)`에 대응하지만
`"PROXY host:80; DIRECT"` 같은 PAC 문자열 대신 파싱할 필요 없는 구조화 목록을 돌려줍니다.
독립 Host 권한 `network.resolveProxy`가 필요합니다.

- 입력 `url`은 사용자 정보와 fragment가 없는 `http:` 또는 `https:` 절대 URL입니다. `timeoutMs`는 1부터
  30000까지이며 기본값은 30000입니다.
- 결과 `entries`는 시도할 순서대로 1개 이상 16개 이하입니다. 항목은 `{ kind: "direct" }`이거나
  `{ kind: "proxy", scheme, host, port }`이고 `scheme`은 `"http"`, `"https"`, `"socks4"`, `"socks5"`입니다.
- 현재 사용자의 인터넷 옵션을 WinHTTP로 읽어 다음 순서로 적용합니다. 루프백(`localhost`, `127.*`, `::1`)과
  링크 로컬 주소는 항상 직접 연결입니다. 그다음 설정에 따라 자동 감지(WPAD), 자동 구성 스크립트(PAC),
  수동 프록시 목록과 예외 목록 순입니다. 자동 구성을 찾지 못하거나 실행하지 못하면 다음 방법으로 넘어가며,
  모두 해당하지 않으면 직접 연결입니다.
- 수동 목록은 `host:port`, `http=host:port;https=host:port;socks=host:port`와 `scheme://host:port` 형식을
  읽습니다. URL 스킴에 맞는 항목, 모든 스킴용 항목 순으로 나열하고, 둘 다 없을 때만 `socks=` 항목을 씁니다. `ftp=` 같은 다른 스킴 항목은 무시합니다.
  예외 목록은 `<local>`, `*` 와일드카드, `scheme://`와 `:port` 조건을 지원합니다.
- 프록시 자격 증명은 반환하지 않습니다. 설정에 `user:password@host:port`가 있어도 호스트와 포트만
  남기며, 자동 구성 스크립트를 가져올 때도 로그온 자격 증명을 보내지 않습니다. 스크립트에는 사용자 정보와
  fragment를 뺀 URL을 넘기고 `https:` URL은 경로와 쿼리 없이 출처만 넘깁니다.
- 자동 감지와 스크립트 조회는 WinHTTP 동기 호출이 끝날 때까지 기다리므로 별도 Worker에서 실행합니다.
  플러그인 실행 스레드는 그동안 다른 요청을 계속 처리합니다. 취소와 기한은 호출자의 대기를 즉시 끝냅니다.
  WinHTTP 안에 있는 호출은 중간에 멈추지 않고 끝나야 핸들을 정리하므로, 그 Worker는 호출이 끝날 때까지
  한 칸을 차지하고 그런 Worker를 포함해 동시에 4개를 넘으면 새 조회는 `BUSY`입니다. 자동 구성 단계마다
  남은 기한을 WinHTTP 대기 시간(연결, 이름 조회, 전송, 수신 단계로 나눔)에 주지만 주소 탐색 단계는 이 시간으로
  제한되지 않아 Worker가 기한보다 오래 남을 수 있습니다. 자동 구성 주소가 잘못되었거나 스크립트를 가져오지
  못하는 등 WinHTTP가 오류 코드로 실패하면 다음 방법으로 넘어갑니다. Worker를 시작하지 못하거나 응답이 깨졌거나
  설정 문자열이 너무 길거나 WinHTTP 세션을 열지 못하면 `INTERNAL`입니다. 어댑터를 정리할 때 WinHTTP 안에
  있는 Worker는 호출이 끝나기를 기다리지 않고 종료하므로, 그 호출의 세션 핸들은 프로세스가 끝날 때까지 남을 수 있습니다. 수동 프록시만 쓰거나 설정이 없으면 Worker를 만들지 않고
  바로 답합니다.
- 설정을 읽지 못해도 `INTERNAL`입니다. 실패 원인은 구분해 알려주지 않습니다.
- 이 조회는 `network.request`가 쓰는 Bun 설정을 바꾸지 않고, 요청이 실제로 그 경로를 따른다고 보장하지도
  않습니다. 시스템 설정을 진단하거나 표시하는 용도입니다.
- 자동 구성 스크립트가 `"PROXY a:80; DIRECT"`처럼 직접 연결을 대체 경로로 두어도 WinHTTP는 그 대체 경로를
  알려주지 않으므로 결과에 포함되지 않습니다.

## 취소, 정리와 오류

한 어댑터에서 HTTP, WebSocket과 호스트 이름 조회를 합쳐 최대 16개까지 실행합니다. 초과하면 `BUSY`입니다.
화면 함수의 마지막 인자는 `NativeInvokeOptions`입니다. `signal`과 `deadline`은
[invoke](/reference/client/invoke/)를 따릅니다. 백엔드는 명령의 취소와 기한을 이어받습니다.
취소, 컨텍스트 폐기나 앱 종료는 HTTP 읽기를 중단하고 WebSocket을 terminate합니다.
이미 서버가 처리한 요청이나 메시지는 되돌리지 않습니다.

잘못된 입력은 `INVALID_ARGUMENT`, 작업 권한 거부는 `PERMISSION_DENIED`, 미등록 작업이나
플랫폼은 `UNSUPPORTED`입니다. HTTP 통신, handshake나 응답 제한 실패는 `INTERNAL`이며
호출자에게 내부 URL, 인증 정보나 네트워크 오류 원문을 노출하지 않습니다.
취소와 폐기는 `CANCELLED`, timeout과 호출 기한 초과는 `TIMEOUT`입니다.
