`@bunaway/plugin-network`를 설치하고 앱의 `plugins`에 `networkPlugin`을 등록합니다.
현재 Windows에서 제공합니다. 화면과 백엔드는 `network`를 사용합니다.

## 권한과 앱의 URL 규칙

`network.request`와 `network.exchange`는 각각 독립 Host 권한입니다. 권한은 작업 호출을
허용하고 대상 URL은 앱 명령이 검사합니다. 이 API는 Bun 네트워크 요청이므로 브라우저의
CORS 제한을 적용하지 않습니다. 승인한 Origin 목록은 앱이 작성하며 임의 Origin header는
입력으로 받지 않습니다. 뷰의 명령과 Host 권한을 통해 호출 가능한 출처를 제한합니다.

예를 들어 앱 명령의 입력에서 URL을 받은 경우 다음처럼 검사한 뒤 요청합니다.

```ts
import { network, networkPlugin } from "@bunaway/plugin-network";
import { BunawayError } from "@bunaway/protocol";

async function readReport(urlText: string) {
  const url = new URL(urlText);
  if (url.origin !== "https://reports.example.com" || url.pathname !== "/daily") {
    throw new BunawayError({ code: "PERMISSION_DENIED", message: "허용하지 않은 보고서 주소입니다." });
  }
  return network.request({ url: url.href });
}
```

앱 명령은 호출한 뷰의 Host 권한을 유지합니다. setup은 `backend.permissions`를 사용합니다.
앱 명령에서 검사할 때는 화면에 `plugin.network.request` 또는 `plugin.network.exchange`를
직접 허용하지 않습니다. 직접 화면 호출을 허용하면 해당 작업의 모든 유효 URL을 호출할 수
있습니다. DNS나 IP 범위 제한이 필요한 앱은 별도 접근 규칙을 설계해야 합니다.

신뢰된 백엔드의 일반 네트워크 작업에는 Bun의 `fetch`와 `WebSocket`을 직접 사용해도 됩니다.
이 플러그인은 WebView cookie를 공유하지 않고 OS의 NTLM이나 integrated authentication을
제공하지 않습니다. proxy는 Bun이 실행 환경에서 읽는 신뢰된 설정을 따릅니다. 호출자가
proxy, TLS 검증 해제나 인증 설정을 바꾸는 입력은 없습니다.

## HTTP 요청

```ts
const result = await network.request({
  url: "https://reports.example.com/daily",
  method: "POST",
  headers: [["content-type", "application/octet-stream"]],
  bodyBase64: "AP8B",
  maxResponseBytes: 65536,
  timeoutMs: 30000,
});
```

`NetworkRequest`의 `url`은 절대 HTTP/HTTPS URL입니다. credentials, fragment, 공백과
backslash를 거부합니다. `method`는 GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS이며
기본값은 GET입니다. `headers`는 이름과 값의 쌍 배열이며 기본값은 빈 배열입니다.
header는 64개, 합계 16 KiB까지입니다. Host, Content-Length, Connection, Transfer-Encoding,
Upgrade, Proxy-Authorization, Proxy-Connection, Origin, Referer, Cookie, Accept-Encoding,
Expect와 Sec- 접두사 header는 받지 않습니다. Authorization은 앱이 직접 지정할 수 있습니다.

`bodyBase64`는 선택적인 base64 bytes이며 최대 64 KiB입니다. GET과 HEAD는 body를 받지
않습니다. `maxResponseBytes`는 0부터 65536까지이며 기본값은 65536입니다.
응답 body는 Bun이 압축을 해제한 후의 bytes를 셉니다. HEAD의 빈 body는 0 상한에서도
성공합니다. `timeoutMs`는 1부터 30000까지이며 기본값은 30000입니다.

`NetworkResponse`는 `{ status, headers, bodyBase64 }`입니다. HTTP 4xx/5xx도 응답으로
반환합니다. redirect를 자동으로 따라가지 않으며 3xx와 Location header를 반환합니다.
앱은 새 대상 URL에 접근 규칙을 적용한 뒤 별도 호출해야 합니다. 자동 재시도는 없습니다.
응답 header 상한도 64개와 16 KiB입니다. 응답이 상한을 넘으면 자르지 않고 실패합니다.
공개 stream과 progress는 아직 제공하지 않습니다.

## 신뢰된 backend의 HTTP stream 대응

Node/Electron stream 이름을 앱의 별도 구현으로 복제하지 않고 Bun의 다음 API를 사용합니다.
이 경로는 신뢰된 backend의 직접 실행이며 `network.request`의 제한된 정책 중재 응답과 구분합니다.

| 기존 역할 | Bun 대응 |
| --- | --- |
| `ClientRequest`의 method, URL, header와 body 작성 | `fetch(url, { method, headers, body, signal })` |
| `IncomingMessage`의 status와 header | 반환한 `Response.status`, `Response.headers` |
| `IncomingMessage`의 응답 stream | `Response.body`의 `ReadableStream<Uint8Array>` |
| 응답 완료까지의 timeout과 취소 | 호출자가 소유한 `AbortController` 또는 `AbortSignal.timeout` |
| 요청 body stream | `RequestInit.body`에 `ReadableStream` 전달 |

```ts
async function readChunks(url: string, signal: AbortSignal) {
  const response = await fetch(url, { signal });
  if (!response.body) return;
  for await (const bytes of response.body) {
    // 앱이 chunk 소비와 저장 위치, 총 bytes 및 progress 처리를 소유합니다.
    console.log(bytes.byteLength);
  }
}
```

직접 stream은 플러그인의 64 KiB 상한을 적용하지 않습니다. 앱이 대상 접근 규칙, 읽기 상한,
저장 위치와 취소를 소유합니다. 정책을 중재하는 공개 stream API는 후속 작업입니다.

## WebSocket 교환

```ts
const result = await network.exchange({
  url: "wss://reports.example.com/socket",
  messages: ["daily"],
  receiveCount: 1,
  timeoutMs: 30000,
});
```

`network.exchange`는 호출 하나에 소켓 하나를 소유합니다. 절대 ws/wss URL만 받으며 HTTP와
같은 URL 제약을 적용합니다. 연결 후 `messages`의 text를 순서대로 보냅니다. 최대 64개이며
UTF-8 합계 64 KiB까지입니다. send buffer가 64 KiB를 넘으면 `BUSY`로 실패합니다.
`receiveCount`는 1부터 64까지입니다. 수신 text와 binary의 합계도 64 KiB까지입니다.
이 제한은 Bun이 메시지를 전달한 뒤 적용하며 Bun 자체의 frame 메모리 상한을 바꾸지 않습니다.

결과는 `{ messages, close: { code, reason, wasClean } }`입니다. text는
`{ kind: "text", text }`, binary는 `{ kind: "binary", base64 }`로 반환합니다.
수신 개수가 채워지면 code 1000으로 close를 시작하고 close 이벤트까지 기다립니다.
상대가 먼저 닫으면 그때까지의 메시지와 실제 close 정보를 반환합니다. close handshake를
포함한 전체 교환에 timeout을 적용합니다. redirect는 따라가지 않습니다.
장기 연결 handle, 독립 send/receive, 상태 이벤트와 사용자 지정 handshake header는 아직 없습니다.

## 취소, 정리와 오류

한 어댑터에서 HTTP와 WebSocket 호출을 합쳐 최대 16개까지 실행합니다. 초과하면 `BUSY`입니다.
화면 함수의 마지막 인자는 `NativeInvokeOptions`입니다. `signal`과 `deadline`은
[invoke](/reference/client/invoke/)를 따릅니다. 백엔드는 명령의 취소와 기한을 이어받습니다.
취소, 컨텍스트 폐기나 앱 종료는 HTTP 읽기를 중단하고 WebSocket을 terminate합니다.
이미 서버가 처리한 요청이나 메시지는 되돌리지 않습니다.

잘못된 입력은 `INVALID_ARGUMENT`, 작업 권한 거부는 `PERMISSION_DENIED`, 미등록 작업이나
플랫폼은 `UNSUPPORTED`입니다. HTTP 통신, handshake나 응답 제한 실패는 `INTERNAL`이며
호출자에게 내부 URL, 인증 정보나 네트워크 오류 원문을 노출하지 않습니다.
취소와 폐기는 `CANCELLED`, timeout과 호출 기한 초과는 `TIMEOUT`입니다.
