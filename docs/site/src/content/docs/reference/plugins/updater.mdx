기본 export(`default`)를 `updater`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-updater` 패키지를 설치하고 앱의 `plugins`에 `updater`를 등록합니다. Windows와
macOS에서 같은 코드로 제공합니다. 화면과 백엔드는 같은 패키지의 `updater`를 사용합니다.
이 플러그인은 업데이트가 있는지 조회하고, 직전 조회가 찾은 패키지를 내려받아 매니페스트가 선언한 SHA-256과 크기로 확인합니다. 앱이 게시자를 고정하면 Windows 설치 파일의 Authenticode 서명도 확인합니다. 설치와 재시작은 하지 않습니다.

```ts
import updater from "@bunaway/plugin-updater";

const update = await updater.check(null);
if (update.updateAvailable) {
  const file = await updater.download(null);
  console.log(update.version, update.notes, file.path);
}
```

| 함수 | 입력 | 결과 | 권한 |
| --- | --- | --- | --- |
| `updater.check` | `null` | `Promise<UpdaterCheckResult>` | `updater.check` |
| `updater.download` | `null` | `Promise<UpdaterDownloadResult>` | `updater.download` |

## 설정

엔드포인트는 호출 인자가 아니라 앱의 `src-bunaway/bunaway.json`에 고정합니다. 화면이 요청할 주소를 정할
수 없으므로 화면이 임의의 서버에 요청을 보내게 하는 데 쓰일 수 없습니다.

```json
{
  "plugins": {
    "updater": {
      "endpoint": "https://updates.example.com/{{target}}/{{arch}}/{{channel}}/{{current_version}}",
      "channel": "stable",
      "authenticode": {
        "publisherNames": ["Example Corp"]
      }
    }
  }
}
```

- `endpoint`(필수): 2048자 이하의 절대 URL 템플릿입니다. 자리표시자는 `{{target}}`, `{{arch}}`,
  `{{channel}}`, `{{current_version}}` 네 개만 쓸 수 있고 경로와 질의에만 둘 수 있습니다. 값은
  URL 인코딩되어 들어갑니다(`1.0.0+build`는 `1.0.0%2Bbuild`). 알 수 없는 자리표시자, 공백과 제어 문자, 값에 따라
  요청 주소의 호스트가 달라지는 템플릿(스킴이나 호스트 안의 자리표시자, 호스트 앞의 `\` 등), 사용자 정보
  (`user:pass@`), 프래그먼트는 거부합니다.
- `channel`: 소문자 영숫자와 `-`로 된 32자 이하 이름이며 기본값은 `stable`입니다.
- `authenticode`(선택): 받은 설치 파일이 이 게시자의 유효한 Authenticode 서명을 가져야 `download`가 성공하게 합니다.
  `publisherNames`는 1개에서 8개의 문자열이고 각각 256자 이하입니다. 하나라도 서명한 인증서의 subject와 맞으면 통과합니다.
  `=`가 없는 항목은 인증서 subject의 CN(common name)과 정확히 같아야 하며, subject에 CN이 둘 이상이면 어느 것도 맞지 않습니다. `=`가 있는 항목은
  `CN=Example Corp, O=Example Corp, C=US`처럼 RFC 2253 형식의 distinguished name으로 읽고, 적은 속성이
  모두 subject에 같은 값으로 있어야 합니다(적지 않은 속성은 보지 않습니다). 비교는 대소문자를 구분하고 값을 정규화하지
  않으며 부분 일치나 접두 일치를 허용하지 않습니다. 형식이 잘못된 항목은 어댑터를 만들 때 `INVALID_ARGUMENT`입니다.
  설정이 없으면 SHA-256과 크기만 확인합니다.
- `target`은 Windows가 `windows`, macOS가 `darwin`이고 `arch`는 `x86_64` 또는 `aarch64`입니다.
  이 값은 앱이 아니라 실행 중인 호스트에서 정해집니다. 다른 CPU에서는 `UNSUPPORTED`입니다.
  자리표시자를 가장 긴 값으로 채웠을 때 주소가 4096자를 넘을 수 있는 템플릿도 어댑터를 만들 때 거부합니다.

주소는 `https`만 허용합니다. 개발 실행(`bunaway dev`)에서만 호스트가 `localhost`, `127.0.0.1`, `[::1]`인
`http` 주소를 허용하며 패키지된 앱에서는 이를 켤 수 없습니다. 설정이 잘못되면 어댑터를 만들 때
`INVALID_ARGUMENT`로 실패합니다. `plugins.updater`가 없으면 `check`가
`UNSUPPORTED`(`details.reason: "notConfigured"`)로 실패합니다.

Windows에서 MSIX 패키지로 설치돼 실행 중인 앱은 패키지 교체를 패키지 관리자(Store 포함)만 하므로, `check`와 `download`가
요청을 보내기 전에 `UNSUPPORTED`(`details.reason: "managedByStore"`)로 실패합니다. 앱은 같은 코드에서 이 오류를 보고
업데이트 화면을 숨기거나 Store의 업데이트 안내로 바꿀 수 있습니다. 실행 중인 호스트가 프로세스의 패키지 ID와 실행 파일이
패키지 설치 폴더 안에 있는지를 함께 확인하며 앱 설정으로 바꿀 수 없습니다. 패키지 ID만 붙이고 실행 파일은 패키지 밖에 있는
앱은 거부하지 않습니다. 패키지 ID가 없는 일반 프로세스가 거부되지 않는 것은 Windows CI에서 실행해 확인합니다. MSIX 패키지로
설치한 프로세스에서의 판별은 `win-store-msix` 패키지 생성이 열리기 전이라 실제로 확인하지 못했고, 패키지 ID와 폴더 비교는
주입한 값으로만 시험했습니다.

## 매니페스트

서버는 Tauri 정적 JSON의 읽기 전용 부분집합을 돌려줍니다. 응답 본문은 압축을 푼 뒤 64 KiB 이하여야 합니다.

```json
{
  "version": "1.2.0",
  "notes": "수정 내용",
  "pub_date": "2026-10-20T09:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "url": "https://downloads.example.com/app-1.2.0.exe",
      "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
      "size": 48213504
    }
  }
}
```

- `version`: 필수이며 SemVer 2.0.0이어야 합니다. 앞의 `v`, 앞자리 0, 빈 식별자는 거부합니다.
- `platforms["<target>-<arch>"].url`: 업데이트가 있을 때 필요합니다. 동적 서버처럼 최상위 `url`만 있어도 됩니다.
- `sha256`, `size`: 다운로드에 필요합니다. `url`과 같은 위치(플랫폼 항목, 없으면 최상위)에 64자리 16진수 SHA-256과 바이트 수(1 이상 1 GiB 이하 정수)를 둡니다. `check`는 이 값이 없어도 통과하므로 업데이트를 알리기만 하는 앱은 영향을 받지 않습니다.
- `notes`, `pub_date`: 선택입니다. `signature` 같은 다른 필드는 읽지도 돌려주지도 않습니다.
- HTTP 204는 업데이트 없음으로 봅니다.

## 결과

`UpdaterCheckResult`는 `updateAvailable`, `currentVersion`, `version`, `notes`, `publishedAt`,
`downloadUrl`을 돌려줍니다. 원격 버전이 현재 버전보다 클 때만 `updateAvailable`이 `true`입니다. 같거나
낮은 버전은 내리지 않으며, 업데이트가 없으면 `version`, `notes`, `publishedAt`, `downloadUrl`이 `null`입니다.
비교는 SemVer 11절을 따릅니다. build metadata는 무시하고 prerelease는 같은 버전의 정식 릴리스보다 낮습니다.
prerelease를 받을지는 채널의 엔드포인트가 정합니다.

- `notes`는 16384자 이하이며 탭과 줄바꿈 외의 제어 문자(C0, DEL, C1)가 있으면 잘라 보내지 않고 오류로 처리합니다.
  서버가 준 값이므로 HTML로 렌더링하지 말고 일반 텍스트로 표시해야 합니다.
- `publishedAt`은 RFC 3339 시각을 UTC ISO 8601로 정규화한 값입니다. 존재하지 않는 날짜, 24시, 60초와 UTC로 바꾸면 0000년에서 9999년을 벗어나는 시각은 거부합니다.
- `downloadUrl`은 정규화한 뒤 2048자 이하인 `https` 주소이며 사용자 정보가 없어야 합니다. 서명 없이 받은 안내 값이므로
  업데이트의 출처를 증명하지 않습니다. `download`는 이 값을 입력으로 받지 않고 어댑터가 직전 `check`에서 기억한
  주소만 사용합니다. 설치 단계는 백엔드가 매니페스트를 다시 받아 앱에 내장된 공개키로 서명을 확인해야 합니다.

## 다운로드

`updater.download(null)`은 마지막으로 성공한 `check`가 찾은 업데이트의 패키지를 받습니다. 주소, 해시, 크기는 호출 인자가
아니라 그 `check`의 매니페스트에서 오므로 화면은 받을 주소나 저장 위치를 정할 수 없습니다. 업데이트가 없다고 답한 `check`
뒤나 `check`를 부르기 전에는 `UNSUPPORTED`(`notChecked`)입니다.

```ts
interface UpdaterDownloadResult {
  path: string;    // 검증된 패키지의 절대 경로
  version: string;
  size: number;
  sha256: string;  // 소문자 16진수
}
```

- 파일은 앱 데이터 폴더의 `data/updates/<sha256>.package`에 저장됩니다. 이름은 서버가 정하지 않고 해시에서 만듭니다.
  받는 동안은 `<sha256>.partial`에 쓰고, 크기와 SHA-256이 모두 맞을 때만 최종 이름으로 바꿉니다. 실패, 취소, 시간 초과,
  dispose에서는 부분 파일을 지웁니다. 성공하면 그 폴더의 다른 `.package`와 `.partial` 파일도 지웁니다.
- 같은 해시의 파일이 이미 있으면 크기와 SHA-256을 다시 계산해 맞을 때 네트워크 없이 그 경로를 돌려주고, 맞지 않으면 지우고 다시 받습니다.
- 크기 상한은 1 GiB입니다. 선언 크기가 상한을 넘으면 요청하지 않고 `tooLarge`입니다. `content-length`(인코딩 없는 응답)와 실제로 받은 바이트가
  선언 크기와 다르면 `sizeMismatch`이고, 받은 바이트가 선언 크기를 넘는 즉시 중단합니다.
- 전체 제한 시간은 30분이며 리다이렉트 규칙은 `check`와 같습니다. 재시도와 이어 받기는 내장하지 않으므로 실패하면 앱이 다시 호출하고, 다시 호출하면 처음부터 받습니다.
  `TIMEOUT`, `details.reason`이 `network`인 오류, 5xx나 429인 `httpStatus`, `revocationUnavailable`은 다시 시도할 만합니다. `tooLarge`와 `integrityInvalid`는 매니페스트 값이 원인이라 같은 매니페스트면 같은 결과이고, 그 밖의 서명 거부 계열도 같은 파일이면 같은 결과입니다. `sizeMismatch`와 `integrityMismatch`는 전송 중 손상인지 잘못 게시된 파일인지 오류만으로 알 수 없고, `verifierBusy`와 `verifierFailed`는 일시적일 수 있으므로 이 네 가지는 한두 번만 다시 시도합니다. `redirectLimit`, `redirectScheme`, 404 같은 4xx `httpStatus`, `storage`는 조건이 바뀌기 전에는 같은 결과입니다. 오류별 판단은 [ADR 0113](https://github.com/mathbook3948/bunaway/blob/main/docs/decisions/0113-updater-download-retry-and-resume.md)에 있습니다.
- 한 번에 하나만 받을 수 있고 실행 중에 다시 부르면 `BUSY`(`downloadInProgress`)입니다. 호출을 취소하면 `CANCELLED`입니다.
  다운로드 중에는 호스트의 자동 종료가 미뤄집니다.
- 반환하는 `path`에는 사용자 이름이 들어갈 수 있습니다. 화면에 경로를 보이지 않으려면 백엔드 앱 명령 안에서 호출하고 필요한 값만 넘기세요.
- SHA-256은 전송 오류와 전송 중 변조를 찾아냅니다. 매니페스트와 패키지가 같은 서버에서 오면 서버가 침해됐을 때는 막지 못하므로,
  패키지를 만든 쪽을 증명하려면 아래 `authenticode` 설정으로 게시자를 고정합니다.
- 진행률 이벤트는 없습니다. 플러그인 이벤트를 WebView로 보내는 서비스가 이 플러그인이 실행되는 워커에 주입되지 않기 때문입니다.

### 게시자 서명 검증

`plugins.updater.authenticode`를 설정하면 `download`는 해시와 크기가 맞은 파일에 대해 Windows `WinVerifyTrust`
(`WINTRUST_ACTION_GENERIC_VERIFY_V2`, UI 없음)로 Authenticode 서명을 확인하고, 서명자 인증서가 `publisherNames`에 맞을 때만
성공합니다. 새로 받은 파일은 `<sha256>.partial` 상태에서 확인한 뒤 최종 이름으로 바꾸므로 거부된 파일은 최종 이름을 갖지
않습니다. 이미 있는 파일을 재사용할 때도 다시 확인합니다. 호출자가 경로를 넘기지 않고 `download`가 만든 앱 전용 폴더의 파일만
확인하므로 별도의 검증 연산은 없습니다.

- 대상은 PE 파일(exe)과 MSI 파일입니다. 형식은 파일 이름이 아니라 처음 몇 바이트로 판별하며, 둘 다 아니면 서명을 확인할 수
  없으므로 `UNSUPPORTED`(`signatureUnsupported`)로 거부합니다. 설정이 없으면 형식을 따지지 않습니다.
- 서명이 없으면 `signatureMissing`, 서명이 깨졌거나 변조됐거나 폐기됐거나 신뢰하는 루트로 이어지지 않으면 `signatureUntrusted`,
  서명은 유효하지만 서명자가 목록에 없으면 `publisherMismatch`입니다. 모두 `INTERNAL`이며 받은 파일을 지웁니다.
- `WinVerifyTrust`에 루트를 뺀 체인 전체의 폐기 확인을 요청합니다. 폐기된 인증서는 `signatureUntrusted`입니다. 폐기 확인 서버에
  닿지 못했다고 `WinVerifyTrust`가 알려 오면(`CRYPT_E_REVOCATION_OFFLINE` 등) `revocationUnavailable`로 실패하므로 앱은
  네트워크가 돌아온 뒤 `download`를 다시 부를 수 있습니다. 다만 서버에 닿지 못할 때 성공을 돌려줄지는 Windows의 기본 신뢰
  정책(오프라인 폐기 상태를 허용하는 정책 플래그)이 정하며, 이 플러그인은 그 정책을 바꾸지 않고 검증하지도 않았습니다.
  서명 시각의 타임스탬프가 유효하면 서명 인증서가 만료된 뒤에도 서명은 유효합니다(Windows의 기본 정책).
- 플러그인은 검증을 건너뛰고 통과시키지 않습니다. 검증 호출 실패, 결과를 읽을 수 없음, 시간 초과, 서명 없음, 형식 불일치는
  모두 실패입니다.
- 오류 메시지와 `details`에는 인증서 subject, 지문, 파일 경로, 운영체제 오류 코드를 넣지 않습니다.
- 검증은 별도 스레드(Worker)에서 실행해 호스트의 다른 요청을 막지 않습니다. 호출을 취소하거나 시간이 지나면 호출자는 곧바로
  돌아오고, 이미 시작된 네이티브 호출은 끝난 뒤 정리됩니다. 어댑터를 dispose하면 남아 있는 검증 스레드는 종료합니다.
  동시에 남아 있을 수 있는 검증은 2개이며 넘으면 `INTERNAL`(`verifierBusy`)입니다. 검증 스레드를 시작하거나 설치 파일을
  읽을 수 없으면 `INTERNAL`(`verifierFailed`)입니다.
- 인증서 지문이나 공개 키 해시는 고정하지 않습니다. 인증서를 갱신하면 이미 배포된 앱이 새 설치 파일을 받지 못하기 때문입니다.
  대신 이름을 고정하므로, 같은 인증 기관이 같은 이름의 인증서를 다른 조직에 발급하면 통과합니다. 갱신 중에는
  `publisherNames`에 이전 이름과 새 이름을 함께 둘 수 있습니다.
- 검증이 끝난 뒤 설치 전에 같은 사용자 권한의 다른 프로세스가 파일을 바꾸는 것은 막지 않습니다. 설치 단계는 실행 직전에
  다시 확인해야 합니다.
- macOS에는 서명 검증이 없습니다. 설정이 있는 앱은 macOS에서 요청을 보내기 전에 `UNSUPPORTED`(`signatureUnsupported`)로
  실패하므로, macOS용 검증이 생길 때까지 `download`를 쓸 수 없습니다. `check`는 그대로 동작합니다.
- 서명 전용 앱 키(minisign 방식)는 지원하지 않습니다.

## 요청과 오류

요청은 GET이며 쿠키와 인증 정보를 보내지 않습니다. 리다이렉트는 3번까지 직접 따르며, 매 단계에서 위 주소
규칙을 다시 검사하고 `https`에서 `http`로 낮아지면 거부합니다. 다른 호스트로의 리다이렉트는 허용합니다.
`check`의 전체 제한 시간은 15초입니다.

| 코드 | `details.reason` |
| --- | --- |
| `UNSUPPORTED` | `notConfigured`, `appVersionMissing`, `appVersionInvalid`, `unsupportedArch`, `notChecked`, `integrityMissing`, `notAvailable`(업데이트 폴더를 제공하지 않는 어댑터), `signatureUnsupported`, `managedByStore`(Windows에서 MSIX로 설치된 프로세스) |
| `TIMEOUT` | 제한 시간 초과 |
| `CANCELLED` | 호출 취소, 어댑터 dispose |
| `INTERNAL` | `network`, `httpStatus`(`details.status`), `redirectLimit`, `redirectScheme`, `tooLarge`, `invalidJson`, `invalidManifest`, `invalidVersion`, `platformMissing`, `integrityInvalid`, `integrityMismatch`, `sizeMismatch`, `signatureMissing`, `signatureUntrusted`, `revocationUnavailable`, `publisherMismatch`, `verifierBusy`, `verifierFailed`, `storage` |
| `BUSY` | `downloadInProgress` |

앱 버전은 패키지 `manifest.json`의 `app.version`(`ctx.app.version`과 같은 값)이며 기록되지 않았으면
`appVersionMissing`입니다. 오류 메시지에는 서버 응답이나 주소를 넣지 않습니다.

## 검증 범위

테스트는 주입한 `fetch`로 버전 비교, 매니페스트 검증, 크기 상한, 리다이렉트, 오류 분류를 확인합니다.
압축 해제 후 크기 상한, 본문 전송 중 시간 초과와 등록된 플러그인의 호출 경로는 같은 컴퓨터의 loopback HTTP 서버로 확인합니다.
`updater.download`는 주입한 `fetch`와 임시 데이터 폴더로 정상 저장, 해시와 크기 불일치, 선언 크기 초과, 취소, 시간 초과,
dispose, 재사용과 변조 감지, 정리 범위를 확인합니다. 실제 업데이트 서버와의 왕복은 검증하지 않았습니다.
게시자 서명 검증은 Linux에서 검증기 대역으로 설정 검사, 게시자 대조, 결과별 오류와 파일 삭제, 취소, 워커 상한을 확인하고,
Windows CI에서 실제 `WinVerifyTrust`로 확인합니다. Windows 시험은 CI 실행기에 자체 서명 코드 서명 인증서를 신뢰 루트로 넣고
서명한 exe, 서명 없는 파일, 변조한 파일, 신뢰되지 않는 인증서, 형식이 다른 파일을 검사합니다. 서명한 MSI 파일은 실제 서명으로
시험하지 못했고, MSI는 형식 판별만 시험했습니다. Windows Installer COM으로 만든 최소 MSI를 `Set-AuthenticodeSignature`로
서명하자 windows-2022 러너에서 `Get-AuthenticodeSignature`가 `HashMismatch`를 돌려줬고, 원인은 확인하지 못했습니다. 운영 인증 기관 체인,
실제 폐기 서버 응답과 오프라인에서의 `revocationUnavailable`, 타임스탬프로 만료 인증서를 허용하는 동작은 실행하지 않았습니다.
설치는 후속 작업입니다.
