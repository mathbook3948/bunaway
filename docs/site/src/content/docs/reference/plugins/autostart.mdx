기본 export(`default`)를 `autostart`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-autostart`는 현재 사용자의 Windows와 macOS 로그인 자동 실행을 제공합니다.
Windows는 사용자 Run 값, MSIX 패키지로 실행하는 Windows 앱은 manifest StartupTask,
macOS는 `~/Library/LaunchAgents`의 LaunchAgent plist에 등록합니다.
패키지를 설치하고 `autostart`를 등록해야 합니다. 설치와 등록만으로 자동 실행이
켜지지 않습니다. 사용자가 동의한 설정 변경에서 `enableAutostart`를 호출하세요.

```ts
import { defineApp } from "@bunaway/backend";
import autostart from "@bunaway/plugin-autostart";

export default defineApp({ modules: [], plugins: [autostart] });
```

## 등록, 조회와 해제

```ts
autostart.enableAutostart(settings?: string[] | AutostartOptions, options?: NativeInvokeOptions): Promise<AutostartStatus>
autostart.getAutostartStatus(options?: NativeInvokeOptions): Promise<AutostartStatus>
autostart.disableAutostart(options?: NativeInvokeOptions): Promise<null>
```

```ts
import autostart from "@bunaway/plugin-autostart";

await autostart.enableAutostart(["--login", "한글 값", '인용"값', ""]);
const status = await autostart.getAutostartStatus();
if (status.registered && status.startupState === "disabled") {
  // Windows 설정이나 작업 관리자에서 사용자가 다시 활성화하도록 안내합니다.
}
await autostart.disableAutostart();
```

`AutostartOptions`는 `{ args?: string[], hidden?: boolean }`입니다. 기존 인자 배열도 받습니다.
`args`의 기본값은 빈 배열이고 `hidden`의 기본값은 `false`입니다. 인자는 최대 64개이며 각 문자열은 최대 260자입니다.
Windows에 저장하는 전체 명령줄은 **260 UTF-16 코드 단위**를 넘을 수 없습니다.
경로, 프레임워크 시작 인자, 인자 사이 공백과 따옴표 이스케이프도 이 제한에 포함합니다.
공백, Unicode, 빈 문자열, 따옴표와 끝의 역슬래시는 원래 인자 그대로 전달합니다.
NUL과 짝이 없는 UTF-16 surrogate는 거부합니다. `%PATH%`, `&` 등은 문자열이며
환경 변수 확장이나 셸 실행을 하지 않습니다.

macOS는 인자를 plist의 `ProgramArguments` 배열에 문자열 하나씩 저장하므로 전체 길이 제한과
따옴표 이스케이프가 없습니다. 대신 plist(XML)로 그대로 저장할 수 없는 줄바꿈을 포함한
제어 문자와 짝이 없는 surrogate는 `INVALID_ARGUMENT`로 거부합니다. 이스케이프를 거친
plist 전체가 64KiB를 넘는 인자도 `INVALID_ARGUMENT`로 거부합니다.

## 로그인 실행 구분과 숨김 시작

등록 명령줄에는 프레임워크 인자 뒤에 예약 시작 인자를 하나 추가합니다. 일반 등록은
`--bunaway-autostart`, 숨김 등록은 `--bunaway-autostart-hidden`입니다. 두 인자도
260 UTF-16 코드 단위 제한에 포함합니다. 호스트는 앱 인자의 첫 항목에 있는 예약 인자를
소비하고 `desktop.onOpen`의 `request.launchReason`에 `"autostart"`를 전달합니다.
예약 인자가 없는 실행은 `"manual"`입니다. `request.source`는 별도로 최초 실행
`"initial"`과 이미 실행 중인 앱으로 전달한 `"second-instance"`를 구분합니다.
`request.argv`, `urls`, `files`에는 소비한 예약 인자를 포함하지 않습니다.
뒤에 있는 같은 문자열과 `--` 뒤의 문자열은 앱 인자로 유지합니다.

이 값은 실행 인자로 전달한 모드이며 Windows 로그인 실행의 인증 결과가 아닙니다.
수동 실행도 같은 예약 인자를 전달할 수 있습니다. 권한 승인이나 신뢰된 출처 판단에
사용하지 마세요. 기존 등록은 명시적으로 재등록하기 전까지 예약 인자가 없을 수 있습니다.
`--login`과 같은 앱 고유 인자는 계속 그대로 전달합니다.

macOS에는 아직 트레이 아이콘이 없어 호스트가 숨김 시작을 허용하지 않습니다.
`hidden: true`는 항상 `INVALID_ARGUMENT`로 거부하며 plist를 변경하지 않습니다.

숨김 등록에는 앱 정의의 `desktop.tray`가 필요합니다. 트레이가 없는 앱의
`autostart.enableAutostart({ hidden: true })`는 `INVALID_ARGUMENT`로 거부하며 Run 값을 변경하지 않습니다.
숨김 등록 뒤 앱에서 트레이를 제거하면 해당 시작도 UI Worker 생성 전에 실패합니다.

```ts
import { defineApp } from "@bunaway/backend";
import autostart from "@bunaway/plugin-autostart";

export default defineApp({
  modules: [],
  plugins: [autostart],
  desktop: {
    tray: { tooltip: "Memo" },
    closeBehavior: "hide",
    onOpen(request) {
      console.log(request.source, request.launchReason, request.argv);
    },
  },
});

// 사용자가 동의한 설정 명령에서 autostart.enable 권한으로 호출합니다.
// await autostart.enableAutostart({ args: ["--sync"], hidden: true });
```

숨김 로그인 시작은 선언한 시작 창의 HWND와 WebView, SDK 세션을 만들되 표시하거나
활성화하지 않습니다. 초기 `visible`과 `showWhenReady`의 자동 표시 조건도 이 실행에서는
적용하지 않습니다. 백엔드와 UI는 준비를 계속하며 트레이 Open, 수동 재실행이나
`DesktopContext.show()`로 같은 창과 세션을 복원합니다. 이후 창 생성에는 원래 선언의
표시 설정을 사용합니다. 앱이 `onOpen`에서 `show()`를 호출하거나 직접 창을 표시하면
숨김 시작 후에도 창이 표시됩니다.

이미 실행 중인 앱에 숨김 자동 실행 요청을 전달하면 현재 표시 상태를 유지하고
`onOpen`을 호출합니다. 이미 표시한 창을 숨기거나 숨긴 창을 자동으로 복원하지 않습니다.
일반 자동 실행과 수동 두 번째 실행은 기존 규칙대로 먼저 창 표시를 요청합니다.
실제 로그아웃, 로그인 실행과 작업 관리자 조작은 별도 대화형 검증입니다.

## 결과

`AutostartStatus`는 서로 독립인 등록과 Windows 활성 상태를 반환합니다.

| 필드 | 의미 |
| --- | --- |
| `registrationName` | 현재 앱과 실행 모드의 Run 값 이름 |
| `registered` | 해당 Run 값이 실제로 존재하는지 여부 |
| `commandLine` | 저장된 REG_SZ 명령줄. 값이 없거나 문자열 형식이 유효하지 않으면 `null` |
| `executablePath` | 저장된 명령줄에서 파싱한 절대 실행 경로. 관리 형식으로 읽을 수 없으면 `null` |
| `args` | 실행 파일 다음의 실제 저장 인자 배열. 개발 모드의 프레임워크 인자도 포함. 파싱할 수 없으면 `null` |
| `startupState` | `enabled`, `disabled`, `unknown` 중 하나. 등록 존재 여부와 별개 |
| `matchesCurrentLaunch` | 저장 경로와 프레임워크 인자 접두어가 현재 호스트 실행과 일치하는지 여부. 앱 인자는 비교하지 않음 |

macOS에서는 `registrationName`이 plist의 `Label`이자 파일 이름(`<Label>.plist`)입니다.
`registered`는 `Label`이 일치하고 `RunAtLoad`가 `true`인 plist가 있는지 나타냅니다.
`commandLine`은 `ProgramArguments`를 셸 인용으로 합친 표시용 문자열이며 실행에 사용하지 않습니다.
`executablePath`와 `args`는 첫 항목이 절대 경로이고 제어 문자가 없을 때만 채웁니다.
macOS에는 사용자가 시스템 설정의 로그인 항목에서 끈 상태를 읽는 공개 API가 없어
`startupState`는 항상 `unknown`입니다. `enabled`나 `disabled`로 추정하지 마세요.

조회는 등록을 고치거나 앱을 활성화하지 않습니다. Run 값이 남아 있어도 작업 관리자에서
비활성화하면 `registered: true`, `startupState: "disabled"`일 수 있습니다.
등록을 해제해도 Windows의 기존 비활성화 기록은 남을 수 있습니다.

Windows의 `StartupApproved\\Run`은 공개된 안정적 API가 아닙니다. 현재 구현은
알려진 12바이트 REG_BINARY에서 상태 0과 2는 `enabled`, 1과 3은 `disabled`로 읽습니다.
0과 1은 Windows Server 2022의 실제 시작 앱 설정에서 On과 Off 전환으로 확인했습니다.
값이 없거나 형식, 상태가 다르면 `unknown`입니다. 이를 활성 상태로 추정하지 마세요.
`enabled`도 실제 로그인 실행을 보장하지 않습니다. OS 정책, 안전 모드나 실행 파일
삭제가 실행을 막을 수 있으며 Windows가 실행을 지연할 수도 있습니다.

## 식별자와 실행 경로

등록 이름은 `bunaway.packaged.<appId>` 또는 `bunaway.development.<appId>`입니다.
`appId`는 검증한 앱 설정의 ID를 그대로 사용하며 앱 표시 이름이나 실행 파일 이름은
사용하지 않습니다. 동일 ID의 두 배포 앱은 같은 사용자 설정을 공유합니다.
개발 등록은 배포 등록을 바꾸지 않습니다. 런타임에서 ID를 변경하면 이전 ID의 등록을 자동으로
찾거나 삭제하지 않으므로 이전 ID로 실행하는 앱에서 먼저 해제해야 합니다.
Inno 설치는 이전 ID가 기록된 설치를 업데이트할 때 소유한 이전 등록을 정리합니다.

배포 앱은 현재 실행 중인 compiled EXE의 절대 경로와 앱 인자를 저장합니다.
PATH나 사용자 Bun 설치에 의존하지 않습니다. 개발 앱은 사용 중인 Bun의 절대 경로,
`--no-env-file`, `--no-install`, 절대 bunfig와 tsconfig 경로, 빌드한
`assets/boot.js`의 절대 경로를 저장합니다. 현재 Vite 서버 주소와 DevTools 옵션은
저장하지 않으며 로그인 시 디스크의 빌드된 웹 자산을 사용합니다. 개발 실행 경로가
길어 전체 명령줄 제한을 넘으면 등록할 수 없습니다. 짧은 개발 경로를 쓰거나 배포
EXE로 검증하세요. 앱 인자의 첫 항목으로 개발용 `--devtools`, `--dev-url`을 전달할 수 없습니다.

macOS의 plist는 `Label`, `ProgramArguments`, `RunAtLoad`(`true`)만 담습니다. 배포 앱은
앱 번들 안 compiled 실행 파일의 절대 경로를 저장합니다. 개발 앱은 Windows와 같은
Bun 실행 경로와 `boot.js` 인자를 저장합니다. 파일은 임시 파일에 쓴 뒤 `rename`으로 교체해
`0644` 권한으로 만들고, 같은 내용으로 다시 등록하면 쓰기를 생략합니다. 등록해도
`launchctl`로 즉시 적재하지 않으므로 현재 세션에서는 실행되지 않고 다음 로그인부터 실행됩니다.
같은 이름의 plist가 있지만 이 앱이 만든 것이 아니면(`Label` 불일치, 읽을 수 없는 형식,
심볼릭 링크 등) 등록과 해제 모두 `INTERNAL`로 거부하고 파일을 변경하지 않습니다.
해제는 이 앱의 plist만 지우며 이미 실행 중인 프로세스를 종료하지 않습니다.

로그인 실행의 작업 디렉터리는 Windows가 정하며 등록 API로 설정하지 않습니다.
상대 파일 인자는 로그인 시 작업 디렉터리 기준이므로 재실행해야 하는 파일은 절대 경로로
전달하세요. 개발 자산이나 EXE를 옮기거나 지우면 기존 등록도 그 옛 경로를 유지합니다.

## 갱신과 사용자 선택

`enableAutostart`는 현재 실행 모드의 값 하나를 현재 경로와 새 인자로 교체합니다.
같은 요청을 반복하면 기존 값이 같을 때 쓰기를 생략합니다. 업데이트나 이동 뒤에는
동의한 자동 실행 설정을 유지하는 앱이 새 위치에서 명시적으로 재등록해야 합니다.
앱 시작 시 무조건 재등록하거나 다른 ID의 값을 삭제하지 마세요.

재등록과 해제는 Windows 시작 앱 활성 기록을 수정하지 않습니다. 특히 사용자가
작업 관리자에서 비활성화한 선택을 우회하지 않습니다. `enableAutostart`가 성공해도
`startupState`가 `disabled`일 수 있습니다. 사용자는 Windows에서 직접 활성화해야 합니다.
`disableAutostart`는 등록이 없거나 반복 호출해도 성공하며 다른 앱의 값은 지우지 않습니다.
등록 변경은 현재 사용자 SID와 전체 Run 값 이름의 전역 mutex를 Inno 설치 프로그램과
공유합니다. 확인과 변경을 같은 잠금 안에서 수행합니다. I/O Worker를 막지 않도록
런타임은 잠금을 기다리지 않습니다.
다른 참여 프로세스가 계속 소유 중이면 `BUSY`로 거부하고 값을 변경하지 않습니다.
이전 버전과 외부 레지스트리 도구는 이 잠금에 참여하지 않습니다.
앱 EXE만 삭제하면 Run 값이 남습니다. `perUser` Inno 제거 프로그램은 해당 설치의
EXE를 가리키는 등록과 기록된 이전 ID의 소유 등록을 정리합니다.
설치 프로그램에 `autostart: true`를 선언하면 선택하지 않은 opt-in 작업을 제공합니다.
업데이트도 작업을 다시 선택해야 하며 작업 해제는 소유한 등록을 제거합니다.
옵션이 없으면 기존 런타임 등록의 인자를 유지하고 설치 경로만 갱신합니다.
`perMachine` 설치는 사용자 Run 정리를 제공하지 않습니다.
[설치 계약](/reference/packaging/channels/#로그인-자동-실행)에 ID 변경과 복구 규칙이 있습니다.

## MSIX 패키지

패키지 ID가 있는 프로세스에서는 같은 API가 manifest의 `desktop:StartupTask`로 동작합니다.
MSIX 패키지는 작업 ID `BunawayAutostart`를 `Enabled="false"`로 선언하므로 사용자가
앱을 실행하는 것만으로 로그인 실행이 켜지지 않습니다. 사용자가 동의한 설정 변경에서
`enableAutostart`를 호출해야 켜집니다.

`StartupTaskState`는 기존 `AutostartStatus` 필드로 표현하며 새 필드는 없습니다.

| `StartupTaskState` | `registered` | `startupState` |
| --- | --- | --- |
| `Disabled` | `false` | `disabled` |
| `DisabledByUser` | `true` | `disabled` |
| `DisabledByPolicy` | `false` | `disabled` |
| `Enabled`, `EnabledByPolicy` | `true` | `enabled` |

사용자나 정책이 끈 작업은 앱이 다시 켤 수 없습니다. 이때 `enableAutostart`는 실패하지 않고
`startupState: "disabled"`를 반환하며, 사용자는 Windows 설정의 시작 앱에서 직접 켜야 합니다.
정의된 값이 아닌 상태는 `unknown`입니다. `registrationName`은 작업 ID이고 `commandLine`,
`executablePath`, `args`는 `null`, `matchesCurrentLaunch`는 `false`입니다.
`disableAutostart`는 작업을 끕니다.

manifest의 StartupTask는 실행 파일을 인자 없이 시작합니다. 그래서 MSIX에서
`args`가 비어 있지 않거나 `hidden: true`인 `enableAutostart`는 `INVALID_ARGUMENT`로 거부하고,
예약 시작 인자가 없으므로 로그인 실행을 `launchReason: "autostart"`로 구분하지 못합니다. manifest에 이 작업을 선언하지 않은
패키지는 `UNSUPPORTED`입니다. 호출은 비동기 WinRT 작업이므로 호출 취소와 10초 기한을 따릅니다.
작업이 이미 바뀐 뒤 취소되거나 기한이 지나면 변경을 되돌리지 않으므로 `getAutostartStatus`로 현재 상태를
다시 확인하세요. MSIX 패키지는 `autostart` 플러그인을 쓰지 않아도 비활성 상태의 작업을 선언하며,
Windows 설정의 시작 앱 목록에 앱 항목이 나타납니다.

## 정책과 오류

| 작업 | 입력 | 권한 |
| --- | --- | --- |
| `autostart.enable` | `{ args: string[], hidden?: boolean }` | `autostart.enable` |
| `autostart.disable` | `null` | `autostart.disable` |
| `autostart.getStatus` | `null` | `autostart.getStatus` |

뷰에서 직접 호출하면 `commands`에 대응하는 `plugin.autostart.enable`,
`plugin.autostart.disable`, `plugin.autostart.getStatus`를 추가하고 필요한 권한을
`host.permissions`에 허용합니다. 명령 핸들러는 원래 뷰 권한을 사용합니다.
setup에서는 루트 `backend.permissions`를 사용합니다. 실행 파일이나 다른 앱 ID를
선택하는 입력과 관리자 범위는 제공하지 않습니다.

- `INVALID_ARGUMENT`: 입력, 인자 인코딩이나 전체 명령줄 길이가 유효하지 않거나 숨김 등록에 필요한 트레이가 없습니다.
- `PERMISSION_DENIED`: 정책 권한이나 사용자 레지스트리 접근 권한이 없습니다.
- `UNSUPPORTED`: Windows 어댑터나 호스트 실행 정보가 없거나, MSIX 패키지의 manifest에 StartupTask가 없습니다.
- `INTERNAL`: 레지스트리 조회, 갱신이나 명령줄 파싱에 실패했습니다. macOS에서는 plist 파일 접근에 실패했거나
  같은 이름의 기존 plist를 이 앱이 만들지 않았습니다.
- `CANCELLED`, `TIMEOUT`, `BUSY`: 기존 Host API의 취소, 기한과 대기열 제한입니다.

어댑터 종료는 DLL과 열린 핸들을 정리하지만 영속 등록을 해제하지 않습니다.
작업이 이미 레지스트리를 변경한 뒤 취소되거나 결과 조회가 실패하면 변경을 되돌리지
않습니다. 설정 화면은 다시 조회해서 현재 상태를 확인하세요.

현재 Windows x64의 개발 실행, 직접 배포와 Store 비패키지 실행을 지원합니다.
macOS는 사용자 LaunchAgent 등록, 조회와 해제를 지원합니다. plist는 앱을 실행한 프로세스의 HOME 아래 `Library/LaunchAgents`에 씁니다. SMAppService 로그인 항목은 서명된 앱
번들과 macOS 13 이상이 필요해 사용하지 않습니다. 숨김 시작, 로그인 항목 활성 상태 조회,
업데이트 뒤 등록 유지와 App Sandbox는 지원하지 않습니다. 임시 홈 디렉터리에서 plist를
쓰고 읽는 동작은 테스트로 검증했습니다. macOS CI는 shared Bun과 ad-hoc 서명한 compiled 앱을 실행해 등록, 반복 등록,
해제, 재실행 뒤 조회와 `plutil`의 plist 검사를 확인합니다. 실제 로그인 때 launchd가 앱을 실행하는지는 검증하지 않았습니다.
Linux와 모바일은 지원하지 않습니다.

MSIX 경로는 manifest 생성 결과와 상태 변환, 입력 거부를 테스트로 검증했습니다.
WinRT 호출은 패키지 ID가 없는 Windows 프로세스에서 호출이 오류로 끝나는 것까지 확인했습니다.
`win-store-msix` 채널은 컴파일된 앱 패키징을 아직 지원하지 않아 설치된 MSIX에서
StartupTask 활성화, 상태 조회와 로그인 실행은 검증하지 않았습니다.
