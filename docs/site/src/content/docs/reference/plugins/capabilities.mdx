```ts
capabilities(options?: InvokeOptions): Promise<Capabilities>
```

앱에 등록된 플러그인 작업의 플랫폼 지원 상태를 반환합니다.
직접 import한 `capabilities`는 기본 연결을 사용하며 연결 준비를 기다립니다.
options에 signal 또는 deadline을 전달할 수 있습니다.
[invoke의 취소와 기한](/reference/client/invoke/)과 같은 규칙을 적용합니다.

먼저 `@bunaway/plugin-capabilities`를 설치하고 앱에 capabilitiesPlugin을 등록합니다.
조회 결과에는 앱에 등록한 네이티브 플러그인 작업이 포함됩니다.
창 제어 작업도 windowsPlugin을 등록한 경우에만 조회 결과에 포함됩니다.

## 정책과 사용법

호출할 뷰의 `commands` 배열에 `plugin.capabilities.get`를 허용해야 합니다. host.permissions에도 `capabilities.get`을 추가합니다. 기본 템플릿에는 이 기능을 포함하지 않습니다.

```json
{ "commands": ["message.read", "message.save", "plugin.capabilities.get"] }
```

```ts
import { capabilities } from "@bunaway/plugin-capabilities";

const features = await capabilities();
const read = features.find((feature) => feature.name === "storage.readText");
console.log(read?.support);
```

위 JSON의 commands를 기존 뷰 객체에 추가합니다. 나머지 필수 정책 필드는 유지합니다.

## 결과

`name`, `support`, 선택적 `reason`을 가진 배열입니다.
`support`는 `supported`, `experimental`, `unsupported` 중 하나입니다.

## 의미와 실패

`support`는 플랫폼 어댑터의 구현 상태입니다. Windows 창 제어 플러그인은 `supported`입니다.
지원 여부는 호출 권한을 부여하지 않으며 실제 Host API 호출은 출처의 작업 권한을 검사합니다.
OS 동의 상태의 조회와 요청은 해당 기능 플러그인이 담당합니다.
앱 WebView가 없는 환경은 `UNSUPPORTED`, 정책 미허용은 `PERMISSION_DENIED`, 잘못된 기능 응답은 `INTERNAL`로 실패합니다.
조회는 현재 상태만 반환하며 OS 권한 요청이나 정책 변경은 실행하지 않습니다.

백엔드에서 조회하려면 [capabilities.get](/reference/host/capabilities-get/)을 사용합니다.
