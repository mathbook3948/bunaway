기본 export(`default`)를 `appearance`로 가져와 앱에 등록하고 호출합니다.

`@bunaway/plugin-appearance`를 설치하고 `appearance`를 앱의 plugins에 등록합니다.
`appearance.getPreferences()`에는 `appearance.getPreferences` 작업 권한이 필요합니다.
화면에서 직접 호출하면 commands에 `plugin.appearance.getPreferences`도 허용합니다.
Windows와 macOS arm64의 UI 실행을 지원합니다. macOS 조회는 AppKit의
메인 스레드에서 처리하며 다른 플랫폼은 `UNSUPPORTED`입니다.

```ts
import appearance from "@bunaway/plugin-appearance";
// 앱 정의: plugins: [appearance]
const preferences = await appearance.getPreferences();
```

매 호출에서 현재 값을 읽고 다음 객체를 반환합니다. Windows 매핑은 다음과 같습니다.

| 필드 | 의미 |
| --- | --- |
| appsTheme, systemTheme | HKCU Personalize의 AppsUseLightTheme와 SystemUsesLightTheme 선호. light, dark 또는 null |
| accentColor | DWM colorization의 RGB 부분. #rrggbb |
| highContrast, forcedColors | Windows 고대비 활성 플래그. OS의 강제 색 적용을 나타냄 |
| invertedColors | 고대비가 켜져 있고 COLOR_WINDOW의 상대 휘도(sRGB 선형화, WCAG 가중치)가 검정과 흰색 대비가 같은 휘도(약 0.179) 미만이면 true. Electron의 `nativeTheme.shouldUseInvertedColorScheme`(어두운 고대비 구성)에 대응 |
| reducedMotion | Windows client-area animation 설정이 비활성인지 여부 |
| transparencyEnabled | HKCU Personalize의 EnableTransparency 선호. boolean 또는 null |
| screenReaderEnabled | Windows SPI_GETSCREENREADER 설정 플래그 |
| colors | GetSysColor의 window, windowText, highlight와 highlightText. #rrggbb |

테마와 transparency는 사용자의 저장된 선호를 조회합니다. 관련 DWORD가 없거나 0과 1이
아니면 null이며 임의 기본값으로 대체하지 않습니다. 고대비가 적용되면 실제 렌더링 색은
테마 선호와 다를 수 있습니다. accentColor에는 DWM 알파 값을 포함하지 않습니다.
Windows의 invertedColors는 어두운 고대비 색 구성을 뜻하며, 고대비가 꺼져 있으면 항상 false입니다.
설정 > 접근성 > 색 필터와 색 반전 필터는 공개 조회 API가 없어 반영하지 않습니다.
플래그는 실제 스크린 리더 프로세스나 WebView 접근성 트리의 활성 여부를 보장하지 않습니다.
Windows에서는 `appearance.changed`로 OS 설정 변경을 구독할 수 있습니다. 아래의 창 프레임
테마 API와 별개로 `getPreferences()`는 항상 OS 설정을 읽습니다.

macOS 매핑은 다음과 같습니다.

| 필드 | 의미 |
| --- | --- |
| appsTheme | NSApplication.effectiveAppearance를 Aqua와 DarkAqua에 best-match한 light 또는 dark. 일치하지 않으면 null |
| systemTheme | null. Windows의 별도 시스템 셸 테마에 대응하는 값을 제공하지 않음 |
| accentColor | NSColor.controlAccentColor를 sRGB로 변환한 #rrggbb |
| highContrast | NSWorkspace.accessibilityDisplayShouldIncreaseContrast |
| forcedColors | false. Increase Contrast는 Windows의 강제 색 팔레트와 다름 |
| invertedColors | NSWorkspace.accessibilityDisplayShouldInvertColors |
| reducedMotion | NSWorkspace.accessibilityDisplayShouldReduceMotion |
| transparencyEnabled | NSWorkspace.accessibilityDisplayShouldReduceTransparency의 반대 값 |
| screenReaderEnabled | NSWorkspace.isVoiceOverEnabled. VoiceOver의 활성 플래그만 조회 |
| colors.window | NSColor.windowBackgroundColor |
| colors.windowText | NSColor.textColor |
| colors.highlight | NSColor.selectedTextBackgroundColor |
| colors.highlightText | NSColor.selectedTextColor |

macOS 색은 앱의 현재 유효 appearance에서 평가하고 sRGB로 변환합니다. RGB 성분을
0부터 1 사이로 제한한 뒤 가장 가까운 8-bit 값으로 반올림하며 알파는 포함하지 않습니다.
조회 중 임시로 선택한 스레드 drawing appearance는 성공과 실패 모두에서 복원합니다.
appsTheme은 저장된 사용자 선호와 다를 수 있으며 앱의 appearance override를 반영합니다.
AppKit가 앱 override와 OS 접근성 설정으로 유효 appearance를 결정하므로 지정한
appearance와 유효 appearance는 다를 수 있습니다.
Auto 모드는 조회 시점의 유효 light 또는 dark로 반환합니다. 실제 창의 배경색이나
WebView의 CSS 색을 읽는 기능은 아닙니다.
screenReaderEnabled는 다른 보조 기술의 사용 여부, Accessibility 신뢰 권한 또는
WebView 접근성 트리의 활성 여부를 나타내지 않습니다. 설정을 바꾸거나 Accessibility
신뢰 권한을 요청하지 않으며 변경 알림은 구독하지 않습니다.

권한 거부는 `PERMISSION_DENIED`, OS 조회 실패는 `INTERNAL`입니다.
호스트 종료 뒤 호출은 `CANCELLED`입니다. 실제 사용자 테마 전환, 고대비 화면 및 보조 기술의
동작 검증은 사용자 세션의 수동 검증이 필요합니다.

## Windows 변경 구독

`appearance.changed`의 payload는 `AppearancePreferences`입니다. 화면 정책의 events에
`appearance.changed`, host.permissions에 `appearance.getPreferences`를 모두 허용해야 합니다.
구독한 현재 세션에만 전달하며 OS의 테마, accent, 시스템 색, 접근성 설정 변경과 절전 복귀 때
값을 다시 읽습니다. 같은 값의 반복 알림은 보내지 않습니다. 초기 값은 `getPreferences()`로
조회합니다. macOS에서는 이 이벤트를 발생시키지 않습니다.

```ts
const stop = await client.listen("appearance.changed", ({ payload: preferences }) => {
  console.log(preferences.appsTheme, preferences.accentColor, preferences.highContrast);
}, { onError(error) { console.error(error); } });
// 컴포넌트 정리 때 호출합니다.
await stop();
```

읽기 실패는 기존 값을 유지하고 호스트 진단에 기록합니다. 다음 OS 알림에서 다시 시도합니다.
구독 해제와 문서 이동 뒤에는 이전 세션으로 이벤트를 보내지 않습니다. 플러그인 종료 때
네이티브 구독과 DLL을 정리합니다. OS 설정의 실제 전환과 보조 기술 표시는 수동 검증 대상입니다.

## Windows 접근성 상태

`appearance.getAccessibilityState()`는 신뢰된 백엔드에서 호출하며 `appearance.getAccessibilityState`
권한이 필요합니다. 보조 기술 사용 여부는 민감한 정보라서 화면에서 직접 호출하거나 화면 명령의 호출 권한을
이어받으면 `PERMISSION_DENIED`입니다. 입력은 `null`이며 macOS와 다른 플랫폼은 `UNSUPPORTED`입니다.

```ts
const { screenReaderEnabled, assistiveTechnologyActive } =
  await appearance.getAccessibilityState();
```

| 필드 | 의미 |
| --- | --- |
| screenReaderEnabled | SPI_GETSCREENREADER 설정 플래그. `getPreferences()`의 같은 이름 필드와 같은 값 |
| assistiveTechnologyActive | uiautomationcore.dll의 `UiaClientsAreListening` 결과. 스크린 리더나 돋보기 같은 UI Automation 클라이언트가 접근성 트리를 구독 중이면 true |

`assistiveTechnologyActive`는 Electron의 `app.accessibilitySupportEnabled`처럼 클라이언트의 실제 연결을
읽는 값이며 설정 플래그와 독립적입니다. 플래그가 꺼져 있어도 클라이언트가 연결되어 있을 수 있고 그 반대도 가능합니다.
이 값은 WebView의 접근성 트리 활성 상태를 직접 읽거나 강제로 켜는 기능이 아닙니다.
WebView 접근성 지원을 강제로 켜거나 끄는 API와 지원 기능을 고르는 API는 제공하지 않습니다. 이 조회는 상태를 읽을 뿐 바꾸지 않습니다.
uiautomationcore.dll은 첫 조회 때 로드합니다. 이 DLL을 로드하거나 함수를 찾을 수 없는 Windows에서는
이 조회만 `UNSUPPORTED`이고 `getPreferences()`와 테마 API는 계속 동작합니다. 호스트 종료 뒤 호출은 `CANCELLED`입니다.

UI Automation 클라이언트 연결 변화는 연결과 해제를 모두 알리는 OS 알림이 없고 폴링은 상시 비용을 지며 주기 사이의 변화를 놓치므로
전용 이벤트를 제공하지 않습니다([ADR 0118](https://github.com/mathbook3948/bunaway/blob/main/docs/decisions/0118-uia-client-connection-change-event.md)).
`screenReaderEnabled`의 변화는 `appearance.changed`로 구독할 수 있으며, 연결 상태는 필요한 시점에 다시 조회합니다.
실제 스크린 리더 연결 시의 값은 보조 기술이 있는 대화형 세션에서 수동으로 검증해야 하며, 자동 검증은 값의 타입만 확인합니다.

## Windows 앱 테마

`appearance.getTheme(null)`와 `appearance.setTheme({ theme })`는
신뢰된 백엔드에서 호출합니다. 각각 `appearance.getTheme`, `appearance.setTheme` 권한이
필요하며 화면에서 직접 호출하거나 화면 명령의 호출 권한을 이어받으면 `PERMISSION_DENIED`입니다.
이 API는 Windows의 기본 창 프레임과 웹 콘텐츠의 `prefers-color-scheme`을 함께 제어합니다.
HTML/CSS와 Windows 사용자 설정은 변경하지 않습니다. 웹 콘텐츠는 반환된 상태에 맞춰 앱의
스타일을 적용할 수 있습니다.

```ts
// 신뢰된 백엔드의 시작 또는 백그라운드 작업에서 호출합니다.
await appearance.setTheme({ theme: "dark" });
const appTheme = await appearance.getTheme(null);
// system은 앱 지정을 지워 OS 설정을 다시 따릅니다.
await appearance.setTheme({ theme: "system" });
```

| 입력 또는 결과 | 의미 |
| --- | --- |
| theme | system, light 또는 dark. 시작값은 system이며 기존 창과 이후 생성할 창에 적용. null은 INVALID_ARGUMENT |
| preference | 요청한 앱 선호 |
| override | 항상 null. 창 단위 지정이 없음 |
| effectiveTheme | 관측한 OS 설정으로 결정한 기본값. 고대비 또는 알 수 없는 system 선호는 null |
| highContrast | 마지막으로 관측한 OS 고대비 상태 |

`system`은 OS의 앱 테마 선호를 따릅니다. 고대비가 활성화되면 DWM dark mode를 끄고 Windows 색 처리를 우선합니다.
요청한 선호는 유지하므로 고대비 종료 뒤 다시 적용합니다. OS 선호가 없으면 dark mode를 끄되
`effectiveTheme`은 null로 유지합니다. 이 값은 화면의 픽셀 색이나 WebView의 CSS 색을 읽은 결과가
아니며 OS 설정 변경 알림을 처리한 시점의 상태입니다. 창 적용에 실패하면 이전 effectiveTheme을
유지하며 preference는 요청 선호를 나타냅니다.

### 웹 콘텐츠의 prefers-color-scheme

`light`와 `dark`는 해당 창의 WebView2 `PreferredColorScheme`을 지정해 CSS 미디어 쿼리
`prefers-color-scheme`이 프레임과 같은 값을 보고합니다. 이미 열린 문서에는 미디어 쿼리 `change`
이벤트로 전달되고, 이후 탐색한 문서와 창을 만들기 전에 선택한 값에도 유지됩니다. `system`은
WebView2의 Auto로 두어 OS의 앱 테마를 따릅니다. 고대비에서도 Auto로 두어 Windows 색 처리를
우선합니다. 플러그인을 종료하면 Auto로 돌려놓습니다.

WebView2 런타임이 프로필 색 구성표를
지원하지 않으면 프레임 적용은 그대로 두고 콘텐츠 적용만 건너뜁니다. 폼 컨트롤과 스크롤바의 색은
CSS `color-scheme` 속성을 따르며 WebView의 배경색은 바꾸지 않습니다.

문서 reload와 창 재생성은 앱 테마를 유지합니다. 앱 재시작이나 플러그인 재초기화는 system으로 돌아가며 디스크에 저장하지
않습니다. 플러그인 종료는 살아 있는 창의 DWM dark mode를 해제합니다.

Windows의 `DWMWA_USE_IMMERSIVE_DARK_MODE`를 사용합니다. 해당 DWM 속성을 지원하지 않는
Windows에서는 OS 조회와 변경 이벤트를 계속 제공하지만 테마 조회와 지정은 `UNSUPPORTED`입니다.
조회는 적용된 창 상태와 별개로 요청 선호를 반환합니다.
macOS는 아래 절의 앱 테마를 지원하며 다른 플랫폼의 테마 작업은 `UNSUPPORTED`입니다. 네이티브 적용 실패는 `INTERNAL`이며
테마 변경 중 실패하면 이전 선호와 창의 적용 상태를 복원하려 시도합니다. 복원도 실패하면
INTERNAL을 반환하며 다음 변경 알림에서 다시 적용합니다. 실제 프레임 색, 사용자 테마 전환 및
고대비 렌더링은 대화형 Windows 세션에서 추가 검증해야 합니다. 콘텐츠의 `prefers-color-scheme`은
실제 WebView2 런타임에서 확인합니다.

## macOS 앱 테마

`appearance.getTheme(null)`와 `appearance.setTheme({ theme })`는
신뢰된 백엔드에서 호출하며 권한 조건은 Windows와 같습니다. 앱 전체 `NSApplication.appearance`를
지정하므로 앱의 모든 창과 WKWebView 콘텐츠의 `prefers-color-scheme`이 함께 바뀝니다.
macOS 사용자 설정과 HTML/CSS는 변경하지 않습니다.

```ts
await appearance.setTheme({ theme: "dark" });
const state = await appearance.getTheme(null);
// system은 앱 지정을 지워 OS 설정을 다시 따릅니다.
await appearance.setTheme({ theme: "system" });
```

| 입력 또는 결과 | 의미 |
| --- | --- |
| theme | system, light 또는 dark. null은 INVALID_ARGUMENT |
| preference | 마지막으로 요청한 앱 선호. 시작값은 system |
| override | 항상 null. 창 단위 지정이 없음 |
| effectiveTheme | 지정 직후 `NSApplication.effectiveAppearance`에서 읽은 light 또는 dark |
| highContrast | 지정 직후 관측한 OS 대비 증가 상태 |

`system`은 `NSApplication.appearance`를 nil로 되돌리는 것이며 현재 OS 외관을 고정하지 않으므로
이후 OS 외관 변경을 계속 따릅니다. 지정한 선호는 디스크에 저장하지 않으며 앱 재시작은 system으로
돌아갑니다. 플러그인을 종료할 때 이 플러그인이 지정한 값을 nil로 되돌립니다. 대비 증가가 켜져
있으면 AppKit이 유효 외관을 정하므로 `effectiveTheme`은 지정한 값과 다를 수 있습니다.
`effectiveTheme`은 화면의 픽셀 색이 아니라 요청을 처리한 시점의 AppKit 상태입니다.
macOS의 `appearance.changed` 이벤트는 아직 제공하지 않으므로 필요하면 다시 조회합니다.
