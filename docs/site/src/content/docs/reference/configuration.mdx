## 최상위 필드

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `version` | 예 | 현재 `1` |
| `build` | 예 | 앱 정의, 프런트엔드 자산 위치와 웹 빌드 명령 |
| `app` | 예 | 앱 ID, 창 정의와 시작 페이지 |
| `bundle` | 패키징 시 | 배포 채널 설정. 선언하면 일반 검증, 개발, 빌드에서도 형식 검사 |
| `dev` | 아니요 | CLI가 관리할 외부 UI 개발 서버 |
| `plugins` | 아니요 | 설치한 선택 플러그인별 설정 |

알 수 없는 설정 필드는 거부합니다. 이전 `build.backend`, `build.windowsApp` 대신 `build.app`을 사용하세요.
객체, 필수 문자열, 알 수 없는 필드와 창 크기 오류에는 설정 파일 이름과 필드 경로를 표시합니다.
예를 들어 창 너비 오류는 `bunaway.json: app.window.width`로 시작합니다.
설정 파일은 `src-bunaway/bunaway.json` 한 곳에서 읽습니다. 이전에 사용하던 루트 설정 파일이나 분리된 설정 파일은 읽지 않습니다.

## build

| 필드 | 설명 |
| --- | --- |
| `app` | 필수. AppDefinition을 default export하는 모듈. 템플릿은 `src-bunaway/app.ts` |
| `frontend` | 필수. 앱에 포함할 웹 UI 자산 디렉터리 |
| `command` | 선택. 웹 프로덕션 빌드의 실행 파일과 인자 배열. 예: `["bun", "run", "build:web"]` |
| `resources` | 선택. 앱 리소스 디렉터리(`ctx.app.paths.resources`)로 복사할 프로젝트 상대 파일과 디렉터리 배열. 예: `["resources/tray.ico"]` |

소스와 패키징 파일의 경로는 프로젝트 루트를 기준으로 해석합니다.
모든 플랫폼에서 `build.app`에 지정한 앱 정의를 사용합니다.

`build.frontend`는 앱 산출물 경로와 분리해야 합니다. `dist` 전체를 웹 출력으로 지정할 수 없습니다.
`dist/windows-x64`, `dist/macos-arm64`, `.bunaway/locks`, `.bunaway`와 같거나
이 경로를 포함하거나 그 안에 속하면 거부합니다. `web-dist`나 `dist/web`처럼
앱 출력과 겹치지 않는 디렉터리를 사용하세요. 웹 도구의 출력 경로도 같은 디렉터리로 지정합니다.

`build.command`는 프로젝트 루트에서 실행합니다. 비어 있지 않은 문자열 배열이어야 하며 빈 인자와 NUL 문자는 거부합니다.
shell 문자열로 해석하지 않습니다. `&&` 같은 연산이 필요하면 package.json의 웹 빌드 스크립트에 작성하세요.
`bun`은 CLI를 실행한 Bun의 절대 경로로 해석합니다. 환경과 stdout/stderr를 이어받습니다.
프로덕션 `build`와 `package --build`는 이 명령을 실행하고 종료 코드 0을 확인한 뒤 `frontend`와 시작 페이지를 검증합니다.
기존 웹 출력이 있어도 명령을 매번 실행합니다. 실패하면 앱 빌드와 패키징을 중단합니다.
Ctrl+C나 SIGTERM으로 빌드를 중단하면 실행한 명령과 하위 프로세스를 정리하고 빌드 잠금을 해제합니다.
명령 종료 후 하위 프로세스의 정리 완료를 확인하지 못하면 빌드는 실패합니다.
생략하면 지정한 정적 자산을 그대로 사용합니다. `dev`, `doctor`, `validate`, `contract`, `package` 단독 실행은 웹 빌드 명령을 실행하지 않습니다.

`build.resources`의 각 항목은 같은 상대 경로로 리소스 디렉터리에 복사됩니다. Windows 패키지에서는 실행 파일 폴더,
개발 빌드에서는 빌드 출력 폴더, macOS에서는 `Contents/Resources`입니다. Windows 설치 파일과 macOS 번들에도 그대로 포함됩니다.
Electron의 `extraResources`나 Tauri의 `bundle.resources`처럼 지정한 파일을 리소스 디렉터리로 복사하지만, 더 엄격합니다.
프로젝트 밖 경로와 glob은 받지 않고, 링크는 따라가지도 다시 만들지도 않고 거부합니다.
패키지에 선언하지 않은 프로젝트 밖 파일이 섞이지 않게 하려는 선택입니다. 항목은 파일이거나 일반 파일만 담은 디렉터리여야 하고,
경로의 어느 구간이든 링크이거나 특수 파일이면 따라가지 않고 거부합니다. 원본 검사는 컴파일 전에 하므로 오류가 있으면 빌드가 바로 중단됩니다. 빈 디렉터리는 복사하지 않습니다.
경로는 `..`, `.`, 빈 세그먼트, 절대 경로, 드라이브 문자와 Windows 파일 이름에 쓸 수 없는 문자를 거부하며 최대 256개입니다.
빌드가 쓰는 `assets`, `licenses`, `runtime`, `packaged`, `manifest.json`, `WebView2Loader.dll`과 앱 실행 파일 이름으로 시작하는 항목,
다른 항목과 같거나 그 안에 속하는 항목, 앱 출력과 `.bunaway`에 겹치는 항목도 거부합니다.
복사 대상에 이미 파일이 있으면 덮어쓰지 않고 빌드를 중단합니다. Windows 8.3 짧은 이름으로 다른 파일을 가리킬 수 있는 `~숫자` 세그먼트도 거부합니다.
디렉터리 항목은 숨김 파일과 `.env`, `.git` 같은 점 파일도 그대로 복사하므로 필요한 파일만 담은 디렉터리를 선언하세요.
복사한 파일은 매니페스트 해시 검증 대상이 아닙니다.

웹 도구와 앱 CLI의 스크립트 이름을 구분하세요. 예를 들어 웹 `build`를 `build:web`으로 옮기고 앱의 `build`를 `bunaway build`로 연결합니다.
웹 `dev`도 `dev:web`으로 구분해 `dev.command`에 연결합니다. 스크립트 이름은 앱에서 정하며 설정의 실행 명령과 일치해야 합니다.
`build.command`가 다시 같은 앱의 `bunaway build`나 `package --build`를 호출하면 재귀 빌드 오류로 중단합니다.

## app

| 필드 | 설명 |
| --- | --- |
| `appId` | 앱 데이터와 Windows 작업 표시줄의 식별자. 1–64자의 소문자 영숫자, 점, 하이픈. 시작과 끝은 영숫자 |
| `title` | 앱 이름. 창 제목으로도 사용. 비어 있지 않은 문자열, 최대 1024자 |
| `executableName` | 선택. Windows GUI 실행 파일 이름. `.exe`를 포함하며 기본값은 `<appId>.exe`. 경로, 예약 장치 이름, 점이나 공백으로 끝나는 이름, 설치 프로그램의 `uninsNNN.exe` 이름과 Windows 파일 이름 금지 문자는 거부 |
| `icon` | 선택. 프로젝트 루트 기준 Windows `.ico` 파일. 실행 파일, 창과 트레이에 사용. 생략하면 기본 앱 아이콘 사용 |
| `view` | 선택. 정책 뷰 ID. 생략하면 정책의 유일한 뷰를 사용하며 정책에는 뷰가 하나만 있어야 함 |
| `home` | 시작 페이지. 현재 로컬 자산 origin `https://app.bunaway.local` 사용 |
| `startup` | 선택 boolean, 기본 `true`. `false`이면 앱이 `windows.create`로 열 때까지 창을 만들지 않음 |
| `visible` | 선택 boolean, 기본 `true`. `false`이면 숨긴 채 생성 |
| `showWhenReady` | 선택 `"document"` 또는 `"sdk"`. 첫 준비 완료 뒤 한 번 표시 |
| `window.width` | 정수, 200–8192 |
| `window.height` | 정수, 200–8192 |
| `window.minWidth`, `window.minHeight` | 선택적 정수 또는 `null`, 200–8192. 생략하거나 `null`이면 해당 축의 최소 제한 없음 |
| `window.maxWidth`, `window.maxHeight` | 선택적 정수 또는 `null`, 200–8192. 생략하거나 `null`이면 해당 축의 최대 제한 없음 |
| `window.x`, `window.y` | Windows 전용. signed 32-bit outer 물리 화면 좌표. 두 축을 함께 지정하며 음수도 허용. 생략하거나 둘 다 `null`이면 위치 미지정 |
| `window.center` | Windows 전용 boolean, 기본 `false`. 주 모니터 작업 영역의 outer 중앙. x/y와 함께 켜면 오류 |
| `window.useContentSize` | Windows 전용 boolean, 기본 `true`. `false`이면 width/height를 논리 outer 크기로 해석. min/max는 항상 content 제약 |
| `window.preventOverflow` | Windows 전용 boolean, 기본 `false`. 선택한 모니터의 작업 영역에 초기 outer 크기와 위치를 보정 |
| `window.focusable` | Windows 전용 boolean, 기본 `true`. `false`는 사용자 클릭과 호스트의 전경 활성화를 차단하며 Windows 기본 동작상 작업 표시줄에도 나타나지 않음 |
| `window.titlebar` | Windows 전용 `"system"` 또는 `"custom"`, 기본 `"system"`. custom은 시스템 caption을 제거하고 네이티브 resize 테두리를 유지함. WebView2 CSS `app-region: drag/no-drag`로 사용자 타이틀바를 구성함 |
| `window.alwaysOnTop` | Windows 전용 boolean, 기본 `false`. 활성화 없이 일반 창보다 위에 배치함 |
| `window.skipTaskbar` | Windows 전용 boolean, 기본 `false`. tool-window style로 작업 표시줄과 Alt+Tab에서 제외함 |
| `window.contentProtection` | boolean, 기본 `false`. 스크린샷과 화면 공유에서 창을 제외함. Windows와 macOS에서 지원함 |
| `window.transparent` | Windows 전용 boolean, 기본 `false`. `true`면 창과 WebView2 배경을 알파 0으로 만들어 페이지가 칠하지 않은 영역에 바탕화면이 보임. `titlebar: "custom"`이 필요하고 `backgroundColor`와 함께 선언할 수 없음 |
| `window.backgroundColor` | Windows 전용 문자열 `#RGB` 또는 `#RRGGBB`. 창과 WebView 문서의 뒤와 문서가 그려지기 전에 보이는 불투명 배경색이며 생략하면 시스템 색과 WebView2 기본 색을 유지함. 알파는 받지 않음 |
| `window.maximized` | Windows 전용 boolean, 기본 `false`. 초기 최대화. 일반 복원 영역에는 초기 크기와 위치 적용 |
| `window.fullscreen` | Windows 전용 boolean, 기본 `false`. 초기 전체화면. maximized와 함께 켜면 전체화면 해제 뒤 최대화 복원 |

초기 크기, 위치, center와 preventOverflow는 일반 복원 영역을 정하며 이후 최대화 또는 전체화면을 적용합니다.
숨김과 `showWhenReady`는 초기 상태와 함께 사용할 수 있습니다. 초기 전체화면을 해제해도 현재 표시 상태를 유지합니다.
따라서 준비 전에 해제하면 계속 숨겨져 있고 준비 후 표시된 창을 해제하면 계속 표시합니다.
생성별 `options.window`도 이 두 boolean을 필드별로 병합하며 `false`는 선언한 초기 상태를 해제합니다.

`home`에는 URL 사용자 정보와 fragment를 넣을 수 없습니다.
창의 너비와 높이는 96 DPI 기준 논리 픽셀입니다. Windows가 대상 모니터의 DPI에 맞춰 실제 픽셀로 변환합니다.
`executableName`, `icon`은 Windows 빌드에서 적용합니다. 아이콘 파일이 없거나 잘못된 ICO이면 빌드가 실패합니다.
Windows에서는 기본 이름 `<appId>.exe`도 같은 파일 이름 검사를 받습니다. 기본 이름이 유효하지 않으면
`app.executableName`에 다른 이름을 지정하세요.
`validate`와 프로덕션 `build`는 시작 페이지의 실제 파일을 확인합니다.
앱은 창 하나와 뷰 하나를 가집니다. `startup`, `visible`, `showWhenReady`는 `app`에 직접 지정합니다.
`startup`은 boolean이며 생략하면 `true`입니다. `false`이면 창을 API로 생성합니다.
`visible?: boolean`과 `showWhenReady?: "document" | "sdk"`도 지정할 수 있습니다.
`visible`의 기본값은 `true`입니다. `false`이면 처음부터 숨긴 채 만들며 창을 표시하거나 활성화하지 않습니다.
`showWhenReady`를 지정하면 `visible` 값과 관계없이 숨겨서 생성하고 첫 준비 완료 뒤 한 번 표시합니다.
`"document"`는 웹 문서 완료, `"sdk"`는 웹 문서와 SDK 완료를 모두 기다립니다. 앱 데이터나 UI 초기화는 포함하지 않습니다.
준비 실패나 취소 중에는 자동으로 표시하지 않습니다. Windows와 macOS가 모두 적용하며,
macOS는 숨겨서 생성한 창을 앞으로 가져오거나 key window로 만들거나 앱을 활성화하지 않고
준비 조건을 만족하면 최초 표시와 같이 key window 전환과 앱 활성화를 요청합니다.
완료 조건과 상태 조회는 [창 준비](/reference/host/windows/#창-준비)를 따릅니다.
설정한 최소값은 최대값보다 클 수 없습니다.
초기 크기가 제약을 벗어나면 제약 범위로 보정합니다.

초기 좌표가 있으면 해당 점의 모니터, 모니터 밖이면 가장 가까운 모니터를 선택합니다.
없으면 주 모니터를 사용합니다. 작업 영역은 태스크바를 제외한 `rcWork`입니다.
창 생성 뒤 실제 창의 DPI와 프레임으로 크기를 다시 계산합니다. 혼합 DPI 모니터 경계에서
창이 다른 모니터에 더 많이 걸쳐도 처음 선택한 작업 영역은 유지합니다.
초기 보정 중 DPI가 다시 바뀌면 크기와 위치를 함께 재계산합니다. 큰 창이 서로 다른
DPI 모니터 사이를 왕복해 배치가 수렴하지 않으면 새 창을 정리하고 생성 실패를 반환합니다.
재생성에서 이미 닫은 이전 창의 복원은 보장하지 않습니다.
`center`와 `preventOverflow` 없이 위치를 생략하면 기존 OS 기본 위치와 그 위치의 DPI를 유지합니다.
위치 없이 `preventOverflow`만 켜면 주 모니터 작업 영역의 왼쪽 위에서 시작합니다.
`center`와 `preventOverflow`는 함께 켤 수 있습니다. 크기와 중앙 좌표의 변환은
`Math.round`를 쓰며 정확한 반은 양의 무한대 방향입니다. x/y는 DPI로 다시 배율하지 않습니다.
outer 크기 요청은 대상 DPI의 프레임을 뺀 뒤 논리 content 제약으로 보정하므로 프레임과 반올림에 따라 달라질 수 있습니다.
`preventOverflow`는 content 제약 적용 뒤 크기를 축별로 줄이고 위치를 이동합니다.
작업 영역에 최소 content 크기와 프레임이 들어가지 않으면 생성 전에 `INVALID_ARGUMENT`입니다.
min이 없으면 자동 축소 결과는 200보다 작아질 수 있지만 content는 최소 1 논리 픽셀입니다.
끄면 작업 영역보다 큰 크기와 화면 밖 위치를 허용합니다. 오른쪽과 아래쪽을 포함한
outer 좌표가 signed 32-bit 범위를 벗어나면 거부합니다. 이후 이동과 크기 조절은 제한하지 않습니다.
macOS는 새 배치 필드를 명시하면 기본값이나 지연 창에서도 `UNSUPPORTED`입니다.
실행 중 사용자 크기 조절과 이동 허용은 [창 API](/reference/host/windows/)의
`setResizable`, `isResizable`, `setMovable`, `isMovable`로 제공합니다.
사용자 크기 조절 중 내용 영역의 가로세로 비율을 고정하거나 해제하는 기능도 같은 창 API의
`setAspectRatio`, `getAspectRatio`로 제공하며, 초기 창 선언에는 비율 필드가 없습니다.
실행 중 중앙 배치는 같은 창 API의 `windows.center`로 제공하며, 현재 모니터 또는 `monitorId`로 지정한 모니터를 사용합니다.
초기 창 선언에서 모니터를 지정하는 기능은 아직 지원하지 않습니다.
`app.view`가 정책의 유일한 뷰가 아니거나 home origin이 그 뷰에 허용되지 않으면 오류입니다.
생성 호출의 `{ options? }`는 제목, 부분 크기와 제약, 표시와 준비 후 표시를
이번 생성에만 바꿀 수 있습니다.
`startup: false`이면 창 없이 시작합니다.
앱 정의의 `desktop.tray` 또는 `desktop.closeBehavior: "keep-alive"`가 필요합니다.
트레이를 쓰려면 @bunaway/plugin-tray 설치와 tray 등록도 필요합니다.
CLI는 창 선언을 검사하고, 호스트는 앱 정의를 읽은 뒤 이 실행 유지 조건을 검사합니다.
조건을 충족하지 않으면 `app.startup is false` 진단과 필요한 desktop 설정을 알리고 시작에 실패합니다.
macOS는 `keep-alive`여도 시작 창이 필요합니다. 호스트가 앱 코드를 실행하기 전에 창 선언을 검증해, `startup: false`이면 `UNSUPPORTED`로 시작에 실패합니다.
창 제목은 1–1024자이며 NUL을 넣을 수 없습니다.
생성하지 않는 창도 프로덕션 시작 페이지 파일을 검증합니다.
macOS에서 앱 자산 origin에 명시적 포트를 지정하면 `home`은 같은 origin을 사용하고,
뷰의 정책에도 그 포트를 포함한 origin을 허용해야 합니다.

## dev

| 필드 | 설명 |
| --- | --- |
| `command` | 실행 파일과 인자의 비어 있지 않은 문자열 배열 |
| `url` | 준비 확인, 탐색에 사용할 정확한 loopback URL |
| `timeoutMs` | 생략 시 30,000. 정수, 100–300,000 |

허용 URL 호스트는 `localhost` 또는 `127.0.0.1`입니다.
서버의 준비 확인 경로는 인증과 redirect 없이 2xx를 반환해야 합니다. HTTPS를 쓰면 유효한 인증서가 필요합니다.
`app.home`은 프로덕션 시작 페이지로 유지하고 개발 서버 주소는 `dev.url`에 지정합니다.

[개발 흐름](/guides/development/)에 Vite 설정과 명령 예시가 있습니다.

## plugins

`plugins.<이름>`에 설치한 선택 플러그인이 읽는 설정을 JSON 객체로 둡니다. 이름은 플러그인 등록 이름
(`updater`)이며 빌드는 설치되지 않은 이름과 객체가 아닌 값을 거부합니다(호스트는 객체 여부와 크기만 다시 검사합니다). 전체 크기는 JSON으로 16 KiB 이하여야
합니다. 호스트는 모양만 검사하고 값을 플러그인 어댑터에 전달하며, 내용 검증은 플러그인이 어댑터를 만들
때 합니다. 화면과 명령 입력은 이 값을 바꿀 수 없습니다. 예시는 [updater](/reference/plugins/updater/)를
참고하세요. 설계 근거는 ADR 0025에 있습니다.

## bundle

`bundle.channels`에 배포 채널별 설정을 둡니다.
최소 `win-direct` 설정과 실행 방법은 [빌드와 패키징](/guides/build-and-package/)을 따릅니다.
전체 필드는 [bundle 설정](/reference/packaging/configuration/)에서 확인할 수 있습니다.
서명과 필요한 도구, 스토어별 동작은 [채널 레퍼런스](/reference/packaging/channels/)에서 설명합니다.

## CLI 명령

아래는 CLI 자체의 명령입니다. 모든 생성 템플릿은 dev, build, package, validate, doctor 스크립트로 이 명령을 연결합니다.

```text
bunaway create <new-directory> [--template vanilla|vite|react|vue|svelte] [--package-dir <tarball-directory>]
bunaway validate [directory]
bunaway contract [directory]
bunaway doctor [directory]
bunaway dev [directory]
bunaway build [directory]
bunaway package <channel> [directory] [--build]
```

디렉터리를 생략하면 현재 앱 디렉터리를 사용합니다.
`doctor`는 개발 설정을 검사하고, `validate`는 프로덕션 UI 자산을 확인합니다.
웹 빌드 도구를 사용하는 앱은 `validate` 전에 프로덕션 자산을 준비하세요.
