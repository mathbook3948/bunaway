## 창과 뷰는 어떤 관계인가요?

**창**은 운영체제의 창입니다. **뷰**는 웹 UI와 접근 정책을 구분하는 단위입니다.
프런트엔드의 라우트가 바뀌어도 뷰의 정책은 유지됩니다.
현재 Windows 구현은 한 창에 뷰 하나를 연결합니다.

```text
창 설정의 view: "main"
         ↓ 같은 ID를 선택
policy.views의 id: "main"
         ↓ 해당 정책을 적용
이 창의 웹 UI
```

`views` 배열의 각 항목이 뷰 하나의 정책입니다.
창은 별도의 창 설정에서 생성하고 사용할 뷰 ID를 연결합니다.

파일 접근은 앱 데이터의 `messages/` 아래로 제한합니다.

| 필드 | 의미 |
| --- | --- |
| `id` | 창 설정이 선택할 뷰 ID. 중복 ID는 허용하지 않음 |
| `origins` | 브리지 요청을 허용할 정확한 문서 origin |
| `commands` | 이 뷰에서 호출할 수 있는 앱 명령 이름 |
| `events` | 이 뷰에서 구독, 전달받을 수 있는 앱 이벤트 이름 |
| `host.permissions` | 이 뷰에서 시작한 작업의 권한 식별자와 허용 범위 |

명령과 이벤트는 정확한 이름을 선언합니다. `"*"` 와일드카드는 지원하지 않습니다.
`commands: []`이면 해당 뷰의 명령 호출은 전부 거부됩니다. 필수 키를 삭제하면 정책 검증이 실패합니다.

## app.ts에도 commands가 있는데 왜 여기에도 있나요?

두 목록의 역할이 다릅니다.

| 위치 | 답하는 질문 |
| --- | --- |
| `app.ts.commands` | 앱에 어떤 명령이 구현돼 있나요? |
| `policy.views[].commands` | 이 뷰가 어떤 명령을 호출할 수 있나요? |

뷰마다 호출할 명령을 정책에 지정합니다.
읽기 전용 `reader`에는 `message.read`만 허용하고 편집용 `editor`에는 두 명령을 모두 허용하는 식입니다.
WebView에서 보낸 요청은 이 허용 목록에 있는 명령만 실행합니다.

## 명령과 Host API 권한은 각각 검사합니다

`message.save` 호출에는 두 검사가 필요합니다.

1. `commands`에 `message.save`가 있어야 **앱 핸들러를 실행**할 수 있습니다.
2. 핸들러가 `storage.writeText`를 요청하면 `host.permissions`에서 **그 파일의 쓰기 범위**를 확인합니다.
   창 제어 플러그인도 `host.permissions`의 **대상 뷰 allow와 deny 범위**를 확인합니다.

파일을 쓰지 않고 앱 상태만 바꾸는 명령도 있습니다.
이런 명령의 호출 여부는 `commands`로 정하고 네이티브 기능 접근은 각 `host` 권한으로 정합니다.

`scope: "appData"`, `pathPrefix: "messages"`는 명명된 앱 데이터 범위 안의
`messages/` 디렉터리와 그 아래 파일을 허용합니다. 호출 경로는 이 범위 안의 상대 경로로 적습니다.
[저장소 가이드](/guides/storage-and-state/)에서 호출 경로와 정책을 함께 확인하세요.

## backend 권한과 뷰 권한은 따로 적용됩니다

UI 명령 핸들러의 `context.host`는 **요청을 보낸 뷰의 권한**을 유지합니다.
`main`에서 시작한 `message.save`는 `main.host.permissions`로 검사합니다.

루트의 `backend`는 플러그인 초기화 등 **백엔드 자체 작업**에 적용하는 별도 Host API 권한입니다.
`backend.permissions: []`는 백엔드 자체 작업의 플러그인 권한을 거부합니다. 뷰에서 시작한 요청은 각 뷰의 정책을 따릅니다.
플러그인 setup에서 창을 제어하려면 backend.permissions에 windows:control과 대상 뷰 범위를 허용합니다.
정책은 Host API에 적용합니다. 신뢰된 백엔드가 직접 호출하는 Bun API는 이 검사 범위 밖입니다.

기본 템플릿은 창과 뷰 하나를 사용합니다. 단일 창 설정에서는 `app.view`와 일치하는 정책 뷰 하나를 선언합니다.
Windows에서는 `app.windows`로 여러 창을 연결하고 각 창의 뷰를 정책에 선언합니다.
[여러 창 만들기](/guides/windows/)에서 보조 창 설정과 공개 API를 사용할 수 있습니다.
플랫폼별 여러 창 지원 상태는 [지원 범위](/reference/platforms/)에서 확인하세요.
