---
title: 취소, 기한, 오류 처리
description: 요청을 취소하고 오류를 처리한 뒤 저장 상태를 확인하는 방법.
---

요청이 실패했어도 파일 쓰기는 이미 끝났을 수 있습니다.
다시 저장하기 전에 현재 파일을 읽어 완료 여부를 확인합니다.

## UI에서 취소하기

```ts
const controller = new AbortController();
const request = client.invoke("message.read", null, {
  signal: controller.signal,
  deadline: Date.now() + 5000,
});
// 사용자가 취소 버튼을 눌렀을 때
controller.abort();
try { await request; } catch (error) { console.error(error); }
```

신호를 취소하면 클라이언트가 로컬 요청을 종료하고 필요한 cancel을 전송합니다.
이미 취소한 신호로는 요청을 시작하지 않습니다.
deadline에는 Unix epoch 밀리초로 계산한 절대 기한을 넣습니다.

## 백엔드에서 취소 관찰

핸들러의 `context.signal.aborted`를 확인하거나 abort 리스너로 외부 자원을 정리합니다.
CancellationSignal은 `aborted`와 abort 리스너 등록 및 해제만 제공합니다.
전체 DOM AbortSignal을 받는 `fetch` 같은 API와 연결할 때는 백엔드 어댑터에서 신호를 변환합니다.
Host API를 호출하면 바인딩 계층이 컨텍스트의 수명과 취소 여부를 검사합니다.

취소는 일반 Promise를 강제로 중단하지 않습니다.
UI가 사라진 뒤에도 계속 실행되는 외부 작업은 앱에서 정리해야 합니다.
취소한 요청의 늦은 응답과 이벤트는 폐기합니다.

## 명시적 앱 오류

```ts
import { BunawayError } from "@bunaway/protocol";
throw new BunawayError({
  code: "INVALID_ARGUMENT", message: "저장할 내용을 입력하세요.",
});
```

일반 예외는 내부 메시지와 스택을 제외한 `INTERNAL` 오류로 전달합니다.
앱에서 공개할 오류는 `code`와 `message`, 선택적 JSON `details`로 작성합니다.
전체 코드와 상한은 [오류 레퍼런스](/reference/errors/)에서 확인하세요.

## 재시도와 복원

1. 연결이 끝났으면 새 연결, 구독을 시작합니다.
2. 읽기 명령으로 실제 저장 상태를 확인합니다.
3. 이전 작업의 성공 여부를 UI에 알립니다.
4. 필요할 때 사용자가 다시 저장하도록 합니다.

프레임워크는 부작용 있는 명령의 자동 재시도, 요청 이력 재전송, 완료된 쓰기의 롤백을 제공하지 않습니다.
구독이 끝나면 listen의 onError에서 버튼을 비활성화하거나 재연결 안내를 표시합니다.
