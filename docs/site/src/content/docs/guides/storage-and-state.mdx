## 앱 상태와 파일 저장의 차이

| 방식 | 용도 | 앱 재시작 후 |
| --- | --- | --- |
| `context.state` | 백엔드 메모리의 앱 데이터 | 초기 정의로 다시 시작 |
| `storage.writeText(...)` | 파일로 저장할 데이터 | 저장된 파일을 다시 읽을 수 있음 |

`storage`는 앱이 지정한 파일 경로의 텍스트와 메타데이터를 다루는 선택적 API입니다.
저장 위치와 파일별 접근 규칙은 앱에서 정합니다.
일반 파일 작업에는 백엔드에서 `Bun.file()`과 `Bun.write()`를 직접 사용할 수 있습니다.

여러 뷰가 있으면 같은 앱 백엔드의 상태를 공유합니다.
뷰별 데이터가 필요하면 상태 키에 뷰 ID를 넣는 등 앱에서 구분합니다.

## 템플릿의 저장 경로 읽기

`message.save` 핸들러는 아래 Host API를 호출합니다.

```ts
import { homedir } from "node:os";
import { join } from "node:path";
import storage from "@bunaway/plugin-storage";
import settings from "../bunaway.json";

const messagePath = join(
  process.env.LOCALAPPDATA ?? join(homedir(), ".local", "share"),
  "bunaway", settings.app.appId, "data", "messages", "current.txt",
);

await storage.writeText({
  path: messagePath,
  text,
});
```

이 경로 선택은 템플릿의 앱 코드에 있습니다. Windows에서는 사용자 로컬 앱 데이터 폴더 아래에 저장합니다.
앱은 다른 폴더를 선택할 수 있으며 플러그인은 기본 저장 폴더를 지정하지 않습니다.
화면에서 받은 값으로 경로를 정한다면 앱 명령에서 허용할 파일을 검사합니다.
개발 중에는 저장 파일을 소스 변경 감시 대상 밖에 둡니다.

`storage`는 명령의 실행 범위에서 사용합니다. 핸들러가 호출한 서비스 함수도
`storage`를 import해 호출할 수 있으며 `context.host`를 전달할 필요가 없습니다.
명령이 끝난 뒤에는 사용할 수 없으므로 저장 완료를 `await`해야 합니다.
[백엔드 Host API](/reference/backend/host-api/)에서 실행 범위와 오류를 확인하세요.

뷰의 정책은 이 호출에 사용할 작업 이름을 허용해야 합니다.

```json
{
  "permissions": [
    "storage.readText",
    "storage.writeText"
  ]
}
```

파일별 접근은 앱 명령에서 검사하고 저장 경로를 정합니다. 화면에는 해당 앱 명령만 허용하면
직접 플러그인 호출이 앱의 검사를 건너뛰지 않습니다.
현재 Windows 구현에는 절대 경로를 전달합니다. 경로에는 저장된 이름의 대소문자와 긴 파일명을 그대로 사용합니다.
다른 대소문자 표기나 8.3 짧은 이름은 `PERMISSION_DENIED`로 실패합니다.

상대 경로, `.` 또는 `..` 경로 요소, NUL과 개행이 든 경로는 `INVALID_ARGUMENT`로 실패합니다.
작업 권한이나 운영체제 접근 권한이 없거나 링크에 접근하면 `PERMISSION_DENIED`로 실패합니다.

Windows와 macOS에서 `storage.readDirectory`로 직접 자식 이름을 읽고
`storage.createDirectory`로 디렉터리를 만들 수 있습니다. recursive 기본값은 false이며
작업별 권한을 각각 허용합니다. macOS에서는 symlink 별칭이 없는 정규 POSIX 절대 경로를
사용합니다. `storage.remove`는 검사한 객체의 핸들로 삭제할 수 있는 Windows에서만 지원합니다.
`storage.directorySize`는 디렉터리 안 일반 파일의 크기 합을 Windows에서 계산합니다.
입력, 목록 상한과 실패는 [디렉터리 작업](/reference/host/storage-directories/)을 확인하세요.

## 읽기와 첫 실행

```ts
const text = await storage.readText({
  path: messagePath,
});
```

첫 실행에는 파일이 없어 읽기에 실패할 수 있습니다. 템플릿은 실패를 표시하고 저장 버튼을 사용할 수 있게 합니다.
메시지를 저장한 뒤 다시 실행하면 파일을 읽어 복원합니다. 읽기 실패는 파일 누락 외에 권한이나 파일 작업 오류로도 발생합니다.

## 메모리 상태 예시

아래는 파일을 쓰지 않는 앱 정의 예시입니다.
실행하려면 호출할 뷰의 정책에 `counter.next`도 추가해야 합니다.

```ts
import { type AppDefinition, command } from "@bunaway/backend";


export default {
  state: { count: 0 },
  events: {},
  commands: {
    "counter.next": command({
      input: { const: null },
      output: { type: "integer" },
      handle(_input, context) {
        const count = Number(context.state.get("count")) + 1;
        context.state.set("count", count);
        return count;
      },
    }),
  },
} satisfies AppDefinition;
```

`state.get()`은 저장된 JSON 값의 복사본을 반환합니다. 반환 객체를 수정하는 것만으로 저장 값은 바뀌지 않습니다.
변경을 반영하려면 `state.set()`을 사용합니다.
비동기 핸들러가 `await`하는 동안 다른 요청이 상태를 바꿀 수 있습니다.
읽은 값을 나중에 덮어쓰는 작업은 직렬로 실행하거나 최신 값을 다시 확인하도록 작성합니다.

## 정책이 적용되는 범위

UI 명령의 `storage`, `log`, `capabilities`와 `context.host`에는 원래 뷰의 권한이 적용됩니다.
백엔드 자체 작업은 루트의 `backend` 권한을 사용합니다.
정책은 Host API 호출에 적용합니다. 신뢰된 백엔드가 직접 호출하는 Bun API는 이 검사 범위 밖입니다.
`storage`의 작업별 호출 권한을 검사하며, 백엔드 전체의 파일 접근을 격리하지 않습니다.
