## 템플릿별 실행 명령

| 작업 | `vanilla` 템플릿 | `vite`, `react`, `vue`, `svelte` 템플릿 |
| --- | --- | --- |
| 네이티브 개발 앱 | `bun run dev` | `bun run dev` |
| 웹 개발 서버만 실행 | 없음 | `bun run dev:web` |
| 웹 프로덕션 빌드만 실행 | CLI가 정적 UI 번들 | `bun run build:web` |
| 웹 UI를 포함한 앱 빌드 | `bun run build` | `bun run build` |
| 채널 패키징 | `bun run package win-direct` | `bun run package win-direct` |

모든 생성 앱의 `bun run dev`는 네이티브 앱을 실행합니다.
`dev.command`가 있으면 CLI가 지정한 웹 개발 서버를 실행하고 관리합니다.
같은 포트에서 실행 중인 서버가 있다면 먼저 종료하세요.

## Vite 앱 생성

[첫 앱](/start/quickstart/)과 같은 로컬 패키지 묶음을 준비한 뒤 저장소 루트에서 실행합니다.

```sh
bun packages/cli/src/main.ts create ../my-vite-app --template vite --package-dir build/framework
cd ../my-vite-app
bun install
bun run doctor
bun run dev
```

Vite 템플릿은 루트 `index.html`, `src/`, `vite.config.ts`를 사용합니다.
`build.frontend`는 `web-dist`를 가리킵니다.
기본 화면은 공식 Vite 템플릿의 로고와 카운터입니다. 메시지 명령과 이벤트는 백엔드에 등록돼 있지만,
화면에는 SDK 연결과 저장 UI가 없습니다. 네이티브 기능을 사용하려면 [프런트엔드 연결](/guides/frontend/)에 따라 SDK 호출을 추가합니다.

## React, Vue, Svelte 앱 생성

생성 명령의 `--template vite`를 `react`, `vue`, `svelte`로 바꿉니다.
세 템플릿 모두 위 표의 Vite 개발, 빌드 명령을 사용하며 공식 create-vite@9.2.1의 TypeScript 샘플 화면으로 시작합니다.

| 템플릿 | UI 시작 파일 | 타입 검사 도구 |
| --- | --- | --- |
| react | `src/App.tsx` | TypeScript 7.0.2 |
| vue | `src/App.vue`, `src/components/HelloWorld.vue` | vue-tsc, TypeScript 6.0.2 |
| svelte | `src/App.svelte`, `src/lib/Counter.svelte` | svelte-check, TypeScript 6.0.2 |

`bun run typecheck`는 UI 컴포넌트, 백엔드와 Vite 설정을 검사합니다.
Vue와 Svelte는 검사 도구의 컴파일러 API 호환성을 위해 TypeScript 6.0.2를 사용합니다.
앱 백엔드와 메시지 저장 정책은 기존 Vite 템플릿과 같습니다. 화면에 네이티브 기능을 추가하려면 `@bunaway/client`를 사용합니다.

## 개발 서버 연결 설정

`src-bunaway/bunaway.json`의 다른 항목은 유지하고 아래 `dev`를 추가합니다.

```json
{
  "dev": {
    "command": ["bun", "run", "dev:web"],
    "url": "http://127.0.0.1:5173/",
    "timeoutMs": 30000
  }
}
```

`command`는 실행 파일과 인자 배열입니다. 정책의 앱 명령 목록 `commands`와는 다른 설정입니다.
CLI는 프로젝트 루트에서 서버를 실행합니다. 지정한 URL이 HTTP 준비 응답을 반환하면 네이티브 창을 엽니다.
템플릿의 Vite 설정은 포트 5173을 고정하고 `strictPort`를 사용합니다.

`app.home`과 `policy.json.origins`는 계속 로컬 자산용 `https://app.bunaway.local`을 사용합니다.
CLI가 **개발 산출물에만** 정확한 loopback origin을 적용합니다.
정책에 HTTP origin을 직접 추가하면 CLI 검증이 거부합니다.

## 변경 시 무엇이 재시작되나요?

| 변경 | `dev` 설정 없음 | 외부 개발 서버 연결 |
| --- | --- | --- |
| UI 소스 | 앱 전체 재시작 | 웹 개발 서버의 HMR, 페이지 갱신 |
| 앱 백엔드 | 앱 전체 재시작 | 네이티브 앱 재시작, UI 서버 유지 |
| Windows 아이콘 파일(`app.icon`) | 앱 전체 재시작 | 네이티브 앱 재시작, UI 서버 유지 |
| 개발 서버 설정 | 앱 재시작 | 앱과 서버를 모두 교체 |

백엔드가 import한 프로젝트 내부의 `shared/`, `services/` 파일도 변경 감시에 포함됩니다.
시작할 때 백엔드 소스가 컴파일되지 않아도 CLI는 오류를 출력하고 감시를 유지합니다. 빌드 실패 중에는 제외 디렉터리 밖의 프로젝트 파일 변경으로 재시도할 수 있으며, 성공하면 일반 감시 범위로 돌아갑니다. 소스를 수정하고 저장하면 다시 빌드합니다. 설정과 정책, 소스 경로, 개발 도구는 유효해야 합니다.

백엔드 재시작은 새 앱 상태와 새 세션을 만듭니다.
SDK는 미완료 요청과 구독을 정리합니다. 이전 요청은 자동으로 재전송하지 않습니다.
파일에 저장한 내용은 남습니다. 저장하지 않은 입력과 앱의 메모리 상태는 재시작 때 사라질 수 있습니다.
Windows에서 CLI가 재시작하거나 종료할 때는 `desktop.beforeQuit`와 트레이 숨김 설정을 우회합니다.
기존 앱의 플러그인 StopHook과 자원 정리가 끝난 뒤 다음 앱을 시작합니다.

Ctrl+C를 누르면 CLI가 관리하던 프로세스를 정리합니다. 창 닫기는 앱의 종료 취소와 숨김 설정을 따르며, 앱이 종료되면 CLI도 정리합니다. 서버가 종료되거나 준비 기한을 넘겨도 정리합니다.
현재 외부 개발 서버를 별도로 실행해 연결만 하는 모드는 제공하지 않습니다.

## 디버깅

Windows 개발 앱에서는 F12 또는 Ctrl+Shift+I로 UI DevTools를 엽니다.
`bun run dev --inspect`로 백엔드 inspector를 함께 시작할 수 있습니다.
소스맵, 중단점, 오류 스택과 재시작 후 연결 방법은 [개발 모드 디버깅](/guides/debugging/)에서 확인하세요.

## 프로덕션 빌드로 넘어가기

`build.command`에 웹 프로덕션 빌드 명령을 연결하면 웹 출력이 없는 최초 실행에서도 아래 명령 하나로 앱을 빌드합니다.

```sh
bun run build
```

출력이 있어도 매번 웹 빌드 명령을 실행하며 실패하면 앱 빌드를 중단합니다.
자산만 검사하려면 앱의 웹 전용 빌드 스크립트로 출력을 만든 뒤 `bun run validate`를 실행합니다.
최종 앱에는 그 빌드가 출력한 정적 자산을 포함하며 Next.js의 SSR 서버는 포함하지 않습니다.
[빌드와 패키징](/guides/build-and-package/)에서 다음 단계를 확인하세요.
