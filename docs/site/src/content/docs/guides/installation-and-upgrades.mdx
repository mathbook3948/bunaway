bunaway 개발 의존성은 앱의 package.json, bun.lock으로 관리합니다.
SDK, CLI를 node_modules에서 읽으며 앱에 별도 vendor 프레임워크나 bunaway.lock.json을 만들지 않습니다.
첫 설치 명령은 [첫 앱](/start/quickstart/)에 있습니다.

## 현재 배포 방식

공개 registry publish는 아직 없습니다. 관리자가 `bun run framework:pack --local`로
같은 버전의 CLI, SDK 묶음을 준비하고 create의 `--package-dir`로 연결합니다.
`--local`의 의존성은 묶음의 절대 경로라서 묶음을 다른 위치로 옮기면 그 위치에서 다시 만들어야 합니다.
깨끗한 재설치를 위해 참조한 tarball 묶음을 보관합니다.

## 설치하는 패키지

| 패키지 | 역할 |
| --- | --- |
| @bunaway/client | WebView 클라이언트 |
| @bunaway/backend | 앱 정의, 명령, 이벤트 타입 |
| @bunaway/core | 공통 실행 계층 |
| @bunaway/runtime-bun | 별도 프로세스 런타임 어댑터 |
| @bunaway/protocol | 메시지, 정책, Host API 계약 |
| @bunaway/packaging | 채널 중립 계약, 어댑터 |
| @bunaway/cli | 생성, 검증, 개발, 빌드, 패키징과 플랫폼 입력 |

앱이 직접/전이 의존하는 SDK는 같은 정확한 릴리스여야 합니다.
isolated, workspace 설치에서 모든 SDK가 앱 루트에 hoist되어야 하는 것은 아닙니다.
CLI는 의존성을 선언한 패키지 위치에서 전이 SDK를 해석합니다.

## 재현 설치

앱 소스, 설정, package.json, bun.lock을 커밋하고 아래로 설치합니다.

```sh
bun install --frozen-lockfile
```

node_modules, .bunaway, dist, web-dist는 생성물입니다.
CLI는 릴리스, artifact inventory, SDK 해석을 검사합니다.
SDK 버전을 바꾸는 overrides/resolutions, TS aliases나 일부 SDK만 교체한 조합은 거부될 수 있습니다.

## 업그레이드와 되돌리기

1. 새 릴리스의 로컬 묶음을 준비합니다.
2. 같은 묶음으로 만든 참조 앱과 @bunaway 의존성 선언을 비교해 모두 갱신합니다.
3. `bun install`로 lockfile을 갱신합니다.
4. 앱의 typecheck, validate, doctor, dev, build와 실제 회귀를 확인합니다.
5. 실패하면 이전 package.json, bun.lock을 복원하고 frozen install합니다.

Vite에서는 validate, build 전에 웹 생산 빌드가 필요합니다.
이전 tarball도 보관해야 롤백 설치가 가능합니다.
현재 이전 vendor/분리 설정으로의 자동 마이그레이션이나 fallback은 없습니다.

CLI 설치본 안의 다운로드 캐시는 node_modules를 지우면 없어질 수 있지만
소스, 해시 pin은 설치 artifact에서 복원합니다.
개발 도구 준비의 네트워크 요구와 최종 앱 실행 요구는 구분합니다.
