앱, 창, 뷰, 세션, 요청은 서로 다른 수명입니다.
같은 뷰 ID로 재연결해도 이전 세션을 이어 쓰지 않습니다.

## 시작

프레임워크가 앱 정의와 정책을 읽고 명령, 이벤트, 상태를 등록합니다.
플러그인은 의존 순서대로 setup하고, 끝나야 코어 준비가 완료됩니다.
호스트는 실제 문서 출처, frame을 확인하고 새 호출 컨텍스트, 세션을 발급합니다.
웹 클라이언트는 hello를 협상하고 ready 뒤 호출, 구독을 진행합니다.

## 수명별 소유 데이터

| 단위 | 소유하거나 구분하는 것 |
| --- | --- |
| 앱 백엔드 | 명령 구현, 공통 메모리 상태, 플러그인 |
| 창 | OS 창과 WebView 자원 |
| 뷰 | 접근 정책 |
| 문서, 세션 | 협상, 요청 ID, 구독, 호스트 컨텍스트 |
| 요청 | 입력, 기한, 취소 신호, 컨텍스트에 묶인 Host 작업 |

요청 ID가 같아도 서로 다른 세션의 응답은 독립입니다.
같은 세션에서는 요청 ID를 재사용하지 않습니다.
HostContext와 런타임 세대는 호스트가 관리하며 프런트엔드가 만들지 않습니다.

## 탐색, 렌더러 복구, 개발 재시작

문서가 교체되거나 호스트가 렌더러를 복구하면 오래된 세션을 폐기합니다.
새 클라이언트가 협상하고 구독, 상태 읽기를 다시 수행합니다.
Windows 다중 창에서는 한 뷰의 렌더러 복구가 다른 뷰, 앱 백엔드를 함께 재시작하는 것은 아닙니다.

CLI의 백엔드 재시작은 새 앱 실행과 메모리 상태를 만듭니다.
Vite HMR만으로 UI를 갱신하는 경우와 구분하세요.
진행 중 요청, 구독은 유지, 자동 재전송하지 않습니다.

## 종료

클라이언트 close는 해당 연결의 대기 작업과 전송을 정리합니다.
호스트의 창 닫기는 해당 뷰 세션을 폐기합니다.
현재 Windows에서 마지막 창을 닫으면 코어, Worker, WebView 자원을 정리하고 앱을 종료합니다.
플러그인 StopHook은 역순으로 실행합니다.

코어 stop의 완료와 OS 자식 프로세스의 실제 종료는 별도 확인입니다.
종료 전 저장을 무제한으로 기다릴 수 있다고 가정하지 말고 중요한 데이터는 정상 작업 중 저장하세요.
