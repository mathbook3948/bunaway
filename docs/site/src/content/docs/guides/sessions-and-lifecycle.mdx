세션은 웹 UI가 백엔드에 연결된 동안의 요청과 구독을 구분합니다.
같은 뷰 ID로 다시 연결해도 이전 요청과 구독은 이어지지 않습니다.

## 시작

앱 정의를 default export하고 policy.json에 사용할 기능을 허용합니다.
플러그인의 setup이 끝나면 명령을 처리할 준비가 됩니다. `client.invoke`와 `client.listen`은 연결이 준비될 때까지 기다립니다.
생성 오류는 초기화 과정에서 처리합니다. 준비 상태를 UI에 표시할 때는 재사용하는 `client.ready`를 사용합니다.
Windows의 네이티브 창 생성, 웹 문서 완료와 SDK 준비는 각각 확인합니다.
SDK 준비는 현재 세션의 협상 확인이며 앱 데이터나 UI 초기화 완료를 뜻하지 않습니다.
숨김 생성, 준비 조회와 구독, splashscreen 전환은 [창 준비](/reference/host/windows/#창-준비)를 따릅니다.

## 수명별 소유 데이터

| 단위 | 소유하거나 구분하는 것 |
| --- | --- |
| 앱 백엔드 | 명령 구현, 공통 메모리 상태, 플러그인 |
| 창 | OS 창과 WebView 자원 |
| 뷰 | 접근 정책 |
| 문서, 세션 | 클라이언트 연결, 진행 중 요청, 이벤트 구독 |
| 요청 | 입력, 기한, 취소 신호, 컨텍스트에 묶인 Host 작업 |

## 탐색, 렌더러 복구, 개발 재시작

문서가 교체되거나 호스트가 렌더러를 복구하면 오래된 세션을 폐기합니다.
새 문서에서 기본 API를 호출하면 새 연결을 사용합니다. 이벤트를 구독한 뒤 상태를 다시 읽습니다.
종료된 기본 연결은 같은 문서에서 다시 호출해도 복구되지 않습니다. 페이지를 다시 로드해 새 연결을 시작합니다.
브라우저 뒤로 가기로 이미 종료된 문서를 복원해도 자동으로 다시 연결하지 않습니다.
Windows에서는 복구가 필요한 뷰만 새 세션을 만들고 다른 뷰와 백엔드는 계속 실행합니다.

CLI의 백엔드 재시작은 새 앱 실행과 메모리 상태를 만듭니다.
Vite HMR이 같은 문서의 UI 모듈만 갱신할 때는 백엔드와 기본 연결을 계속 사용합니다.
컴포넌트를 교체할 때는 이전 컴포넌트의 구독을 해제해 알림을 중복으로 받지 않도록 합니다.
전체 페이지를 갱신하면 새 문서의 연결을 사용합니다.
백엔드가 재시작되면 진행 중 요청과 구독을 정리합니다. 이전 요청은 자동으로 다시 보내지 않습니다.

## 종료

페이지가 종료되면 기본 연결과 구독이 자동으로 정리됩니다.
명시적 `client.close()`는 기본 연결을 사용하는 모든 호출자에게 영향을 줍니다.
컴포넌트 정리에는 연결 종료 대신 `listen()`이 반환한 구독 해제 함수를 사용합니다.
Windows의 기본 동작은 닫힌 창의 뷰 세션을 폐기하고 마지막 창을 닫으면 앱을 종료하는 것입니다.
앱 정의의 `desktop`으로 [열기 요청, 종료 취소와 트레이 실행](/reference/backend/app-definition/#데스크톱-앱-동작)을 설정할 수 있습니다.
종료를 취소하거나 트레이로 숨기면 기존 창과 세션, 백엔드는 계속 실행합니다.
macOS는 트레이와 `closeBehavior: "hide"`를 지원하지 않습니다. 기본 `"quit"`과 `"keep-alive"`는 사용할 수 있고,
Cmd+Q와 앱 메뉴의 Quit은 `beforeQuit`에 `"quit-command"`로 전달합니다. Dock 아이콘을 눌러 창이 없던 앱을 다시 열면
`DesktopContext.show()`와 같이 창을 표시합니다.
Windows에서 시작 창을 생략하려면 트레이 또는 `desktop.closeBehavior: "keep-alive"`가 필요합니다.
macOS는 창 없는 시작을 아직 지원하지 않습니다.
`"keep-alive"`는 마지막 창의 세션을 폐기해도 앱 백엔드를 유지하며 명시적 종료 요청을 기다립니다.
트레이 Open 또는 `DesktopContext.show()`는 열린 창이 없으면 첫 사전 선언 창을 새 세션으로 생성합니다.
[자동 실행](/reference/plugins/autostart/#로그인-실행-구분과-숨김-시작)은 `onOpen`의
`launchReason`으로 호출 모드를 전달합니다. 숨김 자동 실행은 트레이가 필요하며 초기 SDK
준비 뒤에도 창을 표시하지 않습니다. 트레이 Open이나 수동 두 번째 실행은 기존 세션을 복원합니다.
플러그인 StopHook은 역순으로 실행합니다.

종료가 확정되면 `desktop.onWillQuit(reason)`이 코어와 플러그인 StopHook보다 먼저 한 번 실행되고,
정리를 마친 뒤 `desktop.onQuit(reason)`이 실행됩니다. 각 훅은 최대 3초까지만 기다리며 종료를 취소하지 못합니다.
`onReady`는 시작 창의 생성 직전에, `onAllWindowsClosed`는 앱이 계속 실행되는 중에 마지막 창이 닫힐 때 호출합니다.
`reason`과 호출 시점은 [데스크톱 앱 동작](/reference/backend/app-definition/#수명주기-훅의-호출-시점)을 확인하세요.
Windows와 macOS의 로그오프(로그아웃), 재시작과 시스템 종료는 취소할 수 없고 `beforeQuit`를 호출하지 않습니다.
`onWillQuit`과 StopHook은 약 4초를 나눠 쓰며 `onQuit`은 호출하지 못할 수 있습니다.
`onWillQuit` 안의 창이나 클립보드 같은 호스트 작업은 항상 `CANCELLED`로 실패하므로 앱 내부 정리만 합니다.

창을 닫기 전에 저장을 마쳐야 하면 문서에서 `windows.closeRequested`를 구독하고
`windows.respondClose`로 허용 여부를 답합니다. 자세한 흐름은 [닫기 요청](/reference/host/windows/#닫기-요청)을 따릅니다.
창의 생성과 닫힘 시점은 `windows.lifecycle` 이벤트로 알 수 있습니다. 두 기능은 Windows와 macOS에서 같은 규칙으로 동작합니다.
macOS의 사용자 닫기는 타이틀바의 닫기 버튼과 `windows.close`이며 WebView의 `window.close()`는 해당하지 않습니다.

종료에는 기한이 있으므로 중요한 데이터는 사용자가 작업하는 동안 저장합니다.
