bunaway 앱은 **웹 UI + TypeScript 앱 백엔드 + 네이티브 호스트 + 번들 Bun**으로 구성됩니다.
앱 백엔드는 사용자 기기에서 실행하는 앱 코드입니다. 원격 서버를 따로 띄우는 구조가 아닙니다.

## 무엇을 직접 작성하나요?

| 작성할 곳 | 하는 일 | 예시 |
| --- | --- | --- |
| `src/` | 화면과 사용자 입력 처리 | 입력 상자, 저장 버튼, 저장 결과 표시 |
| `src-bunaway/app.ts` | 앱 명령, 상태, 이벤트 정의 | `message.save`, `message.read`, `message.saved` |
| `src-bunaway/bunaway.json` | 소스 위치, 앱 ID, 창, 빌드 설정 | 시작 페이지, 창 크기 |
| `src-bunaway/policy.json` | 뷰, 백엔드의 접근 정책 | 저장 명령 허용, `messages/` 읽기, 쓰기 |

프레임워크가 앱 정의를 읽고 코어와 플랫폼별 호스트를 연결합니다.
앱 개발자가 Windows와 macOS의 부팅 코드를 각각 작성할 필요는 없습니다.

## 각 계층의 책임

**웹 UI**는 WebView에서 실행합니다. `@bunaway/client` SDK로 명령을 호출하고 이벤트를 구독합니다.
파일 시스템이나 Bun API를 프런트엔드에서 직접 호출하지 않습니다.

**앱 백엔드**는 `@bunaway/backend`의 `command()`로 작업을 정의합니다.
**코어**는 명령 등록, 입력과 출력 검증, 상태, 이벤트와 세션을 조정합니다.

**네이티브 호스트**는 창, WebView, 앱 수명주기를 소유합니다.
실제 문서 출처와 호출 권한을 확인하고, Host API로 요청한 운영체제 작업을 실행합니다.

**번들 Bun**은 최종 앱 패키지에 들어가는 런타임입니다.
앱 개발 머신에서는 Bun이 필요하지만, 최종 사용자에게 Bun 설치를 요구하지 않습니다.

명령 이름을 등록하는 것과 호출을 허용하는 것은 별개입니다.
`app.ts`에 `message.save`가 있어도 뷰의 `commands`에 없다면 실행 전에 거부됩니다.
명령을 허용했더라도 파일 쓰기에는 `host.storage`의 저장 권한이 필요합니다.

## Windows의 현재 실행 구조

```text
번들 Bun 프로세스
├─ 메인: 앱 백엔드 + 공통 코어
├─ UI Worker: Win32 창 + WebView2 연결 + 권한 검사
└─ I/O Worker: 범위가 제한된 파일 작업

WebView2의 브라우저, 렌더러는 별도 프로세스
```

현재 macOS는 AppKit, WKWebView 호스트가 별도 Bun 자식 프로세스를 실행합니다.
앱 개발자는 두 플랫폼 모두 같은 `app.ts`를 작성합니다.
플랫폼별 차이와 구현 상태는 [지원 범위](/reference/platforms/)에서 확인할 수 있습니다.

## 뷰가 여러 개라면

Windows 런타임에서는 창별 뷰와 세션이 하나의 앱 백엔드를 공유합니다.
명령 구현과 앱 상태는 공통이고, 허용 명령, 이벤트, Host API 범위는 뷰별로 다릅니다.
현재 CLI는 단일 창과 뷰만 받습니다. 이 차이는 [창, 뷰, 정책](/concepts/views-and-policy/)에서 자세히 설명합니다.

다음으로 [첫 앱 실행하기](/start/quickstart/)에서 이 흐름을 직접 확인하세요.
