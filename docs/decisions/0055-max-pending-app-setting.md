# 동시 대기 요청 상한(maxPending)을 앱 설정으로 128에서 1024까지 올릴 수 있다

결정일: 2026-10-25. 검토 기준: main `28bf9883`.

## 배경

`API_LIMITS.maxPending`(128)은 세션당 동시에 대기할 수 있는 요청 수다. 한도를 넘으면 `BUSY`로 끝난다.
동시 호출이 많은 앱이나 부하 측정은 이 값에 걸린다. 지금은 SDK, Core, `runtime-bun`, 네이티브 호스트가 모두 이
상수를 직접 읽어서 앱이 바꿀 수 없다([오류 레퍼런스](../site/src/content/docs/reference/errors.mdx)).

`maxRequestIds`는 호출 횟수를 제한하지 않고 중복 ID를 거부하는 기록 크기만 정하므로 열지 않는다. `maxSubscriptions`와
`maxCommandDurationMs`도 요구가 없어 이번에는 열지 않는다.

## 결정

1. `maxPending`만 앱이 올릴 수 있다. 앱 정책 파일(`policy.json`)의 `maxPending`(정수)으로 설정하며 범위는 128 이상 1024 이하다.
   설정하지 않으면 지금과 같은 128이다. 128보다 낮추거나 1024를 넘기거나 무제한으로 두는 값은 빌드에서 거부한다.
2. 상한 1024는 기본값의 8배다. 대기 항목은 요청 ID와 완료 콜백 정도의 작은 객체이고, 세션 수와 메시지 크기
   (`MAX_MESSAGE_BYTES`)는 그대로이므로 8배 증가는 메모리를 눈에 띄게 늘리지 않는다. 이 값을 넘는 동시성이 필요한 앱은
   호출을 묶어 보내야 한다.
3. 설정값은 정책 문서의 선택 필드이므로 모든 계층이 이미 받는 경로로 전달된다. 정책은 `policy.json`에서 읽혀 Core,
   `runtime-bun`의 뷰 경계, 네이티브 호스트가 부팅 때 검증하므로 별도 전달 경로가 필요 없다. CLI는 모바일 호스트의 생성 설정
   (Android `ProtocolLimits`, iOS `host.json`, 모바일 브리지)에도 같은 값을 쓴다. 필드가 없으면 128이다.
4. 한 값이 아래 용량을 함께 결정한다. 설정값이 128이든 1024든 아래 관계가 유지된다.
   - Core의 진행 중 요청 수와 구독 이벤트 대기열, `runtime-bun`의 세션별 대기 요청, 취소된 요청, 워커 채널의 레인 용량,
     백엔드 출력 대기열, 문서 연결 수.
   - 네이티브 호스트의 I/O 워커 대기열, 응답 소유자 기록(`2 * maxPending`), 네이티브 요청 수, UI 스레드 호출 수,
     모바일 호스트의 쓰기 대기열과 브리지 대기열.
   - 진단 로그 대기열은 요청 용량이 아니라 로그 보호용이라 128로 둔다.
5. WebView의 SDK는 서버 hello에 실린 선택 필드 `maxPending`을 받아 자기 상한으로 쓴다. hello를 받기 전과 필드가 없을 때는
   128이다. 따라서 SDK, Core, 호스트가 항상 같은 값을 쓴다.

## 근거

- 기본값을 유지하고 설정 가능한 항목을 `maxPending` 하나로 제한해 코어를 작게 둔다.
- 상한이 있어야 앱이 설정으로 메모리와 대기열 크기를 무제한으로 만들 수 없고 `BUSY` 보호가 유지된다.
- 정책 문서를 통한 전달은 새 프로토콜 메시지나 호스트별 설정 경로를 만들지 않는다.

## 영향

- `PROTOCOL_VERSION`은 그대로다. 정책과 hello의 새 필드는 선택 필드이며, 설정하지 않은 앱은 바이트 단위로 같은 문서를 만든다.
- 생성된 프로토콜 스키마(`native/host-api/generated`)가 선택 필드 `maxPending`을 포함하도록 바뀐다.
