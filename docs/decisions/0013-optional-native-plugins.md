# 네이티브 기능은 개별 플러그인으로 설치하고 등록한다

결정일: 2026-10-07. Windows 구현과 개별 로컬 패키지 검증을 완료했다. macOS 어댑터는 후속 작업이다.

저장, 로그, 기능 지원 조회가 SDK와 호스트의 기본 기능으로 고정돼 있다. 새 기능을
추가할 때마다 공통 패키지와 호스트를 수정하는 구조를 끝내고, 앱이 필요한 기능의
플러그인 패키지만 설치하도록 한다. Tauri의 설치, 앱 등록, 권한 허용 흐름을 참고하되
앱 정의와 플러그인 구현은 Bun과 TypeScript를 기준으로 설계한다.

## 결정

1. 저장, 앱 로그, 기능 지원 조회를 각각 `@bunaway/plugin-storage`,
   `@bunaway/plugin-log`, `@bunaway/plugin-capabilities`로 분리한다. 각 패키지는
   공개 함수, 작업의 입력과 출력 계약, 권한 정의, 플랫폼 구현을 소유한다.
2. 패키지 설치와 앱 등록, 권한 허용을 구분한다. 설치는 코드의 의존성이고,
   `AppDefinition.plugins` 등록은 기능의 활성화다. 정책은 활성화한 기능의 사용 범위를
   정한다. 설치하거나 등록하는 것만으로 뷰나 백엔드에 권한을 부여하지 않는다.
3. 공통 SDK와 코어는 명령, 이벤트, 앱 상태, 호출 컨텍스트, 플러그인 등록과 수명주기를
   소유한다. 프로토콜은 메시지 형식과 공통 검증을, 호스트는 실제 출처와 권한 검사,
   플랫폼 실행과 자원 회수를 소유한다. 이 계층은 개별 기능의 작업 목록과 파일,
   로그 구현을 import하지 않는다.
4. 백엔드의 호출 컨텍스트는 한 곳에서 관리한다. 모든 플러그인의 편의 함수는 같은
   공통 호출 API를 사용한다. 뷰 명령은 원래 뷰의 권한을 유지하고, setup에서 시작한
   작업은 백엔드 수명을 따른다. 명령 종료 후의 지연 호출과 종료된 앱의 호출은 거부한다.
5. 플러그인은 index.ts의 선언 한곳에서 작업 계약과 플랫폼 구현을 연결한다.
   공통 작성 SDK인 `@bunaway/plugin`이 입력과 출력 schema에서 호출 함수를 만든다.
   화면과 백엔드는 같은 패키지 경로와 같은 진입점을 사용하며 환경별 호출은 SDK의
   browser와 bun 조건으로 선택한다. 작성자가 contracts.ts, client.ts와 백엔드
   호출 함수를 나눠 작성하게 한 이전 결정을 대체한다. 공식 플러그인은 src/index.ts에서
   선언을 조립하고 공개 export를 제공한다. src/contract.ts는 작업 스키마와 타입, 계약 검증을
   소유한다. 편의 호출과 정규화는 역할에 맞는 내부 파일에 두고 생성한 api를 전달한다.
   추가 처리가 없는 API는 그대로 공개한다. 플랫폼 구현은 src/platforms/<platform>.ts에서
   연결하며 내부 파일은 공개 진입점을 역으로 import하지 않는다.
   외부 제작자에게 같은 내부 파일 분리를 요구하지는 않는다.
   package.json의 bunaway.plugin은 dist/index.js를 가리킨다. API와 플랫폼 구현 정보를
   defineNativePlugin의 선언 한곳에 두고 별도 plugin.json은 사용하지 않는다.
   플러그인 버전은 package.json에만 작성한다. 빌드가 읽어 모든 등록 출력에 기록하며
   원본을 직접 import한 등록 객체의 버전은 development다.
   platforms에는 직접 import한 구현 팩터리 create와 io 또는 ui 실행 위치를 작성한다.
   src/platforms/<platform>.ts를 빌드 경계로 사용해 중립 출력에서는 모든 OS 구현을 제외하고
   native/<platform> 출력에는 대상 OS 구현만 포함한다. 호스트는 이 패키지 export를 지연 import한다.
   SDK는 외부 의존성으로 유지한다. 설치 패키지 밖으로 연결되는 export는 거부한다. 일부 작업만 구현한다면 operations에
   짧은 작업 이름을 지정한다. 생략하면 전체 작업을 지원한다. 이 목록은 지원 조회와
   호출 검사에 함께 사용하며 미지원 작업은 권한 검사 뒤 UNSUPPORTED를 반환한다.
   반환한 definition의 nativePlatforms는 실행 위치, 지원 작업과 열거되지 않는 create 함수를 제공한다.
   함수는 JSON과 structured clone에 포함하지 않는다. 일반 앱 플러그인의 platforms
   배열이 가진 앱 시작 제한과 구분하고 기존 definition과 api 반환 형태는 유지한다.
   화면 번들에 백엔드 컨텍스트와 네이티브 구현을 포함하지 않으며 선언을 읽는 것만으로
   연결과 플랫폼 자원을 초기화하지 않는다. 생성 앱은 환경별 타입을 각각 검사한다.
   제작자는 operations에 input과 output을 선언하고 공식 플러그인은 contract.ts에서 가져온다.
   SDK가 작업 이름의 접두사를 붙이며 작업 이름 자체가 정책 권한 식별자다.
   입력과 출력은 Zod로 작성하고 호출 타입은 Zod에서 추론한다. z.object는 추가 필드를
   제거하고 z.strictObject는 거부한다. 선택 필드는 z.exactOptional로 선언한다. SDK는
   선언을 JSON Schema로 변환하고 필드 제거 규칙을 확장 키워드로 기록한다.
   프로세스와 Worker에는 JSON 계약만 전달한다. 공통 검증기가 입력과 결과의 복사본에
   같은 필드 제거를 적용한다. 변환으로 사라지는 사용자 정의 검사와 임의 값 변환은
   선언 오류로 거부한다.
6. CLI는 공통 프레임워크 패키지와 선택 플러그인을 별도로 관리한다. CLI 설치가 모든
   플러그인의 설치를 뜻하지 않는다. 설치하지 않은 플러그인은 앱 번들에 포함하지
   않으며, 설치했어도 등록하지 않은 네이티브 구현은 초기화하지 않는다.
7. 권한은 완전한 operation 이름의 문자열로 표현한다. 별도 permission
   별칭과 권한 묶음은 두지 않으며 작업마다 독립적으로 허용한다. 공통 정책은
   특정 기능 이름을 필수 필드로 요구하지 않는다. 권한 누락은 기본 거부한다.
   파일별 접근이나 특정 창의 제어 같은 앱 규칙은 백엔드 앱 명령이 소유한다.
   화면에는 해당 앱 명령만 허용하여 검사를 거치게 한다. 범용 scope와 matches 계약은 두지 않는다.
   저장 위치도 앱이 소유한다. 저장 입력은 path이며 현재 Windows 구현에는 절대 경로를 전달한다.
   기본 저장 폴더나 저장 영역 선택자를 두지 않는다. 플랫폼 경로 검증과 링크, 최종 핸들 검사는 유지한다.
   OS 동의 상태 조회와 요청은 해당 기능의 플랫폼 구현이 담당한다. 공통 osPermission
   메타데이터를 두지 않고 capabilities는 지원 여부만 반환한다. 작업 실행 안에서 OS 동의를
   요청할 수 있지만 앱 정책 승인이 먼저다. import와 어댑터 등록 중에는 요청하지 않는다.
   사용자 거부는 PERMISSION_DENIED이며 취소된 요청은 승인돼도 기능 실행을 이어가지 않는다.
8. 앱이 요청하는 로그는 로그 플러그인이 소유한다. 시작 실패, 명령 예외, 권한 거부,
   종료 실패를 기록하는 프레임워크 진단은 플러그인 설치 여부와 관계없이 유지한다.
9. Windows에서 먼저 구현하고 검증한다. 다른 플랫폼은 같은 패키지, 앱 정의와 권한
   계약에 맞춘다. macOS의 기존 자식 프로세스 구현 때문에 별도 앱 진입점을 만들지 않는다.

## 기존 결정과 이관

[ADR 0002](./0002-host-owned-call-context.md)의 호출 출처와 신뢰 모델,
[ADR 0006](./0006-windows-bun-ui-worker.md)의 Windows 실행 책임,
[ADR 0010](./0010-windows-first-platform-model.md)의 개발 우선순위와
[ADR 0011](./0011-app-module-composition.md)의 앱 조립과 수명주기는 유지한다.

[ADR 0008](./0008-installed-framework-packages.md)의 공통 SDK 버전 일치 규칙은
유지한다. 선택 플러그인을 CLI의 필수 의존성에 합치지 않으며, 공식 플러그인은 처음에는
호환하는 프레임워크의 정확한 릴리스 버전을 선언한다. 개별 설치가 서로 다른 SDK나
호출 컨텍스트 저장소를 중복 로드하도록 허용하지 않는다.
`@bunaway/` 범위 밖의 외부 플러그인은 자체 버전을 사용하며 SDK 호환성은
peerDependencies의 정확한 버전으로 검사한다. 외부 플러그인의 릴리스 번호를 프레임워크와 맞추도록 요구하지 않는다.

현재 공개 `storage`, `log`, `capabilities`와 고정 Host operation, 정책 v1을
새 구조로 옮기는 작업은 [플러그인 구조 계약](../architecture/plugins.md)을 따른다.
공개 배포 전 이관이므로 구 API를 새 API로 자동 연결하는 호환 계층이나 자동
마이그레이션은 만들지 않는다. 공식 배포 전까지 정책 형식은 v1을 유지한다.
개발 중 정책 구조가 바뀌어도 v2로 올리지 않고 v1의 계약을 직접 갱신한다.
이전 개발 형식과의 호환 계층은 두지 않으며, 정식 배포 이후의 형식 변경은 별도로 결정한다.
Web 메시지와 프로세스 IPC를 구분해 검증하는 기존 계약은 유지한다.
