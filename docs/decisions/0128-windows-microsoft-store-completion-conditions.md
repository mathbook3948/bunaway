# Microsoft Store 배포 완료는 패키지 생성, 제출 전 검증, 제출, 심사 통과, Store 설치 실행의 다섯 단계로 구분하고, 앞의 두 단계까지만 프레임워크가 증명한다

결정일: 2026-10-29. 검토 기준: main `7290e7b1`.

## 배경

[ADR 0127](./0127-windows-installer-formats-and-channels.md)은 Windows 설치 형식(Inno Setup EXE 채택, MSI 제외, MSIX 차단 유지)과
채널을 정했지만, Microsoft Store로 배포했다고 말할 수 있는 조건은 정하지 않았다.
[ADR 0054](./0054-updater-downgrade-rollback-and-store-channels.md)는 Store가 업데이트를 전달하는 설치의 updater 동작을,
[ADR 0125](./0125-public-release-readiness.md)는 프레임워크 패키지의 공개 배포 준비를 다룬다. 이 결정은 앱을 Store에 내는 경로만 다루며
위 세 결정의 내용을 바꾸지 않는다.

이 결정은 Windows의 Microsoft Store만 다룬다. Mac App Store, Google Play, App Store는 각 플랫폼 TODO에서 따로 정한다.

현재 코드에서 Store와 관련해 만드는 것은 다음이 전부다.

- `win-store-unpackaged`: 서명된 오프라인 Inno EXE 한 개와 `submission.json` 체크리스트. 인스톨러와 내부 PE의 서명과 Microsoft
  AuthRoot CTL 포함 여부를 패키징 중에 검사한다.
- `win-store-msix`: 채널 이름과 매니페스트 렌더러만 있고 패키지 생성은 오류로 거부한다(ADR 0127 결정 3).
- Partner Center 제출과 프로덕션 인증서 사용은 자동 시험 범위에 없다([패키징 README](../../packages/packaging/README.md)).

## 결정

1. Microsoft Store 배포는 아래 다섯 단계로 구분해 기록하고, 단계는 앞 단계의 증거 없이 건너뛰지 않는다. 각 단계의 증거는 다음 단계의
   완료를 대신하지 않는다.

   | 단계 | 뜻 | 완료 증거 | 증거를 내는 쪽 |
   | --- | --- | --- | --- |
   | 1. 패키지 생성됨 | `win-store-unpackaged` 패키징이 성공(`PackageReport.ok`)해 설치 파일과 `submission.json`이 나옴. 서명 없이도 이 단계는 될 수 있다. | 패키징 보고서와 산출물 | 프레임워크 |
   | 2. 제출 전 검증 통과 | `PackageReport.submittable`이 참이다(성공한 실행, 배포 산출물 한 개 이상, 모든 산출물에 서명). 서명 체인과 Microsoft AuthRoot CTL 포함 여부, `bootstrap`을 거부하는 오프라인 요건은 패키징 코드가 검사한다. 무인 설치(`/VERYSILENT`)와 버전별 불변 HTTPS URL은 `submission.json` 체크리스트 문구이고 패키징이 검사하지 않으므로, 이 단계의 증거가 아니라 앱 개발자가 제출 때 직접 확인할 항목이다. | `submittable: true`인 패키징 보고서. 서명 검사 코드의 단위 시험은 도구를 가짜로 바꾸므로 실제 서명 도구 실행 결과는 증거가 아니다. | 프레임워크 |
   | 3. 제출됨 | 앱 개발자가 Partner Center에 제출을 마침 | 제출 ID와 제출 시각 | 앱 개발자 |
   | 4. 심사 통과 | Store 인증이 승인으로 끝나 게시 가능한 상태가 됨 | 심사 결과가 승인임을 보여 주는 Partner Center의 기록 | 앱 개발자 |
   | 5. Store에서 설치해 실행 확인 | Store 목록에서 설치한 앱이 실제로 시작하고 핵심 동작이 됨. 증거는 게시한 버전마다 따로 남기며, 이후 버전의 업데이트(ADR 0054 결정 4)는 그 버전의 3~5단계를 다시 거친다. | Store 설치 기록(버전, 설치 방법, 실행 결과) | 앱 개발자 |

   "Microsoft Store로 배포했다"는 5단계의 증거가 있을 때만 쓴다. 1~4단계는 각각 "패키지 생성됨", "제출 전 검증 통과", "제출됨",
   "심사 통과"로 이름을 붙여 쓴다.
2. 프레임워크가 자동으로 증명하는 범위는 1~2단계까지다. 3~5단계는 앱 개발자의 책임이며 프레임워크는 결과를 보장하지 않고 증거 양식도
   강제하지 않는다. Store 정책 검토와 심사 결과는 Microsoft가 정하고 정책이 바뀔 수 있으므로, 이 저장소의 문서와 시험은 특정
   정책 번호의 통과를 약속하지 않는다.
3. 현재 상태는 다음과 같이 표기한다.

   | 채널 | 상태 |
   | --- | --- |
   | `win-store-unpackaged` | 1~2단계는 패키징 보고서(`ok`, `submittable`)로 확인한다. 3~5단계는 이 저장소 어디에도 기록이 없으며 미제출, 미승인이다. |
   | `win-store-msix` | 패키지 생성이 차단돼 1단계에 이르지 못한다(ADR 0127). 미제출, 미승인이다. |

   MSIX 차단이 풀려도 `win-store-msix`는 ADR 0127의 검증 증거 표가 채워진 뒤에 같은 다섯 단계를 따른다. 그 전에는 프레임워크가
   MSIX Store 배포를 지원한다고 쓰지 않는다.
4. 제외하는 것은 다음과 같다.
   - MSI: 생성하지 않는다(ADR 0127 결정 2). 외부 도구로 만든 MSI의 Store 제출은 프레임워크가 단계를 증명하지 않는다.
   - Partner Center 제출 자동화(API 연동, 제출 ID 수집, 심사 상태 조회): 프레임워크 범위 밖이다. 필요한 앱이나 플러그인이 따로 만들 수 있으며
     코어와 호스트 계약은 늘리지 않는다.
   - Store 외 채널(`win-direct`)의 자동 제출: 하지 않는다. `win-direct`의 결과는 Store 단계로 계산하지 않는다.
5. 이 결정은 코드, 공개 계약, 패키징 채널을 바꾸지 않는다. 지원 표([플랫폼 지원](../platform-support/README.md))에 단계 표기를
   반영하는 일은 별도 변경에서 한다.

## 근거

- 제출과 심사는 Microsoft의 계정, 인증서, 심사 대기 같은 외부 상태에 달려 있어 이 저장소의 시험으로 재현할 수 없다. 그래서 프레임워크가
  증명하는 단계를 패키징 보고서로 확인할 수 있는 생성과 제출 전 검증으로 한정하고, 나머지는 증거를 남기는 책임을 앱 개발자에게 둔다.
- 패키지가 만들어진 것과 Store에서 설치돼 실행되는 것은 서로 다른 사실이다. 서명 체인, 무인 설치, 앱 데이터 경로, 업데이트 경로는 제출
  뒤 심사와 설치에서 다시 드러날 수 있다. 단계를 구분하면 "패키지 생성만으로 배포 완료"로 읽히는 표기를 막는다.
- 제출 자동화는 계정, 토큰, 심사 대기 같은 외부 상태에 의존해 CI에서 재현할 수 없다. 코어를 작게 두는 방침과 맞지 않고, 쓰는 앱이
  확인되지 않았으므로 지금은 넣지 않는다.
- 이 결정은 모든 앱의 보안 경계, 경로 제한, 권한 모델을 바꾸지 않는다.

## 후속

- 지원 표에 단계 표기와 현재 상태(미제출, 미승인)를 반영한다. 별도 변경으로 한다.
- `win-store-msix` 생성을 열 때 ADR 0127의 검증 증거 표를 채운 뒤 이 문서의 3번 표를 갱신한다.
- 외부 MSI 입력 지원 여부는 ADR 0127이 남긴 후보를 따라 쓰는 앱이 생길 때 정한다.
