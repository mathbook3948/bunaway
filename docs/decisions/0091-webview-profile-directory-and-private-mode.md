# WebView 프로필 디렉터리 선택, 시크릿 모드, 프로필 삭제를 제공하지 않는다

결정일: 2026-10-27. 검토 기준: main `c6b9ecc9`.

## 배경

아래 Electron과 Tauri 서술은 해당 프로젝트의 공개 문서와 소스 확인에 따른 것이며 이 저장소의 테스트로 검증한 것은 아니다.

앱이 WebView 프로필(사용자 데이터 폴더)의 위치를 고르거나, 디스크에 남기지 않는 시크릿(InPrivate) 프로필로 WebView를 열거나,
프로필 전체를 지우는 수단을 둘지 정해야 했다. [ADR 0062](./0062-webview-network-identity-options.md) 결정 4가 시크릿 모드를
"프로필 디렉터리와 데이터 저장소 선택 항목이 정해질 때 그 결정에 포함해" 다시 다루기로 미뤘고, 이 결정이 그 항목을 닫는다.

- Electron은 `session.fromPartition('persist:name')`으로 영속 세션을, 접두어 없는 이름으로 메모리 세션을 만들어 저장소를
  나누고, `session.fromPath`와 `app.setPath('userData')`로 디스크 위치를 바꾼다. 영속 여부와 저장 경로는 런타임에 정하는 세션 단위 값이다.
- Tauri 2는 `WebviewWindowBuilder`의 `data_directory`와 `incognito`를 창 생성 옵션으로 둔다. Windows에서 `incognito`는
  WebView2 컨트롤러 옵션의 `IsInPrivateModeEnabled`로 구현하고, `data_directory`를 주지 않으면 앱 로컬 데이터 폴더를 쓴다.
  생성 뒤에 영속 여부나 경로를 묻는 getter는 없다. 프로필 삭제는 WebView 하나의 브라우징 데이터를 지우는 `clear_all_browsing_data`뿐이다.
- WebView2는 환경을 만들 때 사용자 데이터 폴더를 받고, 컨트롤러 옵션(`ICoreWebView2ControllerOptions`)의 `ProfileName`과
  `IsInPrivateModeEnabled`로 한 폴더 안에 이름 있는 프로필이나 InPrivate 프로필을 고른다. InPrivate 프로필도 일반 프로필에서
  파생한 off-the-record 프로필이라 그 프로필 폴더는 디스크에 만들어지거나 열린다. 프로필 삭제는 `ICoreWebView2Profile8`에 있다.
- 이 호스트는 앱 데이터 아래 `webview/` 폴더에 영속 프로필 하나를 두고, 창을 다시 만들어도 같은 프로필을 쓴다
  ([ADR 0026](./0026-single-webview-single-window.md)). 배포 앱에서는 호스트 프로세스의 환경 변수
  `WEBVIEW2_USER_DATA_FOLDER`가 호스트가 넘기는 폴더를 대체하고, 호스트는 이 값을 걸러내거나 검증하지 않는다
  ([ADR 0030](./0030-launch-arguments-and-environment.md) 결정 4). 프로필 폴더의 위치는 공개 계약이 아니다.
- 창 하나에 WebView 하나이고 탐색은 앱 정의의 `origins` 안으로 제한된다. 임의 사이트를 여는 브라우저형 앱을 위한
  기능이 아니므로 시크릿 프로필이 막는 대상(방문 기록, 로그인 상태가 다른 사이트에 남는 문제)이 이 호스트에서는 좁다.
- 프로필 안의 데이터 삭제는 [ADR 0081](./0081-webview-browsing-data.md)이, cookie는 [ADR 0076](./0076-webview-cookies.md)이 정했다.

## 결정

1. 앱 정의, 창 생성, 런타임 API에 프로필 디렉터리, 프로필 이름, 데이터 저장소(partition) 선택 항목을 추가하지 않는다.
   프로필 위치는 호스트가 앱 데이터 아래로 정하며 앱 코드가 바꾸지 않는다. 배포 앱의 운영자가 위치를 바꿔야 하면 ADR 0030 결정 4의
   `WEBVIEW2_USER_DATA_FOLDER`를 쓰고, 그 경로 제한은 앱이 책임진다.
2. 시크릿(InPrivate) 모드 옵션과 API를 추가하지 않는다. WebView는 항상 영속 프로필로 열린다.
3. 프로필 삭제(앱 데이터 초기화) API를 추가하지 않는다. 전체 브라우징 데이터 삭제가 필요한 앱이 확인되면 ADR 0081 결정 4대로
   별도 결정에서 인자 없는 전체 삭제부터 검토하며, 이 결정은 그 방침을 바꾸지 않는다.
4. 쓰는 앱이 확인되어 시크릿 모드를 다시 다룬다면 최소 형태는 앱 정의의 불리언 하나이고 창 생성 때 고정한다(런타임 변경 없음).
   그 결정은 코어 계약 확대이므로 구현 전에 설계 메모를 거치며 다음을 먼저 확인한다.
   - 창을 다시 만들 때 영속 프로필을 재사용하는 현재 규칙과 달리, 시크릿 프로필의 쿠키와 저장소는 재생성 때 사라진다.
   - 시크릿에서도 디스크에 남는 것: WebView2가 만드는 부모 프로필 폴더, 앱 저장소에 기록하는 `window-state`, 알림과 업데이트의 상태.
     "종료 때 디스크에 남기는 것이 없음"을 문서에 쓰려면 이 목록이 실제로 비어 있음을 Windows CI에서 확인해야 한다.

## 근거

- Electron과 Tauri는 위치 선택과 시크릿을 모두 제공하지만 방식이 다르다. Electron은 런타임 partition이고 Tauri는 생성 옵션이다.
  어느 쪽이든 앱 정의나 창 생성 계약에 항목이 늘고, 시크릿은 프로필 모델(영속 하나)과 재생성 규칙을 함께 바꾼다. 쓰는 앱이 확인되지
  않았으므로 코어는 작게 두는 쪽을 따른다.
- 위치 변경은 이미 `WEBVIEW2_USER_DATA_FOLDER`로 가능하다. 앱 정의의 경로 필드를 더하면 경로 검증과 접근 제한을 호스트가 맡게 되어
  경로 제한은 앱 책임이라는 방침과 부딪힌다.
- 프로필 이름과 저장소 선택은 창 하나에 WebView 하나인 구조(ADR 0026)에서 선택할 대상이 없다.
- 시크릿 프로필은 탐색이 `origins`로 제한된 호스트에서 얻는 것이 작고, 앱이 임시 데이터를 쓰려면 앱 백엔드의 저장소 플러그인이나 메모리를 쓸 수 있다.
- 새 권한 표면이 없고 기존 앱의 동작도 바뀌지 않는다.

## 결과

- 스키마, 이벤트, 권한과 네이티브 코드 변경은 없다.
