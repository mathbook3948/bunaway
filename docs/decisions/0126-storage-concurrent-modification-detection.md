# storage는 동시 수정 감지를 제공하지 않고, 앱이 stat으로 비교한다

결정일: 2026-10-28. 검토 기준: main `37221b99`.

## 배경

앱이 파일을 읽은 뒤 다른 프로세스나 사용자가 같은 파일을 바꾸면, 앱이 나중에 쓴 내용이 그 변경을 모르고 덮어쓴다(lost update).
`storage`가 이를 감지해 주는 기능을 제공할지, 제공한다면 어떤 계약일지 정해야 했다. 후보는 세 가지다.

- (a) 제공하지 않는다. 앱이 `storage.stat`의 `modifiedAtMs`와 `sizeBytes`를 쓰기 전에 직접 비교한다.
- (b) `writeText`와 `writeBytes`에 선택 입력(읽기 전에 얻은 `modifiedAtMs`, 크기)을 더하고 불일치이면 실패시킨다.
- (c) 파일 잠금 작업을 따로 둔다.

비교 기준은 다음과 같다.

- Electron은 `fs`를 그대로 노출하며 쓰기 전 변경을 감지하는 기능을 제공하지 않는다. 에디터류 앱은 앱 계층에서 `fs.stat`의
  `mtimeMs`를 저장해 두었다가 쓰기 전에 다시 비교한다.
- Tauri의 fs 플러그인에는 조건부 쓰기나 충돌 감지 API가 없다.
- 위 Electron과 Tauri 서술은 공개 문서에 따른 것이며 이 저장소의 테스트로 검증한 것은 아니다. 아래 저장소 서술은 코드와 문서를 근거로 한다.
- 이 저장소의 `StorageMetadata`는 파일에 `sizeBytes`와 `modifiedAtMs`를 이미 준다. `modifiedAtMs`는 Node 호환 `stat`의
  나노초 수정 시각을 밀리초로 자른 값이다(`plugins/storage/src/platforms/node-storage.ts`). 코드는 나노초 값이 0이거나 밀리초로 바꾼 값이 안전 정수 범위를 넘으면 `null`로 처리한다. Windows에서 시각이 기록되지 않은 파일이 `null`로 오는지는 이 저장소의 테스트로 확인하지 않았다.
  [storage.stat](../site/src/content/docs/reference/host/storage-stat.mdx)가 반환 필드를 설명하며, `null` 조건은 같은 문서에도 코드 기준으로 적는다.
- 쓰기 연산의 입력은 엄격한 스키마라 선택 필드를 더하려면 계약이 바뀐다. 실패 코드에는 충돌을 나타내는 값이 없어
  (b)는 새 오류 코드도 요구한다.
- 경로 제한은 앱 명령의 책임이고 플러그인은 열린 핸들을 고정하거나 최종 경로를 다시 비교하지 않는다([ADR 0024](./0024-plugin-path-responsibility.md)).

## 결정

1. `storage`는 동시 수정 감지를 제공하지 않는다. 쓰기 연산에 기대 수정 시각이나 기대 크기 같은 선택 입력을 더하지 않고,
   충돌을 뜻하는 오류 코드와 잠금 작업도 만들지 않는다. storage 계약, 정책 필드, 플랫폼 어댑터를 바꾸지 않는다.
2. 감지가 필요한 앱은 파일을 읽기 전에 `storage.stat`으로 `modifiedAtMs`와 `sizeBytes`를 함께 기억하고(읽은 뒤에 기억하면 그 사이의 변경을
   기준값으로 삼아 놓친다), 쓰기 직전에 다시 `stat`해서 둘 다 같은지 비교한다. 앱이 직접 쓴 뒤에는 `stat`으로 기준값을 다시 잡는다. 비교 기준은 수정 시각 하나가 아니라 수정 시각과 크기의 쌍이다. 시각이 같아도 길이가 다르면 변경을 잡을 수 있다.
   `modifiedAtMs`가 `null`이면(파일의 `sizeBytes`는 항상 숫자이다) 그 파일에는 이 방법을 쓸 수 없으며, 앱은 내용 비교(작은 파일은 다시 읽어 해시나 문자열 비교)로 대신한다. 시각 해상도가 거친 파일 시스템에서는 쓴 뒤에도 시각이 같을 수 있으므로 시각이 같다는 이유만으로 변경이 없다고 보지 말고 크기와 내용 비교를 함께 쓴다.
3. 이 방법은 최선 노력(best effort)이다. 한계는 아래 "남는 경쟁과 해상도"에 적고, 같은 내용을 아래 영향 절의 세 문서에서 이 결정으로 연결한다.
4. 쓰기 연산이 이미 막아 주는 경쟁과 막지 못하는 경쟁은 아래 표를 기준으로 한다. 이 표는 현행 동작을 정리한 것이며 새 약속을 더하지 않는다.
5. 이 결정은 파일 단위의 낙관적 감지만 다룬다. 파일과 폴더 변경 알림(watch)은 별도 항목이고, 파일 핸들과 stream I/O는 아직 제공하지 않으며 별도 항목에서 정한다.
6. (b)가 필요한 앱이 확인되면 이 결정을 다시 검토한다. (b)는 두 쓰기 연산의 입력 스키마, 오류 코드, 참조 문서를 함께 바꾸는 storage 계약
   변경이므로 소유자 결정이 필요하며, 이 결정에서 구현 후보로 넘기지 않는다.

## 쓰기 연산이 막는 경쟁과 막지 못하는 경쟁

| 상황 | 동작 | 이 연산이 막는가 |
| --- | --- | --- |
| 쓰는 도중 실패하거나 프로세스가 끝나 파일이 반쯤 쓰임 | `atomic: true`는 같은 폴더의 임시 파일에 쓴 뒤 교체한다 | 막는다. 대상은 이전 내용이거나 새 내용이다 |
| 서로 다른 프로세스의 두 쓰기가 같은 대상에 겹침, `atomic` 없음 | 같은 파일에 덮어쓴다 | 막지 못한다. 내용이 섞이거나 뒤의 쓰기가 남을 수 있다 |
| 서로 다른 프로세스의 두 쓰기가 같은 대상에 겹침, 둘 다 `atomic: true` | 각 교체는 전체 단위이다 | 섞이지는 않지만 나중에 교체한 쪽이 앞의 변경을 모르고 덮어쓴다 |
| 앱이 읽은 뒤 다른 프로세스가 바꾸고 앱이 씀 | 쓰기는 대상의 현재 내용을 확인하지 않는다 | 막지 못한다. `stat` 비교가 필요하다 |
| 다른 프로세스가 대상 파일을 열어 두고 있음, Windows `atomic: true` | 교체가 짧게 다시 시도한 뒤 `PERMISSION_DENIED`로 실패하고 기존 파일은 그대로다 | 충돌 감지가 아니라 부수적인 거부이다. 열지 않은 프로세스의 변경은 잡지 못한다 |
| 여러 프로세스가 같은 로그 파일에 append | append가 서로 사이에 들어갈 수 있다 | 막지 못한다. 레코드 순서는 앱이 관리한다 |
| 이미 있는 대상으로 복사 | `copyFile`은 대상을 배타적으로 만들고 기존 대상은 `INVALID_ARGUMENT`로 거부한다 | 기존 대상을 덮어쓰지 않는 것이며 기존 파일의 수정 감지가 아니다. Windows에서 대상이 없는 링크는 링크가 가리키는 위치에 새 파일을 만들고, 네트워크 파일 시스템에서는 배타 생성을 약속하지 않는다. 동시 복사에서 하나만 성공한다는 동작은 Windows CI 로컬 볼륨에서만 확인했다 |

`writeText`와 `writeBytes`에는 "이미 있으면 실패" 같은 배타 생성 옵션이 없다. 새 파일만 만들게 하려면 앱이 먼저 `exists`로 확인할 수 있지만
확인과 쓰기 사이에 다른 프로세스가 만들 수 있다.

## 남는 경쟁과 해상도

- 검사와 쓰기 사이의 구간: 앱이 `stat`으로 비교한 뒤 쓰기까지 사이에 다른 프로세스가 파일을 바꾸면 놓친다. 이 저장소가 쓰는 교체(`MoveFileExW`,
  이름 바꾸기)와 덮어쓰기에는 "시각이 같을 때만 쓴다"는 조건부 연산이 없어, `storage` 연산만으로는 이 구간을 없앨 수 없다.
  `atomic: true`를 쓰면 내용이 섞이는 것은 막지만 구간은 그대로다.
- 파일을 연 채로 비교하는 방식은 호출 사이에 사는 파일 핸들을 요구한다. 이 결정은 핸들 연산을 새로 약속하지 않으므로 storage 플러그인에서는 하지 않는다.
  `node:fs`로 직접 처리해도 조건부 교체나 강제 잠금이 없어 다른 프로세스의 변경과의 경쟁은 없어지지 않는다. 앱은 자기 프로세스 안의 비교와 쓰기를 한 곳으로 모아 앱 내부의 경쟁을 해상도 한계 안에서 막을 수 있다.
- 시각 해상도: `modifiedAtMs`는 밀리초이다. 같은 밀리초 안에 같은 크기로 바뀐 파일은 구별할 수 없다. 파일 시스템 자체의 해상도도 다르다. NTFS는
  100 ns 단위로 기록하지만 FAT32 등 FAT 계열은 2초 단위(exFAT는 10 ms)로 기록하고, 해상도가 거친 파일 시스템에서는 짧은 간격의 변경이 같은 시각으로 남을 수 있다
  (파일 시스템 공개 규격에 따른 서술이며 이 저장소의 테스트로 검증한 것은 아니다).
- 같은 앱의 두 뷰나 명령이 같은 파일에 대해 각자 `stat`, 비교, 쓰기를 하면 두 비교가 모두 통과한 뒤 쓰기가 차례로 일어나 앞의 변경을 덮어쓴다. 쓰기 하나하나는 호스트가 차례로 처리하지만 비교와 쓰기 순서까지 묶어 주지 않으므로 앱이 파일 단위로 비교, 쓰기, 기준값 재설정을 한 번에 하나씩 실행한다(읽기와 편집 동안 잠금을 쥐지 않는다).
- 앱이 쓴 뒤 `stat`으로 기준값을 다시 잡기 전에 다른 프로세스가 파일을 바꾸면 그 변경이 새 기준값에 흡수되어 이후 감지되지 않는다.
- 시각은 시계 변경, 복원 도구, 파일을 복사한 뒤 시각을 되돌리는 동기화 도구로 바뀌지 않거나 거꾸로 갈 수 있다. 같음 비교만 하고 대소 비교로 판단하지 않는다.
- `null`: 수정 시각이 `null`인 파일은 비교할 수 없다. 앱은 내용 비교로 대신한다.
- 네트워크 파일 시스템: 서버와 프로토콜에 따라 시각의 갱신과 노출 시점이 달라 비교가 늦게 반영될 수 있다. 약속하지 않는다.
- 비교는 변경이 있었다는 사실만 알려 준다. 병합은 앱이 정한다. 충돌 때 사용자에게 알리고 다시 읽을지, 다른 이름으로 저장할지, 덮어쓸지는 앱 정책이다.

## 근거

- Electron과 Tauri 모두 파일 API에 충돌 감지를 넣지 않는다. 에디터류 앱은 `stat` 비교를 앱 계층에서 한다(공개 문서와 관행에 따른 서술이며 이 저장소에서 검증하지 않았다). 같은 방식을 따른다.
- storage 계약은 작게 둔다. (b)는 쓰기 스키마, 오류 코드, 참조 문서를 모두 키우지만 경쟁 구간은 어차피 남는다.
- 앱 계층의 `stat` 비교는 지금 계약으로 변경 감지 자체는 준다. (b)는 비교를 호스트 안의 쓰기 호출 하나로 옮긴다. 같은 앱의 여러 뷰 사이 경쟁은 시각 해상도 한계 안에서 막지만 다른 프로세스와의 구간은 줄일 뿐 없애지 못한다. 앱이 파일 단위로 비교, 쓰기, 기준값 재설정을 한 번에 하나씩 실행하면 앞의 이득은 앱에서도 같은 해상도 한계 안에서 얻을 수 있어, 남는 이득이 계약 확대 비용에 못 미친다고 본다.
- 경로 제한이 앱 명령의 책임인 것처럼, 어떤 파일에 감지가 필요하고 충돌 때 무엇을 할지도 앱이 안다.

## 대안

- (b) 기대 수정 시각과 크기를 쓰기 입력에 더한다. 위의 이유로 보류한다. 검사와 교체 사이 구간이 남고, 쓰기 입력과 오류 코드 확대가 필요하다. 같은 앱 안의 경쟁은 해상도 한계 안에서 막지만 앱이 직렬화해도 얻을 수 있다.
- (c) 잠금 작업. 호출 사이에 사는 자원과 정리 규칙이 필요해 파일 핸들과 같은 문제를 가지고, Windows의 공유 모드와 바이트 범위 잠금은 강제이지만 macOS의 기본 잠금은 권고라 두 플랫폼의 의미가 다르고(운영체제 공개 규격에 따른 서술이며 이 저장소의 테스트로 검증한 것은 아니다), 잠금을 오래 쥔 프로세스가 다른 앱의 접근을 막을 수 있다.
- 읽기 결과에 수정 시각을 함께 돌려준다. 읽기 연산의 결과 스키마를 키우면서 `stat`으로 이미 얻는 값을 중복한다.
- 내용 해시 비교를 storage가 제공한다. 큰 파일에서 전체를 다시 읽는 비용이 크고, 필요한 앱은 작은 파일을 직접 비교할 수 있다.

## 영향

- 코드, 정책, 호스트 동작은 바뀌지 않는다.
- [storage.stat](../site/src/content/docs/reference/host/storage-stat.mdx), [storage.writeText](../site/src/content/docs/reference/host/storage-write-text.mdx),
  [바이너리 저장과 append](../site/src/content/docs/reference/host/storage-bytes.mdx)가 이 결정으로 연결한다.
- [파일 복사와 대상 이동](../site/src/content/docs/reference/host/storage-transfers.mdx)의 후속 작업 문장은 이 결정 당시 원자적 저장 부분을 빼서
  이 결정과 어긋나지 않게 했다(이후 [ADR 0136](./0136-storage-copy-and-move-overwrite.md)이 그 문장을 `overwrite` 결정으로 연결되는 문장으로 바꿨다).
- `docs/TODO-windows.md`의 충돌 처리 항목은 이 결정으로 닫는다.
- 복사와 이동의 `overwrite` 옵션은 [ADR 0136](./0136-storage-copy-and-move-overwrite.md)에서 정한다.
