# 신뢰된 백엔드의 별도 프로세스 격리 모델은 제공하지 않는다

결정일: 2026-10-27. 검토 기준: main `7290e7b1`.

## 배경

앱 백엔드(Bun)를 AppContainer, 제한된 토큰, 낮은 무결성 수준, Job Object 제한이나 별도 프로세스로 격리해 실행하는 모델을
프레임워크가 제공할지 정해야 했다.

- Electron은 main 프로세스에 OS 샌드박스를 두지 않는다. 앱 코드가 실행되는 프로세스 중 샌드박스는 renderer에 적용되고, utility process도 Node의 전체
  권한으로 실행된다. 격리가 필요한 앱은 별도 프로세스를 직접 띄워 자체 제한을 둔다.
- Tauri의 Rust 코어도 신뢰된 코드다. 격리는 capability와 WebView 쪽에서만 제공하고 코어 프로세스의 OS 샌드박스는 제공하지 않는다.
- 이 프레임워크의 백엔드는 앱 개발자가 작성해 앱과 함께 배포하는 코드다. PRD는 신뢰할 수 없는 백엔드 플러그인 샌드박스를
  비목표로 둔다([PRD](../PRD.md)).

위 외부 동작은 두 프레임워크의 공개 문서와 구조를 기준으로 한 것이며 이 저장소의 테스트로 검증한 것은 아니다.

## 결정

1. 백엔드를 AppContainer, 제한된 토큰, 낮은 무결성 수준이나 별도 샌드박스 프로세스에서 실행하는 모델과, Job Object로 백엔드의 메모리나 CPU를 제한하는 기능을 제공하지 않는다.
2. 호스트, 코어 계약, 권한, 정책 스키마는 바꾸지 않는다.
3. 아래 "이미 있는 격리"는 이 결정이 코드와 기존 ADR에서 확인한 범위다. 표는 백엔드 프로세스를 OS 수준으로 가두는 모델이 있는지를 정리한 것이며 정책 권한 검사 같은 다른 경계를 모두 나열하지 않는다.
4. 격리가 필요한 앱은 아래 "격리가 필요한 앱의 선택지"를 쓴다.

## 이미 있는 격리

| 경계 | 내용 | 근거 |
| --- | --- | --- |
| UI Worker 분리(Windows) | 창과 WebView2(COM 포함)는 UI Worker가 소유하고 앱 명령은 메인 스레드에서 실행한다. 파일 I/O는 별도 I/O Worker가 맡는다. 셋은 같은 프로세스의 신뢰 코드이며 Worker 분리는 책임 분리이지 보안 샌드박스가 아니다. | [ADR 0006](./0006-windows-bun-ui-worker.md) |
| 호출 컨텍스트 | 호스트가 관찰한 뷰, 세션, origin, frame으로 컨텍스트를 발급한다. 웹 메시지의 자기 신고값은 인증 수단이 아니다. | [ADR 0002](./0002-host-owned-call-context.md) |
| WebView 권한 경계 | 뷰는 정책에 허용된 `commands`와 권한만 호출한다. WebView 브라우저와 렌더러는 호스트와 별도 프로세스로 유지된다. | 별도 프로세스 유지: [ADR 0006](./0006-windows-bun-ui-worker.md). 정책이 범위를 정함: [ADR 0013 optional native plugins](./0013-optional-native-plugins.md) |
| 경로 책임 | 플러그인은 경로 형식만 검사하고 허용 범위는 앱 명령이 정한다. | [ADR 0024](./0024-plugin-path-responsibility.md) |
| process 플러그인 | shell 없이 argv로만 실행하고 인자 개수와 크기, 동시 실행 수, `run`에는 출력 상한과 30초 timeout이 있다(핸들에는 적용되지 않는다). Windows는 자식마다 전용 Job Object에 넣어 루트가 끝나면 하위 프로세스까지 종료한다. 앱 종료 때의 정리는 어댑터 폐기와 호스트 Job이 맡는다. 이 Job Object는 종료 범위를 위한 것이며 메모리, CPU, 파일 접근을 제한하지 않는다. | [process](../site/src/content/docs/reference/plugins/process.mdx), `plugins/process/src/platforms/windows-child.ts`(Job 제한은 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 하나) |

## 격리가 필요한 앱의 선택지

- 앱이 신뢰하지 않는 코드를 실행해야 하면, 앱이 신뢰하는 래퍼 실행 파일 하나를 앱 명령이 `processes.spawn`(Windows)이나
  `processes.run`으로 띄우고 실행 파일과 인자를 앱 명령이 검사한다. 신뢰하지 않는 코드는 그 래퍼가 토큰, 무결성 수준, 자원
  제한을 낮춘 뒤 실행한다. 이 플러그인은 신뢰된 도구와 허용한 인자만 연결하는 용도이며, 신뢰하지 않는 실행 파일을 직접 연결하라는 뜻이 아니다. 별도 Bun 프로세스를 띄워 자체 제한을 두는 것도 같은 방식이다. 오래 실행하는 보조 프로세스는 Windows에서만 `processes.spawn`으로 띄울 수 있고, macOS에서는 백엔드가 `Bun.spawn`을 직접 쓴다. Windows 자식은 작업 디렉터리와 dotenv 값을 포함한 백엔드 환경을
  상속하고 호출자가 이를 바꾸는 입력이 없으며, 래퍼가 스스로 권한을 낮추기 전까지 백엔드와 같은 권한으로 실행된다. 비밀 값을 dotenv에 둔 앱은 신뢰하지 않는 도구에 그 값이 노출될 수 있다.
- 신뢰할 수 없는 입력(원격 문서, 사용자가 올린 콘텐츠)은 백엔드에서 처리하지 않고 WebView에서 표시한다.
  그런 뷰에는 `plugin.*` 명령을 직접 허용하지 않는다([ADR 0024](./0024-plugin-path-responsibility.md)). 렌더러 샌드박스 수준은 이 저장소의 테스트로 검증하지 않았으므로 보장으로 쓰지 않는다.

## 근거

- 두 프레임워크 모두 신뢰된 메인 코드의 OS 샌드박스를 제공하지 않는다. 이 결정은 둘과 같다.
- 쓰는 곳이 없다. 백엔드는 앱 개발자가 쓴 코드이고, 신뢰할 수 없는 코드 실행은 비목표다.
- 격리를 켜면 코어 계약이 커진다. 낮은 무결성 수준에서는 파일, 레지스트리, 창, COM 접근이 달라져 모든 플러그인의 동작이
  그 수준에 묶인다. 경로 제한은 앱 책임이라는 방침([ADR 0024](./0024-plugin-path-responsibility.md))과 맞지 않고, 선택 플러그인이 실행 환경에 묶인다.
- 격리가 필요한 앱은 위 선택지로 지금도 구현할 수 있다.

## 재검토 조건

아래 중 하나가 생기면 별도 결정으로 다시 다룬다.

- 앱 밖에서 받은 서드파티 백엔드 플러그인을 로드하는 기능이 생길 때
- 공식 플러그인 레지스트리가 생길 때
- 앱이 신뢰하지 않는 코드를 백엔드에서 실행하는 사용처가 확인될 때

## 결과

- 코드, 이벤트, 권한, 스키마, 테스트 변경은 없다.
