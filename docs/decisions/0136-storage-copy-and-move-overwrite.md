# storage의 copyFile과 move는 호출마다 명시하는 overwrite 옵션으로 일반 파일 교체를 제공한다

결정일: 2026-10-29. 검토 기준: main `32693a1a`. 이 문서는 결정만 다루며 코드, 테스트, 공개 계약은 바꾸지 않는다.

## 배경

`storage.copyFile`은 대상을 배타적으로 만들고(`O_EXCL`, Windows는 `CREATE_NEW`) 기존 대상은 `INVALID_ARGUMENT`로 거부한다.
`storage.move`는 Windows에서 `MoveFileExW`를 덮어쓰기 플래그 없이, macOS에서 `renamex_np`를 `RENAME_EXCL`로 호출한다.
두 연산의 입력은 추가 필드를 받지 않는다. 앱이 기존 파일을 새 내용으로 바꾸려면 지금은 다음 중 하나를 직접 짜야 한다.

- 대상을 지운 뒤 복사한다. 지운 직후 복사가 실패하면 이전 내용은 사라지고 새 내용은 없거나 일부만 남는다.
- 파일 전체를 `readBytes`로 읽어 `writeBytes`의 `atomic: true`로 쓴다. 교체는 원자적이지만 파일 전체를 메모리에 올려야 한다.
- 대상을 다른 이름으로 `move`해 두고 복사한 뒤 성공하면 지우고, 실패하면 되돌린다. 원본을 보존하지만 성공 경로에도 `move`, `copyFile`, 삭제의 세 호출이 필요하고, 중간에 프로세스가 끝나면 앱이 복구 절차를 알아야 한다.

`move`로 임시 이름의 파일을 대상 위에 옮기는 방식은 지금 계약에서 쓸 수 없다. 대상이 있으면 `move`가 거부하기 때문이다.

## 비교 기준

- Electron은 Node `fs`를 노출한다. `fs.copyFile`은 기본이 덮어쓰기이고 `COPYFILE_EXCL`로 거부하며, `fs.rename`은 기존 대상 파일을 대체한다.
- Tauri의 fs 플러그인 `copyFile`은 대상을 덮어쓰고, `rename`도 기존 대상을 대체한다.
- 위 두 서술은 공개 문서에 따른 것이며 이 저장소의 테스트로 검증한 것은 아니다. 두 프레임워크 모두 덮어쓰기를 제공하므로 "제공하지 않는다"는 선택은 앱의 이식 경로를 막는다.
- 이 저장소에서 `writeText`와 `writeBytes`는 기존 파일을 이미 덮어쓰며, `atomic: true`는 같은 폴더의 임시 파일에 쓴 뒤 `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`로 교체한다(`plugins/storage/src/platforms/windows.ts`). 교체 구현이 이미 있고, 실패하면 임시 파일을 지우고 기존 대상은 바뀌지 않는다는 계약도 문서화되어 있다.
- 경로 제한은 앱 명령의 책임이며 플러그인은 범위를 판단하지 않는다([ADR 0024](./0024-plugin-path-responsibility.md)).
- [ADR 0126](./0126-storage-concurrent-modification-detection.md)은 "이미 있는 대상으로 복사 거부"와 "기존 파일의 수정 감지"를 구분하고, 조건부 교체("시각이 같을 때만 쓴다")를 제공하지 않는다고 정했다.

## 결정

1. 덮어쓰기를 제공한다. 기본값은 지금과 같은 "기존 대상 거부"이고 교체는 호출마다 명시한다. Electron과 Tauri는 기본이 덮어쓰기이지만, 이 프레임워크는 복사와 이동 결과가 사용자 파일을 조용히 없앨 수 있다는 이유로 거부를 기본으로 유지한다. 옵션을 주지 않는 기존 호출의 동작과 오류는 바뀌지 않는다.
2. 옵션 모양은 `overwrite?: boolean`이다. 상태가 "실패"와 "교체" 둘뿐이라 `onExists: "fail" | "replace"`가 주는 선택지가 없다. `overwrite`가 `true`가 아니면 지금과 같이 거부한다. 새 오류 코드는 만들지 않는다.
3. 교체 대상은 일반 파일로 한정한다(`copyFile`은 링크가 가리키는 일반 파일 포함). 디렉터리 트리의 합치기와 교체, `copyDirectory`의 덮어쓰기는 이번 결정에 포함하지 않는다.
4. 코어, 프로토콜, 호스트 전송 계약은 바꾸지 않는다. 변경은 storage 플러그인 안(두 연산 입력 스키마, 공통 기반 `node-storage.ts`의 `move`와 `copyContents`, 교체 절차를 담은 `node-atomic-write.ts`, 플랫폼 어댑터)과 참조 문서에 한정한다. 연산 권한 이름도 늘리지 않는다(아래 "권한").
5. 경로 제한은 앱 책임이다. 앱 명령은 `from`과 `to` 두 위치를 모두 검사하고, `overwrite`를 받는 앱 명령은 `to`의 쓰기 규칙을 `writeText`와 같은 기준으로 적용한다.

## 연산별 계약

### copyFile

`overwrite: true`이면 대상으로 풀린 실제 파일과 같은 폴더의 임시 파일에 전체를 복사하고 디스크에 반영한 뒤 대상 위에 교체한다.
`writeBytes`의 `atomic: true`와 같은 교체 절차(임시 파일, 디스크 반영, 교체, 실패 시 정리)를 재사용하며 두 번째 교체 구현을 만들지 않는다.
다만 지금의 `replaceAtomically`는 바이트 전체를 한 번에 받고, 상위 폴더를 항상 만들고, 권한 비트 읽기와 `W_OK` 검사를 한 함수에서 하므로 그대로는 쓸 수 없다.
구현은 이 함수를 나눠 조각 단위 복사 원본을 받을 수 있게 하고, 상위 폴더 생성과 권한 비트 이어받기를 호출자가 고르게 하며 `writeBytes`의 동작은 바꾸지 않는다. `copyFile`의 `copyFile`의 기존 입력 규칙은 `overwrite`와 무관하게 유지한다.

- `to`의 상위 디렉터리가 없으면 `INVALID_ARGUMENT`이고 폴더를 만들지 않는다. `atomic` 쓰기가 상위 폴더를 만드는 동작은 가져오지 않는다.
- 새 파일의 권한은 `copyFile`의 기존 규칙을 따른다(macOS는 `0600`에 umask, Windows는 상속 ACL). 기존 대상의 POSIX 권한 비트를 이어받는 `atomic` 쓰기의 동작은 가져오지 않는다. 같은 함수(`existingMode`)에 있는 `accessSync(W_OK)` 쓰기 권한 사전 검사는 유지한다. `copyFile`에는 지금 이 검사가 없고, 읽기 전용 대상의 `PERMISSION_DENIED`는 이 검사로 플랫폼과 무관하게 성립한다.
- 임시 파일은 링크를 따라간 뒤의 실제 대상 폴더에 만들므로, 링크가 다른 폴더를 가리키면 그 폴더에 쓸 수 있어야 한다.

| 상황 | 결과 | 실패 뒤 상태 |
| --- | --- | --- |
| 대상이 없음 | 새 파일을 만든다 | 성공: 새 파일. 실패: 임시 파일을 지워 대상이 생기지 않는다. 거부 모드는 일부만 쓴 대상이 남을 수 있어 실패 경로가 다르다 |
| 대상이 일반 파일 | 교체한다 | 성공: 새 내용. 실패: 임시 파일을 지우고 대상은 이전 내용, 원본은 그대로 |
| 대상이 디렉터리 | `INVALID_ARGUMENT` | 아무것도 바뀌지 않음 |
| 대상이 파일을 가리키는 링크 | 링크는 두고 가리키는 파일을 교체한다(`atomic` 쓰기와 같다) | 위와 같음 |
| 대상이 가리키는 곳이 없는 링크 | `INVALID_ARGUMENT`. Windows 거부 모드는 이 링크를 따라가 새 파일을 만들므로 같은 입력의 결과가 옵션에 따라 다르다 | 아무것도 바뀌지 않음 |
| 대상이 읽기 전용 파일 | `PERMISSION_DENIED` | 대상은 이전 내용 |
| Windows에서 다른 프로세스가 대상을 열어 둠 | 짧게 다시 시도한 뒤 `PERMISSION_DENIED` | 대상은 이전 내용 |
| 원본과 대상이 같은 파일로 풀림 | `INVALID_ARGUMENT` | 아무것도 바뀌지 않음 |

복사 도중 원본이 줄어드는 경우의 `INTERNAL`은 지금과 같지만, 교체 모드에서는 임시 파일이 대상에 닿기 전에 지워지므로 일부만 쓴 대상이 남지 않는다. 프로세스가 교체 전에 끝나면 같은 폴더에 임시 파일이 남을 수 있다.
교체는 대상 파일을 새 파일로 바꾸므로 `atomic` 쓰기와 같이 기존 파일의 ACL, 대체 데이터 스트림과 하드 링크를 이어받지 않는다. 필요한 공간은 임시 복사본만큼 더 필요하다.

### move

`overwrite: true`는 "대상이 있으면 교체하고 없으면 기본 모드처럼 이동"하는 플래그로 쓸 수 있어야 한다. 그래서 아래 제한은 대상이 이미 있을 때만 적용하고, 대상이 없으면 `overwrite`를 주지 않은 호출과 결과가 같다(디렉터리와 링크 원본, 다른 볼륨 이동 포함).
대상이 이미 있으면 같은 볼륨에서 한 번의 이름 변경으로 교체한다(Windows `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`, macOS는 `RENAME_EXCL`을 빼고 `rename`).

- 대상이 이미 있을 때 원본이 일반 파일이고 대상도 일반 파일이어야 한다. 원본이 디렉터리이거나 링크이면, 또는 대상이 디렉터리나 링크(디렉터리 symlink와 junction 포함)이면 `INVALID_ARGUMENT`이고 아무것도 바뀌지 않는다. 디렉터리와 링크 대상을 교체하는 동작은 두 플랫폼에서 다르고 Windows의 링크 처리는 이 저장소에서 확인하지 않았으므로 계약으로 정하지 않는다. 링크가 가리키는 파일을 교체해야 하면 `copyFile`의 `overwrite`를 쓴다.
- 대상이 이미 있고 다른 볼륨이면 `UNSUPPORTED`이고 원본과 대상 모두 그대로 둔다. 다른 볼륨 이동은 복사 뒤 원본 삭제라 교체가 원자적이지 않고, 중간에 실패하면 대상이 반쯤 쓰인 파일로 바뀔 수 있다. 앱은 `copyFile`의 `overwrite`로 복사한 뒤 원본을 지운다.
- 원본이 없거나 대상 상위 디렉터리가 없으면 `INVALID_ARGUMENT`이다.
- 원본과 대상이 같은 경로이거나 대상이 원본의 하위 경로이면 `INVALID_ARGUMENT`이다. 공통 `move`는 지금 하위 경로만 검사하고, 같은 경로는 Windows에서는 덮어쓰기 금지 이름 변경이 실패하며 걸러지며 macOS 어댑터는 `from === to`를 직접 거부한다. 교체 모드는 이 실패에 기대지 못하므로 같은 경로 검사를 공통 `move`에 하나로 두고 어댑터별 검사를 늘리지 않는다. 대상이 있을 때 같은 파일을 가리키는 서로 다른 이름(하드 링크, 링크 경유)도 `INVALID_ARGUMENT`로 거부하고 둘 다 그대로 둔다. 대소문자만 다른 이름(`a.txt`를 `A.txt`로)은 대소문자를 구분하지 않는 파일 시스템에서 같은 파일로 판정되므로 교체 모드에서 이 규칙으로 거부된다. 기본 모드가 이 이름 변경을 허용하는지는 이 저장소에서 확인하지 않았으며, 허용한다면 같은 입력의 결과가 옵션에 따라 달라지는 예외로 구현 항목이 시험하고 문서에 적는다.
- 읽기 전용 대상과 다른 프로세스가 열어 둔 대상 때문에 교체가 거부되면 `PERMISSION_DENIED`이고 원본과 대상은 그대로다. 지금 `move`의 실패 매핑은 Windows 공유 위반(32)을 `INTERNAL`로 두므로, 교체 모드에서는 `copyFile` 교체가 쓰는 `swapFailure` 매핑(공유 위반 32와 잠금 위반 33을 `PERMISSION_DENIED`로)을 재사용하도록 구현에서 바꾼다(교체 모드에 한정하고 `overwrite`를 주지 않은 호출의 오류는 유지한다). `move`의 다시 시도는 이번 결정에 넣지 않는다.
- macOS의 `rename`은 대상 파일의 쓰기 권한을 보지 않고 교체한다. 읽기 전용 대상의 결과를 Windows와 맞추기 위해 `move` 교체 모드도 위의 `W_OK` 사전 검사를 쓴다.

### 두 연산 공통

- 교체 때문에 이전 대상 내용은 복구할 수 없다. 이전 내용을 보존해야 하면 앱이 교체 전에 대상을 다른 이름으로 `move`하거나 `copyFile`로 백업해 둔다.
- 교체가 끝난 뒤 시간 초과나 연결 종료가 일어나도 교체는 끝났을 수 있다. 재시도 전에 두 위치의 실제 상태를 확인하라는 기존 문장을 유지한다.
- 네트워크 파일 시스템에서의 교체 원자성과 내구성은 약속하지 않는다.

## 수정 감지와의 관계

`overwrite`는 대상의 현재 상태를 확인하지 않는다. ADR 0126이 제공하지 않기로 한 조건부 교체를 이 옵션으로 되살리지 않는다.
대상이 읽은 뒤 바뀌었는지는 앱이 `storage.stat`의 `modifiedAtMs`와 `sizeBytes` 쌍을 교체 직전에 비교해 판단한다. 비교와 교체 사이의 구간은 그대로 남고, 같은 앱의 여러 호출이 같은 대상을 건드릴 때의 직렬화는 앱이 맡는다.
ADR 0126의 (b)는 쓰기 연산의 입력과 새 오류 코드를 요구하는 별도 계약 변경이며, 이번 결정으로 그 선택을 앞당기지 않는다. (b)를 나중에 받아들이면 그 시점에 두 연산의 입력도 다시 정한다.
이 결정의 `overwrite`와 ADR 0126의 "이미 있는 대상으로 복사 거부" 서술은 모순되지 않는다. 기본 모드의 거부는 그대로이고, 표의 해당 줄은 구현이 들어갈 때 "`overwrite`를 주지 않으면"으로 한정한다.
[ADR 0024](./0024-plugin-path-responsibility.md)가 플러그인의 기능 안전 검사로 적은 "무덮어쓰기 복사와 이동은 대상을 덮어쓰지 않는다"는 기본 모드의 서술로 남고, 구현 항목이 그 문장을 "`overwrite`를 주지 않으면"으로 한정한다.

## 권한

연산 권한 이름(`storage.copyFile`, `storage.move`)과 직접 호출용 `plugin.storage.*` 명령 권한은 늘리지 않는다. `overwrite: true`는 같은 연산의 입력이다.
이 선택의 영향: [ADR 0024](./0024-plugin-path-responsibility.md)에 따라 `plugin.storage.copyFile` 또는 `plugin.storage.move`를 화면에 직접 허용한 뷰는 그 작업의 모든 유효한 입력을 쓸 수 있다. 따라서 `overwrite`를 구현한 버전으로 올리는 순간, 정책을 바꾸지 않은 기존 앱의 그 뷰도 기존 파일을 교체할 수 있게 된다. 실효 능력이 넓어지는 것이며 "기존 앱의 권한이 바뀌지 않는다"고 말하지 않는다.
이미 `storage.writeText`를 허용한 앱은 같은 경로에 덮어쓸 수 있으므로 새 종류의 능력은 아니지만, 복사와 이동 권한만 열어 둔 앱에는 범위가 넓어진다. 구현 항목은 이를 다음처럼 알린다.
- 전송 문서 17행의 "이 권한은 다른 전송 작업이나 일반 읽기와 쓰기를 허용하지 않습니다" 근처에, 두 연산의 권한이 `overwrite`로 기존 파일 교체를 포함한다는 문장을 더한다.
- 변경 기록에 같은 내용을 적어, 직접 호출을 연 앱이 `overwrite`가 필요 없다면 앱 명령으로 옮기도록 안내한다.
경로 범위를 앱 명령이 정하는 것은 변하지 않으므로, 화면에 직접 호출을 열지 않고 앱 명령이 `to`를 검사하는 구성이 권장 방식이다.
별도 권한 이름을 두면 이 확대를 막을 수 있지만, 권한 이름과 정책 스키마를 늘려 storage 권한 표면이 커진다. 이번에는 늘리지 않고, 별도 권한이 필요한 앱이 확인되면 그때 다시 정한다.

## 근거

- Electron과 Tauri 모두 복사와 이동에서 기존 대상 파일의 교체를 제공한다. 같은 기능을 제공하되 기본값은 거부로 유지해 데이터 손실을 막는다.
- 앱이 직접 짠 "삭제 뒤 복사"는 중간 실패 때 이전 내용이 사라진다. 플러그인이 임시 파일과 교체로 처리하면 실패한 뒤에도 이전 내용이 남는다. 대상이 잠시도 비지 않는 원자적 교체는 앱이 직접 만들 수 없다. 백업 이름을 쓰는 절차는 이전 내용을 보존하지만 그 사이 대상이 비는 구간이 있다.
- 교체 경로(`MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`)와 실패 계약은 `atomic` 쓰기에 이미 있다. 새 오류 코드나 새 연산 없이 플러그인 입력 하나로 끝난다.
- 별도 `replaceFile` 연산은 같은 기능에 이름을 하나 더 만들고 권한 이름도 늘린다. 두 연산에 옵션 하나를 더하는 쪽이 코어와 문서 표면이 작다.

## 대안

- 제공하지 않는다. 위 세 가지 앱 절차를 문서화하는 방법이다. 큰 파일의 원자적 교체는 앱이 만들 수 없고, 백업 이름을 이용한 절차는 호출이 많아 중간 종료 때 복구가 어렵다. 이식성 면에서도 두 프레임워크와 다르다.
- `onExists: "fail" | "replace"`. 선택지가 둘이라 `boolean`이 단순하다. 나중에 "병합"이나 "건너뜀"이 필요해지면 그때 새 필드를 정한다.
- 기본값을 덮어쓰기로 바꾼다. 기존 호출의 결과가 바뀌고, 복사 한 번이 사용자 파일을 조용히 없앨 수 있다.
- 별도 `replaceFile` 연산. 위 근거로 채택하지 않는다.
- 다른 볼륨 이동에서 `COPY_ALLOWED`로 교체를 허용한다. 교체가 원자적이지 않아 `UNSUPPORTED`로 둔다.
- `copyDirectory`와 디렉터리 `move`의 덮어쓰기. 트리의 합치기와 부분 실패 상태가 커서 이 결정 밖이다.

## 후속 구현 항목과 시험

구현은 이 결정이 머지된 뒤 별도 항목으로 고른다. Windows를 먼저 하고 macOS는 같은 계약을 별도 항목으로 따른다. macOS가 구현되기 전에는 macOS에서 `overwrite: true`를 대상 유무와 관계없이 `UNSUPPORTED`로 거부한다. 이는 위의 "대상이 없으면 기본 모드와 같다"에 대한 macOS 과도기 예외이며, macOS 구현 항목이 이 예외를 없앤다. 플랫폼 지원 표에 그 사실을 적는다.

범위: `plugins/storage`의 두 연산 입력 스키마, 공통 기반 `node-storage.ts`(`move`의 같은 경로와 같은 파일 검사, `copyContents`의 교체 분기), Windows 어댑터, macOS 어댑터의 과도기 `UNSUPPORTED` 거부, 참조 문서(전송 문서 106행의 "공유 위반과 일반 I/O 실패는 `INTERNAL`일 수 있습니다"에서 교체 모드의 공유 위반만 `PERMISSION_DENIED`로 분리하고 일반 I/O 실패 서술은 유지), 변경 기록, `docs/TODO-windows.md`, [전송 문서](../site/src/content/docs/reference/host/storage-transfers.mdx). `tests/lifecycle`의 Windows 시나리오로 CI `windows-native`에서 확인할 것:

- 교체 성공(내용, 크기, 빈 파일, 1 MiB를 넘는 파일), 기본 모드의 거부 유지
- 대상이 디렉터리, 읽기 전용, 링크(`copyFile`은 가리키는 파일을 교체, `move`는 `INVALID_ARGUMENT`), 가리키는 곳이 없는 링크, 상위 디렉터리 없음
- 대상이 없을 때 `overwrite: true`가 기본 모드와 같은 결과(디렉터리 원본 이동 포함)인지와 실패 경로의 차이
- 다른 프로세스가 대상을 열어 둔 상태에서의 `PERMISSION_DENIED`와 대상 불변, 임시 파일 정리
- 복사 도중 원본이 줄어드는 실패에서 대상 불변
- 원본과 대상이 같은 파일로 풀리는 경우(하드 링크와 링크 경유)
- 다른 볼륨 `move`의 `UNSUPPORTED`와 양쪽 불변. 기존 `tests/lifecycle/windows-storage-cross-volume-move.ts`의 가상 디스크 fixture(`tests/fixtures/windows-virtual-disk.ts`)를 쓰며, `diskpart`를 쓸 수 없어 fixture가 건너뛴 경우만 시험하지 못한 항목으로 적는다
- `move`의 같은 경로 거부와 대소문자만 다른 이름, 교체 모드의 공유 위반과 잠금 위반이 `PERMISSION_DENIED`로 매핑되는지

CI로 확인할 수 없는 것: 전원 차단 뒤의 내구성(`WRITE_THROUGH`가 실제로 디스크까지 가는지), 네트워크 파일 시스템의 교체 동작, 프로세스 강제 종료로 임시 파일이 남는 경우의 정리(남을 수 있다고 문서에 적는다).

## 영향

- 코드, 정책, 호스트 동작은 바뀌지 않는다.
- [파일 복사와 대상 이동](../site/src/content/docs/reference/host/storage-transfers.mdx)의 "덮어쓰기에 대한 충돌 및 복구 계약은 후속 작업" 문장을 이 결정으로 연결되는 문장("`overwrite` 옵션은 결정 문서에서 정했고 아직 구현하지 않았습니다")으로 바꿨다. 구현 항목이 옵션을 문서화할 때 이 문장도 고친다.
- `docs/TODO-windows.md`의 덮어쓰기 항목은 구현 전으로 표기하고 체크하지 않는다.
- ADR 0126에는 이 결정으로 가는 링크 한 줄만 더한다.
