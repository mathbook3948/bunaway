# 종료 지연(ShutdownBlockReason) API를 제공하지 않는다

결정일: 2026-10-25.

## 배경

Windows의 `ShutdownBlockReasonCreate`는 앱이 로그오프와 시스템 종료를 지연시키는 용도로 쓰는 호출이다.
앱 정의에 이 기능을 선택 API로 제공할지 정해야 했다. 이 저장소에는 해당 호출을 쓰는 코드와 테스트가 없고,
이 ADR은 그 호출의 동작을 검증하지 않았다. 결정의 근거는 아래 저장소 내부 사정이다.

세션 종료의 현재 계약은 [ADR 0020](./0020-close-and-quit-lifecycle.md)에 있다.

- 로그오프, 재시작, 시스템 종료와 Restart Manager의 앱 닫기에서 `WM_QUERYENDSESSION`은 항상 허용한다.
  `WM_ENDSESSION(TRUE)`는 취소할 수 없는 `"session-end"` 종료이고, UI 스레드는 최대 4초 동안
  `onWillQuit`과 플러그인 StopHook을 기다린다.
- 같은 4초 안에 끝나지 않는 작업(대용량 저장, 업로드, 설치)을 위한 수단은 지금 없다.
- 이 요구를 가진 앱은 확인되지 않았다. 2026-10-25에 `gh issue list`의 열린 이슈 6건과 `rg`로 저장소 전체를
  검색했을 때 예제, 템플릿, 코드에 이 기능을 쓰거나 요구하는 곳이 없었다(ADR 0020과 TODO 문구만 일치).

## 결정

1. `ShutdownBlockReasonCreate`와 `ShutdownBlockReasonDestroy`에 대응하는 공개 API, 설정, 이벤트를 추가하지 않는다.
2. 세션 종료의 ADR 0020 계약(항상 허용, 4초 기한, 취소 불가)을 바꾸지 않는다.
3. 앱은 변경이 생길 때마다 저장하고, 종료 때는 `onWillQuit`의 기한 3초 안에 끝나는 마지막 저장만 한다.
   세션 종료에서는 `onWillQuit`과 Core 정지가 4초를 나눠 쓰므로 `onWillQuit`이 3초를 다 쓰면
   Core 정지에는 1초가 남는다. `onWillQuit` 안에서는 창이나 클립보드 같은 호스트 작업이 `INVALID_ARGUMENT`로
   실패하므로 이 저장은 백엔드 안의 작업(파일 쓰기 등)이어야 한다. 이 방법으로도 부족한 실제 앱 요구가 확인되면 이 ADR을 개정하는 별도 결정으로 다룬다.

## 근거

- 이 기능을 필요로 하는 앱이 없어 계약을 검증할 소비자가 없다.
- 사유 문자열, 해제 규칙, 차단 중 메시지 처리, `onQuit` 보장 범위는 한 번 공개하면 바꾸기 어려운 계약이다.
  쓰임이 확인되기 전에 정하면 ADR 0020이 정한 `onQuit`과 네이티브 정리를 보장하지 않는 범위와 맞물려
  다시 고쳐야 할 가능성이 크다.
- 세션 종료는 UI 스레드의 모든 HWND가 하나의 처리기를 공유한다(클립보드 창 제외). 선택 기능 하나를 위해 이
  처리기에 차단 상태를 더하면 모든 앱의 종료 수명 주기가 복잡해진다.

## 열린 질문

나중에 제공한다면 다음을 먼저 공개 계약으로 정해야 한다.

- 사유 문자열의 길이, 로컬라이즈, 갱신 방법.
- 작업 완료, 앱 정의의 취소, 프로세스 종료, 사용자의 강제 종료 선택에 따른 해제 규칙.
- 차단 중 UI 스레드의 메시지 처리, `onQuit`과 네이티브 정리의 보장 범위.
- 플러그인이 차단 상태를 가질 수 있는지. ADR 0020은 UI 스레드의 모든 HWND가 하나의 처리기를 공유하고
  플러그인 전용 창(클립보드)은 제외한다고 정하므로, 선택 플러그인으로 두려면 이 처리기와의 관계를 먼저 정해야 한다.

## 결과

- 코드, 스키마, 권한, 이벤트 변경은 없다.
- `docs/TODO-windows.md`의 ShutdownBlockReason 항목(243행)을 결정 완료로 바꾸고 이 ADR을 가리킨다.
