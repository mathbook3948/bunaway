# 기능 모듈을 조립하고 최종 명령 이름의 중복을 거부한다

결정일: 2026-10-06

## 배경

단일 앱 정의에 모든 명령의 스키마, 핸들러, 서비스 구현을 쌓으면 기능이 커질 때
유지보수가 어렵다. 객체 spread로 기능별 명령을 합치면 동일한 키가 덮어써져
Core의 중복 등록 검사가 충돌을 발견할 수 없다.

## 결정

1. backend SDK에 `defineModule`과 `defineApp`을 제공한다. 모듈은 기능별 공개
   명령, 이벤트를 정의하고 앱 정의는 모듈을 조립한다. 결과는 기존 `AppDefinition`이며
   Core, 프로토콜, 플랫폼 실행 계약을 바꾸지 않는다.
2. `defineModule("memo").command("save", contract, handle)`는 `memo.save`를 등록한다.
   `contract`는 `{ input, output }` JSON Schema이고 기존 `command`와 같은
   입력, 출력 검증을 사용한다. 별도 스키마 DSL을 만들지 않는다.
3. 실제 기능은 일반 TypeScript 함수나 서비스 클래스로 구현하고 모듈에서 연결한다.
   클래스, 데코레이터, 메서드 자동 공개를 요구하지 않는다. 작은 기능은 한 파일로
   시작하며 커졌을 때 계약과 서비스를 분리한다.
4. 모듈 내부와 앱 조립에서 최종 이름의 중복을 거부한다. 직접 앱 등록과 플러그인
   등록도 검사한다. 뒤의 핸들러로 덮어쓰거나 동일 객체의 재등록을 무시하지 않는다.
   오류는 `INVALID_ARGUMENT`이며 이름과 충돌한 등록 소유자를 표시한다. 모듈, 플러그인
   배열에서는 이름과 인덱스로 등록 위치를 구분한다.
5. 모듈 이름이 다르더라도 최종 이름이 같으면 충돌이다. 서로 다른 기능의 `save`는
   허용한다. 이벤트도 같은 규칙을 적용하고 명령과 이벤트의 이름 공간은 독립이다.
6. 체인은 새 모듈 스냅샷을 반환하고 조립한 명령, 이벤트 목록을 동결한다. 타입 추론을
   유지하며 이전 모듈 객체나 이미 조립한 앱에 이후 등록이 추가되지 않는다.
7. 기존 객체형 앱 정의도 지원한다. 플러그인은 플랫폼, 권한, 의존성, 수명주기를 가진
   기존 확장 단위로 유지하고 기능 모듈은 앱 코드의 조립 단위로 구분한다.

## 범위와 제약

플러그인 setup, 종료는 Core가 담당하고 등록 metadata는 정책 권한을 추가하지 않는다.
프런트엔드는 `CommandsOf`, `EventsOf`로 조립 결과의 타입을 추론할 수 있으며
백엔드 구현을 실행 코드로 import하지 않는다. 플러그인 타입까지 합친 CLI 타입 생성은
기존 후속 작업으로 남긴다. 등록 전에 일반 객체 spread로 덮어쓴 항목은 SDK가
복원할 수 없으므로 기능 조립은 모듈 목록을 이용한다.

Windows 우선, 공통 앱 정의 원칙은 [ADR 0010](./0010-windows-first-platform-model.md)을 따른다.
메모 예제는 계약, 서비스, 모듈 분리를 보여주고 생성 템플릿은 작은 기능을 모듈 한 파일에 둔다.
참고한 구조는 [Wails 서비스](https://v3.wails.io/features/bindings/services/),
[Elysia 모듈 조립](https://elysiajs.com/essential/plugin),
[Electrobun의 공유 RPC 계약](https://github.com/blackboardsh/electrobun)이다.
