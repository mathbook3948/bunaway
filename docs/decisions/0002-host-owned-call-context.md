# 호출 출처와 권한 컨텍스트는 네이티브 호스트가 소유한다

WebView에서 전달한 출처나 권한을 그대로 믿으면 앱 명령이 더 넓은 권한의 네이티브 작업으로 이어질 수 있다. 네이티브 호스트가 관찰한 뷰, 세션, origin, frame을 바탕으로 호출 컨텍스트를 발급하고, 백엔드의 Host API 호출에도 그 컨텍스트를 유지한다. 웹 메시지의 자기 신고값이나 TypeScript 타입 브랜드를 인증 수단으로 사용하지 않는다.

이를 위해 세션과 컨텍스트의 발급, 폐기 및 네이티브 작업 직전의 권한 재검사가 필요하다. 뷰의 요청을 백엔드 자체 작업으로 승격하지 않으며, 정책에 따른 기능 허용과 OS 권한은 각각 확인한다. 앱 백엔드와 네이티브 플러그인은 신뢰 코드이므로 이 경계를 악성 백엔드의 샌드박스로 설명하지 않는다.

현재 Windows 호스트는 실제 WebView의 출처, 최상위 문서와 활성 세션을 검사하고 컨텍스트를 발급, 폐기한다. runtime-bun은 이 컨텍스트로 코어 세션을 열고 Host API 호출에 유지하며, 호스트는 작업 직전 정책을 다시 검사한다. 파일별 접근 규칙은 앱 명령이 소유하며 파일을 여는 플러그인은 플랫폼 경로 문법을 검사하고 경로 제한은 앱 명령이 맡는다([ADR 0024](./0024-plugin-path-responsibility.md)). log, notification, opener와 storage는 링크를 따라간다. 다중 창/뷰의 위조, 권한 거부, 폐기와 파일 경계의 이전 검증 결과는 [Windows 검증 기록](../architecture/windows-host-results.md)에 있다. 뷰별 정책 분리는 [창/뷰 ADR](./0004-multi-window-per-view-policy.md)에 정리하고, 다른 플랫폼은 미검증이다.

근거: [PRD의 권한 모델](../PRD.md), [Host API와 세션 계약](../architecture/common-api.md), [컨텍스트 바인딩](../../packages/runtime-bun/src/host-api.ts), [런타임 연결](../../packages/runtime-bun/src/runtime.ts), [코어 구현](../../packages/core/src/create-core.ts), [Windows 호스트](../../native/windows/bun/entry.ts).

## 호스트 발급 호출 프레임 (opener 대리 호출 전용)

[ADR 0026](./0026-single-webview-single-window.md)은 새 창 요청을 창으로 만들지 않고, 허용된 요청만 시스템 기본 브라우저로 넘긴다. 이 요청은 문서의 SDK 호출이 아니라 호스트가 WebView에서 관찰한 이벤트다. 지금의 `web` 프레임은 문서가 보낸 메시지(`hello`, `invoke`, `cancel`, `listen`, `unlisten`)를 그대로 세션에 전달하는 용도라서 이 요청을 코어에 전달할 수 없다. 호스트가 문서 대신 `invoke`를 끼워 넣는 방식도 쓸 수 없다. 응답이 문서로 돌아가고 요청 ID가 문서의 ID와 겹칠 수 있으며, 문서가 직접 채널을 쓰는 세션에서는 런타임이 이 프레임을 받는 즉시 오류로 백엔드 연결을 끝내기 때문이다. 그래서 호스트 런타임 프레임에 호출 하나를 추가한다.

범위는 이 용도에 한정한다. 이 프레임은 `plugin.opener.openUrl`만 실행하며, 다른 명령이나 일반 확장점으로 쓰지 않는다. 다른 명령에 같은 방식이 필요해지면 새 결정으로 각각 다룬다.

규칙은 다음과 같다.

1. **시작 문서의 세션 핸들.** 호스트는 요청을 시작한 문서의 세션 컨텍스트에 묶어서만 프레임을 보낸다. 세션은 최상위 문서 단위로 발급되므로 시작 프레임이 그 세션을 가진 최상위 문서(메인 프레임)일 때만 보낸다. 하위 프레임(iframe 등)은 SDK 세션을 가질 수 없어 SDK로 같은 명령을 직접 호출할 수 없으므로, 소유 문서의 세션으로 대신 보내면 권한 상승이 된다. 그래서 하위 프레임에서 시작한 요청은 출처와 관계없이 보내지 않는다. 사용자 동작 없이 시작한 요청도 보내지 않으며, 플랫폼이 사용자 동작 여부를 알려 주지 않으면 동작이 없는 것으로 보고 보내지 않는다. 시작 프레임을 알 수 없거나, 세션이 이미 폐기됐거나, 문서가 숨겨져 상주하는 경우에도 보내지 않는다. 보내지 않는 모든 경우에 차단 진단을 남긴다. 백엔드 자체 호출 컨텍스트로 바꿔 보내지 않는다. 뷰의 요청을 백엔드 작업으로 승격하지 않는다는 위 원칙을 그대로 따른다.
2. **두 권한 검사.** 두 검사를 모두 통과해야 열린다. 코어는 일반 `invoke`의 명령 허용 검사와 같게 세션 뷰 정책 `commands`의 `plugin.opener.openUrl`을 확인하고, 호스트는 작업 직전에 host 권한 `opener.openUrl`을 확인한다(일반 호출과 같은 분담이다). 하나라도 없으면 URL은 열리지 않고 코어는 `PERMISSION_DENIED`로 끝낸다.
3. **입력 검증.** URL은 opener의 일반 입력 검증을 그대로 거친다. 프레임이 검증을 대신하거나 완화하지 않는다. 경로 제한은 [ADR 0024](./0024-plugin-path-responsibility.md)대로 앱 명령의 몫이며 이 프레임은 파일 경로를 다루지 않는다.
4. **요청 상한.** 프레임의 요청은 세션의 진행 중 요청 상한(`maxPending`)을 일반 호출과 함께 센다. 상한을 넘으면 `BUSY`로 끝나고 열지 않는다. 호스트는 이 오류를 조용히 버리지 않고 기존 진단 경로에 남긴다.
5. **요청 ID와 응답의 분리.** 프레임의 요청 ID는 호스트가 발급하며, 문서가 고를 수 있는 문자열의 형식(접두사 등)에 기대지 않고 문서의 ID와 구조적으로 분리된 공간에서 관리한다. 문서가 같은 ID를 먼저 써도 대리 요청이 무응답으로 버려지지 않고, 대리 요청이 처리 중이라는 이유로 문서의 요청이 중복으로 버려지지도 않으며, 문서의 `cancel`이 대리 요청을 취소하지도 못한다. 이 ID는 문서 ID의 중복 검출 이력에도 넣지 않아 이력을 밀어내지 않는다. 결과와 오류는 호스트에만 돌려주고 문서로 보내는 응답 경로를 타지 않는다. 문서의 `window.open` 반환값은 항상 `null`이다.
6. **`hello`와 무관.** 이 프레임은 문서의 SDK 핸드셰이크에 의존하지 않는다. 요청을 시작한 세션이 활성이고 규칙 1의 조건을 만족하면 SDK 클라이언트를 띄우지 않은 문서의 요청도 같은 검사를 거쳐 처리한다.
7. **취소와 되돌릴 수 없는 작업.** 세션이 폐기되거나 문서가 교체되면 처리 중인 프레임 요청을 취소하고 결과를 버린다. 앱이나 호스트가 종료될 때도 같다. 기한은 일반 호출과 같이 코어의 명령 최대 시간을 넘지 않는다. 운영체제의 열기 호출이 이미 시작된 뒤에는 되돌릴 수 없으므로, 그 뒤에 세션이 폐기돼도 URL은 열릴 수 있고 호스트는 결과만 버린다.
8. **호스트가 모르는 세션 종료.** 직접 채널이 끊기거나 코어가 응답 전송 실패로 스스로 닫는 것처럼 호스트에 알리지 않고 세션이 닫히는 경로가 있다. 호스트가 이미 닫힌 세션의 컨텍스트로 이 프레임을 보내 런타임이 그 컨텍스트를 모르면 그 요청만 실패시키고 호스트 런타임 연결과 백엔드는 유지한다. 실패는 호스트의 진단 경로에 남기고, 응답 없이 끝나는 경우에 대비해 호스트도 대기 중인 요청에 코어의 명령 최대 시간과 같은 상한을 둔다.

### 외부 링크 열기를 켠 앱의 뷰 정책

외부 링크를 시스템 브라우저로 열려면 앱이 해당 뷰에 두 가지를 허용해야 한다. 뷰 정책 `commands`의 `plugin.opener.openUrl`과 뷰 정책 host 권한의 `opener.openUrl`이다. 하나라도 빠지면 외부 링크는 차단되고 진단만 남는다.

[ADR 0024](./0024-plugin-path-responsibility.md)는 뷰에 `plugin.*` 명령을 직접 허용하지 않고 경로를 제한하는 앱 명령만 허용하라고 하며, 외부 콘텐츠를 표시하는 뷰에는 특히 `plugin.*`를 허용하지 말라고 한다. 이 선택은 앞의 일반 지침에 대한 예외이며 `plugin.opener.openUrl` 하나로 한정한다. 이 프레임은 URL만 다루고 파일 경로를 열지 않으며, 정책 `origins`에 속한 최상위 문서만 대상으로 한다. 이 허용을 둔 뷰의 최상위 문서는 SDK로 같은 명령을 직접 호출할 수 있으므로 프레임이 새 권한을 만들지는 않는다(하위 프레임 제외는 규칙 1). 암묵적 링크 처리에는 사용자 동작 조건을 더한다([ADR 0026](./0026-single-webview-single-window.md)). 외부 콘텐츠를 표시하는 뷰에는 이 예외를 적용하지 않는다. 이는 런타임이 검사하는 제약이 아니라 앱 개발자의 책임이다. 정책에서 그런 뷰를 판별할 수 없으므로, 그런 뷰를 가진 앱은 이 허용을 두지 않아야 한다.

### 기각한 대안: 호스트가 직접 연다

호스트가 허용된 URL을 코어 없이 운영체제의 열기 함수로 바로 여는 방식은 기각한다. 구현은 작지만 위 2와 4를 우회한다. 정책 `commands`와 host 권한이 없는 앱에서도 링크가 열리고, 진행 중 요청 상한과 실행 직전 재검사도 적용되지 않으며, opener의 입력 검증을 거치는 경로가 둘로 갈라진다. 앱이 정책에서 `plugin.opener.openUrl`을 빼서 외부 링크를 막는 방법도 사라진다.

### 선례와의 관계

Electron은 `setWindowOpenHandler`에서 새 창을 거부하고 앱의 신뢰 코드가 `shell.openExternal`로 연다. 요청 정보에는 시작 프레임이 없고 앱이 직접 URL을 판단하므로, 이 구조에서는 앱 코드가 곧 정책이다. 이 프로젝트의 앱 정책은 선언형(host 권한, 뷰 `commands`)이므로 "거부 후 시스템 브라우저로 연다"는 흐름은 같게 두고, 판단 주체를 선언된 정책과 코어 검사로 옮긴다. 시작 프레임은 Windows WebView2의 `OriginalSourceFrameInfo`처럼 플랫폼이 알려 줄 때만 인정하며 알 수 없으면 차단한다(ADR 0026).

### 열린 질문

- **외부 콘텐츠 뷰 제외의 런타임 검사.** 지금은 앱 개발자의 책임이며 정책 필드로 그런 뷰를 판별할 수 없다. 뷰가 외부 콘텐츠를 표시하는지 정책에 선언하게 하고 그 뷰에서 프레임을 거부하는 검사는 후속 과제로 남긴다.
- **호스트로 돌려주는 응답 경로의 실패.** 이 경로가 실패했을 때 문서 세션을 닫을지는 구현 단계에서 정한다.

이 결정은 문서만 바꾼다. 프레임 정의, 런타임과 코어 처리, 호스트 연결은 구현 단계에서 이 규칙에 맞춰 추가하고, 그때까지 코드는 이전 계약을 따른다. 프레임 이름과 필드는 구현에서 정하며 이 문서에 고정하지 않는다.
