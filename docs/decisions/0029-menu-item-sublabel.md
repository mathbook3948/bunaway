# 메뉴 항목에 sublabel과 별도 접근성 label 필드를 두지 않는다

결정일: 2026-10-25. 검토 기준: main `323b57a3`.

## 배경

메뉴 항목에 보조 문구(sublabel)와 접근성 전용 label을 지원할지 정해야 했다.
Windows 메뉴는 `HMENU` 항목이며 다음 사실이 있다.

- 항목은 문자열 하나, accelerator 열(`\t` 뒤 문구), 체크 표시, 비트맵 하나만 가진다. 보조 줄을 그리는 속성이 없다.
  보조 줄을 넣으려면 owner-draw로 직접 그려야 하고, 그러면 테마, 고대비, 다크 모드, DPI 배율과 키보드 탐색
  측정을 모두 직접 맞춰야 한다.
- 접근성 이름은 항목 문자열에서 만들어지며(accelerator 열의 `\t` 뒤 문구가 이름에 포함될 수 있다),
  문자열과 다른 이름을 붙이는 네이티브 속성은 없다.
- 현재 `menu` 입력 스키마는 모든 항목 객체가 `strictObject`라서 정의되지 않은 필드는 `INVALID_ARGUMENT`로 거부된다.
  `sublabel` 같은 필드를 넣으면 조용히 무시되지 않고 호출자가 바로 알 수 있다.

## 결정

1. `sublabel`과 접근성 전용 label 필드는 추가하지 않는다. 항목의 `label`이 화면 표시 문자열이자 접근성 이름의 기준이다.
2. 플랫폼 차이는 필드를 받고 무시하는 방식으로 숨기지 않는다. 지원하지 않는 필드는 스키마가 거부한다.
3. 보조 정보가 필요한 앱은 `label`에 직접 포함한다(`"내보내기 (PDF)"`). `accelerator`는 단축키 표시 문자열 전용이므로
   보조 문구 용도로 쓰지 않는다.
4. 다른 플랫폼 어댑터가 이 항목을 지원할 수 있더라도, 공용 스키마에 필드를 넣기 전에 Windows 동작을 별도로 정한다.
   한 플랫폼에서만 의미가 있는 필드는 공용 입력에 두지 않는다.

## 근거

Windows 네이티브 메뉴에 보조 줄과 별도 접근성 이름 속성이 없다는 점이 결정의 근거다. 한 플랫폼에서만 보이는
필드는 같은 코드가 플랫폼마다 다르게 보이게 만들고, owner-draw 메뉴는 접근성과 시스템 설정 대응 비용이 크다.
코어는 작게 두고 플랫폼 한정 기능은 필요할 때 따로 정한다는 방침과도 맞는다.

## 결과

- 메뉴 스키마, 권한, 이벤트, 네이티브 코드 변경은 없다.
- 문서에 위 결정을 적고, `sublabel`과 `accessibleLabel`이 거부됨을 테스트로 고정한다.
- 접근성 label 구분이 실제 요구로 확인되면 별도 결정으로 다시 다룬다.
